# 守破離

競合を仕様書として模倣せず、ユーザー課題を解くための証拠として使う。公開情報から確認できた事実、そこからの推論、実装上の判断を分け、各変更を根拠と受け入れ条件へ結び付ける。

## 作業範囲を定める

最初に次を一文ずつ定める。

- 対象ユーザーと解決する課題
- 調べる機能と対象リポジトリ
- 完了を確認できる振る舞い
- 期待する成果指標と、悪化させてはいけない指標
- 調査日と対象市場・地域

リポジトリのREADME、既存機能、テスト、ローカル指示を先に確認する。ユーザーが競合を指定しない場合は、同じ課題を解く直接競合または類似製品を2〜4件選ぶ。選択が成果を大きく変える場合だけ確認する。

依頼が調査だけなら「破」の実装判断まで進め、ファイルを変更しない。依頼に実装が含まれる場合は「離」まで完了する。

競合から採用する機能を選ぶ前に [product-feature-research.md](references/product-feature-research.md) を読む。調査手法を儀式的にすべて使わず、変更のリスク、可逆性、利用可能なユーザー数に合わせて証拠の集め方を選ぶ。

## 守: 事実を集める

現在変わりうる競合情報はWebで確認し、次の順で一次情報を優先する。

1. 製品画面、公式ドキュメント、ヘルプ、API仕様
2. 公式の料金、変更履歴、ブログ、デモ
3. 公式リポジトリ、ライセンス、リリース
4. 二次情報。一次情報がない事実の補助または競合候補の発見にだけ使う

各競合について、次を同じ粒度で記録する。

| 項目 | 内容 |
|---|---|
| ユーザー課題 | 誰が何を終えられるか |
| 振る舞い | 入力、主要手順、出力、失敗時の挙動 |
| 既定値と制約 | 権限、上限、価格プラン、対応環境 |
| 利用後の負担 | 学習、操作、保守、切り替えに生じるコスト |
| 根拠 | 主張を直接支えるURLと確認日 |
| 確度 | 確認済みの事実、推論、不明点の別 |

機能名や画面の見た目だけでなく、開始から目的達成までの流れを比較する。古い記事、検索結果の要約、価格プラン違い、地域差を混ぜない。確認できない項目は推測で埋めず「不明」とする。引用は必要最小限にし、本文では要約する。

ログイン、購入、問い合わせ、外部サービスへのデータ送信、アカウント作成は、ユーザーが明示的に許可しない限り行わない。認証、ペイウォール、利用制限を迂回しない。

## 破: 自分たちの要件へ変換する

競合ごとの機能数ではなく、ユーザー課題に対する差を整理する。

新機能だけでなく、既存機能の簡素化、削除、説明改善、何もしない案も候補に含める。競合への追随は学習を速めることがある一方、差別化を弱め、利用後の複雑性を増やしうる。

- `adopt`: 課題と制約が一致し、そのまま採用する価値がある
- `adapt`: 価値はあるが、既存設計や対象ユーザーに合わせて変える
- `reject`: 根拠が弱い、コストやリスクが価値を上回る、または課題と無関係

推奨案を一つ選び、次の実装ブリーフへ落とす。

```markdown
現在の振る舞い:
ユーザー価値:
採用する要素と根拠:
採用しない要素と理由:
受け入れ条件:
価値の仮説と反証条件:
検証方法と観測期間:
非目標:
影響範囲:
リスクと失敗時の挙動:
```

競合が持つこと自体を採用理由にしない。各受け入れ条件を、ユーザー価値、調査根拠、またはリポジトリの制約のいずれかへ結び付ける。情報不足でも安全な最小案を選べるなら、前提を明記して進む。公開API、永続化形式、課金、権限、データ削除など後戻りしにくい判断が必要なら、実装前にユーザーへ確認する。

## 離: 最小実装で検証する

対象リポジトリの指示と既存パターンに従い、次の順で最初に成立する方法を選ぶ。

1. 既存機能または設定で満たす
2. 既存の型、関数、コンポーネントを再利用する
3. 標準ライブラリまたはプラットフォーム機能を使う
4. 導入済み依存を使う
5. 必要なコードだけを追加する

非自明な振る舞いには、受け入れ条件を表す失敗するテストを先に置く。最小の変更で通し、関連する既存テストも実行する。自動テストは実装した振る舞いを証明するものであり、ユーザー価値を証明するものではない。価値は、実装ブリーフで選んだ定性調査、利用データ、段階的ロールアウト、または実験で別に検証する。十分な利用者数や安定した指標がない場合はA/Bテストを前提にしない。

セキュリティ、プライバシー、アクセシビリティ、データ損失防止、エラー処理は競合の挙動より対象プロダクトの基準を優先する。

競合の公開コードを参照する場合はライセンスと必要な表示を確認する。互換ライセンスと明確な必要性がない限りコードをコピーせず、観察した振る舞いから独自に実装する。商標、文章、画像、特徴的な画面表現を複製しない。

実装後は、調査で期待した振る舞いと実際の結果を照合する。通らない仮説が見つかったら、コードを積み増す前に実装ブリーフを修正する。要求に直接対応しない変更は残さない。

## 結果を渡す

完了時は次の順で簡潔に報告する。

1. 調査から得た重要な事実と、各主張の近くに置いた出典リンク
2. `adopt` / `adapt` / `reject` の判断と理由
3. 実装した振る舞いと主な変更箇所
4. 実行した検証と結果
5. 未確認事項、競合との差、意図して実装しなかった範囲

事実と推論を明示的に区別する。実行していないテストや確認していない競合挙動を、完了済みとして報告しない。
