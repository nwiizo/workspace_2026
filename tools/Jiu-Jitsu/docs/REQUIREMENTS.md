# 柔術ディフェンス道場 — 要件定義・技術選定

この文書を、実装再開前の基準とする。`docs/DESIGN.md` は背景・研究・ロードマップ、本文書はプロダクト要件・技術判断・受け入れ基準を扱う。

## 1. プロダクト定義

### 1.1 作るもの

ブラウザ上で動く、柔術の攻防判断を学ぶ 3D 教育ゲーム。

プレイヤーは寝技のロール中に、相手の能動的な攻め・守り・リアクションを読み、数字キーまたはクリックで次のアクションを選ぶ。ゲームは固定問題集ではなく、毎回異なる局面列を生成し、ポジション階層、position before submission、安全なタップ文化を学ばせる。

### 1.2 最重要価値

1. 3D の二人が何をしているか読める。
2. 相手が能動的に動いてくる緊張感がある。
3. 毎回同じシナリオにならない。
4. 防御だけでなく、上を取った後の攻撃継続も学べる。
5. 数字キーで即応でき、クリックなしでも遊べる。
6. 教育内容は誠実で、安全文化を損なわない。

### 1.3 作らないもの

- 実技の代替になる格闘シミュレータ。
- 完全な人体解剖・物理・衝突シミュレーション。
- オンライン対戦、ランキング、ユーザー投稿コンテンツ。
- 3D未検証の技を何でも出す百科事典。全BJJの分類体系は持つが、ゲームに出す体勢は `docs/POSITION_TAXONOMY.md` と検証済み role ペアに限定する。
- 複雑なビルド環境やサーバーアプリ。

## 2. 対象ユーザー

### 2.1 主対象

- 柔術初心者から白帯・青帯初期。
- 「なぜその防御/攻撃が正しいのか」を視覚と選択で学びたい人。
- PC ブラウザで短時間に反復したい人。

### 2.2 副対象

- 指導者が概念説明に使うデモ。
- ゲーム的に柔術の判断順序を理解したい非経験者。

## 3. ゲーム要件

### 3.1 基本ループ

1. ロール開始時に、4〜6 個の局面をランダムに構成する。
2. 各局面は `setup -> opponent action -> player choice -> result -> next state` で進む。
3. 相手は待機せず、判断フェーズで圧を強める。入門では時間制限なし、実戦では一定時間で結果が進む。
4. 各局面では複数の `opponentActions` から相手の初動を選ぶ。相手スタイルと戦術制約に合う初動は出やすくなり、一部の局面では初動に応じて正解 choice も変わる。
5. 相手の初動後、プレイヤーは数字キー `1`〜`4` またはクリックで選択する。
6. 正解なら有利な次局面へ進む。不正解または実戦での時間切れなら相手の攻撃・支配・タップに進む。
7. 正解後は短い演出後に自動で次局面へ進む。ただし結果確認とリプレイは可能にする。
8. 正解/不正解/時間切れでロール全体の「流れ」を変化させる。
9. 混合ロールでは、流れが優勢なら攻め候補、危険なら守り候補の `next` が少し出やすくなる。
10. ロールごとに短いミッション（今回の狙い）を1つ持ち、達成時にボーナスポイントを加える。
11. ロールごとに戦術制約（今回の制約）を1つ持ち、実戦時の判断時間または次局面重みに影響させる。
12. 回答結果は `rollState` として次局面へ引き継ぎ、必要に応じて次局面の選択肢を出し分け、各 scenario の `stateBias` と一致する次局面候補を少し出やすくする。
13. 回答後に、その局面で読めた/見落とした `readCues` と、追加/解除された引き継ぎ状態を短く表示する。
14. ロール終了時に、正解数、ポイント、到達帯、今回の学習原則、局面ごとの相手初動・読む線・テンポ・流れ・引き継ぎ状態、次局面理由、ミッション達成状況、戦術制約、次の稽古ポイントを表示する。
15. ミスまたは時間切れがある場合は、最初の苦手局面と同じ相手初動を先頭にした再ロールを任意で開始できる。

### 3.2 ランダム性

必須:

- 毎回同じ局面順にしない。
- 選択肢の並びを毎回固定しない。
- 攻撃/防御/ミックスのフォーカスで出題プールを変える。
- 同じ scenario でも相手の初動、読む線、pressure 表示が固定されない。
- 一部の scenario では、相手の初動に応じて表示される正解 choice が変わる。
- ギ/ノーギで少なくとも一部の選択肢または正解理由が変わる。
- ロールごとの戦術制約で、同じ局面列でもテンポまたは分岐傾向が変わる。
- 前局面の `rollState` により、一部の選択肢が出たり消えたりし、`stateBias` が一致する次局面候補や時間切れ時の追撃候補が出やすくなる。

禁止:

- 連続性のない完全ランダムな技の羅列。
- 直前の結果と矛盾する次局面。
- 「ランダムだから説明できない」遷移。

### 3.3 相手の能動性

相手は各局面で次のいずれかを行う。

- 攻撃側: 絞める、腕を隔離する、圧を強める、ポジションを上げる。
- 防御側: フレームを作る、腰を逃がす、ガードを戻す、手を防御に戻す。
- アーキタイプ導入後: プレッシャーパサー、レッグロッカー、レスラー等の癖に沿って行動する。

受け入れ基準:

- UI に相手の意図が短く表示される。
- 各 scenario は `readCues` を持ち、首・肘・腰・フレームなど、その局面で観察すべき力の線を 2〜4 個の短い語で示す。
- 各 scenario は `opponentActions` を2件以上持つ。各初動は label と、必要に応じて専用の `pressure` / `readCues` / style / tactic 重みを持つ。
- 主要 scenario は `opponentActions` を3件以上持つことを目標にする。最低限、3件以上の初動を持つ scenario が5件未満にならないよう `scripts/validate-data.mjs` で検証する。
- choice は `requiresAction` / `forbiddenAction` を持てる。初動条件による出し分け後も、state とギ/ノーギ別に正解 choice は必ず1つだけ残る。
- action-gated choice は主要攻防の判断差を表すため、少なくとも6 scenario・18 choices 未満へ退行しないよう `scripts/validate-data.mjs` で検証する。バック防御、マウント脱出、マウント攻撃、バック攻撃、サイド攻撃、クローズドガード姿勢防御は初動によって正解が変わる代表局面とする。
- 回答フィードバックでは、判断フェーズで表示された `readCues` を「読めた線」「見落とした線」「遅れた線」として振り返れる。
- 入門では「時間制限なし」と表示する。実戦では時間経過で「相手が動いている」状態が分かる。
- `setup` 中は回答できず、相手の `attack` ポーズへ切り替わってから判断入力を受け付ける。
- `setup` 中は選ばれた `opponentAction` の label / 専用 readCues / 専用 pressure を先出ししない。`attack` ポーズへ切り替わった判断フェーズで初めて表示する。
- 実戦の時間切れ時は、現在局面に対応した相手の成功結果へ進む。複数の不正解候補がある場合は、表示順ではなく相手スタイルと現在の流れに合う結果を優先する。

### 3.4 入力

必須:

- 選択肢には `1`, `2`, `3`, `4` のキー表示を付ける。
- 判断フェーズが開く前の数字キーとクリックは無視する。
- 数字キー押下はクリックと同じ処理経路を通る。
- 無効な数字、入力欄フォーカス中、修飾キー付き入力は無視する。
- 回答済みの局面では数字キーを無視する。
- 回答後は `Enter` で次へ進み、`R` で同じ局面をリプレイできる。

推奨:

- モバイルでは大きいタップ領域を維持する。
- 将来、`Space` で一時停止を追加できる設計にする。

## 4. 3D 要件

### 4.1 最優先原則

3D は「リアル」より先に「読める」ことを優先する。読めない 3D はゲーム要件未達。

### 4.2 ポーズ品質基準

全ポーズは `_audit.html` で確認し、以下を満たす。

- 赤と青の全身が画面内に入る。
- 攻守、上/下、頭/足、腹/背中の向きが読める。
- 寝技局面で不自然に直立しない。
- マウント、バック、サイド、ガードが視覚的に区別できる。
- 背中合わせ、空中浮遊、極端なめり込み、関節の逆折れがない。
- 足や手の細部より、胴体・頭・腰・膝の位置関係を優先する。

### 4.2.1 重心・接触・力関係の基準

ポーズは単なる関節角ではなく、柔術の力関係として読める必要がある。

必須:

- 上の人の重心は、原則として自分の膝・足・手、または相手の胴体で支えられている。
- 下の人の胴体は床または相手の圧を受ける位置にあり、空中に浮かない。
- マウントでは、上の人の膝が下の人の腰/胴体の左右にあり、骨盤が相手の中心線上にある。
- バックでは、攻め手の胸が守り手の背中側にあり、脚フックが腰の左右に見える。
- サイドでは、上の人の胸/肩が下の人の胸を横切り、腰が相手の腰線を越えすぎない。
- クローズドガードでは、下の人の脚が上の人の腰を囲み、上の人は膝または足で床にベースを作る。
- 腕十字/三角などの極めでは、極められる関節・首・片腕の位置関係が見える。
- 各 pose は `poseSpecs.js` に役割、支持基底、接触点、力の方向を持つ。関節角だけを追加して身体制約を未定義にしない。
- 首、肩、肘、手首、股関節、膝、足首は `scripts/validate-data.mjs` の関節角レンジに収まる。簡易リグで反転して見える 130〜180 度級の首/肩/肘/膝の回転を使わない。
- 膝は簡易リグ上ではヒンジ関節として扱う。`shinL` / `shinR` の `x` は屈曲方向の `0..150` 度だけを許し、負方向の `shin*.x` は逆関節として禁止する。脚を横へ開く・腰を囲む・三角で角度を切る表現は、原則として股関節側の `thigh*` と root 回転で作る。詳細は [HUMAN_BODY_MODEL.md](HUMAN_BODY_MODEL.md) を正とする。
- 関節角の制約は `js/anatomy.js` を単一の定義元とし、`scripts/validate-data.mjs` と `fighter.js` のレンダリング時 clamp の両方で使う。
- 床付近の pose は、`fighter.js` の floor probe により、身体がマットを明確に突き抜ける/浮き続ける場合に root 高さを小さく補正する。これは本格物理ではなく表示用の軽量 kinematics とする。
- 各 pose の root 座標は role ごとの高さレンジに収まる。立位、座位、仰向け、膝立ち上位、サイド上位、ガード下からの極めは高さの前提を混ぜない。
- scenario の赤/青ペアは、水平距離が近接範囲内にあり、マウント/ガード上/サイド上/腕十字などは上位者または捕獲される側の高さ関係が role と矛盾しない。
- scenario の赤/青ペアは、role に応じた方向関係を満たす。バックは同方向かつ背後、マウント/ガード上は下の人の頭側へ向く、サイドは下の人の胴を横切る、下からの腕十字/三角は攻撃側が角度を切る。
- scenario の赤/青ペアは、`js/positionCatalog.js` の `ALLOWED_ROLE_PAIR_RULES` に存在する組み合わせだけを使う。未実装ポジションを既存 role で代用しない。
- 相手に荷重している pose は、`poseSpecs.js` の支持基底中心が相手 root から外れすぎず、`vector` が相手方向へ概ね向いている。これは完全な質量中心計算ではなく、読める重心投影と圧方向の最低条件とする。`_audit.html` では力矢印を支持中心から出し、相手に荷重する pose は支持中心から相手 root への荷重線も表示する。

禁止:

- 上の人が支点なしに相手の上へ浮いている。
- 下の人の脚が攻防と無関係な方向へ跳ね上がっている。
- 頭同士・腰同士の向きが技の説明と逆になる。
- 力をかける側の胸・腰・膝が、実際には相手へ届いていない。

### 4.3 座標規約

`poses.js` の規約を単一の真実にする。設計書と実装で矛盾させない。

採用規約:

- 立位: `root.y=0.92`、顔はローカル `+Z`、脊柱は `+Y`。開始姿勢の赤青は横並びではなく互いの root 方向を向く。
- 仰向け: 腹が上、頭方向を明示する。`supineHeadMinusZ` / `supineHeadPlusZ` のようにヘルパー名で区別する。
- うつ伏せ: 背中が上、頭方向を明示する。
- 上の人: 下の人の胴上に配置し、顔・胸・膝の向きが局面と一致する。

禁止:

- コメントと実際の回転値が矛盾したまま進める。
- `redSideControl` と `blueSideControl` のような左右反転ペアをコピーだけで増やし、向き検証なしに使う。
- 未定義 pose を `{}` にフォールバックして見逃す。

### 4.4 3D 受け入れ基準

リリース前に以下を必ず通す。

```sh
for f in js/*.js; do node --check "$f"; done
```

加えて `_audit.html` のフルページスクリーンショットで、全ペアが上記品質基準を満たすこと。既定の重心投影/支持エリア/支持中心起点の力矢印/荷重線表示で上側の人が支点から外れていないことを確認し、純粋な見た目確認では `markers=off` を使う。未定義 pose は 0 件でなければならない。

`scripts/validate-data.mjs` は、未定義 pose だけでなく、`poseSpecs.js` の仕様漏れ、余分な仕様、参照 pose の仕様漏れ、各 scenario ペアに上/下または攻/守の役割があること、関節角レンジ、root 座標の高さレンジ、scenario ペアの水平距離と高さ関係、role 別の向き関係、相手に荷重する pose の支持中心と力ベクトル、`_audit.html` の身体制約マーカー退行も検証する。

### 4.5 ポジション分類

全BJJの体勢は [POSITION_TAXONOMY.md](POSITION_TAXONOMY.md) と `js/positionCatalog.js` で family と role に分けて管理する。

必須:

- `BJJ_POSITION_FAMILIES` は、実装済みだけでなく未実装の主要BJJポジションファミリーも含める。
- `POSE_ROLE_CATALOG` は、3Dで実装済みの pose role だけを含める。
- `ALLOWED_ROLE_PAIR_RULES` にない赤/青 role ペアは scenario で使えない。
- 未実装ファミリーは `implemented: false` のままにし、scenario から参照しない。
- 新規ポジション追加は、family -> role -> pose -> poseSpec -> allowed pair -> scenario の順に進める。

## 5. シナリオ要件

### 5.1 データモデル

固定配列をそのまま順番に流すのではなく、シナリオグラフとして扱う。

推奨スキーマ:

```js
{
  id: "mount_escape_upa",
  role: "defense", // defense | offense | mixed
  tags: ["mount", "white-belt", "gi", "nogi"],
  readCues: ["片腕", "同側の足", "腰の橋"],
  setup: { red: "redMountTop", blue: "blueUnderMount", badge: "..." },
  opponentAction: {
    red: "redMountArmbar",
    blue: "blueUnderMount",
    intent: "赤が腕を隔離して腕十字へ移る",
    timeLimitSec: 8
  },
  choices: [
    {
      key: 1,
      label: "...",
      correct: true,
      result: { red: "...", blue: "...", badge: "..." },
      next: ["guard_pass", "side_control_attack"],
      feedback: "..."
    }
  ]
}
```

### 5.2 遷移

必須:

- 正解 choice は `next` を持つ。
- `next` が複数ある場合は重み付きランダムにできる。文字列 `"scenario-id"` は weight=1 として扱い、自然な展開は `{ id: "scenario-id", weight: 3 }` のように明示できる。
- 不正解 choice はタップ、支配悪化、相手の再攻撃、ガード回復などの明確な結果へ進む。
- 同じロール内で同一 scenario id を繰り返しすぎない。`next` で次スロットを差し替える場合も、過去に解いた局面と既に予定されている未来スロットの重複を避ける。
- choice は `stateEffects` を持てる。`add` された状態は次局面以降へ残り、`remove` された状態は解除される。
- choice は `requiresState` / `forbiddenState` を持てる。状態条件による出し分け後も、ギ/ノーギ別に正解 choice は必ず1つだけ残る。
- choice は `requiresAction` / `forbiddenAction` を持てる。相手初動による出し分け後も、状態条件とギ/ノーギ別に正解 choice は必ず1つだけ残る。
- scenario は `stateBias` を持てる。現在の `rollState` に一致する scenario は、正解/不正解の `next` 候補選択と時間切れ時の悪手結果選択で少し優先される。

### 5.3 初期 MVP のロール構成

最初に作るロールは 3 系統に限定する。

1. 防御フォーカス: バック/マウント/サイドなど、下から生き残る。
2. 攻撃フォーカス: ガードパス、サイド維持、マウント、極め。
3. ミックスロール: 防御で生き残り、スイープ/パスで上を取り、攻撃へ移る。

## 6. UI 要件

### 6.1 第一画面

アプリ起動直後はゲーム画面であること。ランディングページや説明ページにしない。

必須表示:

- 3D ステージ。
- 現在局面。
- 相手の意図。
- 入門では時間制限なし、実戦では判断時間または圧の状態。
- 数字付き選択肢。
- スコア/帯/ロール状況。
- 攻防フォーカスとギ/ノーギ切替。

### 6.2 説明量

プレイ中は短く、結果後に理由を出す。

禁止:

- プレイ前から長文説明で画面を埋める。
- UI 内で操作説明を過剰に出す。
- 3D を隠すほどのパネル肥大。

## 7. 採点・難易度

### 7.1 採点

- 初回正解のみ加点する。
- リプレイの再正解で二重加点しない。
- 連続正解ボーナスは、同一 scenario のリプレイでは伸びない。
- 実戦での速い初回正解は小さなテンポボーナスを与えてよい。ただし入門、リプレイ再回答、時間切れ、不正解では加点しない。
- リプレイの再回答で流れを二重に変えない。
- 苦手局面からの再ロールは新しいロールとして扱い、前回ロールの点数・連続正解・流れを引き継がない。
- 時間切れは不正解扱い。
- 流れは UI 表示に加え、実戦モードの判断時間と混合ロールの `next` 候補重みに小さく影響してよい。ただし入門モードでは学習しやすさを優先して時間補正しない。
- ミッション達成ボーナスは終了時に一度だけ加点する。リプレイや終了画面の再描画で二重加点しない。

### 7.2 難易度

初期 MVP は 2 段階。

- 入門: 時間制限なし、選択肢 3 つ、相手の意図が明示的。
- 実戦: 制限時間短め、選択肢 4 つ、相手の意図が抽象的。

## 8. 技術選定

### 8.1 決定

MVP は既存方針を維持し、ビルド不要の静的 Three.js アプリとして実装する。

- レンダリング: Three.js 0.169 CDN importmap。
- UI: HTML/CSS/素の JavaScript。
- 状態管理: `Game` クラス内の明示的な reducer 風状態遷移。
- 3D モデル: 当面は `fighter.js` のプリミティブ関節リグ。
- ポーズ仕様: `poses.js` の関節角と `poseSpecs.js` の身体制約をセットで管理する。
- アニメーション: key pose + quaternion interpolation。
- シナリオ: JS 定数の scenario graph。
- 検証: Node 構文チェック、pose ID 整合スクリプト、Playwright/Chrome スクリーンショット、`_audit.html` 目視。

### 8.2 採用理由

Three.js を継続する理由:

- 既に実装済みで、ビルド不要制約に合う。
- CDN importmap で静的サーバーだけで動く。
- OrbitControls、RoomEnvironment、将来の GLTFLoader へ自然に拡張できる。
- 現在の破綻原因は Three.js ではなく pose authoring と仕様未固定である。

素の JS を継続する理由:

- 現在の規模では React/Vue 導入より状態遷移の明確化が効く。
- ビルド不要を守れる。
- UI はフォームアプリではなく、ゲーム画面の少数コンポーネントで足りる。

プリミティブ関節リグを継続する理由:

- BJJ の寝技ポーズを自前で制御しやすい。
- 外部 3D アセットのライセンス・容量・読み込み失敗を避けられる。
- まず「読める」ポーズを作るには、解剖学的精密さより制御性が重要。

### 8.3 不採用

React Three Fiber:

- ビルド環境が必要になり、現行の静的配布方針とズレる。
- 現時点の問題は React 化では解決しない。

Babylon.js:

- Three.js から乗り換えるほどの利得がない。
- 既存実装・検証資産を捨てるコストが大きい。

物理エンジン / ragdoll:

- BJJ の正しい接触・関節制約を物理で自然に作るのは高コスト。
- 教育ゲームに必要なのは物理的リアリズムではなく、局面の可読性。

即時 glTF キャラクター化:

- 将来的には検討するが、現時点ではポーズ数・寝技接触・アセット管理がリスク。
- MVP では `_audit.html` で全ポーズを安定させてから判断する。

### 8.4 将来移行条件

次の条件を満たした場合のみ glTF/スキンドメッシュへ移行を検討する。

- プリミティブリグで全 MVP 要件を満たした。
- ポーズの可読性が安定している。
- 追加したい表現が、プリミティブでは明確に限界である。
- ライセンス確認済みの軽量アセットを用意できる。
- `_audit.html` と同等の全ポーズ検証を維持できる。

## 9. 実装順

実装再開は次の順序で行う。

1. 3D 座標規約を `poses.js` と `docs/DESIGN.md` で一致させる。
2. `_audit.html` で全 pose ペアを表示し、破綻ポーズを修正する。
3. 未定義 pose フォールバックを禁止し、整合チェックで fail させる。
4. シナリオを graph schema に寄せる。
5. 数字キー入力とクリック入力を同一処理に統合する。
6. 相手の能動アクションと時間切れ結果を scenario data に移す。
7. ランダムロール生成を scenario graph ベースにする。
8. ギ/ノーギ差分を最小 2〜3 箇所で実装する。
9. README/TODO/DESIGN を実装後の仕様へ同期する。

## 10. MVP 完了条件

MVP は以下を全て満たした時点で完了。

- `_audit.html` の全ポーズが可読性基準を満たす。
- 起動ごとにロール構成が変わる。
- 相手の能動アクションと時間切れ結果がある。
- ロールごとのミッションと戦術制約があり、どちらも UI とロール終了レビューに表示される。
- 数字キーで全選択肢に回答できる。
- 防御、攻撃、ミックスの少なくとも 3 フォーカスが動く。
- ギ/ノーギ切替が見た目だけでなく選択肢か解説に影響する。
- リプレイでスコア二重加算しない。
- `node --check` と pose ID 整合チェックが通る。
- Playwright または Chrome スクリーンショットで desktop/mobile の非白画面を確認済み。
