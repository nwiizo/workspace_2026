# Domain Boundary Quest - 境界を切る者、システムを制す

> *「正しい境界を見つけることは、正しいコードを書くことより難しい。しかし、その価値は100倍ある」*
> — Eric Evans, Domain-Driven Design より

## 1. 概要

**前提クエスト:** メインシナリオ Chapter 4「進化の方向」完了後

このクエストでは、ドメインの境界を「正しく切る」技術を習得します。
境界の引き方ひとつで、チームの自律性、コードの保守性、システムの進化可能性が決まります。

```
┌─────────────────────────────────────────────────────────────────┐
│                   Domain Boundary Quest                         │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   「モノリスを分割したい」                                     │
│   「マイクロサービスがスパゲッティになった」                   │
│   「どこでコンテキストを切ればいいかわからない」               │
│                                                                 │
│   これらの悩みの答えは、すべて「境界」にある。                 │
│                                                                 │
│   ┌─────────────────────────────────────────────────────────┐ │
│   │                                                         │ │
│   │    正しい境界 ────► チームの自律性                      │ │
│   │         │                                               │ │
│   │         ├───────► 変更の局所化                         │ │
│   │         │                                               │ │
│   │         ├───────► 認知負荷の軽減                       │ │
│   │         │                                               │ │

│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### コンパクトモード

コンテキスト節約のため、以下のコマンドが使えます：

| コマンド | 効果 |
|----------|------|
| 「コンパクトモード」 | 出力を1行要約+選択肢+状態のみに圧縮 |
| 「通常モード」 | 標準出力に戻す |
| 「状態確認」 | 現在のスコアのみ表示 |
| 「サマリー」 | これまでの決定を箇条書きで要約 |

## 3. 境界を見つける技術

### 3.1 言語の違いに注目する

```
┌─────────────────────────────────────────────────────────────────┐
│ 言語境界の発見                                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   同じ言葉、違う意味 ＝ コンテキスト境界のサイン               │
│                                                                 │
│   「商品」                                                      │
│   ├─ カタログ: 説明、画像、カテゴリ、レビュー                  │
│   ├─ 在庫: SKU、ロケーション、数量                             │
│   ├─ 注文: 注文明細、価格スナップショット                      │
│   └─ 配送: 重量、サイズ、梱包タイプ                            │
│                                                                 │
│   「注文」                                                      │
│   ├─ 販売: 顧客注文、売上                                      │
│   ├─ 在庫: 引当、ピッキング指示                                │
│   ├─ 配送: 出荷指示、追跡                                      │
│   └─ 経理: 売掛、請求                                          │
│                                                                 │
│   「顧客」                                                      │
│   ├─ 営業: 見込み客、商談                                      │
│   ├─ サポート: 問い合わせ者、チケット                          │
│   ├─ マーケ: セグメント、キャンペーン対象                      │
│   └─ 経理: 請求先、与信                                        │
│                                                                 │
│   ヒント: 「〇〇から見た□□」という言い方が必要なら、          │
│          そこに境界がある可能性が高い                          │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 変更の軸に注目する

```
┌─────────────────────────────────────────────────────────────────┐
│ 変更頻度マトリクス                                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│            変更頻度                                             │
│   高い ◄─────────────────────────► 低い                        │
│                                                                 │
│   ┌─────────────────┐        ┌─────────────────┐              │
│   │ プロモーション  │        │ 商品マスタ      │              │
│   │ キャンペーン    │        │ 基本属性        │              │
│   │ （週次変更）    │        │ （年数回変更）  │              │
│   └─────────────────┘        └─────────────────┘              │
│                                                                 │
│   ┌─────────────────┐        ┌─────────────────┐              │
│   │ 価格設定        │        │ 認証基盤        │              │
│   │ 割引ルール      │        │ ユーザー管理    │              │
│   │ （日次変更可能）│        │ （四半期変更）  │              │
│   └─────────────────┘        └─────────────────┘              │
│                                                                 │
│   変更頻度が大きく異なる領域は、別コンテキストにすべき。       │
│   高頻度変更領域を低頻度領域から分離 → デプロイ独立性確保      │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 3.3 チーム構造に注目する（逆コンウェイ戦略）

```
┌─────────────────────────────────────────────────────────────────┐
│ Team Topologies × Bounded Context                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   コンウェイの法則:                                             │
│   「システムの構造は、組織の構造を反映する」                   │
│                                                                 │
│   逆コンウェイ戦略:                                             │
│   「望ましいシステム構造に合わせて、組織を設計する」           │
│                                                                 │
│   ┌───────────────────────────────────────────────────────┐   │
│   │                                                       │   │
│   │   1チームが担当できる認知負荷 ≒ 1コンテキストの上限   │   │
│   │                                                       │   │
│   │   目安: 1チーム（5-9人）= 1-3 Bounded Context         │   │
│   │                                                       │   │
│   └───────────────────────────────────────────────────────┘   │
│                                                                 │
│   Anti-pattern: 1つのBounded Contextを複数チームで担当         │
│   → 調整コスト爆発、オーナーシップ不明確                       │
│                                                                 │
│   Good pattern: 1チームが明確なオーナーシップを持つ            │
│   → Stream-aligned team がコンテキストを所有                   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 Anti-Corruption Layer（腐敗防止層）

```
┌─────────────────────────────────────────────────────────────────┐
│ ACL: 外部システムとの境界を守る                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   レガシーシステム         ACL              新システム          │
│   ┌─────────────────┐  ┌────────────┐  ┌─────────────────┐    │
│   │                 │  │            │  │                 │    │
│   │  CustomerMaster │──│  Adapter   │──│    Customer     │    │
│   │  (COBOL DB)     │  │  +         │  │    (Domain)     │    │
│   │                 │  │  Translator│  │                 │    │
│   │  CUST_NO        │  │            │  │  customerId     │    │
│   │  CUST_NM        │──│            │──│  name           │    │
│   │  CUST_ADDR_1    │  │            │  │  address        │    │
│   │  CUST_ADDR_2    │  │            │  │                 │    │
│   │  FLG_1          │  │            │  │                 │    │
│   │  FLG_2          │  │            │  │                 │    │
│   │                 │  │            │  │                 │    │
│   └─────────────────┘  └────────────┘  └─────────────────┘    │
│                                                                 │
│   ACLの役割:                                                    │
│   • レガシーの複雑さを新システムに漏らさない                   │
│   • 命名規則の変換                                              │
│   • データ構造の変換                                            │
│   • 欠損データのデフォルト値設定                               │
│   • レガシー特有のフラグの解釈                                 │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

```rust
// infrastructure/acl/legacy_customer_adapter.rs

pub struct LegacyCustomerAdapter {
    legacy_client: LegacySystemClient,
}

impl CustomerRepository for LegacyCustomerAdapter {
    async fn find_by_id(&self, id: CustomerId) -> Result<Option<Customer>, Error> {
        // レガシーシステムから取得
        let legacy = self.legacy_client
            .get_customer_master(&id.to_legacy_format())
            .await?;

        match legacy {
            Some(record) => {
                // ACL: レガシー形式からドメインモデルへ変換
                let customer = Customer {
                    id,
                    name: CustomerName::new(&record.CUST_NM.trim())?,
                    address: self.translate_address(&record)?,
                    status: self.interpret_status_flags(&record)?,
                    // レガシーにない項目はデフォルト値
                    preferences: CustomerPreferences::default(),
                };
                Ok(Some(customer))
            }
            None => Ok(None),
        }
    }

    fn interpret_status_flags(&self, record: &LegacyRecord) -> Result<CustomerStatus, Error> {
        // レガシーの謎フラグを解釈
        match (record.FLG_1.as_str(), record.FLG_2.as_str()) {
            ("1", "0") => Ok(CustomerStatus::Active),
            ("0", _) => Ok(CustomerStatus::Inactive),
            ("1", "1") => Ok(CustomerStatus::Suspended),
            _ => Err(Error::UnknownLegacyStatus),
        }
    }
}
```

## 5. よくある失敗と対処法

### 5.1 境界の切り方の失敗パターン

```
┌─────────────────────────────────────────────────────────────────┐
│ Anti-Pattern: 技術レイヤーで分割                                │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│ ❌ 悪い分割（技術的関心で分割）                                 │
│                                                                 │
│   ┌─────────┐  ┌─────────┐  ┌─────────┐                       │
│   │ Frontend│  │  API    │  │ Database│                       │
│   │ Service │  │ Gateway │  │ Service │                       │
│   └─────────┘  └─────────┘  └─────────┘                       │
│                                                                 │
│   問題:                                                         │
│   • 1つの機能変更で3サービス全て変更が必要                     │
│   • チーム間の調整コスト大                                     │
│   • ドメイン知識が分散                                         │
│                                                                 │
│ ✅ 良い分割（ビジネスケイパビリティで分割）                    │
│                                                                 │
│   ┌─────────┐  ┌─────────┐  ┌─────────┐                       │
│   │  Order  │  │Inventory│  │ Catalog │                       │
│   │ Service │  │ Service │  │ Service │                       │
│   │ (全層)  │  │ (全層)  │  │ (全層)  │                       │
│   └─────────┘  └─────────┘  └─────────┘                       │
│                                                                 │
│   各サービスがUI→API→DBを縦に持つ                              │
│   機能変更は1サービス内で完結                                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 5.2 境界を超えた密結合

```
┌─────────────────────────────────────────────────────────────────┐
│ Anti-Pattern: 分散モノリス                                      │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
```

### 5.3 境界を守る実装テクニック

```rust
// コンパイル時に境界違反を検出する

// ordering/mod.rs
// pub でないものは他モジュールからアクセス不可
mod domain;          // private - 外部から直接アクセス不可
mod infrastructure;  // private

pub mod api;         // public - HTTP APIのみ公開

// ドメインモデルは直接公開しない
// 代わりにDTOを通じてデータをやり取り
pub use api::dto::{OrderResponse, CreateOrderRequest};

// ❌ これはコンパイルエラーになる
// 他のモジュールから
use ordering::domain::order::Order;  // Error: module `domain` is private

// ✅ これはOK
use ordering::api::dto::OrderResponse;
```

```rust
// モジュール境界をテストで守る
#[cfg(test)]
mod architecture_tests {
    use super::*;

    #[test]
    fn ordering_should_not_depend_on_inventory_internals() {
        // 依存関係をコードで検証
        // (実際にはArchUnitのようなツールを使う)

        let ordering_deps = get_module_dependencies("ordering");

        // 許可された依存のみ
        assert!(ordering_deps.contains("shared_kernel"));
        assert!(ordering_deps.contains("inventory::api"));

        // 内部への依存は禁止
        assert!(!ordering_deps.contains("inventory::domain"));
        assert!(!ordering_deps.contains("inventory::infrastructure"));
    }
}
```
