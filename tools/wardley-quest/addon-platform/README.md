# Platform Engineering Quest

[Strategic Evolution Quest](../) のアドオンシナリオ

内部開発者プラットフォーム（IDP）の設計と運用を学ぶRPG。Platform as a Product思考でゴールデンパスを設計し、開発者体験を最適化します。

## 前提

**単体でもプレイ可能です。** [Strategic Evolution Quest](../) をプレイ済みだとより深く理解できます。

## 学べる概念

### Platform as a Product

プラットフォームを製品として扱う思考法：

| 従来のアプローチ | Platform as a Product |
|---|---|
| 運用チームが全てを管理 | 開発者がセルフサービスで利用 |
| 標準化を強制 | ゴールデンパスを提供 |
| 技術視点で設計 | 顧客（開発者）視点で設計 |
| 使わせる | 使いたくなる |

### ゴールデンパス

開発者が最も効率的にビジネス価値を提供できる標準フロー：

- **80/20の法則**: 80%のユースケースを20%の労力でカバー
- **セルフサービス化**: 開発者が自律的に利用できる仕組み
- **ガードレール**: 安全な制約の中での自由
- **段階的進化**: ドキュメント化 → 部分自動化 → 完全自動化 → セルフサービス

### 認知負荷の管理

Team Topologiesの核心概念：

- **内在的負荷**: ドメインの本質的な複雑さ（削減不可、これに集中すべき）
- **外在的負荷**: 不必要に追加された複雑さ（プラットフォームで削減）
- **学習負荷**: スキル習得のための負荷（ゴールデンパスで効率化）

### 開発者体験（DevEx）

Michaela Greilerの DevEx Framework に基づく3つの次元：

- **フローステート**: 中断されずに作業に集中できるか
- **フィードバックループ**: 変更の結果をすぐに確認できるか
- **認知負荷**: 覚えることが少なく直感的に使えるか

### You Build It, You Run It

> 「開発したなら運用も」

プラットフォームは「You Build It, You Run It」を可能にするツール、サポート、教育を提供し、運用コストを低く抑える。

### 既にあるものを正しく使う

プラットフォーム構築における重要な原則：

- **自前開発への依存を避ける**: 既存のOSSやSaaSを活用し、車輪の再発明を防ぐ
- **組織の成熟度に合わせた選択**: 組織が扱える複雑さのレベルでツールを選定
- **OSSへの貢献**: 利用するだけでなく、フィードバックや貢献を通じてエコシステムに参加
- **シンプルさの追求**: Matthew Skeltonの言葉「良いプラットフォームは、wikiページだけということもあり得る」

### AI協働時代のプラットフォーム

生成AIとの協働を前提としたプラットフォーム設計：

- **AIが生成したコードの品質判定**: プラットフォームがガードレールとして機能
- **自動化の拡張**: AIによるコード生成とCI/CDの統合
- **開発者の判断力支援**: AIの出力を評価・選択する能力を支援するツール

## 想定される学習成果

- 開発者を「顧客」として捉えるプロダクト思考
- ゴールデンパスの設計と段階的な成熟度向上
- プラットフォームチームの立ち上げと運営
- 採用率を上げるための戦略と施策

## 遊び方
