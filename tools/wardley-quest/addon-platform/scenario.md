# 第1章: ゲーム概要

## 1.1 このゲームについて

**Platform Engineering Quest** は、Strategic Evolution Questの拡張として、**内部開発者プラットフォーム（IDP）の設計と運用を学ぶ**戦略シミュレーションRPGです。

Team Topologiesのプラットフォームチームの概念を実践に落とし込み、開発者体験（DX）を向上させながら認知負荷を軽減するプラットフォームを構築します。

### 核心的な問い

> **「どうすれば、開発チームの認知負荷を軽減しながら、自律性を高め、ビジネス価値の提供を加速できるのか？」**

### Platform as a Product

| 従来のアプローチ | Platform as a Product |
|---|---|
| 運用チームが全てを管理 | 開発者がセルフサービスで利用 |
| 標準化を強制 | ゴールデンパスを提供 |
| コスト削減が目的 | 開発者体験が目的 |
| 技術視点で設計 | 顧客（開発者）視点で設計 |
| 使わせる | 使いたくなる |

## 1.2 プラットフォームエンジニアリングの本質

### Nick Tuneの洞察

Architecture Modernizationでは、プラットフォームは**開発チームの認知負荷を軽減し、自律性を高めるための手段**として位置づけられています。

| 観点 | 説明 |
|---|---|
| **目的** | 開発者がビジネス価値の提供に集中できるようにする |
| **手段** | 複雑なインフラやツールを抽象化してセルフサービス化 |
| **成功基準** | 開発者が「使いたい」と思うプラットフォーム |
| **失敗パターン** | 使われない「完璧な」プラットフォーム |

### 認知負荷の種類

```
┌─────────────────────────────────────────────────────────────┐
│  認知負荷の3つの種類                                         │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ 内在的負荷（Intrinsic）                              │   │
│  │ └── ドメインの本質的な複雑さ                         │   │
│  │     例: ビジネスロジック、ドメインモデル             │   │
│  │     → 削減不可、これに集中すべき                     │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ 外在的負荷（Extraneous）                             │   │
│  │ └── 不必要に追加された複雑さ                         │   │
│  │     例: 悪いツール、複雑なプロセス                   │   │
│  │     → プラットフォームで削減すべき                   │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ 学習負荷（Germane）                                  │   │
│  │ └── スキル習得のための負荷                           │   │
│  │     例: 新技術の学習、ベストプラクティス             │   │
│  │     → ゴールデンパスで効率化すべき                   │   │
│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

## 1.3 ゲームの厳しさについて

このゲームでは以下のことが起こります：

| 現象 | 説明 | 学び |
|---|---|---|
| **使われないプラットフォーム** | 完璧を目指して開発者のニーズを無視 | 顧客視点の重要性 |
| **Shadow IT** | 開発者が独自ツールを使い始める | 強制は逆効果 |
| **技術負債の集中** | プラットフォームがボトルネックに | 分散と自律のバランス |
| **チーム間摩擦** | 「使いにくい」「要望が通らない」 | コミュニケーションの重要性 |
| **スコープクリープ** | 何でも屋になって疲弊 | 境界の明確化 |
| **進化の停滞** | メンテナンスに追われて改善できない | 持続可能性の設計 |

**これらは現実のプラットフォームチームが直面する課題です。**

## 2.2 判定システム

### 基本判定（2D6）

| 出目 | 結果 | 効果 |
|:---:|---|---|
| 2 | **致命的失敗** | プラットフォーム障害。全チームに影響。信頼喪失。 |
| 3-4 | **失敗** | 機能不全。採用率低下。負債+1。 |
| 5-6 | **部分的失敗** | 一部成功。予期せぬ複雑性が発生。 |
| 7-8 | **部分的成功** | 条件付き成功。追加作業が必要。 |
| 9-10 | **成功** | 目標達成。採用率・満足度向上。 |
| 11 | **大成功** | ボーナス効果。開発者からの賞賛。 |
| 12 | **完全成功** | 最高の結果。他チームが自発的に採用。 |

### 修正値

#### 開発者視点関連

| 状況 | 修正 | 根拠 |
|---|:---:|---|
| 開発者からのフィードバックを反映 | +2 | 顧客視点 |
| ゴールデンパスが明確に定義 | +2 | 使いやすさ |
| ドキュメントが充実 | +1 | 学習コスト削減 |
| セルフサービスで利用可能 | +1 | 自律性向上 |
| 開発者の要望を無視 | -2 | 信頼喪失 |
| 使い方が複雑 | -2 | 採用の障壁 |
| ドキュメント不足 | -1 | 学習コスト増大 |

#### 技術関連

| 状況 | 修正 | 根拠 |
|---|:---:|---|
| 既存ツールとの統合が良好 | +1 | 移行コスト削減 |
| 段階的なロールアウト | +1 | リスク軽減 |
| 自動化が進んでいる | +1 | 運用負荷軽減 |
| 技術的負債が4以上 | -1 | 変更の困難さ |
| 技術的負債が7以上 | -3 | 致命的な制約 |
| 手動作業が多い | -2 | スケールしない |

#### 組織関連

| 状況 | 修正 | 根拠 |
|---|:---:|---|
| 経営層のサポートあり | +2 | リソース確保 |
| ストリームアラインドチームと協力 | +1 | ニーズ把握 |
| イネーブリングチームと連携 | +1 | 採用促進 |
| プラットフォームチームが孤立 | -2 | ニーズとの乖離 |
| 強制的な採用を推進 | -2 | 反発を招く |

## 2.3 組織イベント

毎ターン開始時にD6を2回振り、2つのイベントが発生します。

### 組織イベント表

| D6 | イベント | 効果 | 対応のヒント |
|:---:|---|---|---|
| 1 | **緊急要望** | チームから「今すぐ必要」な機能要求。対応しないと満足度-2。 | 優先順位の判断 |
| 2 | **Shadow IT発覚** | チームが独自ツールを使用。採用率の脅威。 | 理由を理解し対応 |
| 3 | **新チーム参入** | 新しいチームがプラットフォームを使いたい。オンボーディングが必要。 | 拡張の機会 |
| 4 | **セキュリティ要件** | コンプライアンス要件の追加。機能制限の可能性。 | バランスの判断 |
| 5 | **技術進化** | 新しい技術やツールの登場。プラットフォームの進化機会。 | 採用判断 |
| 6 | **予算変更** | リソースの増減。計画の見直しが必要。 | 優先順位の調整 |

### 常時適用パターン

| パターン | 効果 |
|---|---|
| **開発者は最短経路を選ぶ** | 使いにくいツールは回避される |
| **信頼は時間がかかる** | 採用率は急には上がらない |
| **障害は信頼を破壊する** | 1回の障害で複数ターンの努力が無駄に |
| **強制は反発を生む** | 使わせるのではなく使いたくなる |
| **フィードバックは宝** | 開発者の声を聞かないと失敗する |

# 第3章: ゴールデンパスの設計

## 3.1 概要

ゴールデンパスは、**開発者が最も効率的にビジネス価値を提供できる標準的なフロー**です。

### このフレームワークで答える問い

- 「開発者が最も頻繁に行う作業は何か？」
- 「その作業をどれだけ簡単にできるか？」
- 「例外的なケースにどう対応するか？」
- 「ゴールデンパスからの逸脱をどう扱うか？」

---

## 3.2 ゴールデンパスの原則

### 80/20の法則

```
┌─────────────────────────────────────────────────────────────┐
│  ゴールデンパスの設計原則                                    │
│                                                             │
│  80%のユースケースを                                        │
│  20%の労力でカバーする                                      │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ ゴールデンパス（80%）                                │   │
│  │ ・最も一般的なユースケース                           │   │
│  │ ・シンプルで明確な手順                               │   │
│  │ ・自動化されている                                   │   │
│  │ ・ドキュメントが充実                                 │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ 例外パス（20%）                                      │   │
│  │ ・特殊なユースケース                                 │   │
│  │ ・カスタマイズが必要                                 │   │
│  │ ・サポートで対応                                     │   │
│  │ ・将来のゴールデンパス候補                           │   │
│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

### ゴールデンパスの要素

| 要素 | 説明 | 例 |
|---|---|---|
| **トリガー** | 開始点 | 「新しいサービスを作りたい」 |
| **ステップ** | 必要な手順 | テンプレート選択→設定→デプロイ |
| **自動化** | 手動作業の排除 | CI/CD、IaC、プロビジョニング |
| **ガードレール** | 安全な制約 | セキュリティスキャン、リソース制限 |
| **フィードバック** | 進捗の可視化 | ダッシュボード、通知 |

---

## 3.3 典型的なゴールデンパス

### サービス作成のゴールデンパス

```
開発者のアクション          プラットフォームの動作
─────────────────────────────────────────────────────────
1. 「新規サービス」          → サービステンプレート一覧
   ボタンをクリック             を表示

2. テンプレートを選択        → リポジトリ自動作成
   （REST API、GraphQL等）      CI/CDパイプライン設定
                                モニタリング設定

3. サービス名を入力          → 命名規則の検証
                                名前空間の確保

4. 設定を確認して作成        → インフラプロビジョニング
                                開発環境の準備
                                ドキュメントテンプレート

5. 開発を開始               → 開発者は即座にコーディング可能
```

### デプロイのゴールデンパス

```
開発者のアクション          プラットフォームの動作
─────────────────────────────────────────────────────────
```

# 付録A: クイックリファレンス

## 主要修正値

| 条件 | 修正 |
|---|:---:|
| 開発者フィードバック反映 | +2 |
| ゴールデンパス明確 | +2 |
| 経営層サポートあり | +2 |
| セルフサービス可能 | +1 |
| ドキュメント充実 | +1 |
| 開発者の要望無視 | -2 |
| 使い方が複雑 | -2 |
| プラットフォームチーム孤立 | -2 |
| 技術的負債4+ | -1 |
| 技術的負債7+ | -3 |

## プラットフォーム成熟度

| レベル | 特徴 |
|:---:|---|
| 1 | ドキュメント化された手順 |
| 2 | 部分的な自動化 |
| 3 | 完全な自動化 |
| 4 | セルフサービス |
| 5 | インテリジェント（AI支援） |

## よくある失敗パターン

1. **技術先行** - 開発者のニーズを無視
2. **完璧主義** - 使われる前に作り込みすぎ
3. **強制採用** - 反発と回避を招く
4. **孤立** - 開発チームとの断絶
5. **スコープクリープ** - 何でも屋になる
