# 第1章: ゲーム概要

## 1.1 このゲームについて

**Platform Engineering Quest** は、Strategic Evolution Questの拡張として、**内部開発者プラットフォーム（IDP）の設計と運用を学ぶ**戦略シミュレーションRPGです。

Team Topologiesのプラットフォームチームの概念を実践に落とし込み、開発者体験（DX）を向上させながら認知負荷を軽減するプラットフォームを構築します。

### 核心的な問い

> **「どうすれば、開発チームの認知負荷を軽減しながら、自律性を高め、ビジネス価値の提供を加速できるのか？」**

### Platform as a Product

| 従来のアプローチ | Platform as a Product |
|---|---|
| 運用チームが全てを管理 | 開発者がセルフサービスで利用 |
| 標準化を強制 | ゴールデンパスを提供 |
| コスト削減が目的 | 開発者体験が目的 |
| 技術視点で設計 | 顧客（開発者）視点で設計 |
| 使わせる | 使いたくなる |

### フレームワークの関係

**Team Topologies（チーム設計の指針）**
- プラットフォームチーム → 認知負荷を軽減するサービスを提供
- ストリームアラインドチーム → プラットフォームを活用してビジネス価値を提供

**Internal Developer Platform（IDP）**
- ゴールデンパス: 推奨される開発フロー
- セルフサービス: 開発者が自律的に利用
- 抽象化: 複雑性を隠蔽
- 開発者体験: 使いやすさの追求

### プレイ形式

| 項目 | 内容 |
|---|---|
| プレイヤー | 1名（プラットフォームエンジニア/アーキテクト） |
| GM | Claude（シナリオ・判定・組織イベント） |
| 所要時間 | 60〜120分 |
| 前提 | Strategic Evolution Questの基礎知識（推奨） |

### コンパクトモード

| コマンド | 効果 |
|----------|------|
| 「コンパクトモード」 | 出力を1行要約+選択肢+状態のみに圧縮 |
| 「通常モード」 | 標準出力に戻す |
| 「状態確認」 | 現在のスコアのみ表示 |
| 「サマリー」 | これまでの決定を箇条書きで要約 |

## 1.2 プラットフォームエンジニアリングの本質

プラットフォームは**開発チームの認知負荷を軽減し、自律性を高めるための手段**。成功基準は開発者が「使いたい」と思うこと、失敗パターンは使われない「完璧な」プラットフォーム。

### 認知負荷の種類

| 種類 | 内容 | 例 | 対応 |
|---|---|---|---|
| **内在的負荷（Intrinsic）** | ドメインの本質的な複雑さ | ビジネスロジック、ドメインモデル | 削減不可、これに集中すべき |
| **外在的負荷（Extraneous）** | 不必要に追加された複雑さ | 悪いツール、複雑なプロセス | プラットフォームで削減すべき |
| **学習負荷（Germane）** | スキル習得のための負荷 | 新技術の学習、ベストプラクティス | ゴールデンパスで効率化すべき |

### 開発者体験（DX）の重要指標

| 指標 | 目標 | 説明 |
|---|---|---|
| **0から本番まで** | 数時間以内 | 新アプリケーションの起動から本番デプロイまで |
| **変更リードタイム** | 1時間未満 | コードコミットから本番デプロイまで |
| **オンボーディング** | 初日にコードを本番へ | 新メンバーが即座に貢献できる環境 |
| **セルフサービス率** | 100% | チケットやリクエストなしで利用可能 |

### プラットフォーム機能一覧

| カテゴリ | 含まれる機能 |
|---|---|
| **ゴールデンパス** | アプリテンプレート、CI/CDパイプライン設定、Backstageカタログ |
| **オブザーバビリティ** | ロギング、モニタリング（4ゴールデンシグナル）、標準ダッシュボード |
| **環境管理** | IaCプロビジョニング、シークレット管理 |
| **ソフトウェアカタログ** | API/サービス一覧、オーナーシップ明確化 |

### 重要な原則

- **You Build It, You Run It**: プラットフォームは開発者自身が本番運用できるようツール・サポート・教育を提供する
- **IDPは必ずしも大規模な取り組みである必要はない**（Skelton: 「よいプラットフォームとは、特定のサービスの使い方を明記したwikiページだけのこともある」）

# 第2章: ゲームルール

## 2.1 セッション構造

**Phase 1: 現状分析** → 認知負荷評価、ツールマッピング、ペインポイント特定、ビジョン設定

**Phase 2: プラットフォーム構築（ターン制）** 各ターン:
1. 組織イベント（D6 × 2）: チームからの要望、技術変化、障害が発生
2. 状況分析: 採用率 / 満足度 / セルフサービス度 / 負債
3. アクション宣言（最大3つ）: 機能追加、改善、サポートなど
4. 判定（2D6 + 修正値）: 技術と組織の両面を評価
5. 結果適用: 採用率・満足度・負債の更新

**Phase 3: 評価と進化** → 目標達成度判定、フィードバック収集、ロードマップ更新、学びの言語化

---

## 2.2 判定システム

基本判定（2D6）はメインscenario参照。追加効果: 致命的失敗=信頼喪失、成功=採用率・満足度向上、完全成功=他チーム自発的採用。

### 修正値

#### 開発者視点関連

| 状況 | 修正 | 根拠 |
|---|:---:|---|
| 開発者からのフィードバックを反映 | +2 | 顧客視点 |
| ゴールデンパスが明確に定義 | +2 | 使いやすさ |
| ドキュメントが充実 | +1 | 学習コスト削減 |
| セルフサービスで利用可能 | +1 | 自律性向上 |
| 開発者の要望を無視 | -2 | 信頼喪失 |
| 使い方が複雑 | -2 | 採用の障壁 |
| ドキュメント不足 | -1 | 学習コスト増大 |

#### 技術関連

| 状況 | 修正 | 根拠 |
|---|:---:|---|
| 既存ツールとの統合が良好 | +1 | 移行コスト削減 |
| 段階的なロールアウト | +1 | リスク軽減 |
| 自動化が進んでいる | +1 | 運用負荷軽減 |
| 技術的負債が4以上 | -1 | 変更の困難さ |
| 技術的負債が7以上 | -3 | 致命的な制約 |
| 手動作業が多い | -2 | スケールしない |

#### 組織関連

| 状況 | 修正 | 根拠 |
|---|:---:|---|
| 経営層のサポートあり | +2 | リソース確保 |
| ストリームアラインドチームと協力 | +1 | ニーズ把握 |
| イネーブリングチームと連携 | +1 | 採用促進 |
| プラットフォームチームが孤立 | -2 | ニーズとの乖離 |
| 強制的な採用を推進 | -2 | 反発を招く |

---

## 2.3 組織イベント

毎ターン開始時にD6を2回振り、2つのイベントが発生します。

### 組織イベント表

| D6 | イベント | 効果 | 対応のヒント |
|:---:|---|---|---|
| 1 | **緊急要望** | チームから「今すぐ必要」な機能要求。対応しないと満足度-2。 | 優先順位の判断 |
| 2 | **Shadow IT発覚** | チームが独自ツールを使用。採用率の脅威。 | 理由を理解し対応 |
| 3 | **新チーム参入** | 新しいチームがプラットフォームを使いたい。オンボーディングが必要。 | 拡張の機会 |
| 4 | **セキュリティ要件** | コンプライアンス要件の追加。機能制限の可能性。 | バランスの判断 |
| 5 | **技術進化** | 新しい技術やツールの登場。プラットフォームの進化機会。 | 採用判断 |
| 6 | **予算変更** | リソースの増減。計画の見直しが必要。 | 優先順位の調整 |

### 常時適用パターン

| パターン | 効果 |
|---|---|
| **開発者は最短経路を選ぶ** | 使いにくいツールは回避される |
| **信頼は時間がかかる** | 採用率は急には上がらない |
| **障害は信頼を破壊する** | 1回の障害で複数ターンの努力が無駄に |
| **強制は反発を生む** | 使わせるのではなく使いたくなる |
| **フィードバックは宝** | 開発者の声を聞かないと失敗する |

# 第3章: ゴールデンパスの設計

## 3.1 概要

ゴールデンパスは、**開発者が最も効率的にビジネス価値を提供できる標準的なフロー**です。

### このフレームワークで答える問い

- 「開発者が最も頻繁に行う作業は何か？」
- 「その作業をどれだけ簡単にできるか？」
- 「例外的なケースにどう対応するか？」
- 「ゴールデンパスからの逸脱をどう扱うか？」

---

## 3.2 ゴールデンパスの原則

### 80/20の法則

> 80%のユースケースを20%の労力でカバーする

| パス | 特徴 |
|---|---|
| **ゴールデンパス（80%）** | 一般的なユースケース、シンプルな手順、自動化済み、ドキュメント充実 |
| **例外パス（20%）** | 特殊なユースケース、カスタマイズ必要、サポート対応、将来のゴールデンパス候補 |

### ゴールデンパスの要素

| 要素 | 説明 | 例 |
|---|---|---|
| **トリガー** | 開始点 | 「新しいサービスを作りたい」 |
| **ステップ** | 必要な手順 | テンプレート選択→設定→デプロイ |
| **自動化** | 手動作業の排除 | CI/CD、IaC、プロビジョニング |
| **ガードレール** | 安全な制約 | セキュリティスキャン、リソース制限 |
| **フィードバック** | 進捗の可視化 | ダッシュボード、通知 |

---

## 3.3 典型的なゴールデンパス

### サービス作成

| ステップ | 開発者 | プラットフォーム |
|:---:|---|---|
| 1 | 「新規サービス」クリック | テンプレート一覧表示 |
| 2 | テンプレート選択 | リポジトリ・CI/CD・モニタリング自動設定 |
| 3 | サービス名入力 | 命名規則検証・名前空間確保 |
| 4 | 設定確認・作成 | インフラプロビジョニング・環境準備 |
| 5 | 開発開始 | 即座にコーディング可能 |

### デプロイ

| ステップ | 開発者 | プラットフォーム |
|:---:|---|---|
| 1 | mainにマージ | 自動ビルド・テスト・セキュリティスキャン |
| 2 | （待機） | ステージング自動デプロイ |
| 3 | ステージング確認 | 本番承認待ち |
| 4 | 本番デプロイ承認 | 本番デプロイ・ロールバック準備・モニタリング強化 |

---

## 3.4 ゴールデンパスの進化

### 成熟度レベル

| レベル | 状態 | 特徴 |
|:---:|---|---|
| 1 | ドキュメント化 | 手順書として存在 |
| 2 | 部分自動化 | 一部がスクリプト化 |
| 3 | 完全自動化 | エンドツーエンドで自動 |
| 4 | セルフサービス | 開発者が自律的に利用 |
| 5 | インテリジェント | AIによる最適化・推奨 |

### 判定への影響

| 状況 | 判定修正 |
|---|:---:|
| ゴールデンパスが成熟度4以上 | +2 |
| ゴールデンパスが成熟度3 | +1 |
| ゴールデンパスが未定義 | -2 |
| 例外処理が多すぎる | -1 |

# 第4章: 開発者体験（DX）の設計

## 4.1 概要

開発者体験は、**プラットフォームの採用と成功を決定する最重要要素**です。

### DevExの3つの次元（Michaela Greiler）

| 次元 | 評価ポイント |
|---|---|
| **フローステート** | 中断なし・コンテキストスイッチ少・待ち時間少 |
| **フィードバックループ** | 結果即時確認・エラー明瞭・学習サイクル短 |
| **認知負荷** | 覚えること少・直感的・情報アクセス容易 |

---

## 4.2 DX向上のパターン

### ポータルの提供

開発者ポータルの要素: サービスカタログ、ゴールデンパス、ドキュメント、セルフサービス、ダッシュボード、サポート（例: Backstage, Port, Cortex）

### APIファーストの設計

| 原則 | 説明 |
|---|---|
| **一貫性** | 全てのAPIが同じパターンに従う |
| **発見可能性** | APIが自己文書化されている |
| **バージョニング** | 後方互換性を維持 |
| **エラー処理** | 分かりやすいエラーメッセージ |

### 即座のフィードバック

| 場面 | 期待される時間 |
|---|---|
| ローカルビルド | 秒単位 |
| CI/CDパイプライン | 分単位 |
| 環境プロビジョニング | 分単位 |
| デプロイ完了 | 分単位 |

---

## 4.3 DXアンチパターン

### 避けるべきパターン

| パターン | 問題 | 対策 |
|---|---|---|
| **ドキュメントなし** | 使い方が分からない | ドキュメント駆動開発 |
| **例外だらけ** | ルールが信用されない | ゴールデンパスの徹底 |
| **遅いフィードバック** | 開発効率低下 | 自動化・並列化 |
| **複雑なUI** | 学習コスト増大 | シンプルさの追求 |
| **強制的な採用** | 反発と回避 | 価値の証明 |

---

## 4.4 判定への影響

| 状況 | 判定修正 |
|---|:---:|
| 開発者ポータルが充実 | +2 |
| フィードバックが5分以内 | +1 |
| ドキュメントが最新 | +1 |
| APIが一貫している | +1 |
| フィードバックが30分以上 | -2 |
| ドキュメントが古い | -1 |
| UIが複雑 | -1 |

# 第5章: プラットフォームチームの運営

## 5.1 概要

プラットフォームチームは、**開発チームの成功を支援するサービス提供者**です。

### Team Topologiesの原則

- **ストリームアラインドチーム** →（X-as-a-Service）→ **プラットフォームチーム**: 認知負荷を軽減するサービス提供、適切な抽象化、顧客視点で設計
- **イネーブリングチーム** →（コラボレーション）→ **プラットフォームチーム**: スキル向上を支援

---

## 5.2 チーム構成パターン

### スキルセット

| 役割 | 責任 |
|---|---|
| **プラットフォームPM** | ロードマップ、優先順位、ステークホルダー管理 |
| **プラットフォームエンジニア** | 機能開発、自動化、運用 |
| **SRE** | 信頼性、可観測性、インシデント対応 |
| **DevRelエンジニア** | ドキュメント、オンボーディング、サポート |
| **セキュリティエンジニア** | セキュリティ要件、ガードレール |

### チームサイズの目安

| 組織規模 | プラットフォームチーム規模 | 比率 |
|---|---|---|
| 〜50名 | 2-4名 | 5-8% |
| 50-200名 | 4-8名 | 4-6% |
| 200-500名 | 8-15名 | 3-4% |
| 500名以上 | 複数チーム | 2-3% |

---

## 5.3 運営のパターン

### プロダクトとしての運営

### サポートモデル

| モデル | 説明 | 適用場面 |
|---|---|---|

| **コミュニティ** | Slackチャンネルで相互サポート | 質問・共有 |
| **ティアードサポート** | L1→L2→L3のエスカレーション | 複雑な問題 |
| **オフィスアワー** | 定期的な相談タイム | 対話が必要な場合 |

## 7.3 バッドエンディング

終了条件による敗北時、以下のエンディングが表示されます。

### 「Shadow ITの勝利」エンディング
**条件**: プラットフォーム採用率が30%未満で終了
**学び**: プラットフォームは「製品」として選ばれる必要がある / DevExが採用の鍵 / Shadow ITは禁止しても生まれる、競争して勝つしかない

### 「開発者離反」エンディング
**条件**: 開発者満足度が3以下で終了
**学び**: プラットフォームは「サービス」であり開発者は「顧客」 / フィードバックを迅速に反映する / 標準化と柔軟性のバランス

### 「過剰エンジニアリングの罠」エンディング
**条件**: プラットフォーム負債が8以上で終了
**学び**: TVP（Thinnest Viable Platform）から始める / 早期に価値を届けフィードバックを得る / 完璧主義は何も届けないことの言い訳

### 「強制採用の反乱」エンディング
**条件**: 「強制的な採用を実施」を2回以上行った
**学び**: 強制は短期的な数字改善、長期的な信頼喪失 / プラットフォームは「選ばれる」存在であるべき / 納得のない採用は見えない抵抗を生む

### 「単一障害点」エンディング
**条件**: プラットフォーム障害が全チームのデプロイを停止させた
**学び**: プラットフォームの可用性は全社の可用性 / 中央集権にはリスク集中が伴う / SLO/SLAを明確にしフォールバックを用意する

### 7.4 決められていないバッドエンディング

| パターン | 発生条件（目安） | 結末の方向性 |
|---------|-----------------|-------------|
| 「認知負荷の転嫁」 | 開発者満足度が3ターン連続低下 | プラットフォームが複雑すぎて逆効果 |
| 「ドキュメント砂漠」 | ゴールデンパス0かつ採用率30%以上 | 使い方が分からず、サポート地獄に |
| 「抽象化の漏れ」 | プラットフォーム負債5以上かつ障害2回 | 抽象化が不完全で、複雑さが漏れ出す |
| 「政治的敗北」 | スポンサーを失い予算削減 | 組織の理解を得られず縮小・廃止 |

## 7.5 グッドエンディング

### 「選ばれるプラットフォーム」エンディング
**条件**: 採用率90%以上、開発者満足度8以上で終了
**学び**: 開発者を「顧客」として扱う / フィードバックを受け入れ迅速に改善 / 「使わせる」ではなく「選ばれる」を目指す

### 「開発者体験の革命」エンディング
**条件**: ゴールデンパス3つ以上確立、セルフサービス度8以上
**学び**: ゴールデンパスで「迷わない」体験を提供 / セルフサービスで「待たない」環境を実現 / 認知負荷を最小化し開発に集中

### 「組織を変えたプラットフォーム」エンディング
**条件**: 全ボーナス条件を達成（採用率90%、満足度8、負債2以下、ゴールデンパス3、セルフサービス8、Shadow ITなし）
**学び**: 技術だけでなく文化の変革として取り組む / フィードバックから学び続ける / 小さな成功を積み重ね信頼を獲得する
