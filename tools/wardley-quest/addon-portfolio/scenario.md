# 第1章: ゲーム概要

## 1.1 このゲームについて

**Portfolio Modernization Quest** は、Strategic Evolution Questの拡張として、**ITポートフォリオの戦略的管理とモダナイゼーション判断を学ぶ**戦略シミュレーションRPGです。

限られたリソースの中で、どのシステムに投資し、どのシステムを廃止するかの判断を下しながら、組織全体のIT資産を最適化します。

### 核心的な問い

> **「限られたリソースの中で、どのシステムにどれだけ投資すべきか？何を捨て、何を育てるべきか？」**

### ポートフォリオ管理の視点

| 従来のアプローチ | 戦略的ポートフォリオ管理 |
|---|---|
| 「壊れたら直す」 | ビジネス価値に基づく優先順位付け |
| 全てを維持しようとする | 戦略的に廃止・統合を判断 |
| 技術的負債を先送り | 計画的な負債返済 |
| コスト削減のみが目標 | 価値創造とコストのバランス |
| サイロ化した投資判断 | 全体最適の視点 |

### フレームワークの関係

1. **Wardley Mapping（進化の視点）**: 各システムの進化段階を可視化（Genesis → Custom → Product → Commodity）
2. **Core Domain Chart（DDDの視点）**: Core（差別化の源泉）/ Supporting（必要だが差別化ではない）/ Generic（外部化・標準化を検討）
3. **Portfolio Decision Matrix**: Invest（積極投資）/ Maintain（現状維持）/ Migrate（移行・統合）/ Sunset（廃止）

### プレイ形式

| 項目 | 内容 |
|---|---|
| プレイヤー | 1名（CTO/エンタープライズアーキテクト） |
| GM | Claude（シナリオ・判定・組織イベント） |
| 所要時間 | 60〜120分 |
| 前提 | Strategic Evolution Questの基礎知識（推奨） |

### コンパクトモード

コンテキスト節約のため、以下のコマンドが使えます：

| コマンド | 効果 |
|----------|------|
| 「コンパクトモード」 | 出力を1行要約+選択肢+状態のみに圧縮 |
| 「通常モード」 | 標準出力に戻す |
| 「状態確認」 | 現在のスコアのみ表示 |
| 「サマリー」 | これまでの決定を箇条書きで要約 |

## 1.2 ポートフォリオ管理の本質

### Nick Tuneの洞察

Architecture Modernizationでは、**ポートフォリオ管理は技術判断ではなくビジネス判断**であると強調されています。

| 視点 | 説明 |
|---|---|
| **ビジネス価値** | このシステムはどれだけのビジネス価値を生むか |
| **戦略的重要性** | 将来の競争優位にどう貢献するか |
| **技術的健全性** | 維持・進化にどれだけコストがかかるか |
| **リスク** | 障害・セキュリティ・コンプライアンスリスク |

### Core Domain Chartとは

縦軸: ビジネス差別化（低→高）、横軸: 複雑性（低→高）

| 分類 | 位置 | 方針 |
|---|---|---|
| **CORE** | 差別化 高 | 最優先投資、内製 |
| **SUPPORTING** | 差別化 中 | 必要だが差別化ではない |
| **GENERIC** | 差別化 低 | 外部化・標準化を検討 |

### ユーティリティIT vs 戦略的IT

Martin Fowlerの「ユーティリティIT vs 戦略的IT二分法」に基づく分類です。

| 分類 | 定義 | 投資方針 |
|---|---|---|
| **戦略的IT** | ビジネスの差別化に直接貢献。市場シェアを決定する要因。 | 社内で構築、最高の人材、積極投資 |
| **ユーティリティIT** | 差別化には貢献しないが必要。市場シェアへの影響なし。 | 既製品、SaaS、最小コスト |

**注：企業のITのうち戦略的となるのは5〜20%にすぎない**（Martin Fowler）

### 調整された運用モデル

戦略的ITとユーティリティITでは運用モデルを調整する（チームサイズ、スキル構成、アーキテクチャ深度、構築/購入判断など全てが異なる）。

# 第2章: ゲームルール

## 2.1 セッション構造

**Phase 1: ポートフォリオ分析** → システム一覧把握、Core Domain Chart分類、技術的健全性・ビジネス価値評価、Wardley Mapで進化段階確認

**Phase 2: 投資判断と実行（ターン制）** — 各ターン:
1. 環境イベント（D6 × 2）: ビジネス変化、技術進化、障害
2. 状況分析: 健全性 / アライメント / レガシー負荷 / 利用可能リソース
3. 投資配分決定: どのシステムにどれだけ投資するか
4. 判定（2D6 + 修正値）: 投資の成否を評価
5. 結果適用: システム状態・ビジネス価値・技術的負債の更新

**Phase 3: 評価とロードマップ更新** → 目標達成度判定、ROI評価、ロードマップ更新、学びの言語化

---

## 2.2 判定システム

### 基本判定（2D6）

| 出目 | 結果 | 効果 |
|:---:|---|---|
| 2 | **致命的失敗** | プロジェクト失敗。投資損失。信頼失墜。 |
| 3-4 | **失敗** | 目標未達。一部の投資が無駄に。 |
| 5-6 | **部分的失敗** | 限定的な成果。追加投資が必要。 |
| 7-8 | **部分的成功** | 基本目標は達成。予算超過。 |
| 9-10 | **成功** | 計画通りの成果。 |
| 11 | **大成功** | 予想以上の成果。追加のビジネス価値。 |
| 12 | **完全成功** | 最高の結果。ベストプラクティスとして認知。 |

### 修正値

#### 戦略的整合関連

| 状況 | 修正 | 根拠 |
|---|:---:|---|
| Core Domainへの投資 | +2 | 戦略的優先度が高い |
| Core Domain Chartに基づく判断 | +1 | 明確な根拠 |
| ビジネス部門との合意 | +2 | 組織的サポート |
| Wardley Mapで分析済み | +1 | 進化段階を考慮 |
| Generic領域への過剰投資 | -2 | 差別化に寄与しない |
| 戦略との不整合 | -2 | リソースの無駄 |

#### 技術的複雑性関連

| 状況 | 修正 | 根拠 |
|---|:---:|---|
| 明確な移行計画がある | +2 | リスク軽減 |
| 段階的アプローチ | +1 | 失敗時の影響限定 |
| 依存関係を把握している | +1 | 予期せぬ問題を回避 |
| 技術的負債が高い（6+） | -2 | 変更の困難さ |
| 依存関係が複雑 | -1 | 予期せぬ影響 |
| ビッグバン移行 | -2 | 高リスク |

#### 組織関連

| 状況 | 修正 | 根拠 |
|---|:---:|---|
| 経営層のスポンサーシップ | +2 | リソース確保 |
| チームのスキルが十分 | +1 | 実行能力 |
| 明確なオーナーシップ | +1 | 責任の明確化 |
| 政治的抵抗がある | -2 | 実行の障壁 |
| スキル不足 | -1 | 実行の困難さ |
| オーナー不在 | -2 | 責任の曖昧さ |

## 2.3 環境イベント

毎ターン開始時にD6を2回振り、2つのイベントが発生します。

### 環境イベント表

| D6 | イベント | 効果 | 対応のヒント |
|:---:|---|---|---|
| 1 | **ビジネス要件変更** | ビジネス部門から新機能要求。優先度の見直し。 | 戦略的重要性の再評価 |
| 2 | **技術の陳腐化** | 主要技術のサポート終了が発表。移行検討が必要。 | リスク評価と計画 |
| 3 | **競合の動き** | 競合が新サービスを発表。差別化の見直し。 | Core Domainの再評価 |
| 4 | **コスト圧力** | 予算削減要求。効率化が必要。 | Generic領域の外部化検討 |
| 5 | **セキュリティ問題** | 脆弱性が発見される。緊急対応が必要。 | リスク対応 |
| 6 | **M&A/組織変更** | 組織構造の変更。ポートフォリオ統合の機会。 | 全体最適の見直し |

### 常時適用パターン

| パターン | 効果 |
|---|---|
| **技術的負債は利息がつく** | 放置するほど返済コストが増大 |
| **レガシーは依存を増やす** | 統合が進むほど廃止が困難に |
| **Coreは変化する** | 今日のCoreが明日のGenericに |
| **政治は論理に勝る** | 正しい判断でも実行できないことがある |
| **完璧な計画は存在しない** | 不確実性を前提に意思決定 |

# 第3章: Core Domain Chart

## 3.1 概要

Core Domain Chartは、**ドメインをビジネス価値と複雑性で分類し、投資優先度を決定する**ためのフレームワークです。

### このフレームワークで答える問い

- 「このシステムは差別化に貢献しているか？」
- 「どこに最も優秀な人材を配置すべきか？」
- 「何を外部化・標準化できるか？」
- 「リソースをどう配分すべきか？」

---

## 3.2 ドメイン分類

| 分類 | 特徴 | 投資方針 | 例 |
|---|---|---|---|
| **Core** | 競争優位の源泉、他社と差別化、核心的価値 | 最優先投資、最高チーム配置、内製維持、継続的改善 | レコメンデーション、配送最適化、リスク分析 |
| **Supporting** | Coreを支援、差別化には直接寄与しない、ビジネス固有要件あり | 必要機能維持、過剰投資回避、部分的外部化、効率化重視 | 社内承認WF、サポートチケット管理、社内報告 |
| **Generic** | 業界共通、差別化に貢献しない、標準ソリューション存在 | 外部サービス利用、標準化、最小カスタマイズ、コスト最適化 | メール送信、認証・認可、請求・支払い |

---

## 3.3 判定への影響

| 状況 | 判定修正 |
|---|:---:|
| Core Domainへの投資 | +2 |
| Supporting Domainの効率化 | +1 |
| Generic Domainの外部化 | +1 |
| Core Domainの外部化 | -3 |
| Generic Domainへの過剰投資 | -2 |
| 分類なしの投資判断 | -1 |

# 第4章: モダナイゼーション戦略

## 4.1 概要

モダナイゼーションには複数のアプローチがあり、**状況に応じて最適な戦略を選択する**必要があります。

### 戦略の選択基準

| | 技術的複雑性 低 | 技術的複雑性 高 |
|---|---|---|
| **ビジネス価値 高** | Refactor（リファクタリング） | Rebuild（全面刷新） |
| **ビジネス価値 低** | Retire（廃止） | Replatform（リプラットフォーム） |

---

## 4.2 6つのR戦略

### Retire（廃止）

| 項目 | 内容 |
|---|---|
| **適用場面** | ビジネス価値がない、代替手段がある |
| **コスト** | 低（移行計画は必要） |
| **リスク** | 低〜中 |
| **期間** | 短期 |

判断基準: 利用者が極少 / 代替システム存在 / 維持コスト > ビジネス価値 / コンプライアンス問題なし

**人間的インパクト**: 担当者のアイデンティティ喪失、キャリア転換の必要性、感情的反発。推奨: 廃止理由の丁寧な説明、次のキャリアパス設計、知識移転期間の確保。

### Retain（現状維持）

| 項目 | 内容 |
|---|---|
| **適用場面** | 変更のリスク・コストが高く、現状で問題ない |
| **コスト** | 維持コストのみ |
| **リスク** | 低（短期）、高（長期） |
| **期間** | 継続 |

判断基準: 安定稼働 / 変更のビジネス理由なし / 移行コスト過大 / 近い将来廃止予定

**人間的インパクト**: 「塩漬け」チームの士気低下、スキル陳腐化、キャリア停滞感。推奨: 戦略的意義の説明、新技術に触れる機会提供、将来の主導的役割の約束。

### Rehost（Lift-and-Shift）

| 項目 | 内容 |
|---|---|
| **適用場面** | インフラのみ移行、アプリは変更なし |
| **コスト** | 中 |
| **リスク** | 低〜中 |
| **期間** | 短期〜中期 |

判断基準: クラウド移行必要 / アプリ変更余裕なし / 運用コスト削減目的 / 将来最適化は後回し

**人間的インパクト**: インフラチームのスキルギャップ、本質的改善でない物足りなさ、一時的負荷増大。推奨: クラウド研修の事前実施、「まず動かす、後で最適化」戦略の共有。

### Replatform（リプラットフォーム）

| 項目 | 内容 |
|---|---|
| **適用場面** | 一部最適化しながらクラウド移行 |
| **コスト** | 中〜高 |
| **リスク** | 中 |
| **期間** | 中期 |

判断基準: クラウドネイティブ機能活用 / DB マネージド化 / コンテナ化 / 大規模変更は回避

**人間的インパクト**: 学習曲線のストレス、「どこまで変えるか」の曖昧さ、成功定義の不明確さ。推奨: 変更範囲のチェックリスト定義、ペアプロで知識移転、Quick Win の早期達成。

### Refactor（リファクタリング）

| 項目 | 内容 |
|---|---|
| **適用場面** | アーキテクチャの根本的な改善 |
| **コスト** | 高 |
| **リスク** | 中〜高 |
| **期間** | 中期〜長期 |

判断基準: アーキテクチャが古く拡張性なし / マイクロサービス化必要 / ビジネス価値が高く継続投資必要

**人間的インパクト**: 高い期待と長期疲弊リスク、スキルミスマッチへの不安。推奨: マイルストーンで進捗可視化、定期振り返り、スキルギャップ研修、段階的改善の許容。

### Replace（置換）

| 項目 | 内容 |
|---|---|
| **適用場面** | SaaS/パッケージへの移行 |
| **コスト** | 中〜高 |
| **リスク** | 中 |
| **期間** | 中期 |

判断基準: 市場に優れた既製品がある / Generic領域で差別化に貢献しない

**人間的インパクト**: 「作った意味がなかった」という喪失感、役割の根本変化（開発者→管理者）。推奨: 内製経験がSaaS選定に活きることを伝える、空きリソースをCore Domainへ振り向けるビジョン共有。

> **Note**: 6つのRは技術的判断であると同時に人間的判断。各戦略がチームのキャリアと心理にどう影響するか常に考慮すること。

---

## 4.3 ストラングラーフィグパターン

### 段階的移行の原則

1. **Phase 1**: ファサード導入 → レガシー（100%）
2. **Phase 2**: ファサード → 新（30%）+ 旧（70%）を段階的に移行

# 第5章: 投資判断フレームワーク

## 5.1 概要

投資判断は、**ビジネス価値、技術的健全性、リスク、コストを総合的に評価**して行います。

---

## 5.2 投資判断マトリクス

### 4つの象限

| | 技術的健全性 高 | 技術的健全性 低 |
|---|---|---|
| **ビジネス価値 高** | Invest（積極投資）健全で重要 | Transform（変革投資）重要だが問題あり |
| **ビジネス価値 低** | Tolerate（許容）健全だが重要度低 | Sunset（廃止）問題あり・重要度低 |

### 各象限の戦略

| 象限 | 戦略 | アクション |
|---|---|---|
| **Invest** | 積極投資 | 新機能開発、チーム強化、競争優位の維持 |
| **Transform** | 変革投資 | モダナイゼーション、技術的負債返済、アーキテクチャ刷新 |
| **Tolerate** | 許容 | 最小限の維持、効率化、外部化検討 |
| **Sunset** | 廃止 | 計画的な廃止、代替手段への移行 |

---

## 5.3 優先順位付けの基準

### スコアリングモデル

| 評価項目 | 重み | 説明 |
|---|:---:|---|
| **ビジネスインパクト** | 30% | ビジネス価値への貢献度 |
| **戦略的整合性** | 25% | Core Domain Chartとの整合 |
| **技術的リスク** | 20% | 障害・セキュリティリスク |
| **実現可能性** | 15% | スキル・リソースの可用性 |
| **コスト効率** | 10% | 投資対効果 |

優先度スコア = ビジネスインパクト(30%) + 戦略的整合性(25%) + 技術的リスク(20%) + 実現可能性(15%) + コスト効率(10%)
