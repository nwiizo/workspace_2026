# 第1章: ゲーム概要

## 1.1 このゲームについて

**Portfolio Modernization Quest** は、Strategic Evolution Questの拡張として、**ITポートフォリオの戦略的管理とモダナイゼーション判断を学ぶ**戦略シミュレーションRPGです。

限られたリソースの中で、どのシステムに投資し、どのシステムを廃止するかの判断を下しながら、組織全体のIT資産を最適化します。

### 核心的な問い

> **「限られたリソースの中で、どのシステムにどれだけ投資すべきか？何を捨て、何を育てるべきか？」**

### ポートフォリオ管理の視点

| 従来のアプローチ | 戦略的ポートフォリオ管理 |
|---|---|
| 「壊れたら直す」 | ビジネス価値に基づく優先順位付け |
| 全てを維持しようとする | 戦略的に廃止・統合を判断 |
| 技術的負債を先送り | 計画的な負債返済 |
| コスト削減のみが目標 | 価値創造とコストのバランス |
| サイロ化した投資判断 | 全体最適の視点 |

## 1.2 ポートフォリオ管理の本質

### Nick Tuneの洞察

Architecture Modernizationでは、**ポートフォリオ管理は技術判断ではなくビジネス判断**であると強調されています。

| 視点 | 説明 |
|---|---|
| **ビジネス価値** | このシステムはどれだけのビジネス価値を生むか |
| **戦略的重要性** | 将来の競争優位にどう貢献するか |
| **技術的健全性** | 維持・進化にどれだけコストがかかるか |
| **リスク** | 障害・セキュリティ・コンプライアンスリスク |

### Core Domain Chartとは

```
┌─────────────────────────────────────────────────────────────┐
│  Core Domain Chart                                          │
│                                                             │
│  ビジネス差別化（高）                                       │
│        ↑                                                    │
│        │    ┌───────────────┐                              │
│        │    │    CORE       │ ← 最優先投資、内製          │
│        │    │  差別化の源泉  │                              │
│        │    └───────────────┘                              │
│        │                                                    │
│        │    ┌───────────────┐                              │
│        │    │  SUPPORTING   │ ← 必要だが差別化ではない     │
│        │    │   サポート     │                              │
│        │    └───────────────┘                              │
│        │                                                    │
│        │    ┌───────────────┐                              │
│        │    │   GENERIC     │ ← 外部化・標準化を検討       │
│        │    │   汎用         │                              │
│        │    └───────────────┘                              │
│        │                                                    │
│  ビジネス差別化（低）                                       │
│                                                             │
│  複雑性: 低 ─────────────────────────────────→ 高          │
└─────────────────────────────────────────────────────────────┘
```

### ユーティリティIT vs 戦略的IT

Martin Fowlerの「ユーティリティIT vs 戦略的IT二分法」に基づく分類です。

| 分類 | 定義 | 投資方針 |
|---|---|---|
| **戦略的IT** | ビジネスの差別化に直接貢献。市場シェアを決定する要因。 | 社内で構築、最高の人材、積極投資 |
| **ユーティリティIT** | 差別化には貢献しないが必要。市場シェアへの影響なし。 | 既製品、SaaS、最小コスト |

**注：企業のITのうち戦略的となるのは5〜20%にすぎない**（Martin Fowler）

### モデルの複雑さの種類

| 複雑さの種類 | 説明 |
|---|---|
| **ユーザーニーズ発見の複雑さ** | 満たされていないユーザーニーズを特定する労力 |
| **プロダクト設計の複雑さ** | 効果的なUIやUXを設計する難しさ |
| **ドメインモデル設計の複雑さ** | ビジネスルールやアルゴリズムの複雑さ |
| **cruft（回避可能な複雑さ）** | 技術的負債。現在のコードと理想のコードの差異 |
| **スケールの複雑さ** | 運用規模の大きさによる複雑さ |
| **統合の複雑さ** | 他システムとの連携の難しさ |
| **運用の複雑さ** | 手動プロセスやスプレッドシートでの管理 |

### 調整された運用モデル

戦略的ITとユーティリティITでは、運用モデルの各側面を調整する。

| 側面 | 戦略的IT | ユーティリティIT |
|---|---|---|
| **チームサイズ** | より大きなチーム | 最小限 |
| **チーム構成** | 経験豊富な人材 | 一般的なスキル |
| **コラボレーション** | イベントストーミング等を活用 | 最小限の調整 |
| **ディスカバリー** | 積極的な探索 | 要件に基づく |
| **アーキテクチャ** | 高度なパターン | シンプルな技術 |
| **ドメインモデリング** | 豊富なモデル開発 | 基本的なCRUD |
| **構築/購入判断** | 社内で構築 | 既製品・SaaS |

## 1.3 ゲームの厳しさについて

このゲームでは以下のことが起こります：

| 現象 | 説明 | 学び |
|---|---|---|
| **リソース不足** | 全てを同時には改善できない | 優先順位の重要性 |
| **政治的抵抗** | 「うちのシステムを廃止するな」 | ステークホルダー管理 |
| **技術的負債の利息** | 放置するほどコストが増大 | 早期対処の価値 |
| **予想外の依存関係** | 廃止しようとしたら他が動かない | 影響分析の重要性 |
| **短期と長期のトレードオフ** | 今の効率 vs 将来の柔軟性 | 戦略的視点 |
| **機会損失** | 投資しなかったシステムが重要に | 不確実性への対応 |

**これらは現実の組織が直面するポートフォリオ管理の課題です。**

## 2.2 判定システム

### 基本判定（2D6）

| 出目 | 結果 | 効果 |
|:---:|---|---|
| 2 | **致命的失敗** | プロジェクト失敗。投資損失。信頼失墜。 |
| 3-4 | **失敗** | 目標未達。一部の投資が無駄に。 |
| 5-6 | **部分的失敗** | 限定的な成果。追加投資が必要。 |
| 7-8 | **部分的成功** | 基本目標は達成。予算超過。 |
| 9-10 | **成功** | 計画通りの成果。 |
| 11 | **大成功** | 予想以上の成果。追加のビジネス価値。 |
| 12 | **完全成功** | 最高の結果。ベストプラクティスとして認知。 |

### 修正値

#### 戦略的整合関連

| 状況 | 修正 | 根拠 |
|---|:---:|---|
| Core Domainへの投資 | +2 | 戦略的優先度が高い |
| Core Domain Chartに基づく判断 | +1 | 明確な根拠 |
| ビジネス部門との合意 | +2 | 組織的サポート |
| Wardley Mapで分析済み | +1 | 進化段階を考慮 |
| Generic領域への過剰投資 | -2 | 差別化に寄与しない |
| 戦略との不整合 | -2 | リソースの無駄 |

#### 技術的複雑性関連

| 状況 | 修正 | 根拠 |
|---|:---:|---|

## 2.3 環境イベント

毎ターン開始時にD6を2回振り、2つのイベントが発生します。

### 環境イベント表

| D6 | イベント | 効果 | 対応のヒント |
|:---:|---|---|---|
| 1 | **ビジネス要件変更** | ビジネス部門から新機能要求。優先度の見直し。 | 戦略的重要性の再評価 |
| 2 | **技術の陳腐化** | 主要技術のサポート終了が発表。移行検討が必要。 | リスク評価と計画 |
| 3 | **競合の動き** | 競合が新サービスを発表。差別化の見直し。 | Core Domainの再評価 |
| 4 | **コスト圧力** | 予算削減要求。効率化が必要。 | Generic領域の外部化検討 |
| 5 | **セキュリティ問題** | 脆弱性が発見される。緊急対応が必要。 | リスク対応 |
| 6 | **M&A/組織変更** | 組織構造の変更。ポートフォリオ統合の機会。 | 全体最適の見直し |

### 常時適用パターン

| パターン | 効果 |
|---|---|
| **技術的負債は利息がつく** | 放置するほど返済コストが増大 |
| **レガシーは依存を増やす** | 統合が進むほど廃止が困難に |
| **Coreは変化する** | 今日のCoreが明日のGenericに |
| **政治は論理に勝る** | 正しい判断でも実行できないことがある |
| **完璧な計画は存在しない** | 不確実性を前提に意思決定 |

# 第3章: Core Domain Chart

## 3.1 概要

Core Domain Chartは、**ドメインをビジネス価値と複雑性で分類し、投資優先度を決定する**ためのフレームワークです。

### このフレームワークで答える問い

- 「このシステムは差別化に貢献しているか？」
- 「どこに最も優秀な人材を配置すべきか？」
- 「何を外部化・標準化できるか？」
- 「リソースをどう配分すべきか？」

---

## 3.2 ドメイン分類

### Core Domain

```
┌─────────────────────────────────────────────────────────────┐
│  Core Domain                                                │
│                                                             │
│  特徴:                                                      │
│  ・競争優位の源泉                                           │
│  ・他社と差別化される領域                                   │
│  ・ビジネスの核心的価値を提供                               │
│                                                             │
│  投資方針:                                                  │
│  ・最優先で投資                                             │
│  ・最高のチームを配置                                       │
│  ・内製を維持                                               │
│  ・継続的な改善と革新                                       │
│                                                             │
│  例:                                                        │
│  ・ECサイトのレコメンデーションエンジン                     │
│  ・物流企業の配送最適化システム                             │
│  ・金融機関のリスク分析システム                             │
└─────────────────────────────────────────────────────────────┘
```

### Supporting Domain

```
┌─────────────────────────────────────────────────────────────┐
│  Supporting Domain                                          │
│                                                             │
│  特徴:                                                      │
│  ・Coreを支援するために必要                                 │
│  ・差別化には直接貢献しない                                 │
│  ・ビジネス固有の要件がある                                 │
│                                                             │
│  投資方針:                                                  │
│  ・必要な機能を維持                                         │
│  ・過剰投資を避ける                                         │
│  ・部分的な外部化を検討                                     │
│  ・効率化を重視                                             │
│                                                             │
│  例:                                                        │
│  ・社内承認ワークフロー                                     │
│  ・顧客サポートチケット管理                                 │
│  ・社内報告システム                                         │
└─────────────────────────────────────────────────────────────┘
```

### Generic Domain

```
┌─────────────────────────────────────────────────────────────┐
│  Generic Domain                                             │
│                                                             │
│  特徴:                                                      │
│  ・業界で共通の機能                                         │
│  ・差別化には貢献しない                                     │
│  ・標準的なソリューションが存在                             │
│                                                             │
│  投資方針:                                                  │
│  ・外部サービス/製品の利用                                  │
│  ・標準化・コモディティ化                                   │
│  ・最小限のカスタマイズ                                     │
│  ・コスト最適化を重視                                       │
│                                                             │
│  例:                                                        │
│  ・メール送信                                               │
│  ・認証・認可                                               │
│  ・請求・支払い（特殊要件がない場合）                       │
└─────────────────────────────────────────────────────────────┘
```

---

## 3.3 判定への影響

| 状況 | 判定修正 |
|---|:---:|
| Core Domainへの投資 | +2 |
| Supporting Domainの効率化 | +1 |
| Generic Domainの外部化 | +1 |
| Core Domainの外部化 | -3 |
| Generic Domainへの過剰投資 | -2 |
| 分類なしの投資判断 | -1 |

# 第4章: モダナイゼーション戦略

## 4.1 概要

モダナイゼーションには複数のアプローチがあり、**状況に応じて最適な戦略を選択する**必要があります。

### 戦略の選択基準

```
┌─────────────────────────────────────────────────────────────┐
│  モダナイゼーション戦略の選択                                │
│                                                             │
│  ビジネス価値                                               │
│     高 │    Refactor     │    Rebuild                      │
│        │  (リファクタリング) │   (全面刷新)                   │
│        ├─────────────────┼─────────────────────            │
│     低 │    Retire       │    Replatform                   │
│        │   (廃止)        │  (リプラットフォーム)              │
│        └─────────────────┴─────────────────────            │
│              低                  高                         │
│                    技術的複雑性                             │
└─────────────────────────────────────────────────────────────┘
```

---

## 4.2 6つのR戦略

### Retire（廃止）

| 項目 | 内容 |
|---|---|
| **適用場面** | ビジネス価値がない、代替手段がある |
| **コスト** | 低（移行計画は必要） |
| **リスク** | 低〜中 |
| **期間** | 短期 |

```
判断基準:
・利用者がいない、または極めて少ない
・同じ機能を持つ別システムが存在
・維持コストがビジネス価値を上回る
・コンプライアンス上の問題がない
```

**人間的インパクト:**
```
┌─────────────────────────────────────────────────────────────┐
│ チームへの影響                                              │
├─────────────────────────────────────────────────────────────┤
│ • 担当者のアイデンティティ喪失リスク                        │
│   「10年育ててきたシステムが廃止される」                    │
│ • キャリア転換の必要性                                      │
│   新しいスキル習得か、別プロジェクトへの移動                │
│ • 感情的反発への対応                                        │
│   「必要ない」=「あなたの仕事は無駄だった」と受け取られる   │
├─────────────────────────────────────────────────────────────┤
│ 推奨アプローチ:                                             │
│ • 廃止理由を丁寧に説明し、担当者の貢献を認める              │
│ • 次のキャリアパスを一緒に設計する                          │
│ • 知識移転期間を十分に確保する                              │
└─────────────────────────────────────────────────────────────┘
```

### Retain（現状維持）

| 項目 | 内容 |
|---|---|
| **適用場面** | 変更のリスク・コストが高く、現状で問題ない |
| **コスト** | 維持コストのみ |
| **リスク** | 低（短期）、高（長期） |
| **期間** | 継続 |

```
判断基準:
・安定稼働している
・変更するビジネス理由がない
・移行コストが高すぎる
・近い将来に廃止予定
```

**人間的インパクト:**
```
┌─────────────────────────────────────────────────────────────┐
│ チームへの影響                                              │
├─────────────────────────────────────────────────────────────┤
│ • 「塩漬け」チームの士気低下リスク                          │
│   「うちのシステムは投資対象外なんだ」                      │
│ • スキルの陳腐化                                            │
│   レガシー技術のみを扱い続けることへの不安                  │
│ • キャリア停滞感                                            │
│   「このままでいいのか」という焦り                          │
├─────────────────────────────────────────────────────────────┤
│ 推奨アプローチ:                                             │
│ • 「現状維持」の戦略的意義を明確に説明する                  │
│ • 20%ルールなどで新技術に触れる機会を作る                   │
│ • 将来のモダナイゼーション時に主導的役割を約束する          │
└─────────────────────────────────────────────────────────────┘
```

### Rehost（Lift-and-Shift）

| 項目 | 内容 |
|---|---|
| **適用場面** | インフラのみ移行、アプリは変更なし |
| **コスト** | 中 |
| **リスク** | 低〜中 |
| **期間** | 短期〜中期 |

```
判断基準:
・クラウド移行が必要
・アプリケーション変更の余裕がない
・運用コスト削減が目的
・将来的な最適化は後回し
```

**人間的インパクト:**
```
┌─────────────────────────────────────────────────────────────┐
│ チームへの影響                                              │
├─────────────────────────────────────────────────────────────┤
│ • インフラチームのスキルギャップ                            │
│   オンプレからクラウドへの急激な変化                        │
│ • 「本質的な改善ではない」という物足りなさ                  │
│   「どうせ移行するなら、もっと良くしたかった」              │
│ • 一時的な負荷増大                                          │
│   移行作業と通常運用の両立                                  │
├─────────────────────────────────────────────────────────────┤
│ 推奨アプローチ:                                             │
│ • クラウド研修を移行前に実施する                            │
│ • 「まず動かす、後で最適化」の戦略を共有                    │
│ • 移行後の最適化フェーズへの参加を約束する                  │
└─────────────────────────────────────────────────────────────┘
```

### Replatform（リプラットフォーム）

| 項目 | 内容 |
|---|---|
| **適用場面** | 一部最適化しながらクラウド移行 |
| **コスト** | 中〜高 |
| **リスク** | 中 |
| **期間** | 中期 |

```
判断基準:
・クラウドネイティブ機能を活用したい
・データベースのマネージド化
・コンテナ化による運用効率化
・大規模な変更は避けたい
```

**人間的インパクト:**
```
┌─────────────────────────────────────────────────────────────┐
│ チームへの影響                                              │
├─────────────────────────────────────────────────────────────┤
│ • 学習曲線のストレス                                        │
│   新しいプラットフォーム技術の習得が必要                    │
│ • 判断の曖昧さへの不安                                      │
│   「どこまで変えるのか」の線引きが難しい                    │
│ • 成功の定義が曖昧                                          │
│   「最適化」の程度は人により異なる                          │
├─────────────────────────────────────────────────────────────┤
│ 推奨アプローチ:                                             │
│ • 変更範囲を明確なチェックリストで定義                      │
│ • ペアプログラミングで知識移転を促進                        │
│ • 小さな成功を早期に祝う（Quick Win）                       │
└─────────────────────────────────────────────────────────────┘
```

### Refactor（リファクタリング）

| 項目 | 内容 |
|---|---|
| **適用場面** | アーキテクチャの根本的な改善 |
| **コスト** | 高 |
| **リスク** | 中〜高 |
| **期間** | 中期〜長期 |

```
判断基準:
・アーキテクチャが古く拡張性がない
・マイクロサービス化が必要
・クラウドネイティブ化
・ビジネス価値が高く継続投資が必要
```

**人間的インパクト:**
```
┌─────────────────────────────────────────────────────────────┐
│ チームへの影響                                              │
├─────────────────────────────────────────────────────────────┤
│ • 高いモチベーションと高い期待                              │
│   「やっと本格的に改善できる」という興奮                    │
│ • 長期プロジェクトへの疲弊リスク                            │
│   「終わりが見えない」という焦り                            │
│ • スキルのミスマッチ                                        │
│   新アーキテクチャに対応できるか不安                        │
├─────────────────────────────────────────────────────────────┤
│ 推奨アプローチ:                                             │
│ • 明確なマイルストーンで進捗を可視化する                    │
│ • 定期的な振り返りでチームの健康状態を確認                  │
│ • スキルギャップを埋める研修・メンタリングを提供            │
│ • 「完璧」を求めず、段階的な改善を許容する                  │
└─────────────────────────────────────────────────────────────┘
```

### Replace（置換）

| 項目 | 内容 |
|---|---|
| **適用場面** | SaaS/パッケージへの移行 |
| **コスト** | 中〜高 |
| **リスク** | 中 |
| **期間** | 中期 |

```
判断基準:
・市場に優れた既製品がある
・差別化に貢献しないGeneric領域
```

**人間的インパクト:**
```
┌─────────────────────────────────────────────────────────────┐
│ チームへの影響                                              │
├─────────────────────────────────────────────────────────────┤
│ • 「作った意味がなかった」という喪失感                      │
│   内製システムへの愛着と誇りの否定                          │
│ • 役割の根本的変化                                          │
│   開発者から管理者/設定者へのシフト                         │
│ • 「外注＝楽」への誤解                                      │
│   SaaSも運用・カスタマイズは必要                            │
├─────────────────────────────────────────────────────────────┤
│ 推奨アプローチ:                                             │
│ • 内製の経験が SaaS 選定・運用に活きることを伝える          │
│ • 新しい役割（ベンダー管理、インテグレーション）の価値を示す│
│ • 置換で空いたリソースをCore Domainへ振り向けるビジョンを共有│
└─────────────────────────────────────────────────────────────┘
```

> **Note**: 6つのRは技術的判断だけでなく、人間的判断でもあります。
> 各戦略がチームメンバーのキャリアと心理にどう影響するかを常に考慮してください。

# 第5章: 投資判断フレームワーク

## 5.1 概要

投資判断は、**ビジネス価値、技術的健全性、リスク、コストを総合的に評価**して行います。

---

## 5.2 投資判断マトリクス

### 4つの象限

```
┌─────────────────────────────────────────────────────────────┐
│  投資判断マトリクス                                          │
│                                                             │
│  ビジネス価値                                               │
│     高 │   Invest       │   Transform                      │
│        │  （積極投資）   │   （変革投資）                    │
│        │  健全で重要     │   重要だが問題あり                │
│        ├─────────────────┼─────────────────────            │
│     低 │   Tolerate     │   Sunset                         │
│        │  （許容）       │   （廃止）                        │
│        │  健全だが重要度低│   問題あり・重要度低              │
│        └─────────────────┴─────────────────────            │
│              高                  低                         │
│                    技術的健全性                             │
└─────────────────────────────────────────────────────────────┘
```

### 各象限の戦略

| 象限 | 戦略 | アクション |
|---|---|---|
| **Invest** | 積極投資 | 新機能開発、チーム強化、競争優位の維持 |
| **Transform** | 変革投資 | モダナイゼーション、技術的負債返済、アーキテクチャ刷新 |
| **Tolerate** | 許容 | 最小限の維持、効率化、外部化検討 |
| **Sunset** | 廃止 | 計画的な廃止、代替手段への移行 |

---

## 5.3 優先順位付けの基準

### スコアリングモデル

| 評価項目 | 重み | 説明 |
|---|:---:|---|
| **ビジネスインパクト** | 30% | ビジネス価値への貢献度 |
| **戦略的整合性** | 25% | Core Domain Chartとの整合 |
| **技術的リスク** | 20% | 障害・セキュリティリスク |
| **実現可能性** | 15% | スキル・リソースの可用性 |
| **コスト効率** | 10% | 投資対効果 |

### 優先順位の決定

```
優先度スコア =
  (ビジネスインパクト × 0.30) +
  (戦略的整合性 × 0.25) +
  (技術的リスク × 0.20) +
  (実現可能性 × 0.15) +
  (コスト効率 × 0.10)
```

# 第7章: 勝敗と評価

## 7.1 終了条件

以下のいずれかで終了：

- 指定ターン数の完了
- ポートフォリオ健全性が0（敗北：運用不能）
- 全ての目標システムのモダナイゼーション完了（早期勝利）

## 7.2 評価基準

### 基本得点

| 条件 | ポイント |
|---|:---:|
| 生存（ターン完了） | +10 |
| 主要目標達成 | +10 |

### ボーナス

| 条件 | ポイント |
|---|:---:|
| ポートフォリオ健全性8以上 | +10 |
| ビジネスアライメント8以上 | +10 |
| Core Domainへの集中投資 | +5 |
| レガシー負荷50%以下に削減 | +5 |
| 計画的なSunset実行 | +3 |
| ROI目標達成 | +5 |

### ペナルティ

| 条件 | ポイント |

# 第10章: RPG強化システム

このゲームでは、学習体験を強化するための要素を導入しています。これらの要素は**オプション**であり、基本ルールのみでもプレイ可能です。

> **推奨**: 最初の1〜2ゲームは基本ルール（第1〜9章）のみでプレイし、ゲームに慣れてから本章のシステムを段階的に導入してください。

## 10.1 プレイヤースペシャリティ

プレイヤーは「エンタープライズアーキテクト」として、以下の4つのスペシャリティから1つを選択できます。

### スペシャリティ一覧

| スペシャリティ | 特徴 | 判定ボーナス | 特殊能力（1ゲーム1回） |
|--------|------|:---:|---|
| **ポートフォリオストラテジスト** | 全体最適と優先順位付けに優れる | 投資判断+1 | 「戦略的優先順位」: 投資配分の判定を自動成功 |
| **モダナイゼーションアーキテクト** | 移行戦略と技術選定に強い | モダナイゼーション+1 | 「最適な移行パス」: 6つのR判定を自動成功 |
| **ビジネスアナリスト** | ビジネス価値とROIの分析が得意 | アライメント+1 | 「ビジネスケース」: 経営報告判定を自動成功かつスポンサーシップ+2 |
| **テクニカルデットマネージャー** | 負債管理と合理化に長ける | 負債削減+1 | 「技術的清算」: 技術的負債を即座に-3 |

### スペシャリティ選択のヒント

## 10.2 NPCシステム

ゲーム中に登場する記憶に残るステークホルダーNPCです。

> **Note**: 以下のNPCは代表的な役割パターンです。GMはシナリオのテーマや複雑さに応じて、NPCの追加・削除・変更を自由に行えます。

### 経営層NPC

| NPC | 役職 | 特徴 | 関係値の影響 |
|-----|------|------|-------------|
| **西田CIO** | 最高情報責任者 | ROI重視、政治的手腕 | 良好: 予算確保+2、悪化: 投資承認遅延 |
| **森CFO** | 最高財務責任者 | コスト削減重視、慎重派 | 良好: 予算超過ペナルティ軽減、悪化: 予算カット |

### IT部門NPC

| NPC | 役職 | 特徴 | 関係値の影響 |
|-----|------|------|-------------|
| **加藤インフラリード** | インフラチームリーダー | 安定運用重視、変化に慎重 | 良好: 移行リスク軽減+1、悪化: 抵抗 |
| **山本開発マネージャー** | 開発部門長 | モダナイゼーション推進派 | 良好: 開発効率+1、悪化: リソース競合 |
| **林ベテランSE** | 20年勤務のシステムエンジニア | レガシーの生き字引、退職リスク | 良好: 暗黙知+2、悪化: 知識喪失リスク |

### 関係値システム

NPCとの関係値は **-3〜+3** の範囲で変動します。

| 関係値 | 状態 | 効果 |
|:---:|---|---|
| +3 | 強い信頼 | 積極的支援、リソース優先配分 |
| +1〜+2 | 良好 | 協力的、必要な情報提供 |
| 0 | 中立 | 標準的な対応 |
| -1〜-2 | 警戒 | 消極的協力、情報出し渋り |
| -3 | 敵対 | 積極的妨害、政治的ブロック |

### 関係値の変動

| 行動 | 変動 |
|------|:---:|
| NPCの懸念に対処した判断 | +1 |
| NPCの意見を計画に反映 | +1 |
| NPCの成功を経営に報告 | +1 |
| NPCの意見を無視した判断 | -1 |
| NPCの担当領域を急に変更 | -1 |
| NPCの担当システムを廃止決定 | -2 |
