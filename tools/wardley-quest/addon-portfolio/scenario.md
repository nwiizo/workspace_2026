# 第1章: ゲーム概要

## 1.1 このゲームについて

**Portfolio Modernization Quest** は、Strategic Evolution Questの拡張として、**ITポートフォリオの戦略的管理とモダナイゼーション判断を学ぶ**戦略シミュレーションRPGです。

限られたリソースの中で、どのシステムに投資し、どのシステムを廃止するかの判断を下しながら、組織全体のIT資産を最適化します。

### 核心的な問い

> **「限られたリソースの中で、どのシステムにどれだけ投資すべきか？何を捨て、何を育てるべきか？」**

### ポートフォリオ管理の視点

| 従来のアプローチ | 戦略的ポートフォリオ管理 |
|---|---|
| 「壊れたら直す」 | ビジネス価値に基づく優先順位付け |
| 全てを維持しようとする | 戦略的に廃止・統合を判断 |
| 技術的負債を先送り | 計画的な負債返済 |
| コスト削減のみが目標 | 価値創造とコストのバランス |
| サイロ化した投資判断 | 全体最適の視点 |

## 1.2 ポートフォリオ管理の本質

### Nick Tuneの洞察

Architecture Modernizationでは、**ポートフォリオ管理は技術判断ではなくビジネス判断**であると強調されています。

| 視点 | 説明 |
|---|---|
| **ビジネス価値** | このシステムはどれだけのビジネス価値を生むか |
| **戦略的重要性** | 将来の競争優位にどう貢献するか |
| **技術的健全性** | 維持・進化にどれだけコストがかかるか |
| **リスク** | 障害・セキュリティ・コンプライアンスリスク |

## 1.3 ゲームの厳しさについて

このゲームでは以下のことが起こります：

| 現象 | 説明 | 学び |
|---|---|---|
| **リソース不足** | 全てを同時には改善できない | 優先順位の重要性 |
| **政治的抵抗** | 「うちのシステムを廃止するな」 | ステークホルダー管理 |
| **技術的負債の利息** | 放置するほどコストが増大 | 早期対処の価値 |
| **予想外の依存関係** | 廃止しようとしたら他が動かない | 影響分析の重要性 |
| **短期と長期のトレードオフ** | 今の効率 vs 将来の柔軟性 | 戦略的視点 |
| **機会損失** | 投資しなかったシステムが重要に | 不確実性への対応 |

**これらは現実の組織が直面するポートフォリオ管理の課題です。**

## 2.2 判定システム

### 基本判定（2D6）

| 出目 | 結果 | 効果 |
|:---:|---|---|
| 2 | **致命的失敗** | プロジェクト失敗。投資損失。信頼失墜。 |
| 3-4 | **失敗** | 目標未達。一部の投資が無駄に。 |
| 5-6 | **部分的失敗** | 限定的な成果。追加投資が必要。 |
| 7-8 | **部分的成功** | 基本目標は達成。予算超過。 |
| 9-10 | **成功** | 計画通りの成果。 |
| 11 | **大成功** | 予想以上の成果。追加のビジネス価値。 |
| 12 | **完全成功** | 最高の結果。ベストプラクティスとして認知。 |

### 修正値

#### 戦略的整合関連

| 状況 | 修正 | 根拠 |
|---|:---:|---|
| Core Domainへの投資 | +2 | 戦略的優先度が高い |
| Core Domain Chartに基づく判断 | +1 | 明確な根拠 |
| ビジネス部門との合意 | +2 | 組織的サポート |
| Wardley Mapで分析済み | +1 | 進化段階を考慮 |
| Generic領域への過剰投資 | -2 | 差別化に寄与しない |
| 戦略との不整合 | -2 | リソースの無駄 |

#### 技術的複雑性関連

| 状況 | 修正 | 根拠 |
|---|:---:|---|
| 明確な移行計画がある | +2 | リスク軽減 |
| 段階的アプローチ | +1 | 失敗時の影響限定 |
| 依存関係を把握している | +1 | 予期せぬ問題を回避 |
| 技術的負債が高い（6+） | -2 | 変更の困難さ |
| 依存関係が複雑 | -1 | 予期せぬ影響 |
| ビッグバン移行 | -2 | 高リスク |

#### 組織関連

| 状況 | 修正 | 根拠 |
|---|:---:|---|
| 経営層のスポンサーシップ | +2 | リソース確保 |
| チームのスキルが十分 | +1 | 実行能力 |
| 明確なオーナーシップ | +1 | 責任の明確化 |
| 政治的抵抗がある | -2 | 実行の障壁 |

## 2.3 環境イベント

毎ターン開始時にD6を2回振り、2つのイベントが発生します。

### 環境イベント表

| D6 | イベント | 効果 | 対応のヒント |
|:---:|---|---|---|
| 1 | **ビジネス要件変更** | ビジネス部門から新機能要求。優先度の見直し。 | 戦略的重要性の再評価 |
| 2 | **技術の陳腐化** | 主要技術のサポート終了が発表。移行検討が必要。 | リスク評価と計画 |
| 3 | **競合の動き** | 競合が新サービスを発表。差別化の見直し。 | Core Domainの再評価 |
| 4 | **コスト圧力** | 予算削減要求。効率化が必要。 | Generic領域の外部化検討 |
| 5 | **セキュリティ問題** | 脆弱性が発見される。緊急対応が必要。 | リスク対応 |
| 6 | **M&A/組織変更** | 組織構造の変更。ポートフォリオ統合の機会。 | 全体最適の見直し |

### 常時適用パターン

| パターン | 効果 |
|---|---|
| **技術的負債は利息がつく** | 放置するほど返済コストが増大 |
| **レガシーは依存を増やす** | 統合が進むほど廃止が困難に |
| **Coreは変化する** | 今日のCoreが明日のGenericに |
| **政治は論理に勝る** | 正しい判断でも実行できないことがある |
| **完璧な計画は存在しない** | 不確実性を前提に意思決定 |

# 第3章: Core Domain Chart

## 3.1 概要

Core Domain Chartは、**ドメインをビジネス価値と複雑性で分類し、投資優先度を決定する**ためのフレームワークです。

### このフレームワークで答える問い

- 「このシステムは差別化に貢献しているか？」
- 「どこに最も優秀な人材を配置すべきか？」
- 「何を外部化・標準化できるか？」
- 「リソースをどう配分すべきか？」

---

# 第4章: モダナイゼーション戦略

## 4.1 概要

モダナイゼーションには複数のアプローチがあり、**状況に応じて最適な戦略を選択する**必要があります。

### 戦略の選択基準

```
┌─────────────────────────────────────────────────────────────┐
│  モダナイゼーション戦略の選択                                │
│                                                             │
│  ビジネス価値                                               │
│     高 │    Refactor     │    Rebuild                      │
│        │  (リファクタリング) │   (全面刷新)                   │
│        ├─────────────────┼─────────────────────            │
│     低 │    Retire       │    Replatform                   │
│        │   (廃止)        │  (リプラットフォーム)              │
│        └─────────────────┴─────────────────────            │
│              低                  高                         │
│                    技術的複雑性                             │
└─────────────────────────────────────────────────────────────┘
```

---

## 4.2 6つのR戦略

### Retire（廃止）

| 項目 | 内容 |
|---|---|
| **適用場面** | ビジネス価値がない、代替手段がある |
| **コスト** | 低（移行計画は必要） |
| **リスク** | 低〜中 |
| **期間** | 短期 |

```
判断基準:
・利用者がいない、または極めて少ない
・同じ機能を持つ別システムが存在
・維持コストがビジネス価値を上回る
・コンプライアンス上の問題がない
```

### Retain（現状維持）

| 項目 | 内容 |
|---|---|
| **適用場面** | 変更のリスク・コストが高く、現状で問題ない |
| **コスト** | 維持コストのみ |
| **リスク** | 低（短期）、高（長期） |
| **期間** | 継続 |

```
判断基準:
・安定稼働している
・変更するビジネス理由がない
・移行コストが高すぎる
・近い将来に廃止予定
```

### Rehost（Lift-and-Shift）

| 項目 | 内容 |
|---|---|
| **適用場面** | インフラのみ移行、アプリは変更なし |
| **コスト** | 中 |
| **リスク** | 低〜中 |
| **期間** | 短期〜中期 |

```
判断基準:
・クラウド移行が必要
・アプリケーション変更の余裕がない
・運用コスト削減が目的
・将来的な最適化は後回し
```

### Replatform（リプラットフォーム）

| 項目 | 内容 |
|---|---|
| **適用場面** | 一部最適化しながらクラウド移行 |
| **コスト** | 中〜高 |
| **リスク** | 中 |
| **期間** | 中期 |

```
判断基準:
・クラウドネイティブ機能を活用したい
・データベースのマネージド化
・コンテナ化による運用効率化
・大規模な変更は避けたい
```

### Refactor（リファクタリング）

| 項目 | 内容 |
|---|---|
| **適用場面** | アーキテクチャの根本的な改善 |
| **コスト** | 高 |
| **リスク** | 中〜高 |
| **期間** | 中期〜長期 |

```
判断基準:
・アーキテクチャが古く拡張性がない
・マイクロサービス化が必要
・クラウドネイティブ化
・ビジネス価値が高く継続投資が必要
```

### Replace（置換）

| 項目 | 内容 |
|---|---|
| **適用場面** | SaaS/パッケージへの移行 |
| **コスト** | 中〜高 |
| **リスク** | 中 |
| **期間** | 中期 |

```
判断基準:
・市場に優れた既製品がある
・差別化に貢献しないGeneric領域
・内製維持のコストが高い
・カスタマイズ要件が少ない
```

---

## 4.3 ストラングラーフィグパターン

### 段階的移行の原則

```
┌─────────────────────────────────────────────────────────────┐
│  ストラングラーフィグパターン                                │
│                                                             │

│  ┌───────────┐                                             │
│  │ファサード │ ───────────→ レガシー（100%）               │

│                                                             │

│  ┌───────────┐     ┌───────┐                              │
│  │ファサード │ ─┬→ │新     │（30%）                       │
│  └───────────┘  └→ │旧     │（70%）                       │
```

# 第5章: 投資判断フレームワーク

## 5.1 概要

投資判断は、**ビジネス価値、技術的健全性、リスク、コストを総合的に評価**して行います。

---

## 5.2 投資判断マトリクス

### 4つの象限

```
┌─────────────────────────────────────────────────────────────┐
│  投資判断マトリクス                                          │
│                                                             │
│  ビジネス価値                                               │
│     高 │   Invest       │   Transform                      │
│        │  （積極投資）   │   （変革投資）                    │
│        │  健全で重要     │   重要だが問題あり                │
│        ├─────────────────┼─────────────────────            │
│     低 │   Tolerate     │   Sunset                         │
│        │  （許容）       │   （廃止）                        │
│        │  健全だが重要度低│   問題あり・重要度低              │
│        └─────────────────┴─────────────────────            │
│              高                  低                         │
│                    技術的健全性                             │
└─────────────────────────────────────────────────────────────┘
```

### 各象限の戦略

| 象限 | 戦略 | アクション |
|---|---|---|
| **Invest** | 積極投資 | 新機能開発、チーム強化、競争優位の維持 |
| **Transform** | 変革投資 | モダナイゼーション、技術的負債返済、アーキテクチャ刷新 |
| **Tolerate** | 許容 | 最小限の維持、効率化、外部化検討 |
| **Sunset** | 廃止 | 計画的な廃止、代替手段への移行 |

---

## 5.3 優先順位付けの基準

### スコアリングモデル

| 評価項目 | 重み | 説明 |
|---|:---:|---|
| **ビジネスインパクト** | 30% | ビジネス価値への貢献度 |
| **戦略的整合性** | 25% | Core Domain Chartとの整合 |
| **技術的リスク** | 20% | 障害・セキュリティリスク |
| **実現可能性** | 15% | スキル・リソースの可用性 |
| **コスト効率** | 10% | 投資対効果 |

### 優先順位の決定

```
優先度スコア =
  (ビジネスインパクト × 0.30) +
  (戦略的整合性 × 0.25) +
  (技術的リスク × 0.20) +
  (実現可能性 × 0.15) +
  (コスト効率 × 0.10)
```

# 付録A: クイックリファレンス

## Core Domain Chart

| 分類 | 投資方針 |
|---|---|
| Core | 最優先投資、内製維持 |
| Supporting | 必要最小限、効率化 |
| Generic | 外部化・標準化 |

## 6つのR戦略

| 戦略 | 適用場面 |
|---|---|
| Retire | 価値なし、廃止 |
| Retain | 現状維持 |
| Rehost | そのまま移行 |
| Replatform | 一部最適化して移行 |
| Refactor | 根本的改善 |
| Replace | SaaS/パッケージへ |

## 主要修正値

| 条件 | 修正 |
|---|:---:|
| Core Domainへの投資 | +2 |
| ビジネス部門との合意 | +2 |
| 明確な移行計画 | +2 |
| 経営層スポンサーシップ | +2 |
| Generic領域への過剰投資 | -2 |
| 政治的抵抗 | -2 |
| ビッグバン移行 | -2 |
