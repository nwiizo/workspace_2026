### 3.2 集約とAPIリソースの対応

**実装の醍醐味: 集約設計がAPIに現れる**

```rust
// ドメインモデル（Rust）
pub struct Order {
    id: OrderId,
    customer_id: CustomerId,  // 他の集約への参照
    items: Vec<OrderItem>,    // 集約内のエンティティ
    status: OrderStatus,
    total: Money,             // 値オブジェクト
}

impl Order {
    // ドメインロジックをカプセル化
    pub fn add_item(&mut self, product: &Product, qty: u32) -> Result<(), OrderError> {
        if self.status != OrderStatus::Draft {
            return Err(OrderError::CannotModify);
        }
        // ビジネスルールの適用
        let item = OrderItem::new(product, qty)?;
        self.items.push(item);
        self.recalculate_total();
        Ok(())
    }

    pub fn submit(&mut self) -> Result<OrderSubmittedEvent, OrderError> {
        // 不変条件のチェック
        if self.items.is_empty() {
            return Err(OrderError::EmptyOrder);
        }
        self.status = OrderStatus::Submitted;
        Ok(OrderSubmittedEvent::new(self))
    }
}
```

```yaml
# 対応するOpenAPI定義
```

## 4. バージョニング戦略 - 進化を止めないために

### 4.1 後方互換性の原則

```
┌─────────────────────────────────────────────────────────────────┐
│ 後方互換性を保つ変更 vs 破壊的変更                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│ ✅ 後方互換（Breaking しない）:                                 │
│    • 新しいエンドポイントの追加                                 │
│    • レスポンスへの新しいフィールド追加                         │
│    • オプショナルなリクエストパラメータの追加                   │
│    • 新しいHTTPメソッドのサポート                               │
│                                                                 │
│ ❌ 破壊的変更（Breaking）:                                      │
│    • エンドポイントの削除・名前変更                             │
│    • 必須パラメータの追加                                       │
│    • レスポンスフィールドの削除・型変更                         │
│    • エラーコードの変更                                         │
│    • 認証方式の変更                                             │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 バージョニングパターン

```
┌─────────────────────────────────────────────────────────────────┐
│ バージョニング戦略の選択                                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│ 1. URIバージョニング（最も明確）                               │
│    /api/v1/users                                                │
│    /api/v2/users                                                │
│    ├─ Pros: 明確、キャッシュしやすい                           │
│    └─ Cons: URIが変わる、リダイレクト必要                      │
│                                                                 │
│ 2. ヘッダーバージョニング                                      │
│    Accept: application/vnd.myapi.v2+json                        │
│    ├─ Pros: URIクリーン、コンテンツネゴシエーション            │
│    └─ Cons: テストしづらい、見えづらい                         │
│                                                                 │
│ 3. クエリパラメータ                                            │
│    /api/users?version=2                                         │
│    ├─ Pros: 実装簡単                                           │
│    └─ Cons: オプショナルに見える                               │
│                                                                 │
│ 推奨: URIバージョニング + 明確な移行期間                       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

```
┌─────────────────────────────────────────────────────────────────┐
│ 木村フロントエンドリード（APIの消費者視点）                     │

│                                                                 │
│ 「また仕様変わったの？先週リリースしたばかりなのに...」        │
```
