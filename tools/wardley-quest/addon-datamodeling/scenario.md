# 第1章: ゲーム概要

## 1.1 このゲームについて

**Data Modeling Quest** は、Strategic Evolution Questの続編として、**DDDの視点からデータ設計を学ぶ**戦略シミュレーションRPGです。

Strategic Evolution Questで設計した境界づけられたコンテキストを、具体的なデータモデルとして実装する方法を学びます。「ソフトウェア設計の結合バランス」の指標を用いて、設計の品質を評価します。

### 核心的な問い

> **「境界づけられたコンテキストを、どのようにデータモデルとして表現すれば、チームの自律性を保ちながら整合性を維持できるのか？」**

### DDDとデータモデリング

| DDD概念 | データモデリングでの表現 |
|---|---|
| **境界づけられたコンテキスト** | データの所有境界、スキーマの分離 |
| **集約** | トランザクション境界、テーブル群 |
| **エンティティ** | 主キーを持つテーブル |
| **値オブジェクト** | 埋め込み列、参照テーブル |
| **コンテキストマップ** | データ統合パターン |

### 結合バランスによる指標

「ソフトウェア設計の結合バランス」の概念を、データ設計の品質評価に活用します：

| 指標 | 説明 | 測定方法 |
|---|---|---|
| **結合スコア** | コンテキスト間の依存度 | 外部キー、共有テーブル数 |
| **距離** | 組織的・概念的な遠さ | チーム間、ドメイン間 |
| **揮発性** | 変更頻度 | スキーマ変更回数/期間 |

## 1.2 社会技術的視点とは

### Nick Tuneの洞察

Architecture Modernizationでは、技術的な設計は**常に組織的・社会的な文脈の中で行われる**と強調されています。

データモデリングも例外ではありません：

| 視点 | 従来のアプローチ | 社会技術的アプローチ |
|---|---|---|
| **データ所有** | DBAが一元管理 | ドメインチームが所有 |
| **スキーマ変更** | 変更管理委員会の承認 | チームが自律的に判断 |
| **統合方式** | 共有データベース | ドメインイベント、API |
| **整合性** | 強い一貫性を追求 | 結果整合性を許容 |
| **最適化** | グローバル最適 | ローカル最適の組み合わせ |

### Vlad Khononovの結合バランス

「ソフトウェア設計の結合バランス」では、**結合は悪ではなく、不適切な結合が問題**だと説きます。

データモデリングにおける結合の視点：

```
┌─────────────────────────────────────────────────────────────┐
│  結合のスペクトラム                                          │
│                                                             │
│  強い結合 ←───────────────────────────────────→ 弱い結合   │
│                                                             │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐       │
│  │共有DB   │  │同期API  │  │非同期   │  │イベント │       │
│  │外部キー │  │直接呼出 │  │メッセージ│  │駆動    │       │
│  └─────────┘  └─────────┘  └─────────┘  └─────────┘       │
│                                                             │
│  変更コスト: 高 ←─────────────────────────────→ 低        │
│  整合性:     強 ←─────────────────────────────→ 結果整合  │
│  複雑性:     低 ←─────────────────────────────→ 高        │
└─────────────────────────────────────────────────────────────┘
```

### データメッシュの4つの原則

Zhamak Dehghaniが提唱したデータメッシュの原則：

| 原則 | 説明 | DDDとの関連 |
|---|---|---|
| **ドメインオーナーシップ** | データはドメインチームが所有 | 境界づけられたコンテキストと整合 |
| **データのプロダクト化** | データを内部顧客向けプロダクトとして提供 | データプロダクトはDAUNTIVS特性を持つ |
| **セルフサービス型プラットフォーム** | データの発見・利用を容易に | プラットフォームチームがサポート |
| **連邦型コンピュテーショナル・ガバナンス** | 全社方針とドメイン自律性のバランス | 中央と現場の協調 |

### データプロダクトの特性（DAUNTIVS）

| 特性 | 説明 |
|---|---|
| **D**iscoverable（発見可能） | カタログから見つけられる |
| **A**ddressable（対処可能） | ユニークな識別子でアクセス可能 |
| **U**nderstandable（理解可能） | メタデータと文書で意味がわかる |
| **N**atively accessible（ネイティブにアクセス可能） | 標準的な方法でアクセス可能 |
| **T**rustworthy and truthful（信頼でき、真実である） | データ品質が保証される |
| **I**nteroperable and composable（相互運用可能で組み合わせ可能） | 他のデータプロダクトと組み合わせ可能 |
| **V**aluable on its own（それ自体で価値がある） | 単独でも価値を提供 |
| **S**ecure（セキュア） | 適切なアクセス制御 |

### データクォンタム

データクォンタムは**価値をもたらすデプロイ可能な最小単位のデータ要素**。

```
┌─────────────────────────────────────────────────────────────┐
│  データクォンタム                                            │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ データソース → データオンボーディング → データストア │   │
│  └─────────────────────────────────────────────────────┘   │
│                           │                                 │
│           ┌───────────────┼───────────────┐                │
│           ↓               ↓               ↓                │
│      分析クライアント  運用クライアント  発見クライアント   │
│                                                             │
│  + コントロールサービス（SLA、データ品質、セキュリティ）    │
│  + オブザーバビリティ（監視、ロギング）                     │
└─────────────────────────────────────────────────────────────┘
```

→ 全社データレイクではなく、ドメイン単位で小さく始める

## 1.3 ゲームの厳しさについて

このゲームでは以下のことが起こります：

| 現象 | 説明 | 学び |
|---|---|---|
| **共有データベースの罠** | 「効率的」な共有が全チームを結合させる | 独立性の価値 |
| **外部キーの連鎖** | 1つの変更が複数チームに波及 | 結合の代償 |
| **データオーナー不在** | 誰も責任を取らないデータが腐敗 | 所有権の重要性 |
| **移行地獄** | 結合が強いほど移行が困難に | 進化可能性の価値 |
| **整合性vs自律性** | 強い整合性がチームの足を引っ張る | トレードオフの現実 |
| **揮発性の見落とし** | 安定だと思った領域が実は頻繁に変わる | 変化の予測 |

**これらは現実の組織が直面するデータ設計の課題です。**

## 1.4 用語集

### 社会技術的データ設計用語

| 用語 | 定義 |
|---|---|
| **データオーナーシップ** | 特定のデータに対する責任と権限を持つチーム |
| **データプロダクト** | 他チームが消費可能な形で提供されるデータセット |
| **ドメインデータ** | 特定のビジネスドメインに属するデータ |
| **共有カーネル** | 複数チームが共有する最小限のデータモデル |
| **腐敗防止層（ACL）** | 外部データモデルから自ドメインを守る変換層 |
| **公開言語** | チーム間で共有される標準化されたデータ形式 |

### 結合と凝集用語

| 用語 | 定義 |
|---|---|
| **結合（Coupling）** | モジュール間の依存関係の強さ |
| **凝集（Cohesion）** | モジュール内の要素の関連性の強さ |
| **統合強度** | データ統合の緊密さのレベル |
| **距離** | 結合するコンポーネント間の概念的・組織的距離 |
| **揮発性** | データやスキーマが変更される頻度 |
| **安定性** | 他のモジュールから依存される度合い |

### 結合の種類

| 種類 | 説明 | 例 |
|---|---|---|
| **機能的結合** | 同じ機能を実現するために必要な依存 | 注文処理が在庫を参照 |
| **時間的結合** | 特定の順序やタイミングでの依存 | 請求は出荷後でなければならない |
| **実装結合** | 実装詳細への依存 | 特定のカラム名に依存 |
| **契約結合** | 明示的なインターフェースへの依存 | API契約、イベントスキーマ |
| **データ結合** | データ構造への依存 | 共有テーブル、外部キー |

### 進化可能性用語

| 用語 | 定義 |
|---|---|
| **スキーマ進化** | 互換性を保ちながらスキーマを変更する能力 |
| **後方互換性** | 新しいスキーマが古いクライアントと動作する |
| **前方互換性** | 古いスキーマが新しいデータを処理できる |
| **ストラングラーフィグ** | 段階的に旧システムを新システムに置換する戦略 |
| **並行運用** | 新旧システムを同時に稼働させる移行方式 |

### ゲーム用語

| 用語 | 定義 |
|---|---|
| **ターン** | 1スプリント相当 |
| **結合スコア** | システム全体の結合度（低いほど良い） |
| **チーム自律性** | チームが独立して変更できる度合い |
| **進化可能性** | 将来の変更に対応できる能力 |
| **技術的負債** | 短期解決策の蓄積による長期コスト |

## 2.2 判定システム

### 基本判定（2D6）

| 出目 | 結果 | 効果 |
|:---:|---|---|
| 2 | **致命的失敗** | データ破損。複数チームに影響。技術的負債+2。 |
| 3-4 | **失敗** | 設計ミス。手戻り発生。技術的負債+1。 |
| 5-6 | **部分的失敗** | 一部成功。予期せぬ結合が発生。 |
| 7-8 | **部分的成功** | 条件付き成功。トレードオフが顕在化。 |
| 9-10 | **成功** | 目標達成。計画通りの結合レベル。 |
| 11 | **大成功** | ボーナス効果。チーム自律性+1。 |
| 12 | **完全成功** | 最高の結果。再利用可能なパターン獲得。 |

### 修正値

#### 社会技術的整合関連

| 状況 | 修正 | 根拠 |

## 2.3 組織イベント

毎ターン開始時にD6を2回振り、2つのイベントが発生します。

### 組織イベント表

| D6 | イベント | 効果 | 対応のヒント |
|:---:|---|---|---|
| 1 | **チーム再編** | チーム境界が変わる。データオーナーシップの見直しが必要。 | 境界の再評価 |
| 2 | **新規チーム参入** | 新チームがデータにアクセスしたい。統合方式の決定が必要。 | 結合方式の選択 |
| 3 | **パフォーマンス要求** | 特定クエリの高速化要求。非正規化または分離の検討。 | トレードオフ判断 |
| 4 | **コンプライアンス要件** | データ分離または監査の要求。アクセス制御の強化。 | セキュリティ設計 |
| 5 | **スキーマ変更要求** | 他チームからのスキーマ変更依頼。互換性の判断が必要。 | 進化戦略 |
| 6 | **外部システム統合** | 外部システムとのデータ連携。結合方式の選択。 | 統合パターン |

### 常時適用パターン

| パターン | 効果 |
|---|---|
| **データは複製される** | 共有よりコピーの方が結合が緩い |
| **スキーマは変わる** | 変更を前提とした設計が必要 |
| **チームは独立したい** | 調整コストを最小化する圧力 |
| **整合性は高コスト** | 強い整合性は自律性を犠牲にする |
| **オーナー不在は負債** | 責任者のいないデータは腐敗する |

## 2.4 結合スコアシステム

### 結合の種類と重み

| 結合タイプ | スコア | 説明 |
|---|:---:|---|
| **共有データベース** | +4 | 最も強い結合。全チームに影響。 |
| **外部キー参照** | +3 | スキーマ変更が波及。 |
| **同期API呼び出し** | +2 | 可用性の結合。 |
| **共有スキーマ** | +2 | 変更の調整が必要。 |
| **非同期メッセージ** | +1 | 時間的分離。 |
| **イベント駆動** | +1 | 最も緩い結合。 |
| **データ複製** | +1 | 結果整合性を許容。 |

### 結合スコアの計算

```
結合スコア = Σ(結合タイプのスコア × 発生箇所数)
           + (組織境界を跨ぐ結合 × 2)  ← 距離のペナルティ
           + (揮発性の高い領域の結合 × 1.5) ← 揮発性のペナルティ
```

### 結合スコアの影響

| スコア | 状態 | 効果 |

## 3.2 データオーナーシップ

### オーナーシップのパターン

| パターン | 説明 | 適用場面 |
|---|---|---|
| **単一オーナー** | 1チームが完全な権限を持つ | 明確なドメイン境界 |
| **共同オーナー** | 複数チームが共同で管理 | 共有カーネル |
| **委任オーナー** | 技術的管理を別チームに委任 | プラットフォーム提供 |
| **オーナー不在** | 誰も責任を持たない | **アンチパターン** |

### オーナーシップの決定基準

```
┌─────────────────────────────────────────────────────────────┐
│  データオーナーシップ決定フロー                              │
│                                                             │
│  1. このデータはどのビジネスケイパビリティに属するか？       │
│     └─→ 最も関連するドメインのチームがオーナー候補          │
│                                                             │
│  2. このデータを最も頻繁に変更するのは誰か？                 │
│     └─→ 変更頻度が高いチームがオーナーに適する              │
│                                                             │
│  3. このデータの品質に責任を持つべきは誰か？                 │
│     └─→ ビジネス上の責任者がオーナーに適する                │
│                                                             │
│  4. 複数チームが同等に関与する場合は？                       │
│     └─→ 共有カーネルとして明示的に管理                      │
└─────────────────────────────────────────────────────────────┘
```

### 判定への影響

| 状況 | 判定修正 |
|---|:---:|
| オーナーが明確で権限を持つ | +2 |
| オーナーがドメインエキスパート | +1 |
| 共同オーナーシップが機能 | +1 |
| オーナー不在 | -2 |
| オーナーに権限がない | -1 |

## 3.3 チーム境界とデータ境界

### コンウェイの法則とデータ

> 「システムを設計する組織は、その組織のコミュニケーション構造をコピーした設計を生み出す」

データモデルも例外ではありません：

| 状態 | 結果 |
|---|---|
| **チーム境界 = データ境界** | 高い自律性、低い調整コスト |
| **チーム境界 ≠ データ境界** | 調整コスト増大、変更が遅延 |
| **1データ複数チーム** | 変更に複数チームの合意が必要 |
| **1チーム複数データ** | 認知負荷増大、焦点が分散 |

### 境界の整合パターン

```
【理想的なパターン】

チームA ────────────────── チームB
    │                          │
    ↓                          ↓
┌─────────┐   イベント   ┌─────────┐
│データA  │ ──────────→ │データB  │
│         │             │(コピー) │
└─────────┘             └─────────┘
    ↑                          ↑
 オーナー                   オーナー

【問題のあるパターン】

チームA ──────┬──────── チームB
    │        │              │
    ↓        ↓              ↓
┌─────────────────────────────────┐
│          共有データベース        │
│    (オーナー不在、全員がアクセス) │
└─────────────────────────────────┘
```

# 第4章: 結合と凝集のバランス

## 4.1 概要

Vlad Khononovが説くように、**結合は必要悪ではなく、設計の選択**です。

### このフレームワークで答える問い

- 「この結合は意図的か、偶発的か？」
- 「結合の強さは変更頻度に見合っているか？」
- 「組織的距離を考慮した統合強度か？」
- 「この結合は将来の変更を妨げないか？」

---

## 4.2 結合の種類と選択

### 結合タイプの詳細

| タイプ | 強度 | 特徴 | 適用場面 |
|---|:---:|---|---|
| **同一プロセス内** | 最強 | コンパイル時依存 | 同一チーム、同一サービス |
| **共有データベース** | 強 | スキーマ変更が全員に影響 | **避けるべき** |
| **外部キー制約** | 強 | 参照整合性をDBが保証 | 同一チーム内のみ推奨 |
| **同期API** | 中強 | 可用性の結合 | レスポンス必須時 |
| **共有スキーマ** | 中 | 構造への依存 | 慎重に管理 |
| **非同期メッセージ** | 弱 | 時間的分離 | 多くの場面で推奨 |
| **イベント通知** | 最弱 | 完全な分離 | 組織境界を跨ぐ場合 |

### 結合選択マトリクス

```
┌───────────────────────────────────────────────────────────────┐
│                        揮発性                                 │
│                  低 ←─────────────→ 高                       │
│         ┌─────────────────────────────────────────┐          │
│       近 │  外部キー可    │  API/イベント推奨   │          │
│  距     │  同期API可     │  結合を最小化       │          │
│  離     ├─────────────────────────────────────────┤          │
│       遠 │  API推奨      │  イベント必須       │          │
│         │  イベント可    │  データ複製検討     │          │
│         └─────────────────────────────────────────┘          │
│                                                              │
│  距離 = 組織的距離（チーム間）+ 概念的距離（ドメイン間）     │
│  揮発性 = 変更頻度 × 変更影響範囲                           │
└───────────────────────────────────────────────────────────────┘
```

---

## 4.3 距離と統合強度

### 距離の種類

| 距離タイプ | 説明 | 測定方法 |
|---|---|---|
| **組織的距離** | チーム間の壁 | 報告ライン、コミュニケーション頻度 |
| **概念的距離** | ドメインの違い | ユビキタス言語の共有度 |
| **技術的距離** | 技術スタックの違い | 共通ライブラリ、プロトコル |
| **地理的距離** | 物理的な位置 | タイムゾーン、拠点 |

### 統合強度の原則

> **「距離が遠いほど、統合強度は弱くすべき」**

```
統合強度 ∝ 1 / 距離

同一チーム: 強い統合が許容される
異なるチーム: 明示的な契約が必要
異なる組織: 最も緩い結合（イベント、API）
```

### 判定への影響

| 状況 | 判定修正 |
|---|:---:|
| 距離に応じた適切な統合強度 | +1 |
| 近い距離での緩い結合（過剰分離） | -1 |
| 遠い距離での強い結合（危険） | -2 |

---

## 4.4 揮発性の管理

### 揮発性の評価

| レベル | 変更頻度 | 例 |
|---|---|---|
| **極めて安定** | 年に1回未満 | マスターデータ、設定 |
| **安定** | 四半期に数回 | 基本的なドメインモデル |
| **中程度** | 月に数回 | ビジネスルール、ワークフロー |
| **揮発性高** | 週に数回 | UI関連データ、レポート |
| **極めて揮発** | 毎日/毎時 | キャンペーン、A/Bテスト |

### 揮発性と結合の関係

```
┌─────────────────────────────────────────────────────────────┐
│  揮発性が高い領域への強い結合は危険                          │
│                                                             │
│  例: マーケティングチームの「キャンペーンテーブル」に        │
│      注文チームが外部キーで依存                              │
│                                                             │
│  問題:                                                      │
│  - キャンペーンスキーマの頻繁な変更                         │
│  - 変更のたびに注文チームとの調整が必要                     │
│  - 両チームの開発速度が低下                                 │
│                                                             │
│  解決:                                                      │
│  - 注文側でキャンペーンIDのみ保持                           │
│  - 必要時にAPIで詳細を取得                                  │
│  - または、イベントでキャンペーン情報をコピー               │
└─────────────────────────────────────────────────────────────┘
```

---

## 4.5 凝集の最大化

### 凝集の原則

> **「変更理由が同じものを一緒に、違うものを分離する」**

| 凝集タイプ | 説明 | 好ましさ |
|---|---|---|
| **機能的凝集** | 単一目的のために協働 | 最良 |
| **逐次的凝集** | 処理の流れで関連 | 良 |
| **通信的凝集** | 同じデータを扱う | 許容 |
| **時間的凝集** | 同時に発生する | 注意 |
| **論理的凝集** | 似た機能の寄せ集め | 避ける |
| **偶発的凝集** | 関連なく同居 | 最悪 |

### データモデルでの凝集

```yaml
# 高凝集な例: 注文集約
order_aggregate:
  - orders
  - order_items
  - order_status_history
  # 全て「注文の処理」という単一目的

# 低凝集な例: 汎用テーブル
master_table:
  - customers      # 顧客管理
  - products       # 商品管理
  - orders         # 注文処理
  - campaigns      # マーケティング
  # バラバラな目的が同居
```

## 5.1 概要

- 「ロールバックは可能か？」

## 5.2 スキーマ進化戦略

### 互換性のタイプ

| タイプ | 説明 | 例 |
|---|---|---|
| **後方互換** | 新スキーマが旧クライアントと動作 | 列追加（デフォルト付き） |
| **前方互換** | 旧スキーマが新データを処理 | 未知フィールドの無視 |
| **完全互換** | 両方を満たす | 最も安全 |
| **非互換** | どちらも満たさない | breaking change |

### 安全なスキーマ変更

| 変更タイプ | 互換性 | 対策 |
|---|---|---|
| **列追加（デフォルト有）** | 後方互換 | 安全に実施可能 |
| **列追加（デフォルト無）** | 非互換 | デフォルトを設定 |
| **列削除** | 非互換 | 段階的廃止（deprecation） |
| **列名変更** | 非互換 | 新列追加→データ移行→旧列削除 |
| **型変更** | 非互換 | 新列で対応 |
| **制約追加** | 条件付き | 既存データの検証が必要 |

### スキーマバージョニング

```
┌─────────────────────────────────────────────────────────────┐
│  バージョニング戦略                                          │
│                                                             │
│  1. スキーマにバージョンを持たせる                          │
│     schema_version: "2.3.0"                                 │
│                                                             │
│  2. セマンティックバージョニング                            │
│     MAJOR: 非互換変更                                       │
│     MINOR: 後方互換な機能追加                               │
│     PATCH: 後方互換なバグ修正                               │
│                                                             │
│  3. 複数バージョンの並行サポート                            │
│     /api/v1/customers                                       │
│     /api/v2/customers                                       │
│                                                             │
│  4. 廃止予定の明示                                          │
│     deprecated: true                                        │
│     sunset_date: "2024-06-01"                               │
└─────────────────────────────────────────────────────────────┘
```

## 5.3 移行戦略

### 移行パターン

| パターン | 説明 | リスク | 適用場面 |
|---|---|---|---|
| **ビッグバン** | 一度に切り替え | 高 | 小規模、低リスク |
| **段階的移行** | 機能ごとに移行 | 中 | 中規模 |
| **ストラングラーフィグ** | 徐々に置換 | 低 | 大規模、高リスク |
| **並行運用** | 新旧を同時稼働 | 中 | データ整合性重視 |

### ストラングラーフィグの詳細

```
┌─────────────────────────────────────────────────────────────┐
│  ストラングラーフィグパターン                                │
│                                                             │
│  Phase 1: ファサードの導入                                  │
│  ┌─────────┐                                               │
│  │ファサード│ ───→ 旧DB（100%）                            │
│  └─────────┘                                               │
│                                                             │
│  Phase 2: 一部を新システムへ                                │
│  ┌─────────┐                                               │
│  │ファサード│ ─┬→ 旧DB（70%）                              │
│  └─────────┘  └→ 新DB（30%）                              │
│                                                             │
│  Phase 3: 大部分を移行                                      │
│  ┌─────────┐                                               │
│  │ファサード│ ─┬→ 旧DB（10%）                              │
│  └─────────┘  └→ 新DB（90%）                              │
│                                                             │
│  Phase 4: 完全移行                                          │
│  ┌─────────┐                                               │
│  │ファサード│ ───→ 新DB（100%）                            │
│  └─────────┘                                               │
│            旧DBを削除                                       │
└─────────────────────────────────────────────────────────────┘
```

## 5.4 独立デプロイ可能性

### 目標状態

> **「各チームが他チームの承認なしにデータスキーマを変更し、デプロイできる」**

### 達成のための条件

| 条件 | 説明 |
|---|---|
| **明確なオーナーシップ** | 変更権限がチーム内に閉じている |
| **契約による結合** | 実装ではなく契約（API/イベント）で結合 |
| **後方互換性** | 消費者に影響を与えない変更 |
| **消費者の把握** | 誰が使っているか分かっている |
| **バージョニング** | 非互換変更時の並行サポート |

### 判定への影響

| 状況 | 判定修正 |
|---|:---:|
| 独立デプロイ可能な状態 | +2 |
| 消費者を把握し通知可能 | +1 |
| 変更に他チームの承認が必要 | -2 |
| 消費者が不明 | -2 |

## 6.2 結合管理アクション

### 関係値システム

NPCとの関係値は **-3〜+3** の範囲で変動します。

| 関係値 | 状態 | 効果 |
|:---:|---|---|
| +3 | 強い協力 | 積極的な移行協力、他チームへの推奨 |
| +1〜+2 | 良好 | 協力的、必要な情報提供 |
| 0 | 中立 | 様子見、指示があれば協力 |
| -1〜-2 | 消極的 | 移行への抵抗、情報出し渋り |
| -3 | 敵対 | 移行妨害、スキーマ変更ブロック |

### 関係値の変動

| 行動 | 変動 |
|------|:---:|
| NPCの懸念を移行計画に反映 | +1 |
| データアクセス維持を保証 | +1 |
| 移行の成功事例を共有 | +1 |
| NPCの担当領域を急に変更 | -1 |
| 事前相談なしにスキーマ変更 | -1 |
| breaking changeを強行 | -2 |

## 10.3 コンピテンシー開発（洞察ポイント）

ターン終了時に**洞察ポイント**を獲得し、コンピテンシーを習得できます。

### 洞察ポイントの獲得

| 条件 | 獲得ポイント |
|------|:---:|
| ターンを完了 | +1 |
| 判定で11以上（大成功/完全成功） | +1 |
| 結合スコアが減少 | +1 |
| チーム自律性が向上 | +1 |

### コンピテンシーツリー

```
社会技術スキル              結合スキル                進化スキル
    │                       │                       │
    ├─ オーナーシップ+1     ├─ 統合パターン+1        ├─ スキーマ進化+1
    │  (コスト: 2)          │  (コスト: 2)          │  (コスト: 2)
    │                       │                       │
    ├─ チーム境界調整        ├─ 揮発性分析           ├─ バージョニング
    │  (コスト: 3)          │  (コスト: 3)          │  (コスト: 3)
    │  境界再定義            │  結合タイプ            │  後方互換性
    │  判定+1               │  選択判定+1            │  判定+1
    │                       │                       │
    └─ 社会技術マスター     └─ 結合マスター          └─ 進化マスター
       (コスト: 5)             (コスト: 5)             (コスト: 5)
       整合判定+2            結合削減+2              移行判定+2
```
