# 第1章: ゲーム概要

## 1.1 このゲームについて

**Data Modeling Quest** は、Strategic Evolution Questの続編として、**DDDの視点からデータ設計を学ぶ**戦略シミュレーションRPGです。

Strategic Evolution Questで設計した境界づけられたコンテキストを、具体的なデータモデルとして実装する方法を学びます。「ソフトウェア設計の結合バランス」の指標を用いて、設計の品質を評価します。

### 核心的な問い

> **「境界づけられたコンテキストを、どのようにデータモデルとして表現すれば、チームの自律性を保ちながら整合性を維持できるのか？」**

### DDDとデータモデリング

| DDD概念 | データモデリングでの表現 |
|---|---|
| **境界づけられたコンテキスト** | データの所有境界、スキーマの分離 |
| **集約** | トランザクション境界、テーブル群 |
| **エンティティ** | 主キーを持つテーブル |
| **値オブジェクト** | 埋め込み列、参照テーブル |
| **コンテキストマップ** | データ統合パターン |

### 結合バランスによる指標

「ソフトウェア設計の結合バランス」の概念を、データ設計の品質評価に活用します。特に**揮発性**（データやスキーマが変更される頻度）は、データモデリングにおいて見落とされがちですが極めて重要な指標です。変更頻度の高いデータと安定したデータを同じ境界に配置すると、不必要な変更の連鎖を引き起こします。

| 指標 | 説明 | 測定方法 |
|---|---|---|
| **結合スコア** | コンテキスト間の依存度 | 外部キー、共有テーブル数 |
| **距離** | 組織的・概念的な遠さ | チーム間、ドメイン間 |
| **揮発性** | 変更頻度 | スキーマ変更回数/期間 |

### フレームワークの関係

**DDD（設計の主軸）** → 境界づけられたコンテキスト=データ所有境界、集約=トランザクション境界、コンテキストマップ=データ統合パターン → **結合バランス（品質指標）**: 結合スコア（依存度）/ 距離（組織的・概念的遠さ）/ 揮発性（変更頻度）

### プレイ形式

| 項目 | 内容 |
|---|---|
| プレイヤー | 1名（データアーキテクト/プラットフォームエンジニア） |
| GM | Claude（シナリオ・判定・組織イベント） |
| 所要時間 | 60〜120分 |

### コンパクトモード

|----------|------|

## 1.2 社会技術的視点とは

### Nick Tuneの洞察

Architecture Modernizationでは、技術的な設計は**常に組織的・社会的な文脈の中で行われる**と強調されています。

データモデリングも例外ではありません：

| 視点 | 従来のアプローチ | 社会技術的アプローチ |
|---|---|---|
| **データ所有** | DBAが一元管理 | ドメインチームが所有 |
| **スキーマ変更** | 変更管理委員会の承認 | チームが自律的に判断 |
| **統合方式** | 共有データベース | ドメインイベント、API |
| **整合性** | 強い一貫性を追求 | 結果整合性を許容 |
| **最適化** | グローバル最適 | ローカル最適の組み合わせ |

### Vlad Khononovの結合バランス

「ソフトウェア設計の結合バランス」では、**結合は悪ではなく、不適切な結合が問題**だと説きます。

データモデリングにおける結合の視点：

**結合のスペクトラム**: 共有DB/外部キー（強）→ 同期API → 非同期メッセージ → イベント駆動（弱）。変更コストは強→高/弱→低、整合性は強→強/弱→結果整合、複雑性は強→低/弱→高。

### データメッシュの4つの原則

Zhamak Dehghaniが提唱したデータメッシュの原則：

| 原則 | 説明 | DDDとの関連 |
|---|---|---|
| **ドメインオーナーシップ** | データはドメインチームが所有 | 境界づけられたコンテキストと整合 |
| **データのプロダクト化** | データを内部顧客向けプロダクトとして提供 | データプロダクトはDAUNTIVS特性を持つ |
| **セルフサービス型プラットフォーム** | データの発見・利用を容易に | プラットフォームチームがサポート |
| **連邦型コンピュテーショナル・ガバナンス** | 全社方針とドメイン自律性のバランス | 中央と現場の協調 |

### データプロダクトの特性（DAUNTIVS）

**D**iscoverable / **A**ddressable / **U**nderstandable / **N**atively accessible / **T**rustworthy / **I**nteroperable / **V**aluable on its own / **S**ecure

### データクォンタム

**価値をもたらすデプロイ可能な最小単位のデータ要素**。データソース→オンボーディング→ストア、クライアント（分析/運用/発見）+ コントロールサービス + オブザーバビリティで構成。全社データレイクではなく、ドメイン単位で小さく始める。

## 1.3 用語集

| 用語 | 定義 |
|---|---|
| **データオーナーシップ** | 特定のデータに対する責任と権限を持つチーム |

| **距離** | 結合するコンポーネント間の概念的・組織的距離 |

| **スキーマ進化** | 互換性を保ちながらスキーマを変更する能力 |

| **結合スコア** | システム全体の結合度（低いほど良い） |
| **チーム自律性** | チームが独立して変更できる度合い |
| **進化可能性** | 将来の変更に対応できる能力 |
| **データクォンタム** | 価値をもたらすデプロイ可能な最小単位のデータ要素 |

## 2.2 判定システム

基本判定はメインscenario参照（2D6、2=致命的失敗〜12=完全成功）。データモデリング固有の効果: 致命的失敗=データ破損・技術的負債+2、失敗=技術的負債+1、部分的失敗=予期せぬ結合発生、大成功=チーム自律性+1、完全成功=再利用可能パターン獲得。

## 2.3 組織イベント

### 組織イベント表

| 3 | **パフォーマンス要求** | 特定クエリの高速化要求。非正規化または分離の検討。 | トレードオフ判断 |

### 常時適用パターン

| パターン | 効果 |
|---|---|
| **データは複製される** | 共有よりコピーの方が結合が緩い |

| **オーナー不在は負債** | 責任者のいないデータは腐敗する |

## 2.4 結合スコアシステム

### 結合の種類と重み

| 結合タイプ | スコア | 説明 |
|---|:---:|---|
| **共有データベース** | +4 | 最も強い結合。全チームに影響。 |
| **外部キー参照** | +3 | スキーマ変更が波及。 |
| **同期API呼び出し** | +2 | 可用性の結合。 |
| **共有スキーマ** | +2 | 変更の調整が必要。 |
| **非同期メッセージ** | +1 | 時間的分離。 |
| **イベント駆動** | +1 | 最も緩い結合。 |
| **データ複製** | +1 | 結果整合性を許容。 |

### 結合スコアの計算

```
結合スコア = Σ(結合タイプのスコア × 発生箇所数)
           + (組織境界を跨ぐ結合 × 2)  ← 距離のペナルティ
           + (揮発性の高い領域の結合 × 1.5) ← 揮発性のペナルティ
```

### 結合スコアの影響

| スコア | 状態 | 効果 |
|:---:|---|---|
| 0-5 | 健全 | チームが独立して変更可能 |
| 6-10 | 要注意 | 変更時に調整が必要 |
| 11-15 | 危険 | 変更が複数チームに波及 |
| 16+ | 危機的 | 全ての変更が全員に影響 |

# 第3章: 社会技術的データ設計

## 3.1 概要

Nick Tuneが強調するように、**データ設計は技術的な問題であると同時に組織的な問題**です。

### このフレームワークで答える問い

- 「このデータは誰が所有すべきか？」
- 「チーム境界とデータ境界は一致しているか？」
- 「データの変更に誰の承認が必要か？」
- 「データプロダクトとして他チームに提供できるか？」

---

## 3.2 データオーナーシップ

### オーナーシップのパターン

| パターン | 説明 | 適用場面 |
|---|---|---|
| **単一オーナー** | 1チームが完全な権限を持つ | 明確なドメイン境界 |
| **共同オーナー** | 複数チームが共同で管理 | 共有カーネル |
| **委任オーナー** | 技術的管理を別チームに委任 | プラットフォーム提供 |
| **オーナー不在** | 誰も責任を持たない | **アンチパターン** |

### オーナーシップの決定基準

1. どのビジネスケイパビリティに属するか？ → 最も関連するドメインのチームがオーナー候補
2. 最も頻繁に変更するのは誰か？ → 変更頻度が高いチームがオーナーに適する
3. 品質に責任を持つべきは誰か？ → ビジネス上の責任者がオーナーに適する
4. 複数チームが同等に関与する場合 → 共有カーネルとして明示的に管理

### 判定への影響

| 状況 | 判定修正 |
|---|:---:|
| オーナーが明確で権限を持つ | +2 |
| オーナーがドメインエキスパート | +1 |
| 共同オーナーシップが機能 | +1 |
| オーナー不在 | -2 |
| オーナーに権限がない | -1 |

---

## 3.3 チーム境界とデータ境界

### コンウェイの法則とデータ

> 「システムを設計する組織は、その組織のコミュニケーション構造をコピーした設計を生み出す」

データモデルも例外ではありません：

| 状態 | 結果 |
|---|---|
| **チーム境界 = データ境界** | 高い自律性、低い調整コスト |
| **チーム境界 ≠ データ境界** | 調整コスト増大、変更が遅延 |
| **1データ複数チーム** | 変更に複数チームの合意が必要 |
| **1チーム複数データ** | 認知負荷増大、焦点が分散 |

### 境界の整合パターン

- **理想**: チームA→データA(オーナー) --イベント--> チームB→データB(コピー、オーナー) — 各チームが自分のデータを所有
- **問題**: チームA+チームB → 共有DB（オーナー不在、全員がアクセス） — 結合最大化

---

## 3.4 データプロダクト思考

### Zhamak Dehghaniのデータメッシュ原則

データを**プロダクト**として扱うことで、消費者視点の設計が可能になります：

| 原則 | 説明 | 実践 |
|---|---|---|
| **ドメインオーナーシップ** | データは生成するドメインが所有 | チーム境界に沿った設計 |
| **データをプロダクトとして** | 消費者のニーズを満たす | SLA、ドキュメント、品質保証 |
| **セルフサービスプラットフォーム** | インフラの共通化 | プラットフォームチーム提供 |
| **フェデレーテッドガバナンス** | 分散と標準のバランス | 最低限の共通ルール |

### データプロダクトの要素

```yaml
data_product:
  name: "顧客プロファイル"
  owner: "顧客チーム"
  consumers:
    - "マーケティングチーム"
    - "サポートチーム"
  sla:
    availability: 99.9%
    freshness: "< 1時間"
  schema:
    version: "2.3.0"
    compatibility: "backward"
  documentation: "https://..."
  quality_metrics:
    completeness: "> 99%"
    accuracy: "> 99.5%"
```

## 3.5 DDDコンテキストとの整合

### Strategic Evolution Questとの連携

Strategic Evolution Questで設計したコンテキスト境界は、データ境界の基礎となります：

| DDD概念 | データモデリングへの影響 |
|---|---|
| **境界づけられたコンテキスト** | データの所有境界 |
| **コアドメイン** | 最も重要なデータ、最高の設計品質 |
| **サポーティング** | 必要だが差別化ではない |
| **ジェネリック** | 外部サービス利用、最小限の所有 |
| **コンテキストマップ** | データ統合パターンの決定 |

### コンテキスト関係とデータ統合

| 関係パターン | データ統合方式 |
|---|---|

# 第4章: 結合と凝集のバランス

## 4.1 概要

Vlad Khononovが説くように、**結合は必要悪ではなく、設計の選択**です。

### このフレームワークで答える問い

- 「この結合は意図的か、偶発的か？」
- 「結合の強さは変更頻度に見合っているか？」
- 「組織的距離を考慮した統合強度か？」
- 「この結合は将来の変更を妨げないか？」

---

## 4.2 結合の種類と選択

### 結合タイプの詳細

| タイプ | 強度 | 特徴 | 適用場面 |
|---|:---:|---|---|
| **同一プロセス内** | 最強 | コンパイル時依存 | 同一チーム、同一サービス |
| **共有データベース** | 強 | スキーマ変更が全員に影響 | **避けるべき** |
| **外部キー制約** | 強 | 参照整合性をDBが保証 | 同一チーム内のみ推奨 |
| **同期API** | 中強 | 可用性の結合 | レスポンス必須時 |
| **共有スキーマ** | 中 | 構造への依存 | 慎重に管理 |
| **非同期メッセージ** | 弱 | 時間的分離 | 多くの場面で推奨 |
| **イベント通知** | 最弱 | 完全な分離 | 組織境界を跨ぐ場合 |

### 結合選択マトリクス

| | 揮発性: 低 | 揮発性: 高 |
|---|---|---|
| **距離: 近** | 外部キー可、同期API可 | API/イベント推奨、結合を最小化 |
| **距離: 遠** | API推奨、イベント可 | イベント必須、データ複製検討 |

距離 = 組織的距離 + 概念的距離、揮発性 = 変更頻度 x 変更影響範囲

---

## 4.3 距離と統合強度

### 距離の種類

| 距離タイプ | 説明 | 測定方法 |
|---|---|---|
| **組織的距離** | チーム間の壁 | 報告ライン、コミュニケーション頻度 |
| **概念的距離** | ドメインの違い | ユビキタス言語の共有度 |
| **技術的距離** | 技術スタックの違い | 共通ライブラリ、プロトコル |
| **地理的距離** | 物理的な位置 | タイムゾーン、拠点 |

### 統合強度の原則

> **「距離が遠いほど、統合強度は弱くすべき」**

```
統合強度 ∝ 1 / 距離

同一チーム: 強い統合が許容される
異なるチーム: 明示的な契約が必要
異なる組織: 最も緩い結合（イベント、API）
```

### 判定への影響

| 状況 | 判定修正 |
|---|:---:|
| 距離に応じた適切な統合強度 | +1 |
| 近い距離での緩い結合（過剰分離） | -1 |
| 遠い距離での強い結合（危険） | -2 |

---

## 4.4 揮発性の管理

### 揮発性の評価

| レベル | 変更頻度 | 例 |
|---|---|---|
| **極めて安定** | 年に1回未満 | マスターデータ、設定 |
| **安定** | 四半期に数回 | 基本的なドメインモデル |
| **中程度** | 月に数回 | ビジネスルール、ワークフロー |
| **揮発性高** | 週に数回 | UI関連データ、レポート |
| **極めて揮発** | 毎日/毎時 | キャンペーン、A/Bテスト |

### 揮発性と結合の関係

> **揮発性が高い領域への強い結合は危険**

**例**: マーケティングの「キャンペーンテーブル」に注文チームが外部キーで依存 → 頻繁なスキーマ変更のたびに調整必要、両チーム速度低下。**解決**: IDのみ保持しAPIで取得、またはイベントでコピー。

---

## 4.5 凝集の最大化

### 凝集の原則

> **「変更理由が同じものを一緒に、違うものを分離する」**

| 凝集タイプ | 説明 | 好ましさ |
|---|---|---|
| **機能的凝集** | 単一目的のために協働 | 最良 |
| **逐次的凝集** | 処理の流れで関連 | 良 |
| **通信的凝集** | 同じデータを扱う | 許容 |
| **時間的凝集** | 同時に発生する | 注意 |
| **論理的凝集** | 似た機能の寄せ集め | 避ける |
| **偶発的凝集** | 関連なく同居 | 最悪 |

### データモデルでの凝集

```yaml
# 高凝集な例: 注文集約
order_aggregate:
  - orders
  - order_items
  - order_status_history
  # 全て「注文の処理」という単一目的

# 低凝集な例: 汎用テーブル
master_table:
  - customers      # 顧客管理
  - products       # 商品管理
  - orders         # 注文処理
  - campaigns      # マーケティング
  # バラバラな目的が同居
```

# 第5章: 進化可能なデータアーキテクチャ

## 5.1 概要

- 「ロールバックは可能か？」

---

## 5.2 スキーマ進化戦略

### 互換性のタイプ

| タイプ | 説明 | 例 |
|---|---|---|
| **後方互換** | 新スキーマが旧クライアントと動作 | 列追加（デフォルト付き） |
| **前方互換** | 旧スキーマが新データを処理 | 未知フィールドの無視 |
| **完全互換** | 両方を満たす | 最も安全 |
| **非互換** | どちらも満たさない | breaking change |

### 安全なスキーマ変更

| 変更タイプ | 互換性 | 対策 |
|---|---|---|
| **列追加（デフォルト有）** | 後方互換 | 安全に実施可能 |
| **列追加（デフォルト無）** | 非互換 | デフォルトを設定 |
| **列削除** | 非互換 | 段階的廃止（deprecation） |
| **列名変更** | 非互換 | 新列追加→データ移行→旧列削除 |
| **型変更** | 非互換 | 新列で対応 |
| **制約追加** | 条件付き | 既存データの検証が必要 |

### スキーマバージョニング

1. スキーマにバージョンを持たせる（`schema_version: "2.3.0"`）
2. セマンティックバージョニング（MAJOR=非互換/MINOR=後方互換追加/PATCH=修正）
3. 複数バージョンの並行サポート（`/api/v1/`, `/api/v2/`）
4. 廃止予定の明示（`deprecated: true`, `sunset_date`）

---

## 5.3 移行戦略

### 移行パターン

| パターン | 説明 | リスク | 適用場面 |
|---|---|---|---|
| **ビッグバン** | 一度に切り替え | 高 | 小規模、低リスク |
| **段階的移行** | 機能ごとに移行 | 中 | 中規模 |
| **ストラングラーフィグ** | 徐々に置換 | 低 | 大規模、高リスク |
| **並行運用** | 新旧を同時稼働 | 中 | データ整合性重視 |

### ストラングラーフィグの詳細

ファサードを導入し段階的に移行: Phase1=旧DB100% → Phase2=旧70%/新30% → Phase3=旧10%/新90% → Phase4=新DB100%（旧DB削除）

## 5.4 独立デプロイ可能性

### 目標状態

> **「各チームが他チームの承認なしにデータスキーマを変更し、デプロイできる」**

### 達成のための条件

| 条件 | 説明 |
|---|---|
| **明確なオーナーシップ** | 変更権限がチーム内に閉じている |
| **契約による結合** | 実装ではなく契約（API/イベント）で結合 |
| **後方互換性** | 消費者に影響を与えない変更 |
| **消費者の把握** | 誰が使っているか分かっている |
| **バージョニング** | 非互換変更時の並行サポート |

### 判定への影響

| 状況 | 判定修正 |
|---|:---:|
| 独立デプロイ可能な状態 | +2 |
| 消費者を把握し通知可能 | +1 |
| 変更に他チームの承認が必要 | -2 |
| 消費者が不明 | -2 |

## 8.3 シナリオ1: マイクロサービス分割

# 第10章: RPG強化システム

このゲームでは、学習体験を強化するための要素を導入しています。これらの要素は**オプション**であり、基本ルールのみでもプレイ可能です。

> **推奨**: 最初の1〜2ゲームは基本ルール（第1〜9章）のみでプレイし、ゲームに慣れてから本章のシステムを段階的に導入してください。

## 10.1 プレイヤースペシャリティ

プレイヤーは「データアーキテクト」として、以下の4つのスペシャリティから1つを選択できます。

### スペシャリティ一覧

| スペシャリティ | 特徴 | 判定ボーナス | 特殊能力（1ゲーム1回） |
|--------|------|:---:|---|
| **データモデラー** | スキーマ設計と正規化に優れる | 結合削減+1 | 「完璧な分離」: 外部キー削除の判定を自動成功 |
| **インテグレーションアーキテクト** | 統合パターンと結合設計に強い | 統合設計+1 | 「最適な統合」: 結合タイプ選択の判定を自動成功 |
| **データスチュワード** | オーナーシップとガバナンスが得意 | オーナーシップ+1 | 「明確な責任」: オーナーシップ定義を自動成功かつチーム自律性+2 |
| **マイグレーションエンジニア** | 移行とスキーマ進化に長ける | 移行+1 | 「安全な移行」: breaking changeを回避して移行成功 |

迷ったらデータモデラーがおすすめ。

# 付録A: クイックリファレンス

基本判定はメインscenario参照。データモデリング固有の主要修正値:

| 条件 | 修正 |
|---|:---:|
| データオーナー明確 / チーム境界=データ境界 / スキーマ進化戦略あり | +2 |
| 距離に応じた統合強度 / 契約での結合 | +1 |
| オーナー不在 / 外部キーで組織跨ぎ / breaking change | -2 |
| 共有DB直接アクセス / 技術的負債7+ | -3 |

結合タイプ: 共有DB(最強,避ける) → 外部キー(強,同一チーム内のみ) → 同期API(中強) → 非同期メッセージ(弱,推奨) → イベント(最弱,組織跨ぎ)
