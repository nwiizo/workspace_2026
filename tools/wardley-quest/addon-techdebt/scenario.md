# Technical Debt Quest

## 見えない借金を返す旅

**Strategic Evolution Quest アドオン**

```
『コードは動いている。でも、毎日少しずつ重くなっている。』

新機能の開発速度が落ちている。
バグ修正に時間がかかるようになった。
誰もが「リファクタリングが必要」と言うが、
いつも「今は時間がない」で終わる。

あなたは技術的負債の可視化と返済計画を任された。
ビジネスは止められない。でも、このままでは破綻する。

走りながら、どうやって負債を返すのか？
```

# 第1章: 技術的負債とは何か

## 1.1 負債のメタファー

技術的負債は Ward Cunningham が提唱した概念です。

```
┌─────────────────────────────────────────────────────────────┐
│                    技術的負債の本質                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  金融の負債と同じく:                                        │
│                                                             │
│  • 借りた時は楽になる（開発が速くなる）                     │
│  • 利子がつく（将来の変更コストが増える）                   │
│  • 返済しないと複利で増える（指数関数的に悪化）             │
│  • 破産する可能性がある（システムが変更不能に）             │
│                                                             │
│  ただし、金融と違い:                                        │
│                                                             │
│  • 残高が見えない                                           │
│  • 利率が分からない                                         │
│  • 誰が借りたか不明                                         │
│  • 返済期限がない                                           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 1.2 負債の種類

### 意図的な負債（Strategic Debt）

| 種類 | 説明 | 例 |
|------|------|-----|
| **計画的ショートカット** | 期限を優先した意図的な妥協 | MVP のための簡易実装 |
| **技術的実験** | 新技術の検証のための暫定実装 | PoC からの流用 |
| **ビジネス優先** | 市場機会を逃さないための判断 | 競合への対抗リリース |

### 非意図的な負債（Accidental Debt）

| 種類 | 説明 | 例 |
|------|------|-----|
| **知識不足** | ベストプラクティスを知らなかった | アンチパターンの実装 |
| **設計の腐敗** | 時間とともに設計が劣化 | 継ぎ足し開発による複雑化 |
| **環境の変化** | 外部要因による陳腐化 | フレームワークのEOL |

### ビット腐敗（Bit Rot）

```
時間の経過だけで発生する負債:

• 依存ライブラリのバージョン遅延
• セキュリティパッチの未適用
• ドキュメントと実装の乖離
• 暗黙知を持つメンバーの退職
```

## 1.3 負債の4象限

Martin Fowler の技術的負債の4象限:

```
                    無謀                   慎重
              ┌─────────────────┬─────────────────┐
              │                 │                 │
     意図的   │  「設計する時間  │  「今はこれで   │
              │   なんてない」   │   出荷しよう」  │
              │                 │                 │
              │   危険な負債    │  戦略的な負債   │
              ├─────────────────┼─────────────────┤
              │                 │                 │
    非意図的  │  「レイヤリング  │  「あぁ、こう   │
              │   って何？」     │   すべきだった」│
              │                 │                 │
              │   無知による負債 │  学習による負債 │
              └─────────────────┴─────────────────┘
```

# 第2章: ゲームの概要

## 2.1 あなたの役割

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  あなたは「技術的負債マネージャー」です。                    │
│                                                             │

│  ・負債を可視化し、組織に共有する                           │
│  ・返済計画を立て、ステークホルダーの合意を得る             │
│  ・ビジネス要求とのバランスを取りながら返済を実行する       │
│  ・負債が増えにくい文化を育てる                             │
│                                                             │
│  制約:                                                      │
│  ・新機能開発を完全に止めることはできない                   │
│  ・返済のための追加予算は限られている                       │
│  ・チームメンバーの時間も限られている                       │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 2.2 リソース

| リソース | 説明 | 初期値 |
|---------|------|:------:|
| **開発キャパシティ** | チームが使える開発時間（1ターン=1スプリント相当） | 100% |
| **負債返済枠** | 負債返済に使える開発キャパシティの割合 | 20% |
| **経営信頼** | 経営陣からの信頼度（0-10） | 5 |

| メトリクス | 説明 | 初期値 |

| **負債総量** | 推定返済工数（人日） | シナリオ依存 |
| **利子率** | 負債による開発速度低下（%/ターン） | シナリオ依存 |
| **可視化度** | 負債がどれだけ可視化されているか（0-10） | 2 |
| **コード健全性** | コードベースの健全度（0-10） | シナリオ依存 |

# 第3章: ゲームの流れ

## 3.1 ターン構造

各ターンは以下のフェーズで構成されます:

```
┌─────────────────────────────────────────────────────────────┐
│                      1ターンの流れ                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 状況確認フェーズ                                        │
│     ├── 負債メトリクスの確認                                │
│     ├── 利子の支払い（開発速度低下）                        │
│     └── イベントカードの確認                                │
│                                                             │
│  2. 計画フェーズ                                            │
│     ├── 今ターンの返済対象を選択                            │
│     ├── 返済方法を決定                                      │
│     └── リソース配分を決定                                  │
│                                                             │
│  3. 実行フェーズ                                            │
│     ├── 返済アクションの実行                                │
│     ├── 判定（2D6 + 修正値）                                │
│     └── 結果の適用                                          │
│                                                             │
│  4. 振り返りフェーズ                                        │
│     ├── メトリクスの更新                                    │
│     ├── 新規負債の発生確認                                  │
│     └── 学びの記録                                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 3.2 判定ルール

### 基本判定

```
2D6 + 修正値 ≥ 目標値 → 成功

修正値の例:
• 可視化度が高い: +1〜+2
• チーム士気が高い: +1
• 適切なツール使用: +1
• 経験豊富なメンバー参加: +1
• 時間的余裕がない: -1〜-2
```

### 判定結果

| 出目 | 結果 | 効果 |
|:----:|------|------|
| 12+ | 大成功 | 想定以上の効果、追加ボーナス |
| 10-11 | 成功 | 想定通りの効果 |
| 7-9 | 部分成功 | 効果は出るが副作用あり |
| 4-6 | 失敗 | 効果なし、時間だけ消費 |
| 3以下 | 大失敗 | 状況が悪化、新たな問題発生 |

# 第4章: 負債の可視化

## 4.1 可視化手法

### コードメトリクス分析

| メトリクス | 説明 | 閾値（危険） |
|-----------|------|:----------:|
| **循環的複雑度** | 分岐の複雑さ | 20以上 |
| **認知的複雑度** | 理解の困難さ | 15以上 |
| **重複率** | コピペコードの割合 | 5%以上 |
| **依存度** | モジュール間結合 | 高い依存 |
| **テストカバレッジ** | テストの網羅率 | 60%未満 |

### 負債マッピング

```
┌─────────────────────────────────────────────────────────────┐
│                    負債マップの例                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  [認証モジュール]─────[ユーザー管理]                        │
│       │ 負債:高            │ 負債:中                       │
│       │ 変更頻度:高        │ 変更頻度:低                   │
│       │ → 優先度:最高      │ → 優先度:低                   │
│       │                    │                               │
│  [決済モジュール]─────[レポート機能]                        │
│       │ 負債:中            │ 負債:高                       │
│       │ 変更頻度:中        │ 変更頻度:低                   │
│       │ → 優先度:高        │ → 優先度:中                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 4.2 優先順位付け

### コスト・オブ・ディレイ分析

```
優先度 = (ビジネスインパクト × 変更頻度) / 返済コスト

高 ← 優先度 → 低
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  [すぐやる]     [計画的に]     [機会があれば]   [放置]      │
│   高影響        高影響         低影響          低影響       │
│   低コスト      高コスト       低コスト        高コスト     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

# 第5章: 返済アクション

## 5.1 返済戦略

### リファクタリング（小規模）

| 項目 | 内容 |
|------|------|
| **所要時間** | 1-2ターン |
| **効果** | 負債 -5〜-10 |
| **リスク** | 低 |
| **適用場面** | 局所的な改善、命名変更、メソッド抽出 |

### モジュール再設計（中規模）

| 項目 | 内容 |
|------|------|
| **所要時間** | 3-5ターン |
| **効果** | 負債 -20〜-40 |
| **リスク** | 中 |
| **適用場面** | モジュール境界の再定義、責務の分離 |

### ストラングラーフィグ（大規模）

| 項目 | 内容 |
|------|------|
| **所要時間** | 6-10ターン |
| **効果** | 負債 -50〜-100 |
| **リスク** | 中〜高 |
| **適用場面** | レガシーシステムの段階的置換 |

### ビッグバンリライト（危険）

| 項目 | 内容 |
|------|------|
| **所要時間** | 不明（しばしば失敗） |
| **効果** | 理論上は全負債解消 |
| **リスク** | 非常に高 |
| **適用場面** | 最後の手段（推奨しない） |

## 5.2 予防アクション

### テスト追加

```
効果:
• 将来の負債発生を抑制
• リファクタリングの安全性向上
• チーム士気 +1

コスト: 開発キャパシティの10%
```

### コードレビュー強化

```
効果:
• 新規負債の流入を抑制
• 知識共有による属人化防止
• 可視化度 +1

コスト: 開発キャパシティの5%
```

### アーキテクチャ決定記録（ADR）

```
効果:
• 意図的な負債の追跡
• 将来の返済計画への情報
• 可視化度 +2

コスト: 開発キャパシティの2%
```

# 第7章: 勝敗と評価

## 7.1 終了条件

以下のいずれかで終了:

- 指定ターン数の完了
- 負債総量が目標以下に（勝利）
- コード健全性が0（敗北：変更不能）
- チーム士気が0（敗北：チーム崩壊）

═══════════════════════════════════════════════════════════════

═══════════════════════════════════════════════════════════════

═══════════════════════════════════════════════════════════════

### ターン別ガイド

**ターン1: 可視化から始める**
- まず現状を把握する
- コードメトリクス分析を実行
- 負債マップを作成

**ターン2: 優先順位をつける**
- 最もインパクトの大きい負債を特定
- 小さな返済で信頼を獲得

**ターン3: 本格的な返済**
- リファクタリングを実行
- チームを巻き込む

**ターン4: 予防策の導入**
- テスト追加やコードレビュー強化
- 持続可能な仕組みを作る
