# Technical Debt Quest

## 見えない借金を返す旅

**Strategic Evolution Quest アドオン**

> 『コードは動いている。でも、毎日少しずつ重くなっている。』
> あなたは技術的負債の可視化と返済計画を任された。
> ビジネスは止められない。でも、このままでは破綻する。
> 走りながら、どうやって負債を返すのか？

### コンパクトモード

| コマンド | 効果 |
|----------|------|
| 「コンパクトモード」 | 出力を1行要約+選択肢+状態のみに圧縮 |

# 第1章: 技術的負債とは何か

## 1.1 負債のメタファー

技術的負債は Ward Cunningham が提唱した概念です。

**金融の負債と同じく:**
- 借りた時は楽になる（開発が速くなる）
- 利子がつく（将来の変更コストが増える）
- 返済しないと複利で増える（指数関数的に悪化）
- 破産する可能性がある（システムが変更不能に）

**ただし金融と違い:** 残高が見えない / 利率が分からない / 誰が借りたか不明 / 返済期限がない

## 1.2 負債の種類

### 意図的な負債（Strategic Debt）

| 種類 | 説明 | 例 |
|------|------|-----|
| **計画的ショートカット** | 期限を優先した意図的な妥協 | MVP のための簡易実装 |
| **技術的実験** | 新技術の検証のための暫定実装 | PoC からの流用 |
| **ビジネス優先** | 市場機会を逃さないための判断 | 競合への対抗リリース |

### 非意図的な負債（Accidental Debt）

| 種類 | 説明 | 例 |
|------|------|-----|
| **知識不足** | ベストプラクティスを知らなかった | アンチパターンの実装 |
| **設計の腐敗** | 時間とともに設計が劣化 | 継ぎ足し開発による複雑化 |
| **環境の変化** | 外部要因による陳腐化 | フレームワークのEOL |

### ビット腐敗（Bit Rot）

時間の経過だけで発生する負債: 依存ライブラリのバージョン遅延 / セキュリティパッチの未適用 / ドキュメントと実装の乖離 / 暗黙知を持つメンバーの退職

## 1.3 負債の4象限

Martin Fowler の技術的負債の4象限:

|  | 無謀 | 慎重 |
|---|------|------|
| **意図的** | 「設計する時間なんてない」→ 危険な負債 | 「今はこれで出荷しよう」→ 戦略的な負債 |
| **非意図的** | 「レイヤリングって何？」→ 無知による負債 | 「あぁ、こうすべきだった」→ 学習による負債 |

# 第2章: ゲームの概要

## 2.1 あなたの役割

あなたは**技術的負債マネージャー**です。

**ミッション:**
- 負債を可視化し、組織に共有する
- 返済計画を立て、ステークホルダーの合意を得る
- ビジネス要求とのバランスを取りながら返済を実行する
- 負債が増えにくい文化を育てる

**制約:** 新機能開発を完全に止めることはできない / 返済のための追加予算は限られている / チームメンバーの時間も限られている

## 2.2 リソース

| リソース | 説明 | 初期値 |
|---------|------|:------:|
| **開発キャパシティ** | チームが使える開発時間（1ターン=1スプリント相当） | 100% |
| **負債返済枠** | 負債返済に使える開発キャパシティの割合 | 20% |
| **経営信頼** | 経営陣からの信頼度（0-10） | 5 |
| **チーム士気** | 開発チームの士気（0-10） | 5 |

## 2.3 負債メトリクス

| メトリクス | 説明 | 初期値 |
|-----------|------|:------:|
| **負債総量** | 推定返済工数（人日） | シナリオ依存 |
| **利子率** | 負債による開発速度低下（%/ターン） | シナリオ依存 |
| **可視化度** | 負債がどれだけ可視化されているか（0-10） | 2 |
| **コード健全性** | コードベースの健全度（0-10） | シナリオ依存 |

# 第3章: ゲームの流れ

## 3.1 ターン構造

各ターンは以下の4フェーズで構成:

1. **状況確認フェーズ** — 負債メトリクス確認 → 利子支払い（開発速度低下） → イベントカード確認
2. **計画フェーズ** — 返済対象選択 → 返済方法決定 → リソース配分決定
3. **実行フェーズ** — 返済アクション実行 → 判定（2D6+修正値） → 結果適用
4. **振り返りフェーズ** — メトリクス更新 → 新規負債発生確認 → 学びの記録

## 3.2 判定ルール

基本判定はメインscenario参照。

### アドオン固有修正値

| 状況 | 修正 |
|------|:----:|
| 可視化度が高い（6以上） | +1〜+2 |
| チーム士気が高い（7以上） | +1 |
| 適切なツール使用 | +1 |
| 経験豊富なメンバー参加 | +1 |
| 時間的余裕がない | -1〜-2 |

### 判定結果

| 出目 | 結果 | 効果 |
|:----:|------|------|
| 12+ | 大成功 | 想定以上の効果、追加ボーナス |
| 10-11 | 成功 | 想定通りの効果 |
| 7-9 | 部分成功 | 効果は出るが副作用あり |
| 4-6 | 失敗 | 効果なし、時間だけ消費 |
| 3以下 | 大失敗 | 状況が悪化、新たな問題発生 |

# 第4章: 負債の可視化

## 4.1 可視化手法

### コードメトリクス分析

| メトリクス | 説明 | 閾値（危険） |
|-----------|------|:----------:|
| **循環的複雑度** | 分岐の複雑さ | 20以上 |
| **認知的複雑度** | 理解の困難さ | 15以上 |
| **重複率** | コピペコードの割合 | 5%以上 |
| **依存度** | モジュール間結合 | 高い依存 |
| **テストカバレッジ** | テストの網羅率 | 60%未満 |

### 負債マッピング

負債マップでは各モジュールの「負債レベル」と「変更頻度」を掛け合わせて優先度を決定する:
- **高負債 × 高変更頻度** → 優先度: 最高
- **高負債 × 低変更頻度** → 優先度: 中
- **低負債 × 高変更頻度** → 優先度: 低

## 4.2 優先順位付け

### コスト・オブ・ディレイ分析

**優先度 = (ビジネスインパクト × 変更頻度) / 返済コスト**

| 分類 | 影響 | コスト | 対応 |
|------|------|--------|------|
| すぐやる | 高影響 | 低コスト | 即実行 |
| 計画的に | 高影響 | 高コスト | スプリント計画に組込 |
| 機会があれば | 低影響 | 低コスト | ついでに対応 |
| 放置 | 低影響 | 高コスト | 対応しない |

# 第5章: 返済アクション

## 5.1 返済戦略

| 戦略 | 所要時間 | 効果 | リスク | 適用場面 |
|------|:--------:|------|:------:|---------|
| **リファクタリング（小）** | 1-2ターン | 負債-5〜-10 | 低 | 局所的改善、命名変更、メソッド抽出 |
| **モジュール再設計（中）** | 3-5ターン | 負債-20〜-40 | 中 | モジュール境界の再定義、責務の分離 |
| **ストラングラーフィグ（大）** | 6-10ターン | 負債-50〜-100 | 中〜高 | レガシーシステムの段階的置換 |
| **ビッグバンリライト（危険）** | 不明 | 理論上は全解消 | 非常に高 | 最後の手段（推奨しない） |

## 5.2 予防アクション

| アクション | 効果 | コスト |
|-----------|------|--------|
| **テスト追加** | 将来の負債抑制、リファクタリング安全性向上、チーム士気+1 | キャパシティの10% |
| **コードレビュー強化** | 新規負債流入抑制、知識共有で属人化防止、可視化度+1 | キャパシティの5% |
| **ADR（アーキテクチャ決定記録）** | 意図的負債の追跡、返済計画への情報、可視化度+2 | キャパシティの2% |

# 第6章: NPCシステム

> **Note**: 以下のNPCは代表的な役割パターンです。GMはシナリオのテーマや複雑さに応じて、NPCの追加・削除・変更を自由に行えます。

## 6.1 主要NPC

### 佐藤CTO（経営層）

- **立場**: 技術投資の最終決定者
- **関心**: ビジネス価値、ROI、リスク管理
- **口癖**: 「で、それでどれだけ速くなるの？」
- **攻略**: 負債をビジネス言語で説明 / 具体的ROIを示す / リスクを数値化
- **関係値**(-3〜+3): +3=返済予算増額 / +1〜+2=計画承認 / 0=様子見 / -1〜-2=新機能優先圧力 / -3=返済活動停止

### 田中リードエンジニア（現場の声）

- **立場**: 10年選手、コードベースを最もよく知る
- **関心**: 技術的正しさ、チームの健全性
- **口癖**: 「ここ、本当はこうすべきなんですけどね...」
- **攻略**: 技術的議論を真剣に聞く / 過去の経緯を尊重 / 返済計画に巻き込む
- **関係値**(-3〜+3): +3=返済作業を主導 / +1〜+2=積極的協力 / 0=求められれば手伝う / -1〜-2=「また形だけの改善か」 / -3=返済妨害

### 鈴木プロダクトマネージャー（ビジネス要求）

- **立場**: 新機能のプレッシャーを受けている
- **関心**: リリース速度、顧客満足、市場シェア
- **口癖**: 「競合がもう出してるんです」
- **攻略**: 負債が速度を落としていることを示す / 返済後の速度向上を約束 / 小さな勝利を共有
- **関係値**(-3〜+3): +3=返済のための機能延期を容認 / +1〜+2=バランスを取る / 0=表面的理解 / -1〜-2=常に新機能要求 / -3=「負債なんて言い訳」

### 山本ジュニアエンジニア（次世代）

- **立場**: 入社2年目、新鮮な視点を持つ
- **関心**: 学習、成長、モダンな技術
- **口癖**: 「なんでこうなってるんですか？」
- **攻略**: 疑問を歓迎 / 返済作業を学習機会として提供 / 小さな改善を任せる
- **関係値**(-3〜+3): +3=負債返済のチャンピオン / +1〜+2=積極的に学び貢献 / 0=言われたことはやる / -1〜-2=「このコードベース無理」 / -3=退職検討

### 高橋ドメインエキスパート（業務知識）

- **立場**: 15年勤務、業務ロジックを最も理解している
- **関心**: 業務の正確性、ユーザー体験、運用の安定
- **口癖**: 「この処理には理由があるんです」
- **攻略**: 業務知識の価値を認める / リファクタリング時に業務要件確認 / 暗黙知ドキュメント化の機会を作る
- **関係値**(-3〜+3): +3=業務ロジック整理を手伝う / +1〜+2=業務影響を教える / 0=聞かれれば答える / -1〜-2=「また壊されるんじゃ」 / -3=「エンジニアは業務を分かってない」

| ビッグバンリライト失敗 | -10 |

## 7.3 バッドエンディング

### 「永遠の借金地獄」エンディング
**条件**: 負債総量が開始時の150%以上
**学び**: 負債は複利で増える、早期対処が鍵 / 返済しながら新たな負債を作らない仕組みが必要 / 利子（開発速度低下）を可視化する

### 「チーム崩壊」エンディング
**条件**: チーム士気が0
**学び**: 技術的負債は人的負債を生む / 開発者の士気は最優先で守るべき資産 / 小さな成功を祝い、進捗を可視化する

### 「ビジネス優先の代償」エンディング
**条件**: 経営信頼-3かつコード健全性3以下
**学び**: 負債は「見えない」だけで「ない」わけではない / ビジネスと技術はトレードオフではなく両輪 / 経営層への可視化と教育が重要

### 「リライトの墓場」エンディング
**条件**: ビッグバンリライトを選択して失敗
**学び**: ビッグバンリライトは90%失敗する / 段階的な改善（ストラングラーフィグ）を選ぶ / 既存システムの複雑さを過小評価しない

### 「可視化されない闇」エンディング
**条件**: 可視化度3以下で終了
**学び**: 可視化は返済の前提条件 / 見えないものは管理できない / 「なんとなくヤバい」を「ここが、これだけヤバい」に

### 7.4 決められていないバッドエンディング

| パターン | 発生条件（目安） | 結末の方向性 |
|---------|-----------------|-------------|
| 「政治的敗北」 | NPC関係値が全員-2以下 | 誰も協力せず孤立 |
| 「完璧主義の罠」 | 同じモジュールを5ターン以上リファクタリング | 完璧を求めすぎて進まない |
| 「負債の移転」 | 別チームに負債を押し付けた | 組織全体の信頼崩壊 |

## 7.5 グッドエンディング

### 「返済完了」エンディング
**条件**: 負債目標達成、コード健全性8以上
**学び**: 負債を可視化し全員で共有した / 小さな返済を積み重ね信頼を獲得した / 返済を学習機会としてチームを成長させた

### 「予防文化の確立」エンディング
**条件**: 新規負債発生ゼロ、予防策3つ以上導入
**学び**: 予防を文化として根付かせた / 意図的な妥協は記録し返済計画を立てた / ビジネス側も技術的健全性の価値を理解した

### 「チームの成長」エンディング
**条件**: チーム士気8以上、全NPCとの関係値+2以上
**学び**: 返済作業を学習機会として活用した / 属人化を解消し全員がコードを理解できるようにした / 成功体験を積み重ね自信を育てた

### 基礎コンピテンシー
