# 第1章: ゲーム概要

## 1.1 このゲームについて

**Discovery Workshop Quest** は、Strategic Evolution Questの拡張として、**ステークホルダー理解とドメイン発見のためのワークショップ手法を学ぶ**戦略シミュレーションRPGです。

モダナイゼーションや新規プロジェクトの成功は、最初の「発見」フェーズにかかっています。リスニングツアー、インパクトマッピング、リスクストーミングなどの手法を使いこなし、プロジェクトの成功確率を高めます。

### 核心的な問い

> **「何を作るか、なぜ作るか、誰のために作るかを、どうすれば正しく理解できるのか？」**

### Discoveryの重要性

| よくある失敗 | Discoveryで防げること |
|---|---|
| 「作ったけど使われない」 | ステークホルダーの真のニーズを理解 |
| 「想定と違った」 | 仮説を早期に検証 |
| 「後から大きな問題が」 | リスクの早期発見 |
| 「関係者が協力しない」 | 早期の巻き込みと合意形成 |
| 「ゴールがぶれる」 | 明確な成功基準の定義 |

### フレームワークの関係

**Discovery Phase（発見フェーズ）**
1. リスニングツアー / インパクトマッピング / リスクストーミング / ビジネスモデルキャンバス
2. → EventStorming（Discoveryで得た知識をもとにドメインを探索）
3. → 設計・実装フェーズ（正しい方向に向かって構築）

### プレイ形式

| 項目 | 内容 |
|---|---|
| プレイヤー | 1名（プロダクトマネージャー/アーキテクト） |
| GM | Claude（シナリオ・判定・ステークホルダー反応） |
| 所要時間 | 60〜120分 |
| 前提 | Strategic Evolution Questの基礎知識（推奨） |

### コンパクトモード

| コマンド | 効果 |
|----------|------|
| 「コンパクトモード」 | 出力を1行要約+選択肢+状態のみに圧縮 |
| 「通常モード」 | 標準出力に戻す |
| 「状態確認」 | 現在のスコアのみ表示 |
| 「サマリー」 | これまでの決定を箇条書きで要約 |

## 1.2 Discovery手法の本質

### Nick Tuneの洞察

Architecture Modernizationでは、**技術的な決定の前に、ビジネスとステークホルダーを深く理解すること**の重要性が強調されています。

| 観点 | 説明 |
|---|---|
| **傾聴** | 答えを持っていく前に、問いを持っていく |
| **共感** | ステークホルダーの立場で考える |
| **発見** | 想定外のニーズや制約を見つける |
| **整合** | ビジネス目標と技術判断を結びつける |

### Discoveryで答えるべき問い

- **ビジネス**: なぜこのプロジェクトを行うのか？ / 成功とは何か？ / ビジネス上の制約は？
- **ステークホルダー**: 誰が影響を受けるか？ / 何を求めているか？ / 誰がブロッカーになりうるか？
- **ドメイン**: ビジネスはどう動いているか？ / どこに複雑さがあるか？ / どこに暗黙知があるか？
- **リスク**: 何がプロジェクトを失敗させうるか？ / 技術的リスクは？ / 組織的リスクは？

# 第2章: ゲームルール

## 2.1 セッション構造

**Phase 1: 準備** — 背景理解 → 初期ステークホルダー特定 → Discovery計画策定 → 質問リスト準備

**Phase 2: Discovery実行（ターン制）** — 各ターン:
1. 状況イベント（D6 × 2）: ステークホルダーの反応、新情報が発生
2. 状況分析（4つの視点）: 発見ポイント / 信頼度 / リスク / 残り時間
3. アクション宣言（最大3つ）: インタビュー、ワークショップ、分析など
4. 判定（2D6 + 修正値）: Discovery活動の成否を評価
5. 結果適用: 発見ポイント更新 / 新ステークホルダー発見 / リスク特定

**Phase 3: 統合と報告** — 情報整理 → インサイト抽出 → リスク優先順位付け → 推奨事項 → 報告

毎ターン開始時にD6を2回振り、2つのイベントが発生します。

### 状況イベント表

| D6 | イベント | 効果 | 対応のヒント |

# 第3章: リスニングツアー

## 3.1 概要

リスニングツアーは、**ステークホルダーを訪問して直接話を聴く**活動です。

### このフレームワークで答える問い

- 「この人は何を気にしているか？」
- 「彼らにとっての成功とは何か？」
- 「彼らが抱える課題は何か？」
- 「誰が重要な情報を持っているか？」

---

## 3.2 準備

### ステークホルダーマッピング

| | 関心度: 低 | 関心度: 高 |
|---|---|---|
| **影響力: 高** | Monitor（注視） | Manage Closely（密接に管理）: 経営層、主要ユーザー |
| **影響力: 低** | Minimal（最小限） | Keep Informed（情報提供）: 間接的利害関係者 |

### 質問の準備

- **オープニング**: 「あなたの仕事について教えてください」「このプロジェクトに期待することは？」
- **深掘り**: 「なぜそれが重要なのですか？」「具体的な例を教えてください」「それがうまくいかないとどうなりますか？」
- **クロージング**: 「他に話を聞くべき人はいますか？」「見落としていることはありますか？」

---

## 3.3 進行のコツ

### インタビューの原則

| 原則 | 説明 |
|---|---|
| **傾聴** | 話すより聴く（80:20の法則） |
| **沈黙** | 相手が考える時間を与える |
| **メモ** | 後で詳細を書き起こすために記録 |
| **確認** | 理解が正しいか確認する |
| **感謝** | 時間を取ってくれたことへの感謝 |

### 避けるべきこと

| 避けること | 理由 |
|---|---|
| 誘導質問 | 答えを誘導してしまう |
| 専門用語 | 相手が理解できない可能性 |
| 判断を示す | 相手が萎縮する |
| 長時間 | 45分を超えると集中力低下 |

# 第4章: インパクトマッピング

## 4.1 概要

インパクトマッピングは、**ビジネス目標から逆算して、何を作るべきかを導出する**手法です。

### 4つの質問

**WHY（目標）→ WHO（アクター）→ HOW（インパクト）→ WHAT（成果物）**

- WHY: なぜこれをやるのか？（ビジネス目標）
- WHO: 誰がこの目標達成に関与するか？
- HOW: 彼らの行動をどう変えるか？
- WHAT: その変化を引き起こすために何を作るか？

---

## 4.2 進め方

**ステップ1: 目標の明確化** — 良い例:「新規顧客獲得を20%増加」「処理時間を50%短縮」。悪い例:「新しいシステムを作る」（手段）「モダナイズする」（測定不能）

**ステップ2: アクターの特定** — 目標を達成する人 / 妨げる人 / 助ける人 / 間接的に影響する人

**ステップ3: インパクトの定義** — 行動変化の方向: 始める / やめる / もっとする / 減らす

**ステップ4: 成果物の導出** — インパクトから逆算して機能を考え、目標への貢献度で優先順位を決める

---

## 4.3 判定への影響

| 状況 | 判定修正 |
|---|:---:|
| 測定可能な目標を設定 | +2 |
| 複数のアクターを特定 | +1 |
| インパクトを具体的に定義 | +1 |
| 目標が曖昧 | -2 |
| アクターが不明確 | -1 |

---

# 第5章: リスクストーミング

## 5.1 概要

リスクストーミングは、**チームでリスクを洗い出し、可視化する**ワークショップ手法です。

### リスクの分類

- **技術的リスク**: 未知の技術の採用 / 統合の複雑さ / パフォーマンス要件 / セキュリティ脆弱性
- **組織的リスク**: スキル不足 / ステークホルダーの抵抗 / 予算制約 / チームの分散
- **ビジネスリスク**: 要件の変更 / 市場の変化 / 競合の動き / 規制変更

---

## 5.2 進め方

**ステップ1: リスクの洗い出し（20分）** — サイレントブレインストーミング、1リスク1付箋、判断を入れずに書き出す

**ステップ2: リスクの分類（15分）** — 技術的/組織的/ビジネスにグルーピング、重複の統合

**ステップ3: リスク評価（20分）** — 影響度(高/低) x 発生確率(高/低) のマトリクスで優先度判定。高影響x高確率=対応必須、低影響x低確率=許容

**ステップ4: 対応策の検討（15分）** — 回避（発生させない）/ 軽減（影響を小さく）/ 転嫁（別主体に移す）/ 受容（許容する）

---

## 5.3 判定への影響

| 状況 | 判定修正 |
|---|:---:|
| 多様な参加者でリスク洗い出し | +2 |
| 全リスクに対応策を検討 | +1 |
| リスクの優先順位を明確化 | +1 |
| 一部の視点のみでリスク評価 | -2 |
| 対応策なしで終了 | -1 |

# 第7章: 勝敗と評価

## 7.1 終了条件

以下のいずれかで終了：

- 指定ターン数の完了
- ステークホルダー信頼度が全て0（敗北：協力を得られない）
- 全ての主要発見を達成（早期勝利）

## 7.2 評価基準

### 基本得点

| 条件 | ポイント |
|---|:---:|
| 生存（ターン完了） | +10 |
| 主要目標達成 | +10 |

### ボーナス

| 条件 | ポイント |
|---|:---:|
| 発見ポイント20以上 | +10 |
| 全主要ステークホルダーとの信頼構築 | +5 |
| リスク可視化度8以上 | +5 |
| 隠れたステークホルダーを発見 | +3 |
| 整合性8以上 | +5 |
| 明確な推奨事項をまとめた | +3 |

### ペナルティ

| 条件 | ポイント |
|---|:---:|
| 発見ポイント10未満 | -10 |
| 主要ステークホルダーと不和 | -5 |
| 重大なリスクを見落とし | -5 |
| 時間切れで中途半端 | -3 |

## 7.3 バッドエンディング

終了条件による敗北時、以下のエンディングが表示されます。

### 「信頼崩壊」エンディング
**条件**: ステークホルダー信頼度が全て0になった
**学び**: 信頼関係は発見活動の基盤 / 失った信頼の回復は構築より困難 / 「どう関係を築くか」が重要

### 「見つからなかった真実」エンディング
**条件**: ターン終了時に発見ポイント10未満
**学び**: 表面的なヒアリングでは暗黙知は引き出せない / 複数視点のクロスチェックが重要 / 深掘りする勇気を持つ

### 「対立の火種」エンディング
**条件**: 主要ステークホルダー間の不和を生じさせた
**学び**: 発見情報の取り扱いには細心の注意が必要 / 組織の政治的ダイナミクスを理解する / 「誰が言ったか」を軽々しく共有しない

### 「時間切れの形骸」エンディング
**条件**: ターン終了時に主要発見が3つ未満
**学び**: Discoveryは「量」より「質」 / 重要な発見に集中する勇気を持つ / 「何を調べないか」も重要な判断

### 「バイアスの罠」エンディング
**条件**: 同じステークホルダーばかりにアクセスし、リスク可視化度が3以下
**学び**: 多様な視点からの情報収集が必須 / 確証バイアスは無意識に忍び込む / 現場の声、特に「弱い立場」の声を聞く

### 7.4 決められていないバッドエンディング

| パターン | 発生条件（目安） | 結末の方向性 |
|---------|-----------------|-------------|
| 「情報過多の麻痺」 | 発見ポイント30以上かつ整合性3以下 | 情報が多すぎて何も決められない |
| 「秘密の暴露」 | NPC関係-2以下が2人以上 | 機密情報の取り扱いミスで信用喪失 |
| 「見えない象」 | 隠れたステークホルダー未発見で終了 | 最重要人物を見落とし、後で全てが覆る |
| 「分析麻痺」 | 3ターン連続で同じアクション | 完璧を求めすぎて前に進めない |

GMは状況に応じてカスタムバッドエンディングを生成可能。

## 7.5 グッドエンディング

### 「信頼の架け橋」エンディング
**条件**: 全主要ステークホルダーとの信頼構築、発見ポイント20以上
**学び**: 関係構築を優先して傾聴した / 発見情報を適切に扱い信頼を裏切らなかった / 問題と解決への道筋を一緒に考えた

### 「隠れた宝を見つけた」エンディング
**条件**: 隠れたステークホルダーを発見、リスク可視化度8以上
**学び**: 表面的な回答を鵜呑みにせず深掘りした / 「声の小さい人」の話を聞いた / 発見したリスクを適切にエスカレーションした

### 「組織の通訳者」エンディング
**条件**: 全ボーナス条件達成
**学び**: 各ステークホルダーの「言語」を理解した / 発見を全員が理解できる形で可視化した / 中立的な「翻訳者」として共通目標に焦点を当てた

# 第10章: RPG強化システム

このゲームでは、学習体験を強化するための要素を導入しています。これらの要素は**オプション**であり、基本ルールのみでもプレイ可能です。

> **推奨**: 最初の1〜2ゲームは基本ルール（第1〜9章）のみでプレイし、ゲームに慣れてから本章のシステムを段階的に導入してください。

## 10.1 プレイヤースペシャリティ

プレイヤーは「プロダクトマネージャー/アーキテクト」として、以下の4つのスペシャリティから1つを選択できます。

### スペシャリティ一覧

| スペシャリティ | 特徴 | 判定ボーナス | 特殊能力（1ゲーム1回） |
|--------|------|:---:|---|
| **インタビュアー** | 1on1の対話に優れる | インタビュー+1 | 「本音を引き出す」: インタビュー判定を自動成功 |
| **ファシリテーター** | ワークショップ進行に強い | ワークショップ+1 | 「場の空気を変える」: 対立を解消、信頼度+2 |
| **アナリスト** | 情報整理と分析に長ける | 分析+1 | 「パターン認識」: 隠れた制約/リスクを1つ発見 |
| **ネットワーカー** | 人脈構築と紹介獲得が得意 | 関係構築+1 | 「キーパーソン紹介」: 隠れたステークホルダーへのアクセス獲得 |

迷ったらインタビュアーがおすすめ（汎用性が高い）。

---

## 10.2 NPCシステム

GMはシナリオに応じてNPCの追加・削除・変更を自由に行えます。

| NPC名 | 役割 | 台詞（特徴） | 関係値 | 特殊能力 |
|-------|------|-------------|:------:|----------|
| **高橋部長** | 事業部長（スポンサー） | 結果重視 | 0 | 良好: アクセス権+2 / 悪化: タイムボックス短縮 |
| **中村執行役員** | CTO（スポンサー） | 技術判断重視、慎重派 | 0 | 良好: 技術リスク情報+2 / 悪化: 技術調査制限 |
| **伊藤ベテラン** | ドメインエキスパート（20年勤務） | 暗黙知の宝庫、変化に慎重 | 0 | 良好: 暗黙知発見+2 / 悪化: 情報提供拒否 |
| **木村マネージャー** | 営業マネージャー | 顧客の声を代弁、短期成果志向 | 0 | 良好: 顧客視点+1 / 悪化: 要件の偏り |
| **渡辺エンジニア** | シニアエンジニア | 技術的制約を熟知、懐疑的 | 0 | 良好: 技術判定+1 / 悪化: 「どうせ無理」ムード |

### 関係値システム

NPCとの関係値は **-3〜+3** の範囲で変動します。

| 関係値 | 状態 | 効果 |
|:---:|---|---|
| +3 | 強い信頼 | 本音で話す、他者を紹介してくれる |
| +1〜+2 | 良好 | 協力的、質問に答えてくれる |
| 0 | 中立 | 基本的な協力のみ |
| -1〜-2 | 警戒 | 情報を出し渋る、建前のみ |
| -3 | 敵対 | 積極的に妨害、悪い噂を流す |

### 関係値の変動

| 行動 | 変動 |
|------|:---:|
| NPCの話を傾聴し、理解を示す | +1 |
| NPCの懸念に具体的な対応を提示 | +1 |
| 発見した情報をフィードバック | +1 |
| NPCの意見を無視して進める | -1 |
| NPCの時間を無駄にする（準備不足） | -1 |
| 機密情報を漏らす | -2 |
