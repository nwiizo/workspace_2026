# Incident Management Quest

## 本番障害との戦い

**Strategic Evolution Quest アドオン**

> 『アラートが鳴り響く。Slackが爆発する。電話が鳴り止まない。』
> 午前3時、あなたはインシデントコマンダーとして呼び出された。
> 混乱の中で冷静に判断し、サービスを復旧させ、同じことを二度と起こさないために何を学ぶのか。

---

# 第1章: インシデント対応の基本

## 1.1 インシデントとは何か

**インシデントとは:** サービスの品質低下/停止、顧客体験への悪影響、SLO違反、通常運用では対処できない状況

**インシデントではないもの:** 通常のバグ修正、計画メンテナンス、パフォーマンス改善タスク

## 1.2 重大度（Severity）レベル

| レベル | 名称 | 定義 | 対応 |
|:------:|------|------|------|
| **SEV1** | Critical | サービス全停止、重大なデータ損失リスク | 即時対応、全員招集、経営報告 |
| **SEV2** | Major | 主要機能の停止、多数ユーザーに影響 | 即時対応、オンコール招集、顧客通知 |
| **SEV3** | Minor | 一部機能の低下、限定的な影響 | 営業時間内対応、チケット管理 |
| **SEV4** | Low | 軽微な問題、回避策あり | 通常の優先度でキュー処理 |

### 重大度判定フロー

1. 完全停止？ → **SEV1**
2. 主要収益機能に影響？ → **SEV2**
3. 顧客問い合わせあり？ → **SEV2/3**（影響範囲で判断）
4. 放置で悪化？ → **SEV3** / そうでなければ **SEV4**

※ 迷ったら重大度を上げる

## 1.3 インシデント対応の役割

### インシデントコマンダー（IC）

**責任:** 全体の指揮と調整、重大度の判断と更新、リソースの割り当て、ステークホルダーへの報告、エスカレーションの判断

**やらないこと:** 直接のデバッグ、顧客対応、詳細な技術判断（※ ICは「指揮者」であり楽器は演奏しない）

### その他の役割

| 役割 | 責任 | スキル |
|------|------|--------|
| **技術リード** | 技術的な調査と判断、復旧作業の実施 | 深いシステム知識 |
| **コミュニケーション担当** | 顧客・社内への状況報告 | 明確な文章力 |
| **書記** | タイムラインの記録、決定事項の文書化 | 正確な記録力 |
| **オブザーバー** | 学習のための観察（主にポストモーテム用） | 客観的な視点 |

# 第2章: ゲームの概要

## 2.1 あなたの役割

あなたは**インシデントコマンダー**です。

**ミッション:** 検知→重大度判断→チーム招集→復旧→ステークホルダー報告→再発防止

**制約:** 情報は常に不完全 / チームの時間と集中力は有限 / 顧客と経営層は即座の回答を求める / あなた自身も疲労する

## 2.2 リソース

| リソース | 説明 | 初期値 |
|---------|------|:------:|
| **サービス健全性** | サービスの稼働状態（0-10） | シナリオ依存 |
| **エラーバジェット** | 許容される障害時間の残り（%） | シナリオ依存 |
| **チーム集中力** | チームが効果的に働ける度合い（0-10） | 8 |
| **ステークホルダー信頼** | 経営層・顧客からの信頼（0-10） | 5 |

## 2.3 インシデントメトリクス

| メトリクス | 説明 | 目標 |
|-----------|------|------|
| **MTTD** | 検知までの時間（Mean Time To Detect） | 短いほど良い |
| **MTTR** | 復旧までの時間（Mean Time To Recover） | 短いほど良い |
| **影響範囲** | 影響を受けたユーザー数 | 小さいほど良い |
| **再発率** | 同じ原因のインシデント再発 | 0が理想 |

# 第3章: ゲームの流れ

## 3.1 インシデント対応フェーズ

| Phase | 名称 | ターン | 主なアクション |
|:-----:|------|:------:|---------------|
| 1 | 検知と初動 | 1-2 | アラート確認→重大度判定→チーム招集→第一報 |
| 2 | 調査と緩和 | 2-4 | 影響範囲特定→根本原因調査→緩和策実施→状況報告 |
| 3 | 復旧と確認 | 1-2 | 完全復旧確認→モニタリング強化→クローズ宣言 |
| 4 | 振り返り | 1 | ポストモーテム→アクションアイテム→学びの共有 |

## 3.2 ターン構造

各ターンは約30分〜1時間のインシデント対応時間を表します。

1. **状況確認** — サービス状態・新アラート・イベントカード確認
2. **判断** — アクション決定・人員割り当て・コミュニケーション優先度
3. **実行** — アクション実行 → 判定（2D6+修正値） → 結果適用
4. **更新** — メトリクス更新・タイムライン記録・次ターンへ引き継ぎ

## 3.3 判定ルール

### 基本判定

2D6 + 修正値 ≥ 目標値 → 成功（簡単5 / 標準7 / 困難9 / 非常に困難11）

### 判定結果

| 出目 | 結果 | 効果 |
|:----:|------|------|
| 2 | 致命的失敗 | 状況悪化、新たな問題発生 |
| 3-4 | 失敗 | 進展なし、時間を消費 |
| 5-6 | 部分的失敗 | わずかな進展、副作用あり |
| 7-8 | 部分的成功 | 目標に近づく、完全ではない |
| 9-10 | 成功 | 想定通りの結果 |
| 11 | 大成功 | 追加の発見、効率的な解決 |
| 12 | 完全成功 | 最高の結果、学びも得る |

### 修正値

#### 状況による修正

| 状況 | 修正 | 理由 |
|------|:----:|------|
| ランブックが存在する | +2 | 手順が明確 |
| 最近の類似インシデント経験 | +1 | パターン認識 |
| 十分なオブザーバビリティ | +1 | 情報が豊富 |
| チーム集中力が7以上 | +1 | 効果的に働ける |
| チーム集中力が3以下 | -2 | 疲労によるミス |
| 情報が不完全 | -1 | 推測に頼る |
| 複数システムが関与 | -1 | 複雑性増大 |
| 深夜対応 | -1 | 認知能力低下 |

#### コミュニケーションによる修正

| 状況 | 修正 | 理由 |
|------|:----:|------|
| 定期的な状況報告を実施 | +1 | 信頼の維持 |
| ステークホルダー信頼が7以上 | +1 | 協力を得やすい |
| ステークホルダー信頼が3以下 | -1 | 疑念と干渉 |
| 顧客への適切な通知 | +1 | 混乱を防止 |

# 第5章: イベントカード

## 5.1 インシデント中のイベント

毎ターン開始時にD6を振り、イベントが発生します。

| D6 | イベント | 効果 |
|:--:|----------|------|
| 1 | **新たな症状発見** | 影響範囲が想定より広いことが判明（サービス健全性-1） |
| 2 | **顧客からの緊急連絡** | VIP顧客から直接連絡、即座の説明が必要 |
| 3 | **関連システムの問題** | 別のシステムでも問題が検出される |
| 4 | **有用な情報の発見** | チームメンバーが重要な手がかりを発見（次の判定+2） |
| 5 | **リソースの到着** | 追加の専門家が参加可能に |
| 6 | **自然回復の兆候** | 一部の問題が自然に緩和（サービス健全性+1） |

## 5.2 コミュニケーションイベント

ステークホルダー信頼が低い場合（4以下）、追加でD6を振ります。

| D6 | イベント | 効果 |
|:--:|----------|------|
| 1-2 | **経営層の介入** | 詳細な報告を要求、チーム集中力-1 |
| 3-4 | **SNSでの言及** | 顧客がSNSで問題を報告、対応の圧力 |
| 5-6 | **プレスからの問い合わせ** | メディア対応が必要になる可能性 |

# 第6章: ポストモーテム

## 6.1 ブレームレスポストモーテムとは

**目的:** 再発防止 / 組織学習 / 安心して情報共有できる場

**やること:** 事実の時系列整理 → 「何が」起こったか → システム的改善点 → アクションアイテム

**やらないこと:** 「誰が」悪いか探し、個人を責める、反省文、罰則

> 「人はミスをする。システムがミスを許容しないのが問題。」

## 6.2 ポストモーテムの構造

### 基本セクション

| セクション | 内容 |
|-----------|------|
| **サマリー** | 何が起こったかの1-2文の要約 |
| **影響** | 影響を受けたユーザー数、時間、ビジネス影響 |
| **タイムライン** | 検知から解決までの時系列 |
| **根本原因** | 問題の本質的な原因（複数可） |
| **貢献因子** | 問題を悪化させた要因 |
| **うまくいったこと** | 被害を最小化した対応 |
| **改善点** | 次回より良くできること |
| **アクションアイテム** | 具体的な改善タスクと担当者 |

### 5 Whys 分析（例）

サービスダウン → DB接続タイムアウト → 接続プール枯渇 → 新機能が接続未解放 → レビューで見逃し → チェックリスト不在
→ **アクション:** レビューチェックリストに「接続の確実な解放」を追加

## 6.3 ゲーム内でのポストモーテム

インシデント解決後、以下の質問に答えてポストモーテムを完成させます。

| 質問 | 回答のポイント |
|------|---------------|
| 検知は十分速かったか？ | MTTDの評価、アラート改善の余地 |
| 初動は適切だったか？ | 重大度判定、チーム招集のタイミング |
| 情報は十分だったか？ | オブザーバビリティ、ログの質 |
| コミュニケーションは効果的だったか？ | ステークホルダーへの報告タイミング |
| 復旧は効率的だったか？ | ランブックの有無、手順の改善点 |
| 何を変えるべきか？ | システム、プロセス、文化の改善 |

## 8.2 シナリオ0: 学習モード

### 概要

学習モードは、インシデント対応の基本を段階的に学ぶチュートリアルです。

**判定は緩和されます**（全判定+2）。

### 設定

**会社:** LearnTech（架空のSaaS企業）/ タスク管理アプリ「TaskFlow」/ 朝のピーク時にエラー率上昇

| リソース | 初期値 |

| チーム集中力 | 8 |

**症状:** タスク保存エラー（成功率85%）/ レスポンスタイム3倍 / 一部ログイン不可

**チーム:** 田中エンジニア、佐藤SRE、山本オンコール

### 学習ポイント

## 8.3 シナリオ1: 初の大規模障害

### 概要

初めてのSEV1インシデント。決済システムが完全停止し、全顧客に影響。

### 設定

**会社:** PayQuick（決済プラットフォーム）/ 決済処理が完全停止

| リソース | 初期値 |
|---------|--------|
| サービス健全性 | 2（深刻） |
| エラーバジェット | 95%（加速消費中） |
| チーム集中力 | 7 |
| ステークホルダー信頼 | 6 |

**症状:** 決済API 500エラー / 全マーチャントから問い合わせ殺到 / SNSトレンド入り

**背景:** 昨夜DBマイグレーション実施 / 1週間前に新機能リリース / トラフィック20%増

**勝利条件:** 健全性8以上 / エラーバジェット50%以上 / 信頼4以上

### 特殊ルール

- 3ターン以内に緩和策を講じないとエラーバジェットが毎ターン-20%
- メディアからの問い合わせイベントが発生しやすい

## 8.4 シナリオ2: カスケード障害

### 概要

一つのサービス障害が連鎖し、複数システムに波及。混乱の中で全体を把握し、優先順位を付けて対応する。

### 設定

**会社:** MegaCloud（マイクロサービス）/ 認証サービス障害が全サービスに波及

| リソース | 初期値 |
|---------|--------|
| サービス健全性 | 3 |
| エラーバジェット | 70% |
| チーム集中力 | 6（深夜対応） |
| ステークホルダー信頼 | 5 |

**影響サービス:** Auth（発生源）→ User → Payment → Notification（全依存）

**勝利条件:** 全サービス健全性7以上 / カスケードパターン特定 / サーキットブレーカー1つ以上導入

### 特殊ルール

- 毎ターン、未対応のサービスから隣接サービスへ障害が伝播
- サーキットブレーカーを発動すると伝播を止められるが、その機能は一時停止

## 8.5 シナリオ3: ポストモーテム改革

### 概要

繰り返されるインシデント。根本原因は技術ではなく文化。ブレームレスな振り返りの文化を築く。

### 設定

**会社:** LegacyTech（老舗SIer）/ 同じタイプのインシデントが3ヶ月連続発生

| リソース | 初期値 |
|---------|--------|
| サービス健全性 | 5 |
| エラーバジェット | 30%（危険水域） |
| チーム集中力 | 4（疲弊） |
| ステークホルダー信頼 | 3（不信感） |

**背景:** 過去3回すべて「担当者のミス」で結論 / ポストモーテムが反省文の場 / 問題報告が減少 / 経営層不満

**真の課題:** テストなしパイプライン / ランブック未更新 / 不公平なオンコール / 心理的安全性の低さ

**勝利条件:** インシデント解決 / ブレームレスポストモーテム実施 / 3つ以上のシステム改善 / 集中力6以上

### 特殊ルール

- NPCは最初、ポストモーテムに懐疑的（「また反省文か」）
- ブレームレスな進行を示すと、隠れていた情報が出てくる
- 個人を責めると、NPCの関係値が下がり、情報が得にくくなる

## 8.6 シナリオ4: カスタム

### あなた自身のインシデント

実際に経験した（または経験しそうな）インシデントをシミュレーションします。

### 設定ワークシート

GMに以下を伝えてカスタムシナリオを開始:
- **基本情報:** 会社/サービス名、インシデント種類、想定重大度
- **初期状態:** 健全性/エラーバジェット/集中力/信頼（各0-10）
- **症状:** 3つ程度
- **リソース:** チーム、ツール、ランブック有無
- **勝利条件・学習目標**

# 第9章: 勝敗と評価

## 9.1 勝利条件

各シナリオの勝利条件を満たすと勝利です。一般的な勝利条件：

- サービス健全性を目標値以上に回復
- エラーバジェットを閾値以上で維持
- 制限ターン内に解決

## 9.2 敗北条件

以下のいずれかで敗北：

| 条件 | 説明 |
|------|------|
| エラーバジェット0% | SLO違反、顧客への契約違反 |
| チーム集中力0 | チームが機能停止、燃え尽き |
| ステークホルダー信頼0 | 経営層の介入、担当交代 |
| 制限ターン超過 | 長期化による影響拡大 |

## 9.3 評価基準

ゲーム終了時の評価：

| 項目 | 配点 | 評価基準 |
|------|:----:|----------|
| **解決速度** | 30 | ターン数が少ないほど高得点 |
| **影響最小化** | 25 | エラーバジェット残量、影響範囲 |
| **コミュニケーション** | 20 | ステークホルダー信頼、報告の適切さ |
| **チーム健全性** | 15 | チーム集中力の維持 |
| **学習** | 10 | ポストモーテムの質 |

# 第10章: 実績とチャレンジ

## 10.1 実績

| 実績 | 条件 | 報酬 |
|------|------|------|
| **First Responder** | シナリオ0をクリア | 称号獲得 |
| **Crisis Manager** | シナリオ1をエラーバジェット70%以上でクリア | 次回初期信頼+1 |
| **Chain Breaker** | シナリオ2でカスケードを完全に止める | サーキットブレーカー判定+1 |
| **Culture Changer** | シナリオ3で全NPC関係値+2以上 | ポストモーテム判定+2 |
| **Speed Demon** | 任意のシナリオを最短ターンでクリア | 次回MTTD判定+1 |
| **Zero Blame** | ポストモーテムで一度も個人を責めない | NPC関係値が下がらない |
| **Night Owl** | 深夜対応ペナルティがあっても勝利 | 深夜ペナルティ軽減 |

## 10.2 チャレンジモード

| モード | 制約 | 報酬 |
|--------|------|------|
| **Ironman** | セーブなし、判定振り直しなし | 実績「Iron Will」 |
| **Silent** | 1ターンに1回しかコミュニケーションできない | 実績「Focused」 |
| **Solo** | NPCの特殊能力を使えない | 実績「Self-Reliant」 |
| **Chaos** | 毎ターン2回イベントが発生 | 実績「Chaos Surfer」 |

# 第11章: GMガイド

**緊迫感の演出:** タイマー使用（30秒判断）/ 問い合わせ数を増やす / 予告なし経営層割り込み / ただし学習目的を忘れずに

**失敗からの学び:** 何が起こったか→別の選択肢は→現実なら→次はどうする（※ プレイヤーを責めない = ブレームレスの実践）

| 難易度調整 | 方法 |
|-----------|------|
| 難しく | イベント頻度増、初期状態悪化 |
| 簡単に | 判定ボーナス、ヒント増 |

# 第12章: 付録

## 12.1 用語集

| 用語 | 定義 |
|------|------|
| **SLO** | Service Level Objective。サービスの目標品質レベル |
| **SLI** | Service Level Indicator。SLOを測定する指標 |
| **MTTD** | Mean Time To Detect。検知までの平均時間 |
| **MTTR** | Mean Time To Recover。復旧までの平均時間 |
| **エラーバジェット** | 許容される障害時間/エラー率の予算 |
| **ポストモーテム** | インシデント後の振り返り会議 |
| **ランブック** | 標準的な対応手順書 |
| **オンコール** | 障害時に呼び出される待機体制 |
| **サーキットブレーカー** | 障害の連鎖を止めるパターン |
| **カスケード障害** | 一つの障害が他に波及する連鎖的障害 |
