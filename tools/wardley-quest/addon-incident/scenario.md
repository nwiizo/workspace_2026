# Incident Management Quest

## 本番障害との戦い

**Strategic Evolution Quest アドオン**

```
『アラートが鳴り響く。Slackが爆発する。電話が鳴り止まない。』

午前3時、あなたの携帯が震えた。
「本番環境でエラー率が急上昇しています」

ダッシュボードを開くと、赤い警告が画面を埋め尽くしている。
カスタマーサポートには問い合わせが殺到し始めた。

あなたはインシデントコマンダーとして呼び出された。
混乱の中で冷静に判断し、チームを導き、サービスを復旧させなければならない。

そして最も重要なこと—同じことを二度と起こさないために、
何を学ぶのか。
```

# 第1章: インシデント対応の基本

## 1.1 インシデントとは何か

```
┌─────────────────────────────────────────────────────────────┐
│                    インシデントの定義                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  インシデントとは:                                          │
│                                                             │
│  • サービスの品質低下または停止                             │
│  • 顧客体験への悪影響                                       │
│  • SLO違反またはエラーバジェット消費                        │
│  • 通常運用では対処できない状況                             │
│                                                             │
│  インシデントではないもの:                                  │
│                                                             │
│  • 通常のバグ修正                                           │
│  • 計画されたメンテナンス                                   │
│  • パフォーマンス改善タスク                                 │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 1.2 重大度（Severity）レベル

| レベル | 名称 | 定義 | 対応 |
|:------:|------|------|------|
| **SEV1** | Critical | サービス全停止、重大なデータ損失リスク | 即時対応、全員招集、経営報告 |
| **SEV2** | Major | 主要機能の停止、多数ユーザーに影響 | 即時対応、オンコール招集、顧客通知 |
| **SEV3** | Minor | 一部機能の低下、限定的な影響 | 営業時間内対応、チケット管理 |
| **SEV4** | Low | 軽微な問題、回避策あり | 通常の優先度でキュー処理 |

### 重大度判定のガイドライン

```
┌─────────────────────────────────────────────────────────────┐
│                  重大度判定フローチャート                     │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. サービスは完全に停止しているか？                        │
│     ├─ Yes → SEV1                                          │
│     └─ No → 2へ                                            │
│                                                             │
│  2. 主要な収益機能に影響があるか？                          │
│     ├─ Yes → SEV2                                          │
│     └─ No → 3へ                                            │
│                                                             │
│  3. 顧客から問い合わせが来ているか？                        │
│     ├─ Yes → SEV2 または SEV3（影響範囲で判断）            │
│     └─ No → 4へ                                            │
│                                                             │
│  4. 放置すると悪化する可能性があるか？                      │
│     ├─ Yes → SEV3                                          │
│     └─ No → SEV4                                           │
│                                                             │
│  ※ 迷ったら重大度を上げる（過小評価より過大評価が安全）    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 1.3 インシデント対応の役割

### インシデントコマンダー（IC）

```
┌─────────────────────────────────────────────────────────────┐
│               インシデントコマンダーの責任                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  【主な責任】                                               │
│  • 全体の指揮と調整                                         │
│  • 重大度の判断と更新                                       │
│  • リソースの割り当て                                       │
│  • ステークホルダーへの報告                                 │
│  • エスカレーションの判断                                   │
│                                                             │
│  【やらないこと】                                           │
│  • 直接のデバッグ作業（調査担当に任せる）                   │
│  • 顧客対応（コミュニケーション担当に任せる）               │
│  • 詳細な技術判断（技術リードに任せる）                     │
│                                                             │
│  ※ ICは「オーケストラの指揮者」であり、楽器は演奏しない    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### その他の役割

| 役割 | 責任 | スキル |
|------|------|--------|
| **技術リード** | 技術的な調査と判断、復旧作業の実施 | 深いシステム知識 |
| **コミュニケーション担当** | 顧客・社内への状況報告 | 明確な文章力 |
| **書記** | タイムラインの記録、決定事項の文書化 | 正確な記録力 |
| **オブザーバー** | 学習のための観察（主にポストモーテム用） | 客観的な視点 |

# 第2章: ゲームの概要

## 2.1 あなたの役割

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  あなたは「インシデントコマンダー」です。                    │
│                                                             │
│  ミッション:                                                │
│  ・インシデントを検知し、重大度を判断する                   │
│  ・適切なチームメンバーを招集し、役割を割り当てる           │
│  ・混乱の中で冷静に判断を下し、サービスを復旧させる         │
│  ・ステークホルダーに適切なタイミングで報告する             │
│  ・インシデントから学び、再発を防止する                     │
│                                                             │
│  制約:                                                      │
│  ・情報は常に不完全で、後から判明することもある             │
│  ・チームメンバーの時間と集中力は有限                       │
│  ・顧客と経営層は即座の回答を求める                         │
│  ・あなた自身も疲労する                                     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 2.2 リソース

| リソース | 説明 | 初期値 |
|---------|------|:------:|
| **サービス健全性** | サービスの稼働状態（0-10） | シナリオ依存 |
| **エラーバジェット** | 許容される障害時間の残り（%） | シナリオ依存 |
| **チーム集中力** | チームが効果的に働ける度合い（0-10） | 8 |
| **ステークホルダー信頼** | 経営層・顧客からの信頼（0-10） | 5 |

## 2.3 インシデントメトリクス

| メトリクス | 説明 | 目標 |
|-----------|------|------|
| **MTTD** | 検知までの時間（Mean Time To Detect） | 短いほど良い |
| **MTTR** | 復旧までの時間（Mean Time To Recover） | 短いほど良い |
| **影響範囲** | 影響を受けたユーザー数 | 小さいほど良い |
| **再発率** | 同じ原因のインシデント再発 | 0が理想 |

```
│  └── ステークホルダーへの第一報                            │

│  ├── 影響範囲の特定                                        │
│  ├── 根本原因の調査                                        │
│  ├── 緩和策の実施                                          │
│  └── 定期的な状況報告                                      │
│                                                             │
│  Phase 3: 復旧と確認（1-2ターン）                           │
│  ├── 完全復旧の確認                                        │
│  ├── モニタリング強化                                      │
│  ├── インシデントクローズ宣言                              │
│  └── 関係者への完了報告                                    │
│                                                             │
│  Phase 4: 振り返り（1ターン）                               │
│  ├── ポストモーテムの実施                                  │
│  ├── アクションアイテムの特定                              │
│  └── 学びの共有                                            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 3.2 ターン構造

各ターンは約30分〜1時間のインシデント対応時間を表します。

```
┌─────────────────────────────────────────────────────────────┐
│                      1ターンの流れ                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 状況確認フェーズ                                        │
│     ├── 現在のサービス状態を確認                           │
│     ├── 新しいアラートや情報の確認                         │
│     └── イベントカード（予期せぬ事態）の確認               │
│                                                             │
│  2. 判断フェーズ                                            │
│     ├── 次のアクションを決定                               │
│     ├── リソース（人員）の割り当て                         │
│     └── コミュニケーションの優先度を決定                   │
│                                                             │
│  3. 実行フェーズ                                            │
│     ├── アクションの実行                                   │
│     ├── 判定（2D6 + 修正値）                               │
│     └── 結果の適用                                         │
│                                                             │
│  4. 更新フェーズ                                            │
│     ├── メトリクスの更新                                   │
│     ├── タイムラインの記録                                 │
│     └── 次のターンへの引き継ぎ                             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 3.3 判定ルール

### 基本判定

```
2D6 + 修正値 ≥ 目標値 → 成功

目標値の目安:
• 簡単なタスク: 5
• 標準的なタスク: 7
• 困難なタスク: 9
• 非常に困難なタスク: 11
```

### 判定結果

| 出目 | 結果 | 効果 |
|:----:|------|------|
| 2 | 致命的失敗 | 状況悪化、新たな問題発生 |
| 3-4 | 失敗 | 進展なし、時間を消費 |
| 5-6 | 部分的失敗 | わずかな進展、副作用あり |
| 7-8 | 部分的成功 | 目標に近づく、完全ではない |
| 9-10 | 成功 | 想定通りの結果 |
| 11 | 大成功 | 追加の発見、効率的な解決 |
| 12 | 完全成功 | 最高の結果、学びも得る |

### 修正値

#### 状況による修正

| 状況 | 修正 | 理由 |
|------|:----:|------|
| ランブックが存在する | +2 | 手順が明確 |
| 最近の類似インシデント経験 | +1 | パターン認識 |
| 十分なオブザーバビリティ | +1 | 情報が豊富 |
| チーム集中力が7以上 | +1 | 効果的に働ける |
| チーム集中力が3以下 | -2 | 疲労によるミス |
| 情報が不完全 | -1 | 推測に頼る |
| 複数システムが関与 | -1 | 複雑性増大 |
| 深夜対応 | -1 | 認知能力低下 |

#### コミュニケーションによる修正

| 状況 | 修正 | 理由 |
|------|:----:|------|
| 定期的な状況報告を実施 | +1 | 信頼の維持 |
| ステークホルダー信頼が7以上 | +1 | 協力を得やすい |
| ステークホルダー信頼が3以下 | -1 | 疑念と干渉 |
| 顧客への適切な通知 | +1 | 混乱を防止 |

# 第5章: イベントカード

## 5.1 インシデント中のイベント

毎ターン開始時にD6を振り、イベントが発生します。

| D6 | イベント | 効果 |
|:--:|----------|------|
| 1 | **新たな症状発見** | 影響範囲が想定より広いことが判明（サービス健全性-1） |
| 2 | **顧客からの緊急連絡** | VIP顧客から直接連絡、即座の説明が必要 |
| 3 | **関連システムの問題** | 別のシステムでも問題が検出される |
| 4 | **有用な情報の発見** | チームメンバーが重要な手がかりを発見（次の判定+2） |
| 5 | **リソースの到着** | 追加の専門家が参加可能に |
| 6 | **自然回復の兆候** | 一部の問題が自然に緩和（サービス健全性+1） |

## 5.2 コミュニケーションイベント

ステークホルダー信頼が低い場合（4以下）、追加でD6を振ります。

| D6 | イベント | 効果 |
|:--:|----------|------|
| 1-2 | **経営層の介入** | 詳細な報告を要求、チーム集中力-1 |
| 3-4 | **SNSでの言及** | 顧客がSNSで問題を報告、対応の圧力 |
| 5-6 | **プレスからの問い合わせ** | メディア対応が必要になる可能性 |

# 第6章: ポストモーテム

## 6.1 ブレームレスポストモーテムとは

```
┌─────────────────────────────────────────────────────────────┐
│              ブレームレスポストモーテムの原則                 │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  【目的】                                                   │
│  • 同じインシデントを二度と起こさないこと                   │
│  • 組織として学習し、改善すること                           │
│  • 関係者全員が安心して情報を共有できること                 │
│                                                             │
│  【やること】                                               │
│  • 事実を時系列で整理する                                   │
│  • 「何が」起こったかを明らかにする                         │
│  • システム的な改善点を特定する                             │
│  • 具体的なアクションアイテムを決める                       │
│                                                             │
│  【やらないこと】                                           │
│  • 「誰が」悪いかを探す                                     │
│  • 個人を責める                                             │
│  • 反省文を書かせる                                         │
│  • 罰則を与える                                             │
│                                                             │
│  「人はミスをする。システムがミスを許容しないのが問題。」   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 6.2 ポストモーテムの構造

### 基本セクション

| セクション | 内容 |
|-----------|------|
| **サマリー** | 何が起こったかの1-2文の要約 |
| **影響** | 影響を受けたユーザー数、時間、ビジネス影響 |
| **タイムライン** | 検知から解決までの時系列 |
| **根本原因** | 問題の本質的な原因（複数可） |
| **貢献因子** | 問題を悪化させた要因 |
| **うまくいったこと** | 被害を最小化した対応 |
| **改善点** | 次回より良くできること |
| **アクションアイテム** | 具体的な改善タスクと担当者 |

### 5 Whys 分析

```
問題: デプロイ後にサービスがダウンした

Why 1: なぜダウンしたか？
  → データベース接続がタイムアウトした

Why 2: なぜタイムアウトしたか？
  → 接続プールが枯渇した

Why 3: なぜ接続プールが枯渇したか？
  → 新機能が接続を解放していなかった

Why 4: なぜ接続リークがあったか？
  → コードレビューで見逃された

Why 5: なぜ見逃されたか？
  → 接続管理のチェックリストがなかった

→ アクション: コードレビューチェックリストに
  「接続の確実な解放」を追加
```

## 6.3 ゲーム内でのポストモーテム

インシデント解決後、以下の質問に答えてポストモーテムを完成させます。

| 質問 | 回答のポイント |
|------|---------------|
| 検知は十分速かったか？ | MTTDの評価、アラート改善の余地 |
| 初動は適切だったか？ | 重大度判定、チーム招集のタイミング |
| 情報は十分だったか？ | オブザーバビリティ、ログの質 |
| コミュニケーションは効果的だったか？ | ステークホルダーへの報告タイミング |
| 復旧は効率的だったか？ | ランブックの有無、手順の改善点 |
| 何を変えるべきか？ | システム、プロセス、文化の改善 |

# 第11章: GMガイド

## 11.1 セッション運営のコツ

### 緊迫感の演出

```
【効果的な演出】
• タイマーを使う（実時間で30秒以内に判断を求める）
• Slackの通知音を再現する
• 「顧客からの問い合わせが10件、20件、30件...」と数を増やす
• 「CEOから電話です」と予告なく割り込む

【やりすぎに注意】
• プレイヤーが本当にパニックにならないよう調整
• 学習目的を忘れない
• 適度に休憩を入れる
```

### 失敗からの学びを促す

```
失敗した場合の対応:

1. 「何が起こったか」を客観的に振り返る
2. 「別の選択肢は何だったか」を考える
3. 「現実の組織で同じことが起きたら？」と問いかける
4. 「次はどうする？」と前向きに締める

※ プレイヤーを責めない（これ自体がブレームレスの実践）
```

## 11.2 難易度調整

| 教育的にする | 各判定後にフレームワークの解説を加える |

# 第12章: 付録

## 12.1 用語集

| 用語 | 定義 |
|------|------|
| **SLO** | Service Level Objective。サービスの目標品質レベル |
| **SLI** | Service Level Indicator。SLOを測定する指標 |
| **MTTD** | Mean Time To Detect。検知までの平均時間 |
| **MTTR** | Mean Time To Recover。復旧までの平均時間 |
| **エラーバジェット** | 許容される障害時間/エラー率の予算 |
| **ポストモーテム** | インシデント後の振り返り会議 |
| **ランブック** | 標準的な対応手順書 |
| **オンコール** | 障害時に呼び出される待機体制 |
| **サーキットブレーカー** | 障害の連鎖を止めるパターン |
| **カスケード障害** | 一つの障害が他に波及する連鎖的障害 |

## 12.2 参考リソース

| リソース | 内容 |
|----------|------|
| Google SRE Book | SREの原則とプラクティス |

## 12.3 クイックリファレンス

### 判定早見表

```
2D6 + 修正値

2    = 致命的失敗（状況悪化）
3-4  = 失敗（進展なし）
5-6  = 部分的失敗（微小な進展）
7-8  = 部分的成功（目標に近づく）
9-10 = 成功（想定通り）
11   = 大成功（ボーナス効果）
12   = 完全成功（最高の結果）
```

### 重大度早見表

```
SEV1: 全停止 → 全員招集、経営報告
SEV2: 主要機能停止 → オンコール招集、顧客通知
SEV3: 一部低下 → 営業時間対応
SEV4: 軽微 → 通常キュー
```
