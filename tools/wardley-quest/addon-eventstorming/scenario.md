# 第1章: ゲーム概要

## 1.1 このゲームについて

**EventStorming Quest** は、Strategic Evolution Questの拡張として、**ドメイン発見のためのワークショップ手法を学ぶ**戦略シミュレーションRPGです。

Alberto Brandoliniが考案したEventStormingは、複雑なビジネスドメインを短時間で可視化し、境界づけられたコンテキストを発見するための強力な手法です。

### 核心的な問い

> **「どうすれば、技術者とビジネス関係者が同じ言語でドメインを理解し、適切な境界を見つけられるのか？」**

### EventStormingの3つのレベル

| レベル | 目的 | 参加者 | 所要時間 |
|---|---|---|---|
| **Big Picture** | ビジネス全体の流れを把握 | 全ステークホルダー | 半日〜1日 |
| **Process Level** | 特定プロセスの詳細化 | ドメイン関係者 | 2-4時間 |
| **Design Level** | 実装詳細の設計 | 開発チーム | 1-2時間 |

### DDDとの関係

**EventStorming（発見の手法）→ DDD（設計の実装）**

- Big Picture → 境界づけられたコンテキストの発見
- Process Level → ドメインイベントの詳細化
- Design Level → 集約・コマンド・ポリシーの設計

DDDの主要概念（境界づけられたコンテキスト、集約、ドメインイベント、ユビキタス言語）への入力となる。

### プレイ形式

| 項目 | 内容 |
|---|---|
| プレイヤー | 1名（ファシリテーター/アーキテクト） |
| GM | Claude（シナリオ・判定・ワークショップイベント） |
| 所要時間 | 60〜120分 |
| 前提 | Strategic Evolution Questの基礎知識（推奨） |

### コンパクトモード

| コマンド | 効果 |
|----------|------|
| 「コンパクトモード」 | 出力を1行要約+選択肢+状態のみに圧縮 |
| 「通常モード」 | 標準出力に戻す |
| 「状態確認」 | 現在のスコアのみ表示 |
| 「サマリー」 | これまでの決定を箇条書きで要約 |

## 1.2 EventStormingの本質

### Alberto Brandoliniの洞察

EventStormingは単なるモデリング手法ではなく、**組織学習のプロセス**です：

| 従来のアプローチ | EventStormingアプローチ |
|---|---|
| ドキュメントを読む | 付箋で議論する |
| 専門家にインタビュー | 全員が同じ場に集まる |
| 正解を求める | 矛盾を発見する |
| 完璧なモデルを目指す | 学びを最大化する |
| 技術者が主導 | ビジネス関係者が主役 |

### ドメインイベントが中心

> **「ドメインイベントは、ビジネスの専門家が気にかけること」**

**ドメインイベントの特徴**: 過去形で表現される（「注文が確定された」）/ ビジネス的に意味がある出来事 / 時系列で並べられる / 他のイベントを引き起こす可能性がある / システムの状態を変化させる

# 第2章: ゲームルール

## 2.1 セッション構造

**Phase 1: ワークショップ準備** → 参加者選定、スコープ定義、環境準備、ゴール設定

**Phase 2: ワークショップ実施（ターン制）** 各ターン:
1. ワークショップイベント（D6 x 2）→ 参加者の反応、議論の展開
2. 状況分析（参加者 / ドメイン / プロセスの3視点）
3. アクション宣言（最大3つ）→ ファシリテーション介入方法を選択
4. 判定（2D6 + 修正値）→ 成否を評価
5. 結果適用 → 発見スコア・エンゲージメント・明確度の更新

**Phase 3: 成果の統合と振り返り** → コンテキスト整理、ホットスポット優先順位、次のステップ計画

---

## 2.2 判定システム

基本判定はメインscenario参照（2D6、出目2=致命的失敗〜12=完全成功）。

### EventStorming固有の修正値

| 状況 | 修正 |
|---|:---:|
| 適切な質問で議論を導く | +2 |
| ドメインエキスパートが積極的 | +2 |
| 開発者とビジネス側が協力 | +2 |
| サイレントブレインストーミング実施 | +1 |
| タイムボックスを守る | +1 |
| 全員が付箋を書いている | +1 |
| スコープが明確に定義 | +1 |
| 特定の人が議論を支配 | -2 |
| 対立が解消されない | -2 |
| 参加者が途中退出 | -2 |
| レガシーシステムが複雑 | -2 |
| 政治的な緊張がある | -2 |
| 重要なステークホルダーが不在 | -3 |

## 2.3 ワークショップイベント

毎ターン開始時にD6を2回振り、2つのイベントが発生します。

### ワークショップイベント表

| D6 | イベント | 効果 | 対応のヒント |
|:---:|---|---|---|
| 1 | **沈黙の壁** | 参加者が発言しない。エンゲージメント-1。 | 直接質問、小グループ分割 |
| 2 | **用語の混乱** | 同じ言葉が異なる意味で使われていることが発覚。 | ユビキタス言語の明確化 |
| 3 | **隠れたプロセス発見** | 誰も言及していなかった重要なプロセスが出現。 | 深掘りの機会 |
| 4 | **対立する見解** | 2人以上の参加者が異なる理解を主張。 | 両方を可視化、検証 |
| 5 | **時間のプレッシャー** | 予定時間の半分が経過。スコープ再検討が必要。 | 優先順位付け |
| 6 | **外部システムの影響** | 重要な外部システム依存が発見される。 | 統合ポイントの明確化 |

### 常時適用パターン

| パターン | 効果 |
|---|---|
| **最初の30分は混乱** | 序盤は発見スコアが上がりにくい |
| **専門家は無意識に省略する** | 「当たり前」の部分が抜け落ちやすい |
| **視覚化が理解を加速** | ボード上の整理で発見が促進される |
| **休憩が創造性を回復** | 長時間継続は効率が低下 |
| **ホットスポットは宝** | 矛盾や疑問点こそ最大の発見 |

# 第3章: Big Picture EventStorming

## 3.1 概要

Big Picture EventStormingは、**ビジネス全体の流れを数時間で可視化する**手法です。

### このフレームワークで答える問い

- 「ビジネスで何が起きているのか？」
- 「どこに境界があるのか？」
- 「何が問題になりそうか？」
- 「誰が何を知っているのか？」

---

## 3.2 準備

### 参加者の選定

| 役割 | 人数目安 | 必須度 |
|---|:---:|:---:|
| ドメインエキスパート | 3-5名 | 必須 |
| 開発者 | 2-4名 | 必須 |
| プロダクトオーナー | 1名 | 必須 |
| UXデザイナー | 1名 | 推奨 |
| 運用担当 | 1名 | 推奨 |
| 経営層 | 1名 | 任意 |

### 環境の準備

**物理**: 長い壁面（6m以上）、付箋（色別500枚以上）、太いマーカー、タイマー、軽食

**リモート**: Miro/Mural/FigJam、ビデオ会議（カメラON）、テンプレート事前準備、ブレイクアウトルーム

---

## 3.3 進行の流れ

### Phase 1: Chaotic Exploration（30分）

指示: 「ビジネスで起きていることを、過去形のイベントで書いてください」
- ルール: 議論禁止・各自で書く / 過去形 / 1枚1イベント / 順番不問 / 重複OK
- ファシリテーター: 沈黙を促す / 質問に答えない（「それも書いてください」）/ 手が止まった人に声かけ

### Phase 2: Enforce the Timeline（30分）

指示: 「イベントを時系列に並べてください」
- ルール: 左→右で時間の流れ / 重複は縦に / 並行は上下 / 議論が始まったらホットスポット（赤付箋）
- 発見: 抜けているステップ / 用語の不一致 / 異なる理解

### Phase 3: People and Systems（30分）

指示: 「誰が/何がこのイベントを引き起こすか」
- 追加要素: アクター（黄小） / 外部システム（ピンク） / コマンド（青、オプション）
- 発見: 責任の所在 / 外部依存 / 自動化部分

### Phase 4: Explicit Walkthrough（30分）

指示: 「最初から最後まで、ストーリーとして読み上げる」
- 進め方: 1人がナレーター / 順番に読み上げ / 違和感で停止 / 修正・追加
- 発見: 論理的矛盾 / 抜けステップ / 例外ケース

### Phase 5: Identify Boundaries（30分）

指示: 「境界線を引く」
- 手がかり: 用語が変わる場所 / 担当者が変わる場所 / 時間的ギャップ / ピボタルイベント
- 議論: なぜここに境界があるか / 境界を越える情報 / チーム構成との一致

---

## 3.4 ホットスポットの活用

### ホットスポットとは

**ホットスポット = 赤い付箋**。貼る場面: 意見対立 / 「分からない」/ 「後で確認」/ 重要な疑問 / リスク

重要: ホットスポットは問題ではなく「発見」。その場で解決しようとせず、後で優先順位をつける。

### ホットスポットの分類

| 種類 | 説明 | 対応 |
|---|---|---|
| **知識の欠如** | 誰も答えを知らない | 調査タスク |
| **意見の相違** | 異なる理解がある | 検証・議論 |
| **プロセスの曖昧さ** | 何が正しいか不明 | 業務分析 |
| **技術的負債** | 既知の問題 | 改善計画 |
| **政治的課題** | 組織的な障壁 | 経営への報告 |

---

## 3.5 判定への影響

| 状況 | 判定修正 |
|---|:---:|
| Chaotic Explorationを十分に実施 | +2 |
| 全員がウォークスルーに参加 | +1 |
| ホットスポットを適切に記録 | +1 |
| ウォークスルーを省略 | -2 |
| 特定の人だけが境界を決定 | -2 |
| ホットスポットを無視 | -1 |

# 第4章: Process Level EventStorming

## 4.1 概要

Process Level EventStormingは、**特定のビジネスプロセスを詳細に分析する**手法です。

### Big Pictureとの違い

| 観点 | Big Picture | Process Level |
|---|---|---|
| **スコープ** | ビジネス全体 | 特定プロセス |
| **深さ** | 広く浅く | 狭く深く |
| **参加者** | 多様なステークホルダー | プロセス関係者 |
| **成果物** | コンテキスト境界 | 詳細なフロー |
| **所要時間** | 半日〜1日 | 2-4時間 |

---

## 4.2 追加要素

### コマンドの詳細化

**コマンド（青付箋）**: 命令形で書く（「注文を確定する」）/ イベントの直前に配置 / アクターを明示

フロー: アクター(黄小) → コマンド(青) → イベント(オレンジ)

### ポリシーの発見

**ポリシー（紫付箋）**: 「〜したら〜する」ルール / イベントに反応して別のコマンドを発行 / 自動・手動いずれもあり

フロー: イベント(オレンジ) → ポリシー(紫) → コマンド(青) → イベント(オレンジ)

例: 「注文が確定された」→「在庫を引き当てる」（自動処理ポリシー）

### リードモデルの特定

**リードモデル（緑付箋）**: 意思決定に必要な情報 / コマンド発行前に参照 / UIの画面に相当することが多い

フロー: リードモデル(緑) → アクター(黄小) → コマンド(青)

例: 「注文一覧画面」を見て「注文を承認する」

---

## 4.3 進行の流れ

| ステップ | 時間 | 内容 |
|---|:---:|---|
| 1: スコープ明確化 | 10分 | コンテキスト選択、開始/終了イベント定義、役割確認 |
| 2: ハッピーパス詳細化 | 45分 | 一般的フロー描画、コマンド・ポリシー・リードモデル追加 |
| 3: 例外パス探索 | 30分 | 「もし〜だったら」で例外洗い出し、ポリシー特定 |
| 4: 集約の特定 | 30分 | コマンド受取責任者（集約）特定、整合性・トランザクション境界 |

---

## 4.4 集約の発見パターン

### 集約とは

**集約（黄色大付箋）**: コマンドを受け取り、イベントを発行する整合性の境界。1トランザクションで変更される。

フロー: コマンド(青) → 集約(黄大) → イベント(オレンジ)

### 集約の手がかり

| 手がかり | 説明 |
|---|---|
| **名詞の重要性** | 頻繁に言及される名詞 |
| **整合性要求** | 「同時に変わるべき」もの |
| **ライフサイクル** | 作成から削除まで一貫して管理 |
| **識別子** | IDで特定される概念 |

---

# 第5章: Design Level EventStorming

## 5.1 概要

Design Level EventStormingは、**実装に直結する詳細設計**を行う手法です。

### 目的

- 集約の内部構造の設計
- コマンドハンドラーの特定
- イベントスキーマの定義
- APIの設計

---

## 5.2 詳細化の要素

### コマンドの詳細

```yaml
command:
  name: "PlaceOrder"
  actor: "Customer"
  aggregate: "Order"
  parameters:
    - customerId: UUID
    - items: List<OrderItem>
    - shippingAddress: Address
  preconditions:
    - "Customer must be authenticated"
    - "Items must be in stock"
  produces:
    - "OrderPlaced"
```

### イベントの詳細

```yaml
event:
  name: "OrderPlaced"
  aggregate: "Order"
  attributes:
    - orderId: UUID
    - customerId: UUID
    - items: List<OrderItem>
    - totalAmount: Money
    - placedAt: DateTime
  triggers:
    - policy: "ReserveInventory"
    - policy: "SendOrderConfirmation"
```

### ポリシーの詳細

```yaml
policy:
  name: "ReserveInventory"
  triggers_on: "OrderPlaced"
  issues_command: "ReserveStock"
  target_aggregate: "Inventory"
  conditions:
    - "Order total > 0"
  notes: "Async, eventually consistent"
```

---

## 5.3 設計の検証

### コマンドの検証ポイント

| ポイント | 確認事項 |
|---|---|
| **命名** | ビジネス用語を使用しているか |
| **責任** | 1つの集約に対するコマンドか |
| **パラメータ** | 必要十分な情報を含むか |
| **前提条件** | 明示的に定義されているか |

### イベントの検証ポイント

| ポイント | 確認事項 |
|---|---|
| **過去形** | 完了した事実を表しているか |
| **自己完結** | イベント単体で意味が通るか |
| **不変** | 後から変更されないか |
| **消費者** | 誰がこのイベントを必要とするか |

# 第7章: 勝敗と評価

## 7.1 終了条件

以下のいずれかで終了：

- 指定ターン数の完了
- 参加者エンゲージメントが0（敗北：ワークショップ崩壊）
- 全ての主要ゴールを達成（早期勝利）

## 7.2 評価基準

### 基本得点

| 条件 | ポイント |
|---|:---:|
| 生存（ターン完了） | +10 |
| 主要目標達成 | +10 |

### ボーナス

| 条件 | ポイント |
|---|:---:|
| 発見スコア20以上 | +10 |
| 参加者全員が発言した | +5 |
| 境界が3つ以上特定された | +5 |
| ユビキタス言語が5つ以上定義された | +5 |
| ホットスポットが全て対処方針を持つ | +3 |
| 次のステップが明確 | +3 |

### ペナルティ

| 条件 | ポイント |
|---|:---:|
| 参加者が途中退出 | -5 |
| 重要なホットスポットが未解決 | -3 |
| 時間を30%以上超過 | -3 |
| コンテキスト明確度3以下 | -5 |

## 7.3 バッドエンディング

### 「ワークショップ崩壊」エンディング
**条件**: 参加者エンゲージメントが0になった
**学び**: ファシリテーションは場のエネルギー管理 / 目的とゴールの共有を最初に徹底 / 脱線したら早めに軌道修正

### 「言葉の迷宮」エンディング
**条件**: コンテキスト明確度が3以下で終了
**学び**: ユビキタス言語は合意がなければ意味がない / 定義は具体例とセットで確認 / 「分かったつもり」が最も危険

### 「境界なき混沌」エンディング
**条件**: ホットスポットが3つ以上未解決で終了
**学び**: 可視化は始まりでありゴールではない / ホットスポットには優先順位をつけて対処 / 境界を引く決断には勇気とオーナーシップが必要

### 「声なき沈黙」エンディング
**条件**: 参加者の50%以上が一度も発言せずに終了
**学び**: 沈黙にも意味がある / 心理的安全性はファシリテーターの責任 / 権力勾配が発言を抑制する

### 「実装との乖離」エンディング
**条件**: 発見スコア15以上かつ境界が1つも特定されていない
**学び**: Big PictureとDesign Levelの両方が必要 / 成果物を「次」に繋げる設計 / 開発チームを最初から巻き込む

### 7.4 決められていないバッドエンディング

| パターン | 発生条件（目安） | 結末の方向性 |
|---------|-----------------|-------------|
| 「付箋の山」 | イベント数50以上かつ整理度3以下 | 情報過多で全体像把握不可 |
| 「時間泥棒」 | 時間超過50%以上 | 参加者の信頼喪失 |
| 「技術者の独壇場」 | 技術者以外の発言率20%以下 | ビジネス視点が欠落 |
| 「完璧主義の罠」 | 同じ領域を3ターン以上議論 | 細部に拘り全体が見えない |

GMは組織固有の失敗パターンをカスタムバッドエンディングとして追加可能。

## 7.5 グッドエンディング

### 「全員が見えた瞬間」エンディング
**条件**: 参加者全員が発言、発見スコア20以上
**学び**: 安心して発言できる場を作る / 発見を促し正解を押し付けない / 可視化で暗黙知を形式知に変える

### 「言葉が生まれた日」エンディング
**条件**: ユビキタス言語5つ以上定義、コンテキスト明確度8以上
**学び**: 定義を曖昧にせず具体例で確認 / 文書化して全員がアクセス可能に / ユビキタス言語を日常的に使う文化

### 「境界が見えた瞬間」エンディング
**条件**: 境界3つ以上特定、全ホットスポット対処方針決定
**学び**: ビジネスの自然な境界を発見する / ホットスポットを曖昧にせず対処方針を決める / 組織構造にも境界の考え方を適用
