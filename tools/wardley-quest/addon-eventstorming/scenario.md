# 第1章: ゲーム概要

## 1.1 このゲームについて

**EventStorming Quest** は、Strategic Evolution Questの拡張として、**ドメイン発見のためのワークショップ手法を学ぶ**戦略シミュレーションRPGです。

Alberto Brandoliniが考案したEventStormingは、複雑なビジネスドメインを短時間で可視化し、境界づけられたコンテキストを発見するための強力な手法です。

### 核心的な問い

> **「どうすれば、技術者とビジネス関係者が同じ言語でドメインを理解し、適切な境界を見つけられるのか？」**

### EventStormingの3つのレベル

| レベル | 目的 | 参加者 | 所要時間 |
|---|---|---|---|
| **Big Picture** | ビジネス全体の流れを把握 | 全ステークホルダー | 半日〜1日 |
| **Process Level** | 特定プロセスの詳細化 | ドメイン関係者 | 2-4時間 |
| **Design Level** | 実装詳細の設計 | 開発チーム | 1-2時間 |

### DDDとの関係

```

│  │ Design Level → 集約・コマンド・ポリシーの設計           │   │
│  └─────────────────────────────────────────────────────────┘   │
│                           │                                     │
│                           ↓                                     │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ Domain-Driven Design（設計の実装）                      │   │
│  │ ├── 境界づけられたコンテキスト                         │   │
│  │ ├── 集約                                               │   │
│  │ ├── ドメインイベント                                   │   │
│  │ └── ユビキタス言語                                     │   │

│                                                                 │
```

## 1.2 EventStormingの本質

### Alberto Brandoliniの洞察

EventStormingは単なるモデリング手法ではなく、**組織学習のプロセス**です：

| 従来のアプローチ | EventStormingアプローチ |
|---|---|
| ドキュメントを読む | 付箋で議論する |
| 専門家にインタビュー | 全員が同じ場に集まる |
| 正解を求める | 矛盾を発見する |
| 完璧なモデルを目指す | 学びを最大化する |
| 技術者が主導 | ビジネス関係者が主役 |

### ドメインイベントが中心

> **「ドメインイベントは、ビジネスの専門家が気にかけること」**

```
┌─────────────────────────────────────────────────────────────┐
│  ドメインイベントの特徴                                      │
│                                                             │
│  ・過去形で表現される（「注文が確定された」）               │
│  ・ビジネス的に意味がある出来事                             │
│  ・時系列で並べられる                                       │
│  ・他のイベントを引き起こす可能性がある                     │
│  ・システムの状態を変化させる                               │
└─────────────────────────────────────────────────────────────┘
```

## 1.3 ゲームの厳しさについて

このゲームでは以下のことが起こります：

| 現象 | 説明 | 学び |
|---|---|---|
| **沈黙の参加者** | 発言しない人がいる | ファシリテーションの重要性 |
| **専門用語の衝突** | 同じ言葉が違う意味で使われる | ユビキタス言語の必要性 |
| **境界の曖昧さ** | どこで区切るか合意できない | コンテキストの本質 |
| **政治的抵抗** | 縄張り意識が議論を妨げる | 組織課題の表出 |
| **情報の偏り** | 特定の人だけが知識を持つ | 暗黙知の可視化 |
| **時間切れ** | 全てを議論しきれない | 優先順位の判断 |

**これらは現実のワークショップで直面する課題です。**

## 1.4 用語集

### EventStorming用語

| 用語 | 定義 | 付箋の色 |
|---|---|---|
| **ドメインイベント** | ビジネス上重要な出来事（過去形） | オレンジ |
| **コマンド** | イベントを引き起こすアクション | 青 |
| **アクター** | コマンドを実行する人 | 黄（小） |
| **集約** | コマンドを受け取りイベントを発行 | 黄（大） |
| **ポリシー** | イベントに反応するビジネスルール | 紫/ライラック |
| **外部システム** | 連携する外部サービス | ピンク |
| **リードモデル** | 意思決定に必要な情報 | 緑 |
| **ホットスポット** | 疑問点・課題・矛盾 | 赤/ピンク |
| **タイムライン** | イベントの時系列配置 | - |

### ファシリテーション用語

| 用語 | 定義 |
|---|---|
| **ムービングボード** | 付箋を動的に配置・移動するスペース |
| **サイレントブレインストーミング** | 議論前に各自が付箋を書く時間 |
| **ウォークスルー** | 時系列でイベントを確認する作業 |
| **スイムレーン** | アクター別・システム別の横軸分割 |
| **バウンダリー** | コンテキストの境界線 |

### ゲーム用語

| 用語 | 定義 |
|---|---|
| **ターン** | 1ワークショップセッション相当 |
| **発見スコア** | ドメイン理解の深さ（高いほど良い） |
| **参加者エンゲージメント** | 参加者の積極性 |
| **コンテキスト明確度** | 境界の明確さ |
| **ファシリテーション品質** | 進行の適切さ |

## 2.2 判定システム

### 基本判定（2D6）

| 出目 | 結果 | 効果 |
|:---:|---|---|
| 2 | **致命的失敗** | ワークショップ崩壊。参加者の信頼を失う。 |
| 3-4 | **失敗** | 議論が脱線。時間を浪費。発見スコア-1。 |
| 5-6 | **部分的失敗** | 一部のみ進展。ホットスポット増加。 |
| 7-8 | **部分的成功** | 基本的な発見あり。追加確認が必要。 |
| 9-10 | **成功** | 重要な発見。参加者の理解が深まる。 |
| 11 | **大成功** | 画期的な洞察。隠れた境界を発見。 |
| 12 | **完全成功** | 全員が同じ理解に到達。ユビキタス言語確立。 |

### 修正値

#### ファシリテーション関連

| 状況 | 修正 | 根拠 |
|---|:---:|---|
| 適切な質問で議論を導く | +2 | 本質への集中 |
| サイレントブレインストーミングを実施 | +1 | 全員の参加を促す |
| タイムボックスを守る | +1 | 規律ある進行 |
| 視覚的に整理（スイムレーンなど） | +1 | 理解の促進 |
| 特定の人が議論を支配 | -2 | 偏った情報 |
| 時間配分を失敗 | -1 | 不完全な探索 |
| 参加者が途中退出 | -2 | 情報の欠落 |

#### 参加者関連

| 状況 | 修正 | 根拠 |
|---|:---:|---|
| ドメインエキスパートが積極的 | +2 | 深い知識の共有 |
| 開発者とビジネス側が協力 | +2 | 多角的視点 |
| 全員が付箋を書いている | +1 | 広い参加 |
| 沈黙している参加者がいる | -1 | 情報の欠落 |
| 対立が解消されない | -2 | 進行の停滞 |
| 重要なステークホルダーが不在 | -3 | 致命的な盲点 |

#### ドメイン複雑性関連

| 状況 | 修正 | 根拠 |
|---|:---:|---|
| スコープが明確に定義 | +1 | 集中した議論 |
| 既存のドキュメントがある | +1 | 事前知識 |
| ドメインが単純明快 | +1 | 発見が容易 |
| 複数の部門が関与 | -1 | 調整コスト |
| レガシーシステムが複雑 | -2 | 暗黙知が多い |
| 政治的な緊張がある | -2 | 議論の歪み |

## 2.3 ワークショップイベント

毎ターン開始時にD6を2回振り、2つのイベントが発生します。

### ワークショップイベント表

| D6 | イベント | 効果 | 対応のヒント |
|:---:|---|---|---|
| 1 | **沈黙の壁** | 参加者が発言しない。エンゲージメント-1。 | 直接質問、小グループ分割 |
| 2 | **用語の混乱** | 同じ言葉が異なる意味で使われていることが発覚。 | ユビキタス言語の明確化 |
| 3 | **隠れたプロセス発見** | 誰も言及していなかった重要なプロセスが出現。 | 深掘りの機会 |
| 4 | **対立する見解** | 2人以上の参加者が異なる理解を主張。 | 両方を可視化、検証 |
| 5 | **時間のプレッシャー** | 予定時間の半分が経過。スコープ再検討が必要。 | 優先順位付け |
| 6 | **外部システムの影響** | 重要な外部システム依存が発見される。 | 統合ポイントの明確化 |

### 常時適用パターン

| パターン | 効果 |
|---|---|
| **最初の30分は混乱** | 序盤は発見スコアが上がりにくい |
| **専門家は無意識に省略する** | 「当たり前」の部分が抜け落ちやすい |
| **視覚化が理解を加速** | ボード上の整理で発見が促進される |
| **休憩が創造性を回復** | 長時間継続は効率が低下 |
| **ホットスポットは宝** | 矛盾や疑問点こそ最大の発見 |

# 第3章: Big Picture EventStorming

## 3.1 概要

Big Picture EventStormingは、**ビジネス全体の流れを数時間で可視化する**手法です。

### このフレームワークで答える問い

- 「ビジネスで何が起きているのか？」
- 「どこに境界があるのか？」
- 「何が問題になりそうか？」
- 「誰が何を知っているのか？」

## 3.3 進行の流れ

### Phase 1: Chaotic Exploration（30分）

```
┌─────────────────────────────────────────────────────────────┐
│  「ビジネスで起きていることを、過去形のイベントで書いてください」│
│                                                             │
│  ルール:                                                    │
│  ・議論禁止、各自で書く                                     │
│  ・過去形で書く（「注文が確定された」）                     │
│  ・1枚1イベント                                             │
│  ・順番は気にしない                                         │
│  ・重複OK                                                    │
│                                                             │
│  ファシリテーターの役割:                                    │
│  ・沈黙を促す                                               │
│  ・質問に答えない（「それも書いてください」）               │
│  ・手が止まった人に声をかける                               │
└─────────────────────────────────────────────────────────────┘
```

### Phase 2: Enforce the Timeline（30分）

```
┌─────────────────────────────────────────────────────────────┐
│  「イベントを時系列に並べてください」                        │
│                                                             │
│  ルール:                                                    │
│  ・左から右へ時間が流れる                                   │
│  ・重複は縦に並べる                                         │
│  ・並行して起きることは上下に配置                           │
│  ・議論が始まったらホットスポット（赤付箋）を貼る           │
│                                                             │
│  この段階で発見されること:                                  │
│  ・抜けているステップ                                       │
│  ・用語の不一致                                             │
│  ・異なる理解                                               │
└─────────────────────────────────────────────────────────────┘
```

### Phase 3: People and Systems（30分）

```
┌─────────────────────────────────────────────────────────────┐
│  「誰が/何がこのイベントを引き起こすか」                     │
│                                                             │
│  追加する要素:                                               │
│  ・アクター（黄色小付箋）                                   │
```

# 第4章: Process Level EventStorming

## 4.1 概要

Process Level EventStormingは、**特定のビジネスプロセスを詳細に分析する**手法です。

### Big Pictureとの違い

| 観点 | Big Picture | Process Level |
|---|---|---|
| **スコープ** | ビジネス全体 | 特定プロセス |
| **深さ** | 広く浅く | 狭く深く |
| **参加者** | 多様なステークホルダー | プロセス関係者 |
| **成果物** | コンテキスト境界 | 詳細なフロー |
| **所要時間** | 半日〜1日 | 2-4時間 |

---

## 4.2 追加要素

### コマンドの詳細化

```
┌─────────────────────────────────────────────────────────────┐
│  コマンド（青付箋）                                          │
│                                                             │
│  ・命令形で書く（「注文を確定する」）                       │
│  ・イベントの直前に配置                                     │
│  ・誰が（アクター）実行するかを明示                         │
│                                                             │
│  アクター ──→ コマンド ──→ イベント                        │
│    (黄小)      (青)        (オレンジ)                       │
└─────────────────────────────────────────────────────────────┘
```

### ポリシーの発見

```
┌─────────────────────────────────────────────────────────────┐
│  ポリシー（紫/ライラック付箋）                               │
│                                                             │
│  ・「〜したら、〜する」というルール                         │
│  ・イベントに反応して別のコマンドを発行                     │
│  ・自動化されていることも、手動のこともある                 │
│                                                             │
│  イベント ──→ ポリシー ──→ コマンド ──→ イベント          │
│  (オレンジ)    (紫)         (青)       (オレンジ)           │
│                                                             │
│  例:                                                        │
│  「注文が確定された」──→「在庫を引き当てる」               │
│                        （自動処理ポリシー）                 │
└─────────────────────────────────────────────────────────────┘
```

### リードモデルの特定

```
┌─────────────────────────────────────────────────────────────┐
│  リードモデル（緑付箋）                                      │
│                                                             │
│  ・意思決定に必要な情報                                     │
│  ・コマンド発行前に参照される                               │
│  ・UIの画面に相当することが多い                             │
│                                                             │
│  リードモデル ──→ アクター ──→ コマンド                    │
│     (緑)          (黄小)       (青)                         │
│                                                             │
│  例:                                                        │
│  「注文一覧画面」を見て「注文を承認する」                   │
└─────────────────────────────────────────────────────────────┘
```

---

## 4.3 進行の流れ

### ステップ1: スコープの明確化（10分）

```
- Big Pictureで特定されたコンテキストの1つを選択
- 開始イベントと終了イベントを定義
- 参加者の役割を確認
```

### ステップ2: ハッピーパスの詳細化（45分）

```
- 最も一般的なフローを最初に描く
- コマンド・ポリシー・リードモデルを追加
- 各ステップの「なぜ」を確認
```

### ステップ3: 例外パスの探索（30分）

```
- 「もし〜だったら」で例外を洗い出す
- エラーケース、キャンセル、タイムアウト
- 各例外に対するポリシーを特定
```

### ステップ4: 集約の特定（30分）

```
- コマンドを受け取る責任者（集約）を特定
- 整合性の境界を議論
- トランザクション境界を明確化
```

## 4.4 集約の発見パターン

### 集約とは

```
┌─────────────────────────────────────────────────────────────┐
│  集約（黄色大付箋）                                          │
│                                                             │
│  ・コマンドを受け取る責任を持つ                             │
│  ・イベントを発行する                                       │
│  ・整合性の境界を形成                                       │
│  ・1つのトランザクションで変更される                        │
│                                                             │
│  コマンド ──→ 集約 ──→ イベント                            │
│    (青)       (黄大)    (オレンジ)                          │
└─────────────────────────────────────────────────────────────┘
```

### 集約の手がかり

| 手がかり | 説明 |
|---|---|
| **名詞の重要性** | 頻繁に言及される名詞 |
| **整合性要求** | 「同時に変わるべき」もの |
| **ライフサイクル** | 作成から削除まで一貫して管理 |
| **識別子** | IDで特定される概念 |

# 第5章: Design Level EventStorming

## 5.1 概要

Design Level EventStormingは、**実装に直結する詳細設計**を行う手法です。

### 目的

- 集約の内部構造の設計
- コマンドハンドラーの特定
- イベントスキーマの定義
- APIの設計

---

## 5.2 詳細化の要素

### コマンドの詳細

```yaml
command:
  name: "PlaceOrder"
  actor: "Customer"
  aggregate: "Order"
  parameters:
    - customerId: UUID
    - items: List<OrderItem>
    - shippingAddress: Address
  preconditions:
    - "Customer must be authenticated"
    - "Items must be in stock"
  produces:
    - "OrderPlaced"
```

### イベントの詳細

```yaml
event:
  name: "OrderPlaced"
  aggregate: "Order"
  attributes:
    - orderId: UUID
    - customerId: UUID
    - items: List<OrderItem>
    - totalAmount: Money
    - placedAt: DateTime
  triggers:
    - policy: "ReserveInventory"
    - policy: "SendOrderConfirmation"
```

### ポリシーの詳細

```yaml
policy:
  name: "ReserveInventory"
  triggers_on: "OrderPlaced"
  issues_command: "ReserveStock"
  target_aggregate: "Inventory"
  conditions:
    - "Order total > 0"
  notes: "Async, eventually consistent"
```

---

## 5.3 設計の検証

### コマンドの検証ポイント

| ポイント | 確認事項 |
|---|---|
| **命名** | ビジネス用語を使用しているか |
| **責任** | 1つの集約に対するコマンドか |
| **パラメータ** | 必要十分な情報を含むか |
| **前提条件** | 明示的に定義されているか |

### イベントの検証ポイント

| ポイント | 確認事項 |
|---|---|
| **過去形** | 完了した事実を表しているか |
| **自己完結** | イベント単体で意味が通るか |
| **不変** | 後から変更されないか |
| **消費者** | 誰がこのイベントを必要とするか |

### 7.4 決められていないバッドエンディング

上記は代表的なバッドエンディングですが、EventStormingの失敗パターンは無限にあります。

**プレイ中に発生しうる、その他のバッドエンディング例：**

| パターン | 発生条件（目安） | 結末の方向性 |
|---------|-----------------|-------------|
| 「付箋の山」 | イベント数50以上かつ整理度3以下 | 情報過多で誰も全体像を把握できない |
| 「時間泥棒」 | 時間超過50%以上 | 参加者の信頼を失い、次回開催不可 |
| 「技術者の独壇場」 | 技術者以外の発言率20%以下 | ビジネス視点が欠落したモデルに |
| 「完璧主義の罠」 | 同じ領域を3ターン以上議論 | 細部に拘りすぎて全体が見えない |

**カスタムバッドエンディングの作り方：**

あなた自身の組織で経験した「ワークショップ失敗」をバッドエンディングとして記録できます。

```
═══════════════════════════════════════════════════════════════
                    END: [あなたのエンディング名]
═══════════════════════════════════════════════════════════════

『[印象的な一文]』

[状況の描写]

[キャラクターの台詞]

[結末]

┌─────────────────────────────────────────────────────────────┐
│ 学びのポイント                                              │
├─────────────────────────────────────────────────────────────┤
│ • [学び1]                                                   │
│ • [学び2]                                                   │
│ • [学び3]                                                   │
└─────────────────────────────────────────────────────────────┘

                    GAME OVER
═══════════════════════════════════════════════════════════════
```

# 第10章: RPG強化システム

このゲームでは、学習体験を強化するための要素を導入しています。これらの要素は**オプション**であり、基本ルールのみでもプレイ可能です。

## 10.1 プレイヤースペシャリティ

プレイヤーは「ファシリテーター」として、以下の4つのスペシャリティから1つを選択できます。

### スペシャリティ一覧

| スペシャリティ | 特徴 | 判定ボーナス | 特殊能力（1ゲーム1回） |
|--------|------|:---:|---|
| **イベントハンター** | ドメインイベント発見に優れる | イベント発見+1 | 「見えないイベント」: 隠れたイベントを3つ自動発見 |
| **境界アーキテクト** | コンテキスト境界の特定に強い | 境界発見+1 | 「明確な境界線」: 境界定義の判定を自動成功 |
| **ファシリテーションマスター** | 議論の活性化に長ける | エンゲージメント+1 | 「場の活性化」: エンゲージメントを+3 |
| **ドメインリンガー** | ユビキタス言語の定義が得意 | 言語定義+1 | 「共通言語の創出」: 用語の合意形成を自動成功 |

### スペシャリティ選択のヒント

```
┌─────────────────────────────────────────────────────────────┐
│  スペシャリティ選択ガイド                                    │
│                                                             │
│  イベントハンター → イベント発見を重視したい                │
│  境界アーキテクト → DDD設計につなげたい                     │
│  ファシリテーションマスター → ワークショップ運営を重視      │
│  ドメインリンガー → 用語の統一を重視したい                  │
│                                                             │
│  迷ったらファシリテーションマスターがおすすめ               │
└─────────────────────────────────────────────────────────────┘
```

## 10.2 NPCシステム

ゲーム中に登場する記憶に残るワークショップ参加者NPCです。

> **Note**: 以下のNPCは代表的な役割パターンです。GMはシナリオのテーマや複雑さに応じて、NPCの追加・削除・変更を自由に行えます。

### エキスパートNPC

| NPC | 役割 | 特徴 | 関係値の影響 |
|-----|------|------|-------------|
| **斎藤部長** | 事業部門責任者 | ドメイン知識が豊富、忙しい | 良好: 深いドメイン知識+2、悪化: 早退リスク |
| **川口ベテラン** | 15年勤務のオペレーター | 暗黙知の塊、発言控えめ | 良好: 隠れたイベント発見+2、悪化: 沈黙 |

### 開発チームNPC

| NPC | 役割 | 特徴 | 関係値の影響 |
|-----|------|------|-------------|
| **松本アーキテクト** | テクニカルリード | 技術視点、境界に敏感 | 良好: 境界判定+1、悪化: 技術偏重の議論 |
| **井上デザイナー** | UXデザイナー | ユーザー視点、可視化が得意 | 良好: エンゲージメント+1、悪化: 議論の脱線 |
| **吉田エンジニア** | 若手開発者 | 学習意欲高い、質問多い | 良好: 気づきの促進+1、悪化: 議論の遅延 |

### 関係値システム

NPCとの関係値は **-3〜+3** の範囲で変動します。

| 関係値 | 状態 | 効果 |
|:---:|---|---|
| +3 | 強い信頼 | 積極的に貢献、他者を巻き込む |
| +1〜+2 | 良好 | 協力的、付箋を書く |
| 0 | 中立 | 様子見、促されれば参加 |
| -1〜-2 | 消極的 | 腕組み、スマホを見る |
| -3 | 離脱 | 退出または妨害 |

### 関係値の変動

| 行動 | 変動 |
|------|:---:|
| NPCの発言を可視化（付箋化） | +1 |
| NPCの専門領域を活かす質問 | +1 |
| NPCの貢献を認める | +1 |
| NPCの発言を無視 | -1 |
| NPCの専門外の質問を繰り返す | -1 |
| 一人の意見を過度に採用 | -1（他NPC） |

## 10.3 コンピテンシー開発（洞察ポイント）

ターン終了時に**洞察ポイント**を獲得し、コンピテンシーを習得できます。

### 洞察ポイントの獲得

| 条件 | 獲得ポイント |
|------|:---:|
| ターンを完了 | +1 |
| 判定で11以上（大成功/完全成功） | +1 |
| 新しい境界を発見 | +1 |
| ホットスポットを解消 | +1 |

### コンピテンシーツリー

```
イベント発見スキル          境界設計スキル            ファシリテーションスキル
    │                       │                       │
    ├─ タイムライン構築+1    ├─ 境界の手がかり+1      ├─ サイレントワーク+1
    │  (コスト: 2)          │  (コスト: 2)          │  (コスト: 2)
    │                       │                       │
    ├─ コマンド発見          ├─ コンテキストマップ    ├─ 対立解消
    │  (コスト: 3)          │  (コスト: 3)          │  (コスト: 3)
    │  アクター・コマンド    │  関係性の可視化        │  意見対立時の
    │  追加判定+1           │  判定+1               │  ペナルティ軽減
    │                       │                       │
    └─ ポリシー発見          └─ 集約設計             └─ エネルギー管理
       (コスト: 5)             (コスト: 5)             (コスト: 5)
       隠れたルール           集約境界の             休憩配分で
       発見+2                判定+2                 エンゲージメント維持
```

### コンピテンシー効果詳細

| コンピテンシー | コスト | 効果 |
|--------|:---:|---|
| **タイムライン構築+1** | 2 | イベントの時系列並べの判定+1 |
| **境界の手がかり+1** | 2 | 境界発見の判定+1 |
| **サイレントワーク+1** | 2 | サイレントブレインストーミングの効果+1 |

# 付録A: クイックリファレンス

## 付箋の色と意味

| 色 | 要素 | 例 |
|---|---|---|
| オレンジ | ドメインイベント | 「注文が確定された」 |
| 青 | コマンド | 「注文を確定する」 |
| 黄（小） | アクター | 「顧客」 |
| 黄（大） | 集約 | 「注文」 |
| 紫 | ポリシー | 「在庫引当ルール」 |
| 緑 | リードモデル | 「注文一覧」 |
| ピンク | 外部システム | 「決済サービス」 |
| 赤 | ホットスポット | 「要確認」 |

## 判定修正値サマリー

| 条件 | 修正 |
|---|:---:|
| ドメインエキスパートが積極的 | +2 |
| 適切な質問で導く | +2 |
| 全員が付箋を書いている | +1 |
| サイレントブレインストーミング実施 | +1 |
| 重要なステークホルダー不在 | -3 |
| 特定の人が支配 | -2 |
| 対立が解消されない | -2 |
| レガシーシステムが複雑 | -2 |

## ファシリテーションTips

1. **沈黙は敵ではない** - 考える時間を与える
2. **質問で導く** - 答えを与えない
3. **全てを書く** - 議論を可視化する
4. **ホットスポットは宝** - 問題ではなく発見
5. **完璧を求めない** - 学びを最大化する
