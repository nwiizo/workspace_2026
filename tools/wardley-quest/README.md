Wardley Mapping × DDD × Team Topologies を統合的に学ぶ戦略シミュレーションRPG

**[アーキテクチャモダナイゼーション 組織とビジネスの未来を設計する](https://amzn.to/4qqit8T)**

このゲームは書籍「Architecture Modernization」の概念を体験的に学ぶために設計されています。

### 書籍を読むことで得られるもの

**ゲームだけでは学べないこと：**

- **深い背景知識**: なぜこれらのフレームワークが必要なのか、その歴史と文脈
- **実践的な洞察**: 著者たちが現場で経験した成功と失敗のストーリー
- **思考の枠組み**: 個別のテクニックではなく、判断の軸となる考え方
- **組織変革の現実**: 技術だけでなく、人と組織を動かすための知恵

**読書の前と後でゲーム体験が変わります：**

| 読書前 | 読書後 |
|---|---|
| ルールに従って進める | なぜそのルールなのか理解して判断できる |
| イベントに反応する | イベントの背景を読み、先手を打てる |
| 表面的な戦略 | 深い文脈に基づいた戦略 |
| 「こうすべき」を学ぶ | 「なぜこうすべきか」を理解する |

AIは知識を提供できますが、**体系化された思想と実践の蓄積**は書籍でしか得られません。

ゲームを楽しんだ後は、ぜひ書籍で深く学んでください。そして、また戻ってきてプレイすると、まったく違う体験ができるはずです。

## プレイ支援機能

### 出力モード

LLMのコンテキストを節約するため、3つの出力モードを用意しています。

| モード | 説明 | 使用場面 |
|---|---|---|
| **通常モード** | 標準的な出力量 | 通常プレイ |
| **コンパクトモード** | 最小限の出力で進行 | 長時間プレイ、コンテキスト節約 |
| **詳細モード** | 豊富な説明と演出 | 世界観を楽しみたい時 |

**コマンド例：**

```
コンパクトモードに切り替えてください
通常モードに戻してください
状態確認
サマリー
```

コンパクトモードでは、ターンごとの出力が以下のように簡潔になります：

```
【T3】状況: 経営層からROI説明を求められた
選択肢: A)定量データ提示 B)事例紹介 C)段階的実証提案
状態: 予算[70] モメンタム[+2] 負債[中]
```

**コンパクトモードでやること：**
- 状況を1-2行で要約
- 選択肢を簡潔に提示（A/B/C形式）
- 重要なスコア変動のみ表示
- NPC発言は1文以内

**コンパクトモードでやらないこと：**
- 長い状況説明や背景描写
- ASCII図の毎ターン表示
- 詳細なNPC会話
- 理論の詳しい解説
- 装飾的な演出

※自由入力による質問や詳細説明の要求は常に可能です。

### セーブ機能（引継書）

LLMのコンテキストがいっぱいになった場合、ゲーム状態を引き継ぐための「引継書」を作成できます。

**コマンド：**

```
引継書を作成してください
```

引継書には以下の情報が含まれます：
- 現在のターン数とシナリオ
- 各種スコア（予算、モメンタム、負債など）
- NPC関係値
- 獲得スキル
- 重要な意思決定履歴

**使い方：**

1. 現在のセッションで「引継書を作成してください」と伝える
2. 出力された引継書をコピー
3. 新しいセッションでscenario.mdと引継書を貼り付け
4. 「この引継書から再開してください」と伝える

## 各アドオンの詳細

### Discovery Workshop Quest

**ステークホルダー発見と合意形成**

モダナイゼーションの成功は「聴くこと」から始まります。解決策を持っていく前に、まずステークホルダーの声に耳を傾けます。

**学べる手法：**
- **リスニングツアー** - 経営幹部から現場担当者まで多様な人々と面談し、課題と機会を発見
- **インパクトマッピング** - ビジネス目標→関係者→インパクト→成果物を可視化
- **リスクストーミング** - C4コンテナ図を使ってアーキテクチャ上のリスクを特定
- **ビジネスモデルキャンバス** / **プロダクトビジョンボード** - 価値提案を明確化
- **キックスターターワークショップ** - モダナイゼーションの第一歩を決定する3日間の集中討議

**効果的な質問技法：** 文章完成法、感情選択法、画像選択法、最悪のシナリオ法、悪魔の代弁者法

---

### EventStorming Quest

**ドメイン発見ワークショップ**

Alberto Brandoliniが考案したEventStormingは、ドメインエキスパートと技術者が一緒にビジネスプロセスを探索する強力な手法です。

**3つのレベル：**
- **Big Picture EventStorming** - ビジネス全体の流れを俯瞰し、ドメインの全体像を把握
- **Process Level EventStorming** - 特定のプロセスを詳細に分析し、境界を特定
- **Design Level EventStorming** - 集約、コマンド、イベントを設計レベルで定義

**EventStormingの記法：**
- オレンジ付箋：ドメインイベント（過去形で記述）
- 青付箋：コマンド
- 黄色付箋：アクター
- ピンク付箋：外部システム
- 赤付箋：ホットスポット（問題点、疑問）

---

### Portfolio Modernization Quest

**戦略的ITポートフォリオ管理**

「どのシステムに投資し、何を廃止するか」を戦略的に判断します。限られたリソースを最大の価値に変える投資判断を学びます。

**コアドメインチャート：** ビジネス差別化とモデルの複雑さの2軸でサブドメインを分類
- **Core（コア）** - 差別化の源泉。最優先で投資。社内で構築。
- **Supporting（支援）** - コアを支援。必要だが差別化ではない。
- **Generic（汎用）** - 外部化・SaaS化を検討。

**ユーティリティIT vs 戦略的IT：** Martin Fowlerの二分法
- 戦略的ITはビジネスの差別化に直接貢献（企業のITの5〜20%のみ）
- ユーティリティITは必要だが差別化には貢献しない

**モダナイゼーション戦略パターン：** Sunset（廃止）、Lift-Shift、リプラットフォーム、リファクタリング

---

### Platform Engineering Quest

**内部開発者プラットフォーム（IDP）**

開発チームの認知負荷を軽減し、ビジネス価値の提供に集中できる環境を構築します。「Platform as a Product」の思考で、使いたくなるプラットフォームを設計します。

**開発者体験（DX）の目標：**
- 新アプリケーション起動から本番デプロイまで数時間以内
- 変更リードタイム1時間未満
- 新メンバーが初日にコードを本番へデプロイ
- 100%セルフサービス

**プラットフォーム機能：**
- **ゴールデンパス** - 推奨される開発・デプロイの標準フロー（アプリテンプレート、パイプライン設定）
- **オブザーバビリティ** - ロギング、モニタリング、4つのゴールデンシグナル
- **ソフトウェアカタログ** - 組織内の全サービスをカタログ化（Backstage等）

**Matthew Skeltonの洞察：** 「プラットフォームとは、エンジニアのために厳選された体験です。wikiページだけでも立派なプラットフォームになり得ます。」

---

### Data Modeling Quest

**DDDに基づくデータ設計**

境界づけられたコンテキストをデータモデルとして実装する方法を学びます。データメッシュの原則に基づき、ドメインチームがデータを所有するアーキテクチャを設計します。

**データメッシュの4つの原則（Zhamak Dehghani）：**
1. **ドメインオーナーシップ** - データはドメインチームが所有
2. **データのプロダクト化** - データを内部顧客向けプロダクトとして提供
3. **セルフサービス型プラットフォーム** - データの発見・利用を容易に
4. **連邦型コンピュテーショナル・ガバナンス** - 全社方針とドメイン自律性のバランス

**データプロダクトの特性（DAUNTIVS）：** 発見可能、対処可能、理解可能、ネイティブにアクセス可能、信頼でき真実である、相互運用可能、それ自体で価値がある、セキュア

**結合バランス（Vlad Khononov）：** 結合は悪ではなく、不適切な結合が問題。距離×揮発性×強度で結合コストを評価。

### Domain Boundary Quest

**境界づけられたコンテキスト**

「境界を正しく切る者、システムを制す」。DDDの境界づけられたコンテキストを実践的に学びます。モノリスの分割、マイクロサービス設計、チームの自律性を実現する境界設計を体験します。

**境界を見つける技術：**
- **言語の違いに注目** - 同じ言葉、違う意味 = コンテキスト境界のサイン
- **変更の軸に注目** - 変更頻度が異なる領域は別コンテキストに
- **チーム構造に注目** - 逆コンウェイ戦略：1チームが担当できる認知負荷 ≒ 1コンテキストの上限

**実装パターン：**
- **モジュラーモノリス** - 最初から境界を明確にし、必要に応じて分離
- **Anti-Corruption Layer（ACL）** - レガシーシステムとの境界を守る
- **Context Map** - コンテキスト間の関係性（Partnership、Customer-Supplier、Conformist）

**コードで境界を強制する：** `pub/private`によるモジュール境界、Architecture Testによる依存関係検証

### API Design Quest

**契約としてのAPI設計**

APIを「システム間の技術的インターフェース」としてだけでなく、「チーム間の契約」として捉えます。設計から実装まで、エンジニアとしての実装力を磨きます。

**良いAPIの4つの柱：**
1. **運用可能性（Operability）** - ヘルスチェック、メトリクス、トレーシング
2. **表現力（Expressiveness）** - ドメインモデルを適切に表現するリソース設計
3. **シンプル性（Simplicity）** - 複雑さを隠蔽し、シンプルなインターフェースを提供
4. **予測可能性（Predictability）** - 一貫した命名、エラーレスポンス、ページネーション

**実装の醍醐味：**
- 集約ルートをリソースとして表現
- ドメインイベントとAPI（同期コマンド + 非同期イベント）
- RFC 7807 Problem Detailsによるエラーハンドリング
- バージョニング戦略と後方互換性

### Technical Debt Quest

**技術的負債の戦略的管理**

Ward Cunninghamが1992年に提唱した技術的負債メタファーを深く理解し、負債の可視化・定量化・戦略的返済を学びます。

**技術的負債の4象限（Martin Fowler）：**
|  | 慎重 | 無謀 |
|---|---|---|
| **意図的** | 「リスクを理解した上でリリースを優先」 | 「設計する時間がない」 |
| **無意識** | 「今ならもっと良い方法がわかる」 | 「レイヤリングって何？」 |

**負債の可視化：**
- コードメトリクス（循環的複雑度、結合度、凝集度）
- 変更頻度 × 複雑度マトリクス
- 開発者の「痛みポイント」ヒートマップ

**戦略的返済：** 返済しない負債もある。ビジネス価値と返済コストのバランスで判断。

---

### Incident Management Quest

**インシデント対応とポストモーテム**

本番障害は必ず起こる。問題は、そこから何を学ぶか。インシデントコマンダーとして混乱の中で冷静に判断し、ブレームレスな振り返り文化を築きます。

**インシデント対応の基本：**
- **重大度（Severity）レベル** - SEV1〜SEV4の分類と対応優先度
- **インシデントコマンダー** - 混乱の中で冷静に指揮を執る役割
- **コミュニケーション** - ステークホルダーへの適切な情報伝達

**SRE/DevOpsプラクティス：**
- **SLO/SLI** - サービスレベル目標とエラーバジェット
- **オンコール** - 持続可能な待機体制の設計
- **ランブック** - 標準対応手順書の作成と更新

**ブレームレス文化：**
- **ポストモーテム** - 責任追及ではなく学習のための振り返り
- **貢献因子分析** - 「誰が悪い」ではなく「何が寄与したか」
- **システム思考** - 個人の失敗ではなくシステムの改善に注目

### Change Leadership Quest

**組織変革リーダーシップ**

技術的な変革だけでなく、人と組織を動かすリーダーシップを学びます。AMET（Architecture Modernization Enabling Team）を中心に、持続的な変革を推進します。

**AMETの役割：**
- **キックスタート** - モダナイゼーションの取り組みを開始
- **モメンタム維持** - 推進力を維持し、日常業務に戻らせない
- **よりよい設計** - ドメイン境界、チーム設計、アーキテクチャの改善を支援
- **持続可能な変革** - 長期的な学習文化の醸成
- **コミュニケーション** - ビジョンの共有とステークホルダーとの関係構築

**組織変革の現実：**
- 正しいことをしても抵抗に遭う
- 過去の成功が変化への慣性（Inertia）を生む
- 「構造とプロセスの誤謬」- 構造だけでは高い成果を出す組織は作れない
