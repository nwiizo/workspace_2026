# 第1章: ゲーム概要

## 1.1 このゲームについて

**Strategic Evolution Quest** は、現代のソフトウェア組織に必要な3つのフレームワークを**厳密に**学ぶ戦略シミュレーションRPGです。

このゲームは**シビア**です。現実の組織変革と同様に、正しい判断をしても失敗し、予期せぬ事態が発生し、過去の成功が足かせになります。

### 3つの学習領域

| フレームワーク           | 領域             | 核心概念                                                     |
| ------------------------ | ---------------- | ------------------------------------------------------------ |
| **Wardley Mapping**      | ビジネス戦略     | 戦場の可視化、進化の不可避性、気候パターン                   |
| **Domain-Driven Design** | ソフトウェア設計 | 境界づけられたコンテキスト、コアドメイン、コンテキストマップ |
| **Team Topologies**      | チーム組織       | 認知負荷、チームタイプ、インタラクションモード               |

### 3つのフレームワークの関係

- **Wardley Mapping**（どこで戦うか） ←→ **DDD**（何を作るか）: 進化段階が投資判断を、サブドメイン分類が境界設計を決める
- 両者が **Team Topologies**（誰がどう作るか）を規定する
- **コンウェイの法則**: 組織構造がシステム構造を規定する → 望むアーキテクチャに合わせてチームを設計せよ（逆コンウェイ戦略）

### プレイ形式

| 項目       | 内容                                     |
| ---------- | ---------------------------------------- |
| プレイヤー | 1名（架空企業の変革責任者）              |
| GM         | Claude（シナリオ・判定・気候イベント）   |
| 所要時間   | 60〜120分                                |
| 難易度     | **高い**（学習目的のため意図的にシビア） |

# 第2章: ゲームルール

## 2.1 セッション構造

**Phase 1: As-Is分析** → 現在のチーム構成確認、フロー阻害要因特定、Wardley Map作成、サブドメイン分類、技術的負債・慣性評価

**Phase 2: 戦略フェーズ（ターン制）** → 各ターン: 1)気候イベント(D6×2) → 2)状況分析(Wardley/DDD/Team) → 3)アクション宣言(最大3つ) → 4)判定(2D6+修正値) → 5)結果適用(慣性・負債・認知負荷更新)

**Phase 3: To-Be評価と振り返り** → 目標達成度判定、フロー阻害解消状況、3フレームワーク整合性評価、学びの言語化

## 2.4 気候イベント

毎ターン開始時にD6を2回振り、2つのイベントが発生します。

### 気候イベント表

| D6  | イベント               | 効果                                                                                                    | 対応のヒント          |
| :-: | ---------------------- | ------------------------------------------------------------------------------------------------------- | --------------------- |
|  1  | **新技術の出現**       | 新Genesis機会。無視すると競合が先行（2ターン後に競合参入）。                                            | 探索的投資の検討      |
|  2  | **競合の動き**         | 競合が1コンポーネントを進化。市場期待値が上昇。                                                         | 差別化か追従かの判断  |
|  3  | **コモディティ化加速** | Product段階の1つが急速にCommodityへ。自社開発していると慣性+2。                                         | Build→Buyへの切り替え |
|  4  | **規制変更**           | 新要件追加。対応しないと次ターンから判定-2。                                                            | 優先度の再評価        |
|  5  | **人材流動**           | キーパーソン退職リスク。特定チームの認知負荷が集中していると実際に退職（そのチーム能力-2）。            | 知識の分散            |
|  6  | **エコシステム変動**   | パートナー/ベンダーの戦略変更。依存しているサービスの条件悪化または好転（D6で判定：1-3悪化、4-6好転）。 | 依存関係の見直し      |

### 気候パターン（常時適用）

| パターン                     | 効果                                                         |
| ---------------------------- | ------------------------------------------------------------ |
| **すべては進化する**         | 各コンポーネントは2ターンごとに1段階右へ移動する圧力を受ける |
| **効率化が革新を生む**       | Commodityの上に新しいGenesisが生まれる可能性がある           |
| **成功が慣性を生む**         | Product段階で利益が出ているコンポーネントは慣性+1/ターン     |
| **変化は非線形**             | 気候イベントで「1」が2回連続すると、急激な市場変化が発生     |
| **新規参入者が変化を起こす** | 慣性を持たない競合は常に有利                                 |

## 2.7 認知負荷システム

### 認知負荷の計算

チーム認知負荷 = (担当ドメイン数 × 2) + (曖昧な境界の数 × 1) + (複雑な依存関係の数 × 1) - (明確なチームAPI × 1) - (プラットフォームからの支援 × 1)

### 認知負荷の影響

| 負荷レベル | 効果                                                |
| :--------: | --------------------------------------------------- |
|    0-4     | 正常。フロー状態で高いパフォーマンス。              |
|    5-6     | 警告。判定-1。残業増加。                            |
|    7-8     | 過負荷。判定-2。離職リスク上昇。                    |
|     9+     | 崩壊。判定-3。毎ターン離職判定（D6で1-2なら発生）。 |

### 認知負荷の軽減

| アクション           | 効果                               |
| -------------------- | ---------------------------------- |
| チーム分割           | 負荷を分散（新チームのコスト発生） |
| プラットフォーム提供 | ジェネリック領域の負荷-2           |
| 境界の明確化         | 曖昧さによる負荷-1                 |
| イネーブリング支援   | 一時的に負荷-1（2ターン）          |

# 第4章: Wardley Mapping

## 4.1 概要

Wardley Mappingは、**ビジネス環境を地図として可視化**し、**進化の法則を理解**し、**戦略的意思決定**を行うフレームワークです。気候パターン(~30)、ドクトリン(~40)、ゲームプレイ(~100)が存在します。

**問い**: どこで戦うか？ 各コンポーネントの進化段階は？ 何が変化しつつあるか？ どこに投資し何をやめるか？

---

## 4.2 Mapの構造

- 縦軸: 可視性（ユーザーからの距離）。アンカーは「ユーザーニーズ」
- 横軸: 進化（Genesis → Custom → Product → Commodity）
- 依存関係（バリューチェーン）で上から下へ接続
- 左ほど差別化・不確実・Build、右ほど標準化・確実・Buy

---

## 4.3 進化の4段階

| 段階            | 特徴               | 市場     | 基本修正 | 投資判断 |
| --------------- | -------------------- | -------- | :------: | -------- |
| **I: Genesis**  | 未知、実験、高リスク | 未形成   | -2 | **Build**（実験・探索） |
| **II: Custom**  | 学習中、差別化可能   | 形成中   | -1 | **Build**（差別化構築） |
| **III: Product** | 成熟、ベストプラクティス | 競争的 | +1 | **Build or Buy**（状況判断） |
| **IV: Commodity** | 標準化、差別化不可  | 効率競争 | +2 | **Buy**（外部調達） |

不適切な投資判断のペナルティ: Custom段階でBuy→-1修正、Product段階で判断ミス→慣性+1、Commodity段階でBuild→-2修正+コスト2倍

# 第5章: Domain-Driven Design

## 5.1 概要

DDDは、**複雑なビジネスドメインを理解**し、**適切な境界で分割**し、**ソフトウェアとして表現**するフレームワークです。

**問い**: どこに境界を引くか？ 何がコアで何がジェネリックか？ コンテキスト間はどう連携するか？

---

## 5.2 サブドメインの分類

| タイプ             | 定義                                               | 投資 | 進化段階との対応   |
| ------------------ | -------------------------------------------------- | :--: | ------------------ |
| **コアドメイン**   | 競争優位の源泉。他社と差別化する領域。             | 最大 | Genesis〜Custom    |
| **サポーティング** | コアを支援。差別化ではないが、自社固有の要件あり。 |  中  | Custom〜Product    |
| **ジェネリック**   | 汎用的。業界標準で代替可能。                       | 最小 | Product〜Commodity |

### Core Domain Chart（差別化可能性 × 複雑性）

| パターン | 位置 | 戦略 |
|----------|------|------|
| **決定的コア** | 高差別化＋高複雑性 | 最大投資、最高の人材 |
| **短期コア** | 高差別化＋低複雑性 | 短期集中、次のコアを探す |
| **隠れたコア** | 低差別化＋高複雑性 | 再評価、差別化の種を探す |
| **ジェネリック** | 低差別化＋低複雑性 | 外部調達 |

---

## 5.3 境界づけられたコンテキスト

**境界づけられたコンテキスト**は、特定のドメインモデルが適用される**明確な境界**です。

### 境界設定の原則

| 原則                       | 違反時のペナルティ         |
| -------------------------- | -------------------------- |
| 言語の一貫性（同じ言葉が同じ意味） | コミュニケーションコスト+1 |
| チームの所有（1コンテキスト=1チーム） | 責任の曖昧さ→判定-1 |
| 独立した進化（他に影響なく変更可能） | 変更連鎖→コスト増 |
| 明確なインターフェース | 統合障害リスク |

### Bounded Context Canvas（設計時の考慮要素）

名前、目的、戦略的分類（コア/サポ/ジェネ）、進化段階、ユビキタス言語、インバウンド通信、アウトバウンド通信、依存関係

---

## 5.4 コンテキストマップ

| パターン               | 力関係  | 使用場面             |
| ---------------------- | :------: | -------------------- |
| **パートナーシップ**   | 対等 | 密接な協働が必要 |
| **共有カーネル**       | 対等 | 共通概念がある |
| **顧客/供給者**        | 明確 | 安定した依存関係 |
| **順応者**             | 上流優位 | 上流変更の余地なし |
| **腐敗防止層（ACL）**  | 下流自衛 | レガシー連携 |
| **公開ホストサービス** | 上流提供 | 複数消費者がいる |
| **別々の道**           | なし | 統合コストが高すぎる |

判定修正: マップ定義済+1、ACL隔離+1、パートナーシップ機能+1、関係未定義で連携-2、順応者で振り回される-1

---

## 5.5 Wardley Mappingとの統合

| Wardley段階 | DDDサブドメイン | 推奨アプローチ |
| ----------- | --------------- | -------------- |
| Genesis | **コア** | 探索的開発、高い失敗許容 |
| Custom | **コア** | 差別化構築、アジャイル |
| Product | **サポーティング** | ベストプラクティス適用 |
| Commodity | **ジェネリック** | 外部調達、薄いラッパー |

不整合ペナルティ: Genesisをジェネリック扱い→機会損失、Commodityをコア扱い→判定-2、コア境界曖昧→差別化希薄化

# 第6章: Team Topologies

## 6.1 概要

Team Topologiesは、**効果的なソフトウェアデリバリーのためのチーム構造と相互作用**を定義するフレームワーク。**コンウェイの法則**を逆手に取り、望むアーキテクチャに合わせてチームを設計します。

**問い**: どのようなチームが必要か？ チーム間はどう協働すべきか？ 認知負荷は適切か？

---

## 6.2 4つのチームタイプ

| タイプ | 役割 | サイズ | 適合する進化段階 | 適合するドメイン |
|--------|------|:---:|------------------|------------------|
| **ストリームアラインド** | ビジネス価値の継続的デリバリー | 5-9名 | Genesis〜Product | コア、サポーティング |
| **プラットフォーム** | 内部サービスの提供、認知負荷軽減 | 5-9名 | Product〜Commodity | ジェネリック |
| **イネーブリング** | 他チームの能力向上支援（期間限定） | 3-5名 | 全段階（横断的） | 技術・プロセス |
| **コンプリケイテッド・サブシステム** | 深い専門知識が必要な複雑領域 | 3-7名 | Custom〜Product | 専門領域 |

---

## 6.3 3つのインタラクションモード

| モード | 説明 | 期間 | 使用場面 |
|--------|------|:---:|----------|
| **コラボレーション** | 密接な協働、境界を曖昧に | 一時的 | 新領域の探索、Genesis段階 |
| **X-as-a-Service** | サービスとして利用 | 継続的 | 安定した機能、Commodity |
| **ファシリテーティング** | 支援・指導 | 一時的 | 能力構築、技術移転 |

典型的進化: Genesis(コラボレーション) → Custom(ファシリテーティング) → Product/Commodity(X-as-a-Service)

---

## 6.4 認知負荷

| タイプ | 説明 | 対策 |
|--------|------|------|
| **内在的** | ドメイン固有の本質的な複雑さ | 削減困難。受け入れる。 |
| **外在的** | ツール・プロセス起因の複雑さ | プラットフォームで削減。 |
| **学習的** | 新しい知識習得の負荷 | イネーブリングで支援。 |

| チームサイズ | 担当可能なドメイン数 |
| :----------: | :------------------: |
| 3-4名 | 1 |
| 5-7名 | 1-2 |
| 8-9名 | 2（限界） |
| 10名以上 | 分割すべき |

---

## 6.5 統合マトリクス（Wardley × DDD × Team）

| Wardley段階 | DDDドメイン    | Teamタイプ                 | インタラクション     |
| ----------- | -------------- | -------------------------- | -------------------- |
| Genesis     | コア           | ストリームアラインド（小） | コラボレーション     |
| Custom      | コア           | ストリームアラインド       | ファシリテーティング |
| Product     | サポーティング | SA or コンプリケイテッド   | X-as-a-Service       |
| Commodity   | ジェネリック   | プラットフォーム           | X-as-a-Service       |

不整合ペナルティ: Genesisをプラットフォーム担当→判定-2、コアドメイン3チーム分散→判定-1、1チーム4ドメイン以上→毎ターン離職判定、X-as-a-ServiceなしでCommodity連携→変更コスト2倍

## 8.3 バッドエンディング

### 資金枯渇「静かな終焉」
**条件**: リソースが0以下
**学び**: 戦略的投資判断の重要性 / Build vs Buyの意思決定 / 気候パターンへの早期対応

### 技術的負債「動かない巨象」
**条件**: 技術的負債が10以上
**学び**: 技術的負債は複利で増える / 短期的な「勝ち」が長期的な「負け」を生む / 境界の曖昧さが負債を加速させる

### 競争優位喪失「コモディティの海」
**条件**: 全コアドメインがCommodity化
**学び**: 進化は止められない、適応するか消えるか / コアドメインは常に再定義が必要 / 次のGenesisを探し続けることの重要性

### 人材流出「最後の一人」
**条件**: 認知負荷9以上が3ターン継続、または離職5回以上
**学び**: 認知負荷の限界は人の限界 / 知識は分散させなければ失われる / チームの健康は事業の健康

### 組織麻痺「慣性の勝利」
**条件**: 慣性7以上が4ターン継続
**学び**: 慣性は最強の敵 / 「変わらない」は「後退する」と同義 / 組織文化は一夜にしては変わらない

### 戦略不整合「三つの矢、三つの方向」
**条件**: フレームワーク間の重大な不整合が3ターン以上継続
**学び**: フレームワークは統合してこそ力を発揮する / 社会技術的整合がなければ優秀な部分も無意味 / 全体最適と部分最適は異なる

---

## 8.4 グッドエンディング

### 変革の完遂「学習する組織」
**条件**: 全目標達成 + 3フレームワーク整合ボーナスを3回以上獲得
**学び**: 組織を変えるのではなく、組織が自ら変わる力を育てる / 文化としてのフレームワーク定着 / 変化を「正しく」恐れること

### 後継者たち「連合の勝利」
**条件**: 全NPC関係値が+2以上でゲーム終了
**学び**: リーダーの最高の仕事は自分がいなくても続く仕組みを作ること / ステークホルダーとの信頼構築 / 知識の移転

### 逆境の勝利「不死鳥」
**条件**: 技術的負債8以上から2以下へ回復して勝利
**学び**: Strangler Figパターンの有効性 / 腐敗防止層による段階的移行 / 小さな成功の積み重ね

### 静かなる勝利「持続可能な変革」
**条件**: 劇的な変動なし（技術的負債変動±2以内、リソース変動±3以内）で目標達成
**学び**: 革命は派手だが進化は持続する / 継続的改善の力 / 本当の変革は気づかれないほど自然に起こる

### 開拓者「イノベーターの凱旋」
**条件**: Genesis段階のコンポーネントをProduct段階まで育成して勝利
**学び**: イノベーションは地図上の空白を見つけ先に歩くこと / Wardley Mapによる機会発見 / 先行者利益の確立
