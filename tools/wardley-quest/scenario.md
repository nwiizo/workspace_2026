# 第1章: ゲーム概要

## 1.1 このゲームについて

**Strategic Evolution Quest** は、現代のソフトウェア組織に必要な3つのフレームワークを**厳密に**学ぶ戦略シミュレーションRPGです。

このゲームは**シビア**です。現実の組織変革と同様に、正しい判断をしても失敗し、予期せぬ事態が発生し、過去の成功が足かせになります。理不尽に感じることもあるでしょう。それが学びです。

### 3つの学習領域

| フレームワーク           | 領域             | 核心概念                                                     |
| ------------------------ | ---------------- | ------------------------------------------------------------ |
| **Wardley Mapping**      | ビジネス戦略     | 戦場の可視化、進化の不可避性、気候パターン                   |
| **Domain-Driven Design** | ソフトウェア設計 | 境界づけられたコンテキスト、コアドメイン、コンテキストマップ |
| **Team Topologies**      | チーム組織       | 認知負荷、チームタイプ、インタラクションモード               |

### 3つのフレームワークの関係

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│   「どこで戦うか」         「何を作るか」                        │
│    Wardley Mapping ←────→ Domain-Driven Design                 │
│         │                        │                             │
│    進化段階が              サブドメイン分類が                   │
│    投資判断を決める        境界設計を決める                     │
│         │                        │                             │
│         └──────────┬─────────────┘                             │
│                    │                                            │
│                    ↓                                            │
│            Team Topologies                                      │
│            「誰がどう作るか」                                    │
│                                                                 │
│   ┌─────────────────────────────────────────────────────────┐  │
│   │ コンウェイの法則:                                        │  │
│   │ 「組織構造がシステム構造を規定する」                      │  │
│   │                                                          │  │
│   │ → 望むアーキテクチャに合わせてチームを設計せよ           │  │

│   └─────────────────────────────────────────────────────────┘  │

```

## 1.2 ゲームの厳しさについて

このゲームでは以下のことが起こります：

| 現象                         | 説明                                         | 学び                     |
| ---------------------------- | -------------------------------------------- | ------------------------ |
| **正しくても失敗する**       | 2D6の出目が悪ければ最善の戦略も失敗する      | 不確実性の中での意思決定 |
| **慣性が邪魔をする**         | 過去の成功が変化を阻む                       | 組織変革の困難さ         |
| **気候は制御できない**       | 競合や市場の変化は予測はできても止められない | 適応の重要性             |
| **認知負荷で崩壊する**       | チームに過度な負荷をかけると生産性が急落する | 持続可能性の限界         |
| **技術的負債が蓄積する**     | 短期的な回避策は長期的なコストになる         | トレードオフの現実       |
| **境界の曖昧さが混乱を生む** | コンテキスト境界が不明確だと連携コストが増大 | 設計の重要性             |

**これらは理不尽ではなく、現実の組織が直面する課題の縮図です。**

## 1.3 用語集

### Wardley Mapping 用語

| 用語                  | 定義                                                    |
| --------------------- | ------------------------------------------------------- |
| **Wardley Map**       | 可視性（縦軸）と進化（横軸）で環境を可視化した地図      |
| **進化（Evolution）** | Genesis → Custom → Product → Commodity への不可避な移動 |
| **気候パターン**      | 全プレイヤーに適用される外部変化の法則（約30種類）      |
| **ドクトリン**        | 普遍的に適用可能な組織運営原則（約40種類）              |
| **ゲームプレイ**      | 状況依存の戦略的行動（約100種類）                       |
| **慣性（Inertia）**   | 過去の成功による変化への抵抗                            |
| **Red Queen効果**     | 競争下では進化しなければ相対的に後退する                |

### Domain-Driven Design 用語

| 用語                           | 定義                                       |
| ------------------------------ | ------------------------------------------ |
| **サブドメイン**               | ビジネス領域の論理的な分割単位             |
| **コアドメイン**               | 競争優位の源泉。最大投資すべき領域。       |
| **サポーティングドメイン**     | コアを支援。差別化ではないが必要。         |
| **ジェネリックドメイン**       | 汎用的。外部調達可能。                     |
| **境界づけられたコンテキスト** | 特定のドメインモデルが適用される明確な境界 |
| **コンテキストマップ**         | コンテキスト間の関係を示す図               |
| **ユビキタス言語**             | コンテキスト内で共有される共通言語         |
| **腐敗防止層（ACL）**          | 外部システムの影響からドメインを守る変換層 |

### Team Topologies 用語

| 用語                                       | 定義                                               |
| ------------------------------------------ | -------------------------------------------------- |
| **ストリームアラインドチーム**             | ビジネス価値の流れに沿って働く主要チーム           |
| **プラットフォームチーム**                 | 内部サービスを提供し、他チームの認知負荷を軽減     |
| **イネーブリングチーム**                   | 他チームの能力向上を一時的に支援                   |
| **コンプリケイテッド・サブシステムチーム** | 深い専門知識が必要な複雑領域を担当                 |
| **認知負荷**                               | チームが扱う情報・責任の総量                       |
| **チームAPI**                              | チームが提供する機能の明確な定義                   |
| **X-as-a-Service**                         | サービスとして機能を提供するインタラクションモード |

### ゲーム用語

| 用語                 | 定義                                            |
| -------------------- | ----------------------------------------------- |
| **ターン**           | 1四半期相当。気候イベント→分析→行動→判定→結果。 |
| **リソース**         | 組織の資源（資金・人材）の抽象値                |
| **技術的負債**       | 短期解決策の蓄積による長期コスト                |
| **フロー阻害要因**   | 価値の流れを妨げる組織的・技術的障壁            |
| **変化のストリーム** | 価値を届ける主要な流れ                          |

## 2.2 判定システム

### 基本判定（2D6）

| 出目 | 結果           | 効果                                         |
| :--: | -------------- | -------------------------------------------- |
|  2   | **致命的失敗** | 最悪の結果。技術的負債+2。フロー阻害要因+1。 |
| 3-4  | **失敗**       | 目標未達成。リソース消費。技術的負債+1。     |
| 5-6  | **部分的失敗** | わずかな進展はあるが、予期せぬ副作用。       |
| 7-8  | **部分的成功** | 条件付き成功。トレードオフが発生。           |
| 9-10 | **成功**       | 目標達成。計画通り。                         |
|  11  | **大成功**     | ボーナス効果。技術的負債-1。                 |
|  12  | **完全成功**   | 最高の結果。追加の洞察や機会を獲得。         |

## 2.3 気候イベント

毎ターン開始時にD6を2回振り、2つのイベントが発生します。

### 気候イベント表

| D6  | イベント               | 効果                                                                                                    | 対応のヒント          |
| :-: | ---------------------- | ------------------------------------------------------------------------------------------------------- | --------------------- |
|  1  | **新技術の出現**       | 新Genesis機会。無視すると競合が先行（2ターン後に競合参入）。                                            | 探索的投資の検討      |
|  2  | **競合の動き**         | 競合が1コンポーネントを進化。市場期待値が上昇。                                                         | 差別化か追従かの判断  |
|  3  | **コモディティ化加速** | Product段階の1つが急速にCommodityへ。自社開発していると慣性+2。                                         | Build→Buyへの切り替え |
|  4  | **規制変更**           | 新要件追加。対応しないと次ターンから判定-2。                                                            | 優先度の再評価        |
|  5  | **人材流動**           | キーパーソン退職リスク。特定チームの認知負荷が集中していると実際に退職（そのチーム能力-2）。            | 知識の分散            |
|  6  | **エコシステム変動**   | パートナー/ベンダーの戦略変更。依存しているサービスの条件悪化または好転（D6で判定：1-3悪化、4-6好転）。 | 依存関係の見直し      |

### 気候パターン（常時適用）

以下のパターンは常に作用しています：

| パターン                     | 効果                                                         |
| ---------------------------- | ------------------------------------------------------------ |
| **すべては進化する**         | 各コンポーネントは2ターンごとに1段階右へ移動する圧力を受ける |
| **効率化が革新を生む**       | Commodityの上に新しいGenesisが生まれる可能性がある           |
| **成功が慣性を生む**         | Product段階で利益が出ているコンポーネントは慣性+1/ターン     |
| **変化は非線形**             | 気候イベントで「1」が2回連続すると、急激な市場変化が発生     |
| **新規参入者が変化を起こす** | 慣性を持たない競合は常に有利                                 |

## 2.4 慣性システム

### 慣性レベル

| レベル | 状態   | 効果                             |
| :----: | ------ | -------------------------------- |
|   0    | なし   | 制約なし                         |
|  1-2   | 軽微   | 変更アクションの判定-1           |
|  3-4   | 中程度 | 変更アクションの判定-2、コスト+1 |
|  5-6   | 深刻   | 変更アクションの判定-3、コスト+2 |
|   7+   | 致命的 | 変更不可能。まず慣性対処が必須。 |

### 慣性の発生

| 原因                                  | 増加量 |
| ------------------------------------- | :----: |
| Product段階で高利益を維持（毎ターン） |   +1   |
| 過去3ターン以上変更なしの領域         |   +1   |
| 「今のやり方で十分」と判断した場合    |   +1   |
| 大規模な組織変更の提案を却下          |   +2   |

### 慣性への対処

| アクション             | コスト | 効果                       | 条件                      |
| ---------------------- | :----: | -------------------------- | ------------------------- |
| 危機感の醸成           |   1    | 慣性-1                     | 判定成功時のみ            |
| 経営層の説得           |   2    | 慣性-2                     | 目標10+、失敗すると慣性+1 |
| パイロットプロジェクト |   2    | 成功すると慣性-2           | 小規模から開始            |
| 外部圧力の活用         |   0    | 気候イベントを理由に慣性-1 | 関連イベント発生時のみ    |

## 2.5 技術的負債システム

### 負債レベル

| レベル | 状態   | 効果                                         |
| :----: | ------ | -------------------------------------------- |
|  0-2   | 健全   | 制約なし                                     |
|  3-4   | 要注意 | 全判定-1、変更に追加コスト+1                 |

|   7+   | 破綻   | 全判定-3、モダナイゼーション以外の選択肢なし |

### 負債の発生

| 原因                       |   増加量   |

| 境界が曖昧なまま開発を進行 | +1/ターン  |
| 短期的な回避策を選択       | +1/発生時  |
| ドキュメントなしで進行     | +1/2ターン |
| テストなしでリリース       | +1/発生時  |
| レガシーとの密結合を維持   | +1/ターン  |

### 負債の返済

| アクション               | コスト | 効果                             |
| ------------------------ | :----: | -------------------------------- |
| リファクタリング         |   1    | 負債-1                           |
| 境界の明確化             |   2    | 負債-1、将来の発生を抑制         |
| ストラングラーフィグ開始 |   3    | 長期的に負債-3（3ターン必要）    |
| 完全リビルド             |   5    | 負債リセット、ただし他の進行停止 |

## 2.6 認知負荷システム

### 認知負荷の計算

```
チーム認知負荷 = (担当ドメイン数 × 2)
               + (曖昧な境界の数 × 1)
               + (複雑な依存関係の数 × 1)
               - (明確なチームAPI × 1)
               - (プラットフォームからの支援 × 1)
```

### 認知負荷の影響

| 負荷レベル | 効果                                                |
| :--------: | --------------------------------------------------- |
|    0-4     | 正常。フロー状態で高いパフォーマンス。              |
|    5-6     | 警告。判定-1。残業増加。                            |
|    7-8     | 過負荷。判定-2。離職リスク上昇。                    |
|     9+     | 崩壊。判定-3。毎ターン離職判定（D6で1-2なら発生）。 |

### 認知負荷の軽減

| アクション           | 効果                               |
| -------------------- | ---------------------------------- |
| チーム分割           | 負荷を分散（新チームのコスト発生） |
| プラットフォーム提供 | ジェネリック領域の負荷-2           |
| 境界の明確化         | 曖昧さによる負荷-1                 |
| イネーブリング支援   | 一時的に負荷-1（2ターン）          |

# 第3章: Wardley Mapping

## 3.1 概要

Wardley Mappingは、**ビジネス環境を地図として可視化**し、**進化の法則を理解**し、**戦略的意思決定**を行うフレームワークです。

Simon Wardleyによれば：

- 約30の気候パターン（制御不能な外部変化）
- 約40のドクトリン（普遍的原則）
- 約100のゲームプレイ（状況依存の行動）

が存在します。

### このフレームワークで答える問い

- 「私たちはどこで戦っているのか？」
- 「各コンポーネントはどの進化段階か？」
- 「何が変化しつつあるのか？」
- 「どこに投資すべきか、何をやめるべきか？」

---

## 3.2 Mapの構造

```
可視性（ユーザーからの距離）
  ↑
高 │  [ユーザーニーズ] ← アンカー（すべての起点）
   │        │
   │        ↓ 依存関係（バリューチェーン）
   │  [見えるコンポーネント]
   │        │
   │        ↓
   │  [見えないコンポーネント]
低 │
   └────────────────────────────────→ 進化
      Genesis   Custom    Product   Commodity
      I         II        III       IV

      ←── 差別化・不確実 ──────── 標準化・確実 ──→
      ←── Build ─────────────────────── Buy ──→
```

---

## 3.3 進化の4段階

### 各段階の特徴

| 段階                 | 特徴                     | ユーザー認識   | 市場     | 失敗許容 |
| -------------------- | ------------------------ | -------------- | -------- | :------: |
| 🧪 **I: Genesis**    | 未知、実験、高リスク     | 「画期的」     | 未形成   |    高    |
| ⚒️ **II: Custom**    | 学習中、差別化可能       | 「最先端」     | 形成中   |    中    |
| 📦 **III: Product**  | 成熟、ベストプラクティス | 「あって当然」 | 競争的   |    低    |
| ⛽ **IV: Commodity** | 標準化、差別化不可       | 「インフラ」   | 効率競争 |   極低   |

### 判定修正

| 段階      | 基本修正 | 理由                 |
| --------- | :------: | -------------------- |
| Genesis   |    -2    | 高い不確実性         |
| Custom    |    -1    | 学習中の不確実性     |
| Product   |    +1    | 安定したプラクティス |
| Commodity |    +2    | 高い予測可能性       |

### 投資判断マトリクス

| 進化段階  | 推奨行動                     | 不適切な行動のペナルティ |
| --------- | ---------------------------- | ------------------------ |
| Genesis   | **Build**（実験・探索）      | Buy不可能                |
| Custom    | **Build**（差別化構築）      | Buy→-1修正               |
| Product   | **Build or Buy**（状況判断） | 判断ミス→慣性+1          |
| Commodity | **Buy**（外部調達）          | Build→-2修正、コスト2倍  |

## 3.4 主要な気候パターン

### 競争に関するパターン

| パターン                     | 説明                         | ゲームでの効果              |
| ---------------------------- | ---------------------------- | --------------------------- |
| **すべては進化する**         | 競争がある限り全てが右へ移動 | 2ターンごとに進化圧力       |
| **Red Queen効果**            | 立ち止まれば相対的に後退     | 進化しないと競争力-1/ターン |
| **新規参入者が変化を起こす** | 慣性なき者が先行             | 競合の新技術採用が早い      |

### コンポーネントに関するパターン

| パターン               | 説明                               | ゲームでの効果           |
| ---------------------- | ---------------------------------- | ------------------------ |
| **効率化が革新を生む** | Commodityの上に新Genesisが生まれる | コモディティ化後に新機会 |
| **高次システムの創発** | 土台の進化が新しい可能性を開く     | 基盤投資の遅延リターン   |
| **特性は進化で変わる** | 段階ごとに必要なアプローチが異なる | チームタイプ要変更       |

### 慣性に関するパターン

| パターン                   | 説明                     | ゲームでの効果              |
| -------------------------- | ------------------------ | --------------------------- |
| **成功が慣性を生む**       | 過去の成功モデルへの執着 | 利益→慣性+1                 |
| **慣性が組織を殺す**       | 変化への抵抗が致命傷に   | 慣性7+で行動制限            |
| **既存モデルへの過剰投資** | 衰退市場への継続投資     | Commodity自社開発ペナルティ |

### 予測に関するパターン

| パターン                   | 説明                                       | ゲームでの効果           |
| -------------------------- | ------------------------------------------ | ------------------------ |
| **変化は非線形**           | 徐々に、そして突然変わる                   | 連続イベントで急変       |
| **予測できるが時期は不明** | 何が起こるかは分かるが、いつかは分からない | 気候イベントのランダム性 |

## 3.5 主要なドクトリン

ドクトリンは**普遍的に適用可能な原則**です。

### フェーズ1: 基本（最初に習得すべき）

| ドクトリン               | 説明                       | 適用時の効果   |
| ------------------------ | -------------------------- | -------------- |
| **ユーザーニーズに焦点** | すべてはユーザーから始まる | 判定+1         |
| **状況認識**             | Mapを作り、共有する        | Mapあり→+1     |
| **バイアスを疑う**       | 思い込みを検証する         | 複数視点で+1   |
| **透明性**               | 情報を隠さない             | チーム間信頼+1 |

### フェーズ2: 組織

| ドクトリン           | 説明                     | 適用時の効果         |
| -------------------- | ------------------------ | -------------------- |
| **小さく始めて学ぶ** | 大きな賭けより小さな実験 | 失敗コスト軽減       |
| **適切な手法を使う** | 段階に応じたアプローチ   | 不整合ペナルティ回避 |
| **失敗を早く安く**   | 早期発見、早期対処       | 技術的負債抑制       |

### フェーズ3: 実行

| ドクトリン               | 説明               | 適用時の効果         |
| ------------------------ | ------------------ | -------------------- |
| **コアに集中**           | 差別化領域に投資   | Genesis/Custom投資+1 |
| **慣性を管理**           | 変化への抵抗を認識 | 慣性対処可能         |
| **何をやらないか決める** | 選択と集中         | 宣言時+1             |

# 第4章: Domain-Driven Design

## 4.1 概要

Domain-Driven Designは、**複雑なビジネスドメインを理解**し、**適切な境界で分割**し、**ソフトウェアとして表現**するフレームワークです。

### このフレームワークで答える問い

- 「どこに境界を引くべきか？」
- 「何がコアで、何がジェネリックか？」
- 「コンテキスト間はどう連携するか？」
- 「同じ言葉が違う意味を持つのはどこか？」

---

## 4.2 サブドメインの分類

### 3つのサブドメインタイプ

| タイプ             | 定義                                               | 投資 | 進化段階との対応   |
| ------------------ | -------------------------------------------------- | :--: | ------------------ |
| **コアドメイン**   | 競争優位の源泉。他社と差別化する領域。             | 最大 | Genesis〜Custom    |
| **サポーティング** | コアを支援。差別化ではないが、自社固有の要件あり。 |  中  | Custom〜Product    |
| **ジェネリック**   | 汎用的。業界標準で代替可能。                       | 最小 | Product〜Commodity |

### Core Domain Chart

Nick Tuneが提唱するCore Domain Chartは、**差別化可能性**と**複雑性**の2軸でドメインを分類します。

```
差別化
可能性
  ↑
高 │  ┌─────────────┐    ┌─────────────┐
   │  │ 短期コア    │    │ 決定的コア  │
   │  │ (競合が     │    │ (市場を     │
   │  │  追いつく)  │    │  決める)    │
   │  └─────────────┘    └─────────────┘
   │
   │  ┌─────────────┐    ┌─────────────┐
   │  │ ジェネリック │    │ 隠れたコア  │
低 │  │ (外部調達)  │    │ (見逃し注意)│
   │  └─────────────┘    └─────────────┘
   └──────────────────────────────────→ 複雑性
            低                    高
```

### コアドメインパターン

| パターン       | 説明                                               | 戦略                     |
| -------------- | -------------------------------------------------- | ------------------------ |
| **決定的コア** | 高差別化＋高複雑性。これを制した者が勝つ。         | 最大投資、最高の人材     |
| **短期コア**   | 高差別化＋低複雑性。競合がすぐ追いつく。           | 短期集中、次のコアを探す |
| **隠れたコア** | 低差別化（と思われている）＋高複雑性。見逃しがち。 | 再評価、差別化の種を探す |

---

## 4.3 境界づけられたコンテキスト

### 定義

**境界づけられたコンテキスト**は、特定のドメインモデルが適用される**明確な境界**です。

### 境界設定の原則

| 原則                       | 説明                     | 違反時のペナルティ         |
| -------------------------- | ------------------------ | -------------------------- |
| **言語の一貫性**           | 同じ言葉が同じ意味を持つ | コミュニケーションコスト+1 |
| **チームの所有**           | 1コンテキスト=1チーム    | 責任の曖昧さ→判定-1        |
| **独立した進化**           | 他に影響なく変更可能     | 変更連鎖→コスト増          |
| **明確なインターフェース** | 入出力が定義されている   | 統合障害リスク             |

### Bounded Context Canvas（簡易版）

コンテキストを設計する際に考慮すべき要素：

| 要素                   | 質問                                         |
| ---------------------- | -------------------------------------------- |
| **名前**               | このコンテキストの名前は？                   |
| **目的**               | なぜこのコンテキストが必要か？               |
| **戦略的分類**         | コア/サポーティング/ジェネリックのどれか？   |
| **進化段階**           | Genesis/Custom/Product/Commodityのどれか？   |
| **ユビキタス言語**     | このコンテキスト内の主要な用語は？           |
| **インバウンド通信**   | 何を受け取るか？（コマンド/イベント/クエリ） |
| **アウトバウンド通信** | 何を提供するか？                             |
| **依存関係**           | どのコンテキストに依存するか？               |

---

## 4.4 コンテキストマップ

コンテキスト間の関係を定義します。

### 関係パターン

| パターン               | 説明                         |  力関係  | 使用場面             |
| ---------------------- | ---------------------------- | :------: | -------------------- |
| **パートナーシップ**   | 対等な協力                   |   対等   | 密接な協働が必要     |
| **共有カーネル**       | モデルの一部を共有           |   対等   | 共通概念がある       |
| **顧客/供給者**        | 供給者が顧客のニーズに応える |   明確   | 安定した依存関係     |
| **順応者**             | 下流が上流のモデルに従う     | 上流優位 | 上流変更の余地なし   |
| **腐敗防止層（ACL）**  | 変換層で自衛                 | 下流自衛 | レガシー連携         |
| **公開ホストサービス** | 標準APIを公開                | 上流提供 | 複数消費者がいる     |
| **別々の道**           | 統合しない                   |   なし   | 統合コストが高すぎる |

### 判定への影響

| 状況                               | 判定修正 |
| ---------------------------------- | :------: |
| コンテキストマップが定義済み       |    +1    |
| ACLでレガシーを適切に隔離          |    +1    |
| パートナーシップが機能している     |    +1    |
| 関係が未定義のまま連携             |    -2    |
| 順応者パターンで上流に振り回される |    -1    |

---

## 4.5 Wardley Mappingとの統合

| Wardley段階 | DDDサブドメイン    | 推奨アプローチ           |
| ----------- | ------------------ | ------------------------ |
| Genesis     | **コア**           | 探索的開発、高い失敗許容 |
| Custom      | **コア**           | 差別化構築、アジャイル   |
| Product     | **サポーティング** | ベストプラクティス適用   |
| Commodity   | **ジェネリック**   | 外部調達、薄いラッパー   |

### 不整合のペナルティ

| 不整合                    | ペナルティ                 |
| ------------------------- | -------------------------- |
| Genesisをジェネリック扱い | 機会損失、競合に先行される |
| Commodityをコア扱い       | リソースの無駄、判定-2     |
| コア境界が曖昧            | 差別化の希薄化             |

# 第5章: Team Topologies

## 5.1 概要

Team Topologiesは、**効果的なソフトウェアデリバリーのためのチーム構造と相互作用**を定義するフレームワークです。

**コンウェイの法則**を逆手に取り、望むアーキテクチャに合わせてチームを設計します。

### このフレームワークで答える問い

- 「どのようなチームが必要か？」
- 「チーム間はどう協働すべきか？」
- 「認知負荷は適切か？」
- 「変化のストリームはどこか？」

---

## 5.2 4つのチームタイプ

| タイプ                               | 役割                             | 適合する進化段階   | 適合するドメイン     |
| ------------------------------------ | -------------------------------- | ------------------ | -------------------- |
| **ストリームアラインド**             | ビジネス価値の継続的デリバリー   | Genesis〜Product   | コア、サポーティング |
| **プラットフォーム**                 | 内部サービスの提供、認知負荷軽減 | Product〜Commodity | ジェネリック         |
| **イネーブリング**                   | 他チームの能力向上支援           | 全段階（横断的）   | 技術・プロセス       |
| **コンプリケイテッド・サブシステム** | 専門知識が必要な複雑領域         | Custom〜Product    | 専門領域             |

### チームタイプの詳細

#### ストリームアラインドチーム

```yaml
目的: ユーザーに価値を継続的に届ける
特徴:
  - 1つの変化のストリームに集中
  - エンドツーエンドの責任
  - 自律的に意思決定
サイズ: 5-9名
担当: コアドメイン、サポーティングドメイン
注意: 認知負荷を超えないよう境界を設定
```

#### プラットフォームチーム

```yaml
目的: ストリームアラインドチームの認知負荷を軽減
特徴:
  - 内部サービスを「製品」として提供
  - セルフサービス重視
  - 薄いラッパー、厚いドキュメント
サイズ: 5-9名
担当: ジェネリックドメイン、共通基盤
注意: 使いやすさが命。使われないプラットフォームは失敗。
```

#### イネーブリングチーム

```yaml
目的: 他チームの能力を向上させる
特徴:
  - 期間限定の支援
  - 技術移転が目標
  - 自ら実装しない
サイズ: 3-5名
担当: 新技術導入、プラクティス改善
注意: 依存させない。自立を促す。
```

#### コンプリケイテッド・サブシステムチーム

```yaml
目的: 専門知識が必要な領域を担当
特徴:
  - 深い専門性
  - 他チームへの依存を最小化
  - 明確なインターフェース
サイズ: 3-7名
担当: 複雑なアルゴリズム、専門的技術
注意: ボトルネックにならないよう設計。
```

---

## 5.3 3つのインタラクションモード

| モード                   | 説明                     |  期間  | 使用場面                  |
| ------------------------ | ------------------------ | :----: | ------------------------- |
| **コラボレーション**     | 密接な協働、境界を曖昧に | 一時的 | 新領域の探索、Genesis段階 |
| **X-as-a-Service**       | サービスとして利用       | 継続的 | 安定した機能、Commodity   |
| **ファシリテーティング** | 支援・指導               | 一時的 | 能力構築、技術移転        |

### インタラクションの進化

```
【典型的なパターン】

Genesis段階:
  チームA ←──コラボレーション──→ チームB
  （境界が曖昧、密接に協働）

Custom段階:
  チームA ←──ファシリテーティング──→ チームB
  （スキル移転中）

Product/Commodity段階:
  チームA ←──X-as-a-Service──→ チームB
  （明確なAPI、自立的な利用）
```

---

## 5.4 認知負荷

### 認知負荷の3タイプ

| タイプ     | 説明                         | 対策                     |
| ---------- | ---------------------------- | ------------------------ |
| **内在的** | ドメイン固有の本質的な複雑さ | 削減困難。受け入れる。   |
| **外在的** | ツール・プロセス起因の複雑さ | プラットフォームで削減。 |
| **学習的** | 新しい知識習得の負荷         | イネーブリングで支援。   |

### 認知負荷の警告サイン

- 「あのチームに聞かないと分からない」が頻発
- 同じ人が複数の領域で意思決定
- ドキュメントが追いつかない
- 新メンバーのオンボーディングに3ヶ月以上

### チームサイズと認知負荷

| チームサイズ | 認知負荷の許容量 | 担当可能なドメイン数 |
| :----------: | :--------------: | :------------------: |
|    3-4名     |        低        |          1           |
|    5-7名     |        中        |         1-2          |
|    8-9名     |        高        |      2（限界）       |
|   10名以上   |      過負荷      |      分割すべき      |

---

## 5.5 Wardley MappingおよびDDDとの統合

### 統合マトリクス

| Wardley段階 | DDDドメイン    | Teamタイプ                 | インタラクション     |
| ----------- | -------------- | -------------------------- | -------------------- |
| Genesis     | コア           | ストリームアラインド（小） | コラボレーション     |
| Custom      | コア           | ストリームアラインド       | ファシリテーティング |
| Product     | サポーティング | SA or コンプリケイテッド   | X-as-a-Service       |
| Commodity   | ジェネリック   | プラットフォーム           | X-as-a-Service       |

### 不整合のペナルティ

| 不整合                                | ペナルティ                         |
| ------------------------------------- | ---------------------------------- |
| Genesisをプラットフォームチームが担当 | 探索が阻害される（判定-2）         |
| コアドメインが3チームに分散           | 一貫性欠如、調整コスト増（判定-1） |
| 1チームが4ドメイン以上を担当          | 認知負荷崩壊（毎ターン離職判定）   |
| X-as-a-ServiceなしでCommodity連携     | 依存地獄（変更コスト2倍）          |

# 第6章: アクションカタログ

## 6.1 戦略アクション

| アクション           | コスト | 目標 | 成功効果                          | 失敗効果                 |
| -------------------- | :----: | :--: | --------------------------------- | ------------------------ |
| **Genesis投資**      |   3    |  8+  | 新Genesis追加                     | リソース消費のみ、学び+1 |

## 8.2 シナリオ0: 学習モード

### 概要

学習モードは、3つのフレームワークを**段階的に**学ぶためのチュートリアルです。
各レッスンで1つずつ概念を導入し、最後に統合演習を行います。

**判定は緩和されます**（全判定+2）。失敗しても学びを得ることに焦点を当てます。

## 8.6 シナリオ4: カスタム（あなたの組織）

### 概要

カスタムシナリオでは、**あなた自身の組織や状況**に基づいてゲームをプレイします。
これにより、学んだ概念を実際の課題に適用する練習ができます。

### カスタムシナリオ作成ガイド

以下のテンプレートに沿って、GMと一緒にシナリオを構築します。

#### ステップ1: 基本情報の設定

```
会社名: ____________________
業種: ____________________
規模: ____________________
目的（Purpose）: 「____________________」

現在の課題（1-3つ選択）:
□ 技術的負債が蓄積している
□ チーム間の連携がうまくいかない
□ 新規開発のスピードが遅い
□ レガシーシステムへの依存
□ 組織が急成長して混乱している
□ 競合に追いつかれている
□ 何がコアドメインか不明確
□ その他: ____________________
```

#### ステップ2: 初期状態の設定

GMと相談して、以下の数値を設定します。

| 項目               | 設定ガイド                                   |
| ------------------ | -------------------------------------------- |
| **リソース**       | 小規模: 8-12 / 中規模: 15-25 / 大規模: 30-50 |
| **技術的負債**     | 健全: 0-2 / 課題あり: 3-5 / 危機的: 6-8      |
| **慣性**           | なし: 0 / 軽微: 1-2 / 深刻: 3-5              |
| **フロー阻害要因** | 少ない: 1-2 / 中程度: 3-4 / 多い: 5+         |
| **ターン数**       | 短期: 4-5 / 中期: 6-8 / 長期: 10+            |

#### ステップ3: Wardley Mapの作成

あなたの組織のコンポーネントをリストアップし、進化段階を評価します。

```
[ユーザー: ____________________]
    │
    ├── ________________ ── [Genesis / Custom / Product / Commodity]
    ├── ________________ ── [Genesis / Custom / Product / Commodity]
    ├── ________________ ── [Genesis / Custom / Product / Commodity]
    ├── ________________ ── [Genesis / Custom / Product / Commodity]
    └── ________________ ── [Genesis / Custom / Product / Commodity]
```

**GMからの問い:**

- このコンポーネントは市場にどれくらい普及していますか？
- 競合は同じものを持っていますか？
- 外部サービスとして購入できますか？

#### ステップ4: サブドメインの分類

各コンポーネントをコア/サポーティング/ジェネリックに分類します。

| コンポーネント | 分類                | 理由 |
| -------------- | ------------------- | ---- |
|                | □コア □サポ □ジェネ |      |
|                | □コア □サポ □ジェネ |      |
|                | □コア □サポ □ジェネ |      |
|                | □コア □サポ □ジェネ |      |
|                | □コア □サポ □ジェネ |      |

**GMからの問い:**

- これは競合との差別化要因ですか？
- 外部サービスで代替可能ですか？
- 自社固有の要件がありますか？

#### ステップ5: チーム構成の記述

現在のチーム構成を記述します。

```
├── チーム名: ________________（__名）
│   └── 担当: ________________
│   └── 認知負荷: __ （計算式で算出）
│   └── タイプ: □SA □PF □EN □CSS
│   └── 課題: ________________
│
├── チーム名: ________________（__名）
│   └── 担当: ________________
│   └── 認知負荷: __
│   └── タイプ: □SA □PF □EN □CSS
│   └── 課題: ________________
│
└── （必要に応じて追加）
```

**認知負荷の計算:**

```
認知負荷 = (担当ドメイン数 × 2)
         + (曖昧な境界の数 × 1)
         + (複雑な依存関係の数 × 1)
         - (明確なチームAPI × 1)
         - (プラットフォームからの支援 × 1)
```

#### ステップ6: フロー阻害要因のリストアップ

現在、価値の流れを妨げている要因をリストアップします。

```
フロー阻害要因:
1. ________________
2. ________________
3. ________________
4. ________________
5. ________________
```

**典型的なフロー阻害要因:**

- 手動のデプロイプロセス
- 承認待ちの長さ
- チーム間の責任の曖昧さ
- ドキュメントの不足
- 特定の人への依存
- レガシーシステムとの連携の複雑さ
- テスト環境の不足

#### ステップ7: 目標の設定

```

5. ________________
```

#### ステップ8: 特殊ルールの設定（任意）


### カスタムシナリオ作成のヒント

| ポイント           | 説明                                       |
| ------------------ | ------------------------------------------ |
| **正直に書く**     | 美化せず、現実の課題を反映する             |
