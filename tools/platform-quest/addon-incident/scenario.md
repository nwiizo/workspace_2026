# Addon: Incident

> 「障害は起きる。それは確実だ。
>  問われるのは『起きた時、何を選ぶか』だけだ」

障害対応・ポストモーテム・信頼回復のアドオン。

---

## 1. 中核概念

### 1.1 インシデントの 5 フェーズ

```
┌────────────────────────────────────────────────────────┐
│  1. 検知 (Detect)        どれだけ早く気づくか             │
│      ↓                                                   │
│  2. 招集 (Assemble)      適切な人を集める                 │
│      ↓                                                   │
│  3. 抑制 (Mitigate)      まず被害を止める                 │
│      ↓                                                   │
│  4. 解決 (Resolve)       根本原因を直す                   │
│      ↓                                                   │
│  5. 学習 (Learn)         次に活かす（最も難しい）         │
└────────────────────────────────────────────────────────┘
```

### 1.2 ロール定義

| ロール | 責務 |
|---|---|
| インシデントコマンダー (IC) | 全体統制。技術判断には踏み込まない |
| Tech Lead | 技術的根本解決の主導 |
| Comms Lead | 利用者・経営層への情報発信 |
| Scribe | タイムライン記録 |
| Subject Matter Expert | 領域専門知識を提供 |

**IC は技術が最も詳しい人ではない**。
冷静で、調整能力があり、決断できる人。

### 1.3 ブレームレスの本気

```
× ブレームレス = 誰も叱らない
○ ブレームレス = なぜそういう判断・行動になったかの構造を問う

質問の作法:
  ❌ 「なぜチェックしなかったんですか？」
  ⭕ 「その時、どんな情報が見えていましたか？」
  ⭕ 「同じ状況なら、他の人も同じ判断をしたと思いますか？」
```

## 2. 追加リソースとイベント

### 2.1 追加リソース

| リソース | 説明 |
|---|---|
| MTTR | 平均解決時間 |
| MTTD | 平均検知時間 |
| ポストモーテム品質 | アクションアイテムの実行率 |

### 2.2 追加修正値

| 修正源 | 範囲 |
|---|---|
| IC 制度確立 + 訓練済み | +2 |
| Runbook 整備済み | +1 |
| 障害訓練 (chaos / GameDay) 実施 | +1 |
| 同種障害再発 | -2 |

### 2.3 追加気候イベント

| D6 | 気候 | 内容 |
|---|---|---|
| 1 | P1 障害 | 全社影響大の重大障害 |
| 2 | データロス疑い | データ破損の可能性 |
| 3 | 連鎖障害 | 1 サービスが他を巻き込む |
| 4 | 利用者離反警告 | 障害多発で離脱予告 |
| 5 | ポストモーテム未実施積み | アクション未消化が累積 |
| 6 | 平穏 | インシデントレス |

## 3. NPC

### 3.1 タクヤ（メインから・SRE リード）

このアドオンの主役。
IC 制度の設計と運用を率いる。

### 3.2 サキ（インシデントコマンダー専任・新規）

- 役割: 元 IT サービスマネジメント。IC 制度を導入
- セリフ:
  - 「IC は技術判断をしません。判断を**させます**」
  - 「『俺が直す』というシニアは、IC には向いていません」
- 特殊能力 **〈冷静な統制〉**: 関係値 +2 で、P1 障害気候の MTTR -30%

### 3.3 玲奈（メインから・CTO）

障害時の経営層対応窓口。

## 4. シナリオ 0: 学習モード

3 ターン。最初の IC ローテーション 1 サイクル。
学習補正 +2。

```
T0: サキ「IC ローテーションの最初の参加者、誰にします？」
  A) シニア SRE（経験豊富、忙しい）
  B) ミドル SRE（学習効果大）
  C) プラットフォームエンジニア（領域広い）
```

---

## 5. シナリオ 1: IC 制度の確立 （★★）

8 ターン。
- IC 訓練プログラム
- Runbook 整備
- 最初の P2 障害対応
- ポストモーテム文化

---

## 6. シナリオ 2: 大規模 P1 対応 （★★★）

10 ターン。全社影響の重大障害。
- 即時対応の意思決定
- 経営層・顧客への情報発信
- 二次被害の防止
- 復旧後の学び

---

## 7. シナリオ 3: 信頼の回復 （★★★★）

12 ターン。連続障害で信頼が失墜した状態から立て直す。
- 緊急対応と長期改善
- ステークホルダーへの説明
- 文化の再構築

## 8. バッドエンディング（7 種）

### 8.1 BAD-IC1: 検知の遅れ（技術軸）

> 終局条件: MTTD ≥ 30 分 + 利用者からの報告が先

```
顧客の Slack で初めて、あなたは障害を知った。
「うちの環境、もう 1 時間落ちてますけど？」

ダッシュボードはあった。誰も見ていなかった。
アラートはあった。誰も気づかなかった。
プラットフォームの「観測」は、ただの装飾だった。
```

### 8.2 BAD-IC2: 連鎖崩壊（技術軸）

> 終局条件: 1 障害が 3 サービス以上に波及 + 回避設計なし

```
1 つの DB の障害が、依存する 8 サービスを倒した。
そのうち 3 サービスは「依存していると認識されていなかった」。

復旧は雪だるま式に難しくなり、最終的に 12 時間かかった。
依存関係マップは、ホワイトボードの落書きだった。
```

### 8.3 BAD-IC3: ヒーロー型障害対応（組織軸）

> 終局条件: 障害対応がシニア 1-2 名に集中 + 燃え尽き

```
障害対応は、いつも同じ 2 人がやっていた。
深夜の Slack で、その 2 人だけが起きていた。
2 ヶ月後、1 人が辞めた。1 ヶ月後、もう 1 人が辞めた。

ヒーローに頼る運用は、ヒーローを使い潰した。
```

### 8.4 BAD-IC4: ブレーム文化（組織軸）

> 終局条件: ポストモーテムが「犯人探し」化

```
ポストモーテムは、糾弾大会になっていた。
「お前のせいで」「俺じゃない」。
正直なミス報告が消え、隠蔽が始まった。

ブレームレスを掲げながら、実態はブレームだった。
そして、ブレームは学習を殺した。
```

### 8.5 BAD-IC5: コミュニケーション崩壊（組織軸）

> 終局条件: 障害中の社内通知遅延 + 重複対応

```
障害中、3 つのチームが同じ問題を別々に調査していた。
情報共有はなく、対応は重複し、復旧は遅れた。
利用者への通知は、4 時間遅れた。

「誰がやっているか分からない」のは、誰もやっていないのと同じだった。
```

### 8.6 BAD-IC6: 障害コスト累積（経営財務軸）

> 終局条件: 障害による事業損失 高 + 経営層支持 ≤ -3

```
四半期の障害合計時間: 28 時間。
顧客 5 社が契約解除を通告した。

「99.5% の可用性」は、年間 44 時間まで許容されると経営は知っていた。
あなたが超えたのは、その許容の話ではなく、信頼の話だった。
```

### 8.7 BAD-IC7: 「障害は日常」文化（文化軸）

> 終局条件: 障害頻発に対する慣れ + 改善意欲低下

```
毎週どこかが燃えていた。
SRE は「またか」と言うようになった。
ポストモーテムは形式化し、アクションアイテムは未完のまま積もった。

障害は、改善の機会ではなく、日常の通勤になっていた。
```

### 8.8 BAD-IC未確定

組織固有のインシデント失敗が描写される。

## 9. グッドエンディング（4 種）

### 9.1 GOOD-IC1: 機械のような対応（技術軸）

> 達成条件: MTTR ≤ 30 分 + 同種再発 0

```
障害が起きた。
5 分で検知、3 分で IC アサイン、15 分で抑制完了。
そして、同種障害は二度と起きなかった。

それは奇跡ではなく、訓練と設計の結晶だった。
```

### 9.2 GOOD-IC2: IC 制度の組織化（組織軸）

> 達成条件: IC 訓練済み ≥ 10 名 + ローテーション持続

```
IC は、SRE だけのものではなくなった。
10 名以上のエンジニアが IC 訓練を受け、ローテーションに入っていた。
シニアは、もう深夜の英雄ではなく、後方支援だった。
```

### 9.3 GOOD-IC3: 障害は資産（経営財務軸）

> 達成条件: ポストモーテム由来の予防投資 ROI 高

```
過去 1 年のポストモーテムから生まれた改修が、
推定 5 億円の事業損失を防いでいた。

障害は、最も濃い学習機会だった。
そして、その学習は、確実に投資されていた。
```

### 9.4 GOOD-IC4: 「学ぶ組織」文化（文化軸）

> 達成条件: ブレームレス・ポストモーテムが組織標準化

```
他事業部のミーティングで、「これは PE 部のポストモーテム形式でやろう」と言われた。
ブレームレス、構造分析、アクションの実装。

プラットフォームチームの障害対応文化が、組織の標準になっていた。
```
