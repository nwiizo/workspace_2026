# Addon: Governance

> 「最も優れたガバナンスは、誰にも見えない。
>  違反しようとした時、自然に手が止まる。
>  そして、止まった理由が**理解できる**」

ガバナンス・コンプライアンス・信頼を速度と両立させるアドオン。

---

## 1. 中核概念

### 1.1 「埋め込み統制」の階層

```
┌────────────────────────────────────────────────────────┐
│ Layer A: 検出 (Detect)                                  │
│   違反が起きた後に気づく。最も弱い                       │
├────────────────────────────────────────────────────────┤
│ Layer B: 阻止 (Prevent)                                 │
│   違反を起こさせない。CI / Admission Controller        │
├────────────────────────────────────────────────────────┤
│ Layer C: 不可能化 (Make Impossible)                     │
│   そもそも違反の選択肢が存在しない。最強                │
├────────────────────────────────────────────────────────┤
│ Layer D: 自動修復 (Auto-Remediate)                      │
│   違反が起きても自動で正される                          │
└────────────────────────────────────────────────────────┘
```

**Layer A だけに頼ると「警察」になる**。
Layer B〜D を組み合わせる。

### 1.2 ゴールデンパスへの統制埋め込み

```
誤った設計:
  [テンプレ生成] → [審査] → [デプロイ承認] → [本番]
                    ↑ ここで詰まる

良い設計:
  [テンプレ生成 (統制込み)] → [自動チェック (CI)] → [本番]
                                ↑ 違反は CI で止まり、修正方法も提示
```

### 1.3 「No を言わない」セキュリティ

| 状況 | 旧来の対応 | 良い対応 |
|---|---|---|
| 例外要求 | NO | 「3 ヶ月の期限付き許可」 |
| 新クラウド機能 | 評価待ち（数ヶ月） | 「セーフリスト方式で段階開放」 |
| インシデント | 犯人探し | 「再発を不可能にする設計」 |

## 2. 追加リソースとイベント

### 2.1 追加リソース

| リソース | 説明 |
|---|---|
| コンプライアンス準拠度 | 監査・認証への準備度 |
| 統制摩擦 | 利用者が感じる「セキュリティの面倒さ」。低い方が良い |
| 例外負債 | 期限切れの例外承認の蓄積 |

### 2.2 追加修正値

| 修正源 | 範囲 |
|---|---|
| Policy as Code 化済み | +2 |
| ゴールデンパスに統制埋め込み済み | +2 |
| 統制がチケット制 | -2 |
| 例外承認に期限がない | -1 |

### 2.3 追加気候イベント

| D6 | 気候 | 内容 |
|---|---|---|
| 1 | 監査来訪 | SOC2 / ISMS 監査人来訪。準備度が試される |
| 2 | セキュリティインシデント | 軽微な情報漏洩疑い。対応で予算 -10 |
| 3 | 規制変更 | 新法対応必要。Privacy / AI Act 等 |
| 4 | 監査指摘 | 過去の例外が問題視される |
| 5 | 経営層の質問 | 「うちのコンプライアンス、大丈夫？」 |
| 6 | 認証取得 | SOC2 Type1 取得等の成果 |

## 3. NPC

### 3.1 ハルカ（メインから・セキュリティ）

このアドオンの主役。

- 特殊能力強化版 **〈統制埋め込みの達人〉**: 関係値 +3 で、監査気候を常時 1 段階弱める

### 3.2 ノブ（コンプライアンスオフィサー・新規）

- 役割: 法務出身。コンプライアンス全体の責任者
- セリフ:
  - 「規制は、技術ではなく事業の制約です」
  - 「監査人は敵じゃない。彼らは『見せ方』が分かる味方です」
- 特殊能力 **〈規制翻訳〉**: 関係値 +2 で、規制変更気候の被害 -50%

### 3.3 玲奈（メインから・CTO）

経営層の代弁者。
監査前は彼女の支持が極めて重要。

## 4. シナリオ 0: 学習モード

3 ターン。最初の OPA ポリシー 1 本を書く。
学習補正 +2。

```
T0: ハルカ「最初のポリシー、何にしますか？」
  A) S3 バケット公開禁止
  B) コンテナイメージの脆弱性スキャン必須
  C) 本番デプロイにレビュー必須
```

---

## 5. シナリオ 1: SOC2 Type1 取得 （★★）

8 ターン。半年で SOC2 Type1 監査に通る。
- 統制設計
- 監査ログの整備
- 監査人とのコミュニケーション
- ゴールデンパスへの埋め込み

---

## 6. シナリオ 2: 警察化阻止 （★★★）

10 ターン。あなたのチームが「許可部署」化し始めた。
- 例外承認プロセスの再設計
- セルフサービス化
- 信頼の回復

---

## 7. シナリオ 3: 規制大変動 （★★★★）

12 ターン。AI Act / 個人情報保護法改正で全社対応必要。
- 規制翻訳と影響評価
- スピード対応とリスク管理
- 経営層への説明

---

## 8. バッドエンディング（7 種）

### 8.1 BAD-GV1: 検出のみ依存（技術軸）

> 終局条件: Layer A のみ + 違反検出後の対応遅延

```
あなたは「ダッシュボード」を整えた。
違反は記録された。アラートは飛んだ。
そして、誰も対応しなかった。

検出は予防ではない。
報告書は厚く、現実は変わらなかった。
```

### 8.2 BAD-GV2: 例外負債の崩壊（技術軸）

> 終局条件: 期限切れ例外 ≥ 50 件 + 監査指摘

```
「とりあえず承認」した例外が積み重なった。
誰がいつ何を承認したか、誰も把握していなかった。
監査で指摘された時、あなたは説明できなかった。

例外承認は、ガバナンスの裏口だった。
裏口は、いつか開け放たれる。
```

### 8.3 BAD-GV3: 警察化（組織軸）

> 終局条件: 統制摩擦 高 + 信頼 ≤ -3

```
あなたのチームは「許可を出す部署」と呼ばれた。
新機能の審査に 1 ヶ月。例外申請に 3 ヶ月。
利用者は、あなたを通さずに済む方法を考え始めた。

シャドー IT は、官僚機構の必然的な副産物だった。
```

### 8.4 BAD-GV4: ハルカ離反（組織軸）

> 終局条件: ハルカ関係値 ≤ -1 + ゴールデンパス無統制

```
ハルカが言った。
「私の専門知識は、後付けで足されるだけなんですね」

そして転職した。
セキュリティは外部委託コンサルになり、
組織内の「速度と統制の翻訳者」は不在になった。
```

### 8.5 BAD-GV5: 監査不合格（経営財務軸）

> 終局条件: SOC2 Type2 不合格 + 大口契約失注

```
監査結果は不合格だった。
重要な顧客が、それを理由に契約更新を見送った。
売上が落ちた。

ガバナンスは、コストセンターではなかった。
それを軽視した瞬間、レベニュー直撃の問題になった。
```

### 8.6 BAD-GV6: 規制対応で機能凍結（経営財務軸）

> 終局条件: 規制対応工数 ≥ 全工数の 60% で 2 期連続

```
規制変更が連続した。
プラットフォームチームは規制対応に取られ続けた。
新規機能開発はゼロ。利用者からの要望は積み上がるだけ。

ガバナンスのために、プラットフォームが進化を止めた。
```

### 8.7 BAD-GV7: 「セキュリティ vs 開発」文化（文化軸）

> 終局条件: セキュリティ部署と開発部署の溝深刻化

```
開発者は「セキュリティが邪魔」と語り、
セキュリティは「開発者は脅威」と語った。
両者の Slack チャンネルは別れ、会議は対立の場になった。

統制は、敵対関係の中では成立しなかった。
```

### 8.8 BAD-GV未確定

組織固有のガバナンス失敗が描写される。

## 9. グッドエンディング（4 種）

### 9.1 GOOD-GV1: 見えない統制（技術軸）

> 達成条件: Policy as Code カバー率 ≥ 90% + 統制摩擦 低

```
利用者は「セキュリティ」を意識しなかった。
ただ、ゴールデンパスに乗れば、自然と統制を満たしていた。

ハルカは言った。「これが理想だった。私が**いない**ように見えるのが」
```

### 9.2 GOOD-GV2: 監査人の信頼（組織軸）

> 達成条件: 監査 3 回連続合格 + 重大指摘 0

```
監査人が「あなたの組織の統制設計は、業界の参照例にしたい」と言った。
SOC2 / ISMS / 各種認証が、すべて軽量に維持できていた。

統制は、文書ではなくコードになっていた。
それは監査人にとっても、開発者にとっても、福音だった。
```

### 9.3 GOOD-GV3: コンプライアンス ROI（経営財務軸）

> 達成条件: 認証取得 → 大口契約獲得 ≥ 3 件

```
営業が言った。「あの認証のおかげで、競合に勝てた」

ガバナンスは、ブレーキではなくアクセルだった。
それは事業の信頼を、数字で証明する装置だった。
```

### 9.4 GOOD-GV4: 「ハルカは仲間」（文化軸）

> 達成条件: ハルカ関係値 +3 + 開発者からセキュリティ相談 増加

```
開発者は、設計初期にハルカに相談するようになった。
「これ、後で監査で困りますか？」を、書く前に聞くようになった。

セキュリティと開発は、もう対立軸ではなかった。
同じ目的の、二つの視点だった。
```
