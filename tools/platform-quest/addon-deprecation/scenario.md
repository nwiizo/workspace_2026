# Addon: Deprecation

> 「新しいものを作るのは技術。古いものを終わらせるのは芸術」

機能廃止・移行戦略・信頼を保ったまま変えるアドオン。

---

## 1. 中核概念

### 1.1 廃止の 4 段階

```
┌──────────────────────────────────────────────────────────┐
│  1. 警告 (Announce)        N ヶ月後に廃止すると予告        │
│       ↓                                                    │
│  2. 移行支援 (Assist)      新版への移行ツール・サポート    │
│       ↓                                                    │
│  3. 凍結 (Freeze)          新規利用停止、既存利用は継続    │
│       ↓                                                    │
│  4. 削除 (Remove)          完全停止                       │
└──────────────────────────────────────────────────────────┘
```

各段階のリードタイムは、影響度と利用者数で決まる。
**目安: 重要機能なら 12 ヶ月。軽い機能でも 3 ヶ月**。

### 1.2 廃止判断のマトリクス

| 利用者数 | コスト | 判断 |
|---|---|---|
| 多 | 高 | 段階的置換。即時廃止禁止 |
| 多 | 低 | 維持。「動いているなら触らない」 |
| 少 | 高 | 即時廃止候補 |
| 少 | 低 | 静かに残す or 棚卸し |

### 1.3 通知の作法

| 悪い例 | 良い例 |
|---|---|
| 「3 月末に廃止します」 | 「3 月末に廃止します。理由は X。移行は Y で。困ったら Z へ」 |
| メールで 1 回送信 | 複数チャネル・複数回・段階的に強度上昇 |
| 「ドキュメントを読んでください」 | 影響リポジトリへの自動 PR を用意 |

## 2. 追加リソースとイベント

### 2.1 追加リソース

| リソース | 説明 |
|---|---|
| 廃止予告残期間 | 各機能の廃止までの月数 |
| 移行率 | 旧 → 新への移行完了比率 |
| レガシー負債 | 廃止判断保留の累積 |

### 2.2 追加修正値

| 修正源 | 範囲 |
|---|---|
| 廃止予告 6 ヶ月以上前 | +1 |
| 自動移行ツール提供 | +2 |
| 即時廃止強行 | -3 |
| 影響利用者への個別連絡 | +1 |

### 2.3 追加気候イベント

| D6 | 気候 | 内容 |
|---|---|---|
| 1 | 廃止反発 | 利用者から強い反発 |
| 2 | 廃止漏れ | 廃止後に「使ってた」連絡 |
| 3 | レガシー保守要求 | 「廃止予告のものを残せ」 |
| 4 | 廃止コスト発覚 | 廃止対応のコスト想定オーバー |
| 5 | 移行支援不足 | 移行ツールが不十分 |
| 6 | スムーズ廃止 | 期日通り完了 |

## 3. NPC

### 3.1 シノ（addon-golden-path から）

テンプレートの廃止判断を率いる。

### 3.2 イサミ（レガシー機能オーナー・新規）

- 役割: 元 Mobile API 基盤の管理者。今は廃止対象を持つ
- セリフ:
  - 「『動いてるんだから』は、廃止しない理由にはならない」
  - 「ただし、廃止する正当な理由を、私は欲しい」
- 特殊能力 **〈レガシー処理〉**: 関係値 +2 で、レガシー保守要求気候 -50%

### 3.3 ケンジ（メインから）

最も反発する利用者。
彼を説得できるかが鍵。

## 4. シナリオ 0: 学習モード

3 ターン。最初の廃止予告を 1 件出す。
学習補正 +2。

```
T0: イサミ「最初に廃止する機能、どれにします？」
  A) 利用者 5 名以下の小機能
  B) コスト高だが影響中規模の機能
  C) 影響大だが安全性問題ある機能
```

## 8. バッドエンディング（7 種）

### 8.1 BAD-DC1: 強行廃止（技術軸）

> 終局条件: 通知不十分な廃止 + 本番障害

```
廃止予告は 2 週間前にメール 1 通だった。
廃止当日、5 つのサービスが落ちた。

経営は緊急対応を求め、廃止はロールバックされた。
あなたの信頼は、廃止された機能と一緒に消えた。
```

### 8.2 BAD-DC2: 移行ツール不備（技術軸）

> 終局条件: 移行支援不十分 + 利用者の移行労力 過大

```
廃止予告はあった。移行方法は文書化されていた。
ただ、移行を手動で 100 リポジトリやれと言われ、利用者は怒った。

「廃止します。移行はあなたの責任です」は、
責任転嫁の言葉だった。
```

### 8.3 BAD-DC3: ゾンビ機能（技術軸）

> 終局条件: 廃止予告 ≥ 1 年経過したが廃止できず

```
廃止予告から 14 ヶ月。
まだ 30 のリポジトリが旧機能を使っていた。
廃止延期、再延期、再々延期。

廃止予告は、組織内で「無視していい予定」になっていた。
```

### 8.4 BAD-DC4: 廃止疲労（組織軸）

> 終局条件: 廃止予告連発 + 利用者が変更追従不能

```
四半期に 5 つの廃止予告。
利用者は「もうこのプラットフォームの未来が見えない」と言った。
信頼は失われ、新規利用は止まった。
```

### 8.5 BAD-DC5: イサミ離反（組織軸）

> 終局条件: イサミ関係値 ≤ -1 + 廃止判断強行

```
イサミは「私の領域を、私を通さずに決める組織は怖い」と言った。
そして去った。

レガシー機能の知識は、彼の頭の中にしかなかった。
あなたは、廃止すべき機能の中身が分からなくなった。
```

### 8.6 BAD-DC6: 廃止コスト超過（経営財務軸）

> 終局条件: 廃止対応工数 ≥ 元機能保守工数

```
「廃止すれば楽になる」と計画した。
廃止対応に、保守の 3 倍の工数を要した。
そして、経営は「廃止しない方が安かった」と気づいた。
```

### 8.7 BAD-DC7: 「信頼の傷」文化（文化軸）

> 終局条件: 過去廃止のトラウマ + 新機能採用率低

```
「あの機能、また廃止されるかも」
利用者は、新機能に乗ることを躊躇するようになった。

廃止の失敗は、廃止された機能だけでなく、
未来の機能の信頼まで奪っていた。
```

### 8.8 BAD-DC未確定

組織固有の廃止失敗が描写される。

## 9. グッドエンディング（4 種）

### 9.1 GOOD-DC1: 静かな廃止（技術軸）

> 達成条件: 主要機能廃止 + 影響障害 0 + 移行率 ≥ 95%

```
廃止当日、何も起きなかった。
利用者は、すでに新版に移行していた。
旧機能を呼び出すコードは、自動移行ツールが書き換えていた。

廃止は、最も静かな成功だった。
```

### 9.2 GOOD-DC2: 大規模整理の達成（組織軸）

> 達成条件: 20+ 機能廃止完了 + プラットフォーム機能数 適正化

```
1 年で 20 の旧機能を廃止した。
プラットフォームは、軽くなった。
保守工数は減り、新機能に投資できる余裕ができた。

「捨てる」が、プラットフォームの能力になった。
```

### 9.3 GOOD-DC3: 廃止 ROI（経営財務軸）

> 達成条件: 廃止によるコスト削減累計 + 工数削減

```
廃止された 20 機能の累積コスト削減: 月 800 万円。
保守工数削減: 月 30 人日。

「廃止」は、価値創出の能力だった。
```

### 9.4 GOOD-DC4: 「信頼の廃止」文化（文化軸）

> 達成条件: 廃止予告に利用者が冷静対応 + 新機能採用率高

```
新しい廃止予告が出た。
利用者は「ああ、また来たね」と冷静に対応した。
「ちゃんと予告された通り、ちゃんと移行できた」が、組織の経験値になっていた。

廃止は、信頼を試すイベントではなく、
信頼を**証明する**イベントになった。
```
