# Addon: Product Thinking

> 「私たちはずっと『最高のツール』を作ろうとしていた。
>  ある日、誰も使っていないことに気づいた。
>  最高のツールではなく、**誰かの一日が変わるもの**を作るべきだった」

プラットフォームを**プロダクト**として扱う思考と実践を扱うアドオン。

---

## 1. 中核概念

### 1.1 社内プラットフォームの 5 つの誤解

```
┌─────────────────────────────────────────────────────────────┐
│  ❌ ユーザーは社内だから「使ってもらえる」                       │
│      → 社内ユーザーは最も冷酷な批評家。代替手段を作る力を持つ    │
│                                                              │
│  ❌ 機能を増やせば価値が増す                                    │
│      → 認知負荷は機能数の二乗で増える                          │
│                                                              │
│  ❌ アジャイルだから要件は後で決まる                            │
│      → 顧客の問題定義こそ最も時間をかける部分                   │
│                                                              │
│  ❌ ベストプラクティスに従えば良い                              │
│      → 「あなたの組織にとっての最善」を発見するのが仕事         │
│                                                              │
│  ❌ プラットフォームの成功 = 採用数                            │
│      → 強制された採用は採用ではない                            │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 JTBD（Jobs To Be Done）の社内翻訳

```
社外プロダクト   :「ユーザーは何のために雇うか」
社内プラットフォーム:「開発者は何をやらされたくないか」
```

**社内における主な Job**

| Job | 例 |
|---|---|
| 「これを学ばずに済ませたい」 | Kubernetes の細部、IAMポリシー文法 |
| 「これを覚えていなくて済ませたい」 | 監視・ログ設定、シークレット管理 |
| 「これを正しくやれている自信が欲しい」 | セキュリティ要件、コスト最適化 |
| 「これに時間を取られたくない」 | 環境構築、デプロイ承認 |

プラットフォームの機能は、これらの Job に**直接トレース**できなければならない。

### 1.3 PMF（社内版）の指標

```
社内 PMF = (自発的利用) × (NPS) × (代替手段選択しない率)
```

3 つの要素が揃って初めて PMF と呼ぶ。
1 つでも欠けると「使ってもらえているが、使われたいわけではない」状態。

## 2. 追加リソースとイベント

### 2.1 追加リソース

| リソース | 説明 |
|---|---|
| ユーザーインサイト | 0-100。インタビュー・サーベイで増える。判定 +1 効果 |
| 仮説検証カウンタ | 各機能の仮説が検証されたかを追跡 |

### 2.2 追加修正値

| 修正源 | 範囲 |
|---|---|
| プロダクトインタビュー実施済み機能 | +2 |
| 仮説が未検証の機能リリース | -2 |
| ペルソナ定義あり | +1 |
| アウトカムKPI設定あり | +1 |

### 2.3 追加気候イベント

| D6 | 気候 | 内容 |
|---|---|---|
| 1 | 採用却下 | 主要チームが「使わない」と通告。インサイト不足が露呈 |
| 2 | 隠れた利用者出現 | 想定外のチームが使っていた。インサイト +20 |
| 3 | 競合発見 | OSS / SaaS が同等機能を提供。差別化問いに直面 |
| 4 | フィードバック洪水 | 機能要求が殺到。優先度判断を迫られる |
| 5 | 沈黙 | 誰も何も言わない。**最も恐ろしい状態** |
| 6 | アハ体験 | 利用者が「これがあって助かった」と語る。信頼 +2 |

## 3. NPC

### 3.1 アスカ（プラットフォーム PdM）

メインから引き継ぎ。このアドオンが主戦場。

- 特殊能力強化版 **〈深層インサイト〉**: 関係値 +2 以上で、隠れた利用者を 1 ターン早く検知

### 3.2 マユミ（リサーチ担当・新規）

- 役割: 元 UX リサーチャー。社内に常駐する珍しい存在
- セリフ:
  - 「『使い方を教える』前に『何に困っているか』を聞きませんか」
  - 「ペルソナは想像で作らないでください。観察で作ります」
- 関係値の動き:
  - +1: 1 on 1 リサーチを設定した、観察セッションに同席した
  - -1: 「サーベイで十分」と言った、サンプル N=3 で結論を急いだ
- 特殊能力 **〈観察の眼〉**: 関係値 +2 で、利用者の本音判定 +2

### 3.3 ケンジ（メインから登場）

- このアドオンでは「最も声の大きい利用者」として登場
- 彼の本当の Job を見抜けるかが鍵

## 4. シナリオ 0: 学習モード

### 開幕

```
T0: アスカが最初の機能ロードマップ案を持ってきた。

アスカ「いま、3 つの機能を提案できます。どれをやりますか」
  A) CI/CDテンプレート集（全エンジニアが使う）
  B) 自動コスト可視化（経営層が喜ぶ）
  C) ユーザーインタビュー 10 件（成果が出るまで 1 ヶ月）

学習モード補正: +2
```

C を選ぶと「インタビューだけで予算を 1 ヶ月使う」決断の重みが学べる。
A・B を選んだ場合、3 ターン後に「使われない」結末を体験する。

## 5. シナリオ 1: 最初のユーザーリサーチ （★★）

8 ターン。あなたは予算 50・時間 1 四半期で、
プラットフォームの方向性を決めるリサーチを実施する。

主な決断:
- インタビュー対象の選定基準（パワーユーザー / ジュニア / 経営層）
- リサーチ手法（1on1 / 観察 / サーベイ / 障害分析）
- ロードマップ草案の発表タイミング

---

## 6. シナリオ 2: ロードマップの戦争 （★★★）

10 ターン。複数の事業部から相反する要求が来る。
プロダクト思考でどう交通整理するか。

主な決断:
- 「No」を言う方法（理由付け、代替提案）
- ペルソナ優先度の交渉
- ステークホルダー説明会の設計

---

## 7. シナリオ 3: PMF 直前の崖 （★★★★）

12 ターン。「採用率は上がっているが、NPS は下がっている」現象。
プロダクト思考の真価が問われる。

主な決断:
- 「強制採用」した機能の撤回判断
- パワーユーザーの離反阻止
- ロードマップの大幅修正と経営層への説明

## 8. バッドエンディング（7 種）

### 8.1 BAD-PT1: 機能インフレ（技術軸）

> 終局条件: リリース機能 ≥ 15 かつ NPS ≤ -10

```
四半期に機能リリース 8 件。あなたのチームは誇らしげだった。
そして、誰もそれらを使っていなかった。

利用者は「次の機能、自分には関係ない」と聞き流すようになった。
あなたのロードマップは「やったことリスト」になり、
未来を語る力を失っていた。
```

### 8.2 BAD-PT2: 想像のペルソナ（技術軸）

> 終局条件: ユーザーインサイト ≤ 20 かつ 失敗機能 ≥ 3

```
ペルソナは存在した。スライドにきれいに描かれていた。
ただ、それは社内で**実在しない**人物だった。

「典型的なエンジニア」を想定した機能は、
誰の Job も解かなかった。
あなたは想像の中の理想ユーザーのために働き続けた。
現実のユーザーは、別のツールに移っていた。
```

### 8.3 BAD-PT3: PdM 孤立（組織軸）

> 終局条件: アスカ関係値 ≤ -1 かつ 仮説検証カウンタ ≤ 2

```
アスカが言った。
「私の仕事は、機能を承認するスタンプ係でしょうか」

そして去った。
PdM ロールは「あった方が良いポジション」のままだった。
リサーチは中断され、機能優先度はあなたの直感で決まった。
直感は、データの代わりにはならなかった。
```

### 8.4 BAD-PT4: ステークホルダー混乱（組織軸）

> 終局条件: 経営層支持 ≤ -2 かつ ロードマップ変更 ≥ 4 回

```
「結局、プラットフォームチームは何を作ろうとしているの？」
経営会議で、その質問は 3 ヶ月連続で出た。

毎月変わるロードマップは、コミットメントを失っていた。
利用者は「どうせまた変わる」と機能要求を出さなくなった。
プロダクト思考は、優柔不断の言い訳になっていた。
```

### 8.5 BAD-PT5: ROI 不可視（経営財務軸）

> 終局条件: アウトカムKPI未設定 + 経営層支持 ≤ -3

```
「リサーチを 6 ヶ月やったって聞いたけど、何が分かったの？」

あなたは答えに詰まった。
インサイトはあった。ただ、それを**事業の数字**と接続できなかった。
経営は「リサーチ予算は半分にする」と決めた。
プロダクト思考は、コストセンターの装飾品になった。
```

### 8.6 BAD-PT6: PMF 妄想（経営財務軸）

> 終局条件: 採用率 ≥ 80% かつ NPS ≤ 0 で 3 ターン継続

```
レポートには「採用率 85%」と書かれていた。
あなたはそれを成功と呼んだ。

そして、ある朝、6 つのチームが同時に独自基盤の Slack チャンネルを作った。
強制された採用は、いつか反動を呼ぶ。
あなたの PMF は、PMF ではなかった。
**Procurement Market Force**（調達市場の力）だっただけだ。
```

### 8.7 BAD-PT7: リサーチの罠（文化軸）

> 終局条件: インタビュー実施 ≥ 30 かつ リリース機能 ≤ 2

```
あなたは聞き続けた。
3 ヶ月。半年。1 年。
インタビューは止まらず、機能は止まり続けた。

リサーチは「決めないための言い訳」になっていた。
利用者は「あの人たち、いつになったら作るんだろう」と語り、
プラットフォームチームは「最も詳しいが、最も作らない部署」になった。
```

### 8.8 BAD-PT未確定

あなたの組織で起きた固有の失敗を AI が描写する。

## 9. グッドエンディング（4 種）

### 9.1 GOOD-PT1: 「使う理由」の発見（技術軸）

> 達成条件: 自発的利用率 ≥ 70% かつ 仮説検証カウンタ ≥ 10

```
ケンジが言った。
「あんたたちの基盤に乗ったら、俺の週末が戻ってきた」

それは機能の数ではなく、Job の解消の話だった。
あなたは何を作らないかを学び、
利用者は何を諦めなくて済むかを学んだ。
```

### 9.2 GOOD-PT2: PdM のホーム（組織軸）

> 達成条件: アスカ関係値 +3 かつ ロードマップ承認率 ≥ 90%

```
アスカは「PdM の月例会」を社内で立ち上げた。
プラットフォーム PdM 以外のプロダクト PdM も参加した。
「うちのプラットフォームには、ちゃんと PdM がいる」が、
組織の文化になった。

プラットフォームは、エンジニアリングではなく、
プロダクトの言語で語られるようになった。
```

### 9.3 GOOD-PT3: ROI 連動の証明（経営財務軸）

> 達成条件: アウトカムKPI ≥ 3 個 かつ 各KPI事業指標と連動

```
「PE のロードマップが、事業のロードマップとリンクしている」

CFO レビューで、その一文が共有された。
あなたのチームは、もはや「コストセンター」ではなく、
事業を加速する**梃子**として認識されていた。
予算交渉は議論ではなく、合意になった。
```

### 9.4 GOOD-PT4: 「私たちが頼む」文化（文化軸）

> 達成条件: 利用者からのフィードバック PR ≥ 10 件

```
PR が届く。Issue が立つ。Slack で「これ、プラットフォームに入れたい」と相談が来る。

利用者は、もう「待つ側」ではなかった。
彼らは**共同オーナー**になっていた。
そしてあなたは、彼らを信頼する勇気を持っていた。
```
