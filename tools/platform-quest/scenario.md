# Platform Quest

> 「最高のプラットフォームは、誰にも気づかれない。
>  ただ、それがなくなった瞬間に、組織は呼吸の仕方を忘れる。」

開発者に愛され、組織を倍力する**内部プラットフォーム**を構築・運用・進化させる
戦略シミュレーションRPG。

---

## 1. 世界観

あなたは急成長中のテック企業 **Aurora.inc** に新設された
プラットフォームエンジニアリングチームのリードに着任した。

```
┌─────────────────────────────────────────────────────────────┐
│                    Aurora.inc 現状                            │
├─────────────────────────────────────────────────────────────┤
│  従業員: 800名（うちエンジニア 250名）                          │
│  プロダクト: B2B SaaS 3本 + 社内向け基幹 5本                    │
│  クラウド: AWS + GCP（部署ごとに使い分け）                       │
│                                                              │
│  痛み:                                                        │
│  ・各チームが「独自のCI/CD」「独自のTerraform」「独自の監視」     │
│  ・新規エンジニアのオンボーディングに3週間以上                    │
│  ・本番リリースは「インフラチームのチケット」が必要                 │
│  ・クラウド費が前年比 +180%。経営は説明を求めている               │
│  ・SRE が3人。全プロダクトの障害対応で常に消耗                    │
│                                                              │
│  あなたへの期待（CTOから）:                                     │
│  「プラットフォームエンジニアリング、はじめてくれ。               │
│   開発者が自分で動ける状態を作ってほしい。                       │
│   ただし、コストとガバナンスからは目を逸らさないで。」             │
└─────────────────────────────────────────────────────────────┘
```

あなたに与えられた最初のリソース:

- プラットフォームエンジニア 4名（うち2名はインフラから異動希望）
- 初年度予算 1.2億円
- CTOからの直接レポートライン
- そして、**まだ「プラットフォーム」が何なのか合意していない経営層と開発者たち**

このゲームは、あなたが意思決定を重ね、リソースを動かし、
気候（外圧）を凌ぎ、最終的に **どんなプラットフォームを作り上げたか** を物語る。

## 2. 中核概念

### 2.1 プラットフォームエンジニアリングの 4 つの柱

```
              ┌─────────────────────────────┐
              │   プロダクトとしてのプラットフォーム  │
              │      （Product Thinking）         │
              └──────────────┬──────────────┘
                             │
        ┌────────────────────┼────────────────────┐
        │                    │                    │
        ▼                    ▼                    ▼
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│ 認知負荷の削減 │    │ セルフサービス │    │  進化的設計    │
│  Cognitive   │    │  Self-Service │    │  Evolution    │
│    Load      │    │              │    │              │
└──────────────┘    └──────────────┘    └──────────────┘
        │                    │                    │
        └────────────────────┼────────────────────┘
                             ▼
                  ┌─────────────────────┐
                  │ アウトカム志向の経営   │
                  │  （Outcome-Driven）  │
                  └─────────────────────┘
```

**4つの柱が崩れると何が起きるか**

| 崩れた柱 | 症状 |
|---|---|
| プロダクト思考 | 「使う人がいない高機能な何か」が完成する |
| 認知負荷削減 | 開発者が逃げ、シャドーITに分裂する |
| セルフサービス | プラットフォームチームがチケットの奴隷になる |
| 進化的設計 | 3年で陳腐化し、誰も触りたがらないレガシーになる |
| アウトカム志向 | 機能数とコスト最適化が目的化し、事業から切断される |

### 2.2 プラットフォームの成熟度モデル

```
Lv0  混沌期      各チームが独自に何でもやっている
Lv1  標準化期   ベストプラクティスが文書化される（が強制力はない）
Lv2  共通化期   共有基盤（CI/CD・監視等）が一部チームで使われ始める
Lv3  プロダクト期 IDP・ゴールデンパス・コントロールプレーンが整う
Lv4  内製プロダクト期 利用チームが「いつ使うか」を自分で判断できる
Lv5  プラットフォームエコシステム期 利用者が機能を提案・実装する
```

ゲームは原則 **Lv0 → Lv3 まで** を扱う。
Lv4-5 は addon-ai-augmented 等の上位アドオンで扱う。

### 2.3 ケイパビリティモデル

「**プラットフォームは機能の集合ではなく、ケイパビリティの集合**」

| ケイパビリティ層 | 内容 |
|---|---|
| Foundation | ネットワーク・IAM・基盤クラウド・コスト基盤 |
| Runtime | コンテナ実行・サーバレス・データ基盤 |
| Delivery | CI/CD・テンプレート・ゴールデンパス |
| Observability | メトリクス・ログ・トレース・SLO |
| Governance | ポリシー・コンプライアンス・監査 |
| Experience | ポータル・ドキュメント・サポート |

シナリオ進行中、あなたは **どの層を、どの順序で、どこまで** 積むかを決める。

## 3. ゲーム機構

### 3.1 リソース

あなたは以下のリソースを管理する。値は概ね -10 〜 +100 の範囲で動く。

```
┌────────────────────┬─────────┬─────────────────────────────┐
│ リソース            │ 初期値   │ 説明                         │
├────────────────────┼─────────┼─────────────────────────────┤
│ 予算 (Budget)       │   60    │ 0で行動不能。100で投資余力大   │
│ 開発者信頼度 (Trust) │   ±0    │ -5でシャドーIT発生            │
│ 認知負荷 (Load)     │   +3    │ 低い方が良い。+7で離脱始まる   │
│ 経営層支持 (Exec)   │   ±0    │ -3で予算削減リスク            │
│ 成熟度 (Maturity)   │   10    │ 0-100。Lv換算は10/30/50/70/90 │
│ 技術的負債 (Debt)   │   20    │ 高いほどイベント被害が拡大     │
│ モメンタム          │    0    │ 0-5。成功で増え、消費で恩恵    │
└────────────────────┴─────────┴─────────────────────────────┘
```

**閾値による状態遷移**

| 条件 | 状態 | 効果 |
|---|---|---|
| 信頼 ≤ -5 | シャドーIT発生 | 主要チームが独自ツール構築開始。成熟度ペナ |
| 認知負荷 ≥ +7 | 開発者離脱 | 新規利用チームが増えない |
| 経営層支持 ≤ -3 | 予算監視 | 予算減衰イベントが追加 |
| 技術的負債 ≥ 60 | 運用麻痺 | あらゆる行動に -1 修正 |
| 予算 ≤ 0 | 即時バッドエンディング判定 | エンディングフェーズへ |

### 3.2 判定システム（2D6）

行動を試みるとき、2D6 を振り、以下の修正値を加える。

```
ベース判定 = 2D6 + 関連リソース修正 + NPC関係値 + モメンタム消費

結果:
  ・ 6 以下     失敗（リソースが減る、悪化）
  ・ 7〜9       部分成功（成果は出るが代償あり）
  ・ 10〜11     成功（狙い通りの成果）
  ・ 12 以上    大成功（追加ボーナス、関係値+1）
```

**主な修正値**

| 修正源 | 範囲 |
|---|---|
| プロダクト思考に沿った行動 | +1 |
| データに基づく行動（計測あり） | +1 |
| 主要利用者を巻き込んだ行動 | +1 |
| 認知負荷が高い状態での行動 | -1 |
| 経営層支持が低い状態 | -1 |
| 技術的負債 ≥ 60 | -1 |
| 独断専行（NPC関係値を聞かず動く） | -2 |

### 3.3 モメンタムシステム

成功・大成功でモメンタム +1（上限 5）。消費して以下のいずれか:

- 判定 +2 補正（事前宣言）
- 気候イベントを 1 回スキップ
- 「集中投資」: 1ターンで2行動できる
- 「サクセスストーリー化」: 経営層支持 +1 / モメンタム 2 消費

### 3.4 気候イベント（D6）

毎ターン開始時に D6 を振り、外圧を決定する。

| D6 | 気候 | 内容 |
|---|---|---|
| 1 | **障害発生** | 主要サービスで障害。信頼 -1、対応で予算 -5 |
| 2 | **採用急増** | 新規エンジニア大量入社。認知負荷 +2、機会も増加 |
| 3 | **クラウドコスト急騰** | 経営層支持 -2。FinOps対応を迫られる |
| 4 | **監査・コンプライアンス要求** | ガバナンス整備を強制。負債 +5 or 機能凍結 |
| 5 | **ROI 質問** | 経営層が成果説明を要求。説明できないと支持 -2 |
| 6 | **追い風** | 平穏。または利用者から賛辞。信頼 +1 |

**気候の重ね合わせ**: Expert 難易度では D6 を 2 回振り、両方適用。

### 3.5 ターンの流れ

```
┌──────────────────────────────────────────────────────────┐
│ 1. 気候イベント（D6）                                       │
│ 2. NPC からの相談・要望（1〜2件）                            │
│ 3. プレイヤー行動宣言（A/B/C から選択 or 自由記述）           │
│ 4. 判定（2D6 + 修正）                                       │
│ 5. 結果の反映（リソース、関係値、成熟度）                     │
│ 6. ターン終了サマリー                                        │
└──────────────────────────────────────────────────────────┘
```

1シナリオ = 8〜15 ターンで終局を迎える。

## 4. NPC

各 NPC は **関係値（-3 〜 +3）** と **特殊能力** を持つ。
関係値はあなたの行動・発言で増減し、判定に直接加算される。

### 4.1 玲奈（CTO・経営層スポンサー）

- 役割: あなたの直接上司。経営層と現場の橋渡し
- セリフ:
  - 「数字で語れないなら、経営会議には連れて行けない」
  - 「失敗してもいい。ただし、失敗から何を学んだかは説明して」
- 関係値の動き:
  - +1: ROI・効率指標を提示した、経営層に主体的に説明した
  - -1: 「とりあえずやってみる」を主語にした、コスト話を避けた
- 特殊能力 **〈経営層交渉〉**: 関係値+2以上で、ROI気候イベントを 1 回スキップ可

### 4.2 ケンジ（Payments チーム テックリード・主要利用者代表）

- 役割: 最も忙しく、最も口が悪く、最も影響力のある利用者
- セリフ:
  - 「あんたたちのプラットフォーム、うちのチームが使う理由を 1 分で説明してくれ」
  - 「俺たちは自分で Terraform 書ける。共通基盤に乗るメリットを示せ」
- 関係値の動き:
  - +1: Payments チームの具体的な痛みを起点にした、初期から巻き込んだ
  - -1: 「全社標準だから」で説得した、トップダウン強制を示唆した
- 特殊能力 **〈利用者代弁〉**: 関係値+2以上で、他の利用チーム判定に +1

### 4.3 アスカ（プラットフォーム PdM）

- 役割: あなたが Lv1 達成時に採用できる。プラットフォームをプロダクトとして見る目
- セリフ:
  - 「機能を作る前に、誰がどう困っているかを聞いてきます」
  - 「ロードマップに『たぶん必要』は書かない方針です」
- 関係値の動き:
  - +1: ユーザーインタビューを組み込んだ、定量データを取りに行った
  - -1: 機能数を成果指標にした、PdMを通さず機能を約束した
- 特殊能力 **〈プロダクト思考〉**: 関係値+2以上で、プロダクト判定に常時 +1

### 4.4 タクヤ（SRE リード）

- 役割: 3人の SRE のリーダー。疲弊しているが、誰よりプラットフォームを必要としている
- セリフ:
  - 「俺たちが運用を引き取らない設計にしてくれ。頼む」
  - 「SLO のない機能は、約束のない契約だ」
- 関係値の動き:
  - +1: SLO・運用引き継ぎを設計に組み込んだ、SRE工数を予算化した
  - -1: 「動いたから完成」で済ませた、SREに丸投げした
- 特殊能力 **〈信頼性の砦〉**: 関係値+2以上で、障害気候イベントの被害 -50%

### 4.5 ハルカ（セキュリティ・コンプライアンス）

- 役割: 監査・SOC2・個人情報。NO とは言わないが、条件を積む
- セリフ:
  - 「セキュリティは速度の対義語じゃない。**未制御**が速度の対義語よ」
  - 「ゴールデンパスに統制を埋めてくれれば、私は満足」
- 関係値の動き:
  - +1: ガバナンスをゴールデンパスに統合した、監査ログを設計から織り込んだ
  - -1: 後付けでセキュリティを足した、例外申請を仕組み化しなかった
- 特殊能力 **〈統制の埋め込み〉**: 関係値+2以上で、監査気候イベントを 1 回無効化

### 4.6 ユウト（ジュニア開発者・新規入社）

- 役割: 入社 3 ヶ月目。あなたのプラットフォームの**最初のユーザー体験**を映す鏡
- セリフ:
  - 「ドキュメント、どこから読めば...」
  - 「READMEに書いてあったコマンド、動かないんですが」
- 関係値の動き:
  - +1: オンボーディング体験を磨いた、ドキュメントを更新した
  - -1: 「Slackで聞いて」で済ませた、初回成功体験を設計しなかった
- 特殊能力 **〈認知負荷の鏡〉**: 関係値+2以上で、認知負荷の早期警告（+5を超える前に通知）

### 4.7 NPC関係値による判定への影響

| 関係値 | 判定修正 |
|---|---|
| +3 | +2（最大） |
| +1 〜 +2 | +1 |
| -1 〜 0 | ±0 |
| -2 | -1 |
| -3 | -2（最大） |

複数 NPC が関係する判定では、関係値の **平均** を加える（小数切り捨て）。

## 5. シナリオ 0: 学習モード

**チュートリアル**。3 ターンでゲームの基本ループを体感する。
全判定に **+2 のチュートリアル補正**。

### 開幕

```
T0: 着任初日。
CTO 玲奈があなたを役員フロアの会議室に呼んだ。

玲奈「ようこそ。プラットフォーム、頼んだよ。
     ...で、何から始める？」

選択肢:
  A) 主要プロダクトチーム3つにヒアリングする
  B) 既存の CI/CD・監視・IaC を棚卸しする
  C) まず 6 ヶ月のロードマップを書いて経営層に承認を取る

### 判定例（A を選択）

```
判定: 2D6 + プロダクト思考 +1 + チュートリアル +2 = 結果
  → 出目 8 + 3 = 11 (成功)

結果:
  ・ ケンジ（Payments）: 関係値 +1
  ・ 開発者信頼度: +1
  ・ 認知負荷: ±0
  ・ モメンタム: +1
  ・ 「Payments チームは独自Terraformを持っているが、
     セキュリティパッチ追従に疲れている」と判明
```

### T1〜T2: 気候イベントと意思決定

T1 で D6 を振り、最初の外圧を体験。

### 学習モード終了条件

3 ターン経過、または成熟度 15 達成で終了。

## 6. シナリオ 1: グリーンフィールド （★★）

### 設定

**プラットフォームをゼロから構築できる**、滅多にない機会。
ただし、既存事業の運用も並行する。

```
┌──────────────────────────────────────────────────────────────┐
│  Helios 立ち上げの制約:                                         │
│                                                                │
│  ・ 6 ヶ月で MVP リリース必須                                    │
│  ・ クラウド予算: 月 800 万円（既存事業の 1/3）                   │
│  ・ チーム: あなた + プラットフォームエンジニア4名 + Helios側10名 │
│  ・ コンプライアンス: 個人情報を扱う。SOC2 Type1 を年内取得       │
│                                                                │

└──────────────────────────────────────────────────────────────┘
```

### 開始リソース

```
予算: 70 / 信頼: 0 / 認知負荷: 2 / 経営支持: +1 / 成熟度: 5 / 負債: 5

| ターン | 主な分岐 |

| T9-T10 | 第二利用チーム（既存事業）の引き込み判断 |

## 7. シナリオ 2: 影武者DevOps脱却 （★★★）

### 設定

Aurora.inc には**すでに 5 つの「自称プラットフォーム」が存在する**。
各事業部が独自に作った CI/CD・IaC モジュール・監視基盤。
あなたの任務は「これらを統合する」こと。**ゼロから作るより難しい**。

```
┌──────────────────────────────────────────────────────────────┐
│  既存の「自称プラットフォーム」たち:                              │
│                                                                │
│  ・ Payments基盤  : Terraform + ArgoCD + Datadog。完成度高い   │
│  ・ Search基盤    : Pulumi + GitHub Actions。スクリプト混在    │
│  ・ Analytics基盤 : 半分手動。1名のシニアに依存                  │
│  ・ Mobile API基盤: 完全に GitOps。所有者は退職済み              │
│  ・ Legacy基盤    : 10 年前から動いている。誰も触りたくない      │
│                                                                │
│  各オーナーは「自分のが一番良い」と思っている。                   │
│  全員を統合しようとすれば全員が敵に回る。                         │
└──────────────────────────────────────────────────────────────┘
```

### 開始リソース

```
予算: 55 / 信頼: -1 / 認知負荷: 5 / 経営支持: 0 / 成熟度: 25 / 負債: 45
```

### 主要決断ポイント

| ターン | 主な分岐 |
|---|---|
| T1-T2 | 統合戦略: ベスト・オブ・ブリード / 共通母艦 / 段階的吸収 |
| T3-T4 | 最初のターゲット選定（強い基盤 or 弱い基盤 or 中間） |
| T5-T6 | 統合中の障害発生。誰のせいにするか、誰が直すか |
| T7-T8 | Legacy 基盤の所有権獲得交渉 |
| T9-T10 | 「自分の基盤の方が良い」と反乱を起こす利用者 |
| T11-T12 | 経営層から「もう完成？」の質問 |
| T13-T14 | 全社移行マイルストーン投票 |
| T15 | 終局: 統合か、共存か、敗走か |

## 9. バッドエンディング（10 種）

終局条件のいずれかを満たすと、対応するエンディングが描かれる。
複数条件が同時に成立した場合は、より早く・より深刻な条件のものが優先される。

### 9.1 技術軸

#### BAD-T1: ゴールデンケージ

> 終局条件: 認知負荷 ≥ +8 かつ 成熟度 ≥ 50

```
あなたは「正しい使い方」を完璧に定義したプラットフォームを作り上げた。
ドキュメントは網羅的で、テンプレートは美しく、ガードレールは完璧だった。

そして開発者は窒息した。

「やりたいこと」と「やれること」の距離は遠ざかり、
「逸脱したいだけ」のチームが Slack で結託し始めた。
あなたのプラットフォームは黄金の檻になった。
最も優秀なエンジニアから、檻の外で仕事を見つけ始めた。
```

#### BAD-T2: シャドーIT分裂

> 終局条件: 開発者信頼度 ≤ -5 が 3 ターン継続

```
3 つの事業部が、同じ週に「うちは独自基盤に戻す」と通告した。
あなたが説得に行った時、彼らは静かに笑った。

「議論は終わったんですよ。我々の生産性で証明します」

半年後、Aurora.inc には 6 つの「プラットフォーム」が並走していた。
あなたのチームの仕事は「公式の遺産を守ること」になった。
```

#### BAD-T3: コントロールプレーン融解

> 終局条件: シナリオ3で技術的負債 ≥ 80 かつ大規模障害発生

```
コントロールプレーンが落ちた。

それは一つの API ではなかった。
コントロールプレーンが、すべてのデプロイ、すべての監視、
すべてのシークレット供給を担っていた。

復旧に 14 時間。失った信頼は、年単位。
ポストモーテムには「単一障害点を作ったのは誰か」とは書けなかった。
それはあなただったから。
```

### 9.2 組織軸

#### BAD-O1: 燃え尽き分解

> 終局条件: SRE/プラットフォームチームメンバー残存 ≤ 2

```
タクヤが辞めた。
翌週、プラットフォームエンジニア 2 名が同時に辞めた。
あなたが追加採用を始めた時、業界はすでに知っていた——
「Aurora の PE は地獄らしい」と。

残った 2 名は、毎日チケットを捌くだけのチームになった。
プラットフォームは凍結された。
そして、ゆっくり腐り始めた。
```

#### BAD-O2: プラットフォーム警察化

> 終局条件: ガバナンス強度高 かつ 信頼 ≤ -3

```
あなたのチームは、いつしか「許可を出す部署」になっていた。
新機能リクエストには 30 日の審査。例外申請には 2 ヶ月。

開発者はあなたを「コンプライアンス警察」と呼んだ。
経営層は「あの部署、何のためにあるんだっけ？」と言い始めた。
プラットフォームは、もはやプロダクトではなく、官僚機構だった。
```

#### BAD-O3: サイロ強化

> 終局条件: 主要利用チーム 50% 以上が「独自運用」を選択

```
皮肉だった。
プラットフォームを作るという仕事が、サイロを強化していた。

各チームは「あの基盤は使わない理由」を蓄積し、
組織図には「シャドープラットフォームチーム」が複数生まれた。
あなたが「統合しましょう」と言うたびに、彼らは丁寧に予定を断った。

統合の意志はあった。統合する力は、誰にもなかった。
```

### 9.3 経営・財務軸

#### BAD-F1: 黒字シャットダウン

> 終局条件: 経営層支持 ≤ -4 かつ ROI 説明失敗 3 回

```
取締役会の議事録の一行に、すべてが書かれていた。

「プラットフォームエンジニアリング部の解体、
 機能は各事業部に分散吸収。」

あなたのプラットフォームは動いていた。
障害も少なく、利用者の評判も悪くなかった。
ただ、**経営は「これがなぜ必要か」を最後まで理解しなかった**。

数字で語れなかった。それだけだった。
```

#### BAD-F2: 青天井クラウド破産

> 終局条件: クラウドコスト気候を 4 回以上対処失敗

```
四半期報告で、CFO が一枚のグラフを示した。
「クラウド費の伸びが、売上の伸びを 2 倍上回っています」

経営は緊急コスト削減委員会を発足し、
あなたのチームはそこに「説明者」として呼ばれ続けた。
新規機能開発は凍結。すべてのリソースが「コスト削減」に振られた。

プラットフォームは、最適化されすぎて、誰の問題も解かなくなった。
```

### 9.4 文化・人間軸

#### BAD-C1: 信仰の崩壊

> 終局条件: モメンタム 0 が連続 5 ターン かつ 成功判定 < 30%

```
誰もあなたの会議に来なくなった。
最初は「忙しいから」。次は「議題に関係ないから」。
最後は「あの人の言うこと、もう信じないから」。

プラットフォームは存在し続けた。
ただ、それを **信じている人** が、組織から消えていた。
あなたは正しいことを言い続けたかもしれない。
ただ、組織はもう、あなたの正しさに付き合う体力がなかった。
```

#### BAD-C2: ナレッジディアスポラ

> 終局条件: シニア離職 3 名 かつ ドキュメント化スコア低

```
退職者の Slack DM に、こう書かれていた:
「次の人に必要な知識は、もう俺の頭の中にしか残ってないんだ。
 ごめんな」

ドキュメントは古く、テストカバレッジは低く、
誰もが「なんとなく動くから触らない」と決めた領域が増えた。
プラットフォームは生きていた。
ただ、それを **修復できる人間** が、地上にいなくなった。
```

#### BAD-未確定: 別の終わり方

> あなたが選んだ道が上記のいずれにも当てはまらない場合、
> AI は新しいエンディングを描写する。リソース・関係値・直近の決断から、
> 「あなたの組織で起きた、固有の失敗」をナラティブで提示する。

## 10. グッドエンディング（7 種）

### 10.1 技術軸

#### GOOD-T1: ゴールデンパスの定着

> 達成条件: 成熟度 ≥ 70 かつ 認知負荷 ≤ +3

```
新規エンジニアが入社した翌日、ユウトが微笑んで言った。
「先輩、これ、READMEを読まなくても動きました」

ゴールデンパスは「正しい道」ではなく「自然な道」になっていた。
逸脱したい者は逸脱できた。ただ、ほとんどの場合、
ゴールデンパスの先に、彼らが求めていた答えがあった。

あなたのプラットフォームは、もはや教えられる必要がなかった。
```

#### GOOD-T2: 自己進化プラットフォーム

> 達成条件: 成熟度 ≥ 80 かつ 利用者からのコントリビューション ≥ 5

```
Pull Request が届いた。Payments チームのケンジから。
「うちの障害対応で気づいた。ここにこんな機能があれば、
 みんな助かるはず。書いてみた」

それは初めての「利用者からの機能追加」だった。
半年後、利用者コントリビューションは月10件を超えていた。
プラットフォームチームは、レビューと方向付けに時間を使った。
あなたは、もはや一人で背負っていなかった。
```

### 10.2 組織軸

#### GOOD-O1: 倍力装置（Force Multiplier）

> 達成条件: 経営層支持 ≥ +3 かつ デリバリ速度メトリクス改善 ≥ 2x

```
CFO レビューで、玲奈が一つのスライドを出した:
「PE 導入後、エンジニア 1 人あたりのデリバリ速度: 2.4 倍」

数字は冷たく、説明はシンプルだった。
プラットフォームは、もはや経費ではなく、てこ（lever）だった。
あなたのチームの予算は次年度 1.5 倍になった。
あなたはそれを「もっと採用に」ではなく「もっと利用者調査に」と使った。
```

#### GOOD-O2: 組織の中の中央銀行

> 達成条件: 全社主要事業部の 80% 以上がプラットフォーム利用

```
新しい事業部長会で、誰かが言った。
「これ、プラットフォームで何ができるか聞いてからにしません？」

それは皮肉ではなく、自然な反射だった。
プラットフォームは、組織の意思決定の前提になっていた。
あなたのチームは「拒否権」ではなく「選択肢」を提供していた。
そして、それが組織を一つにしていた。
```

### 10.3 経営・財務軸

#### GOOD-F1: 投資ROI の証明

> 達成条件: 投資回収係数 ≥ 3x （クラウドコスト削減 + 開発工数削減）

```
取締役会で、玲奈がスライドを出した。
「プラットフォームへの累積投資: 6.8 億円。
 効率化と削減による累積ベネフィット: 24 億円」

経営は質問しなかった。彼らは、もう理解していた。
「次年度、もっと投資して良いか？」と聞かれた時、
あなたは「投資先のリストを持ってきます」と答えた。
そのリストには、まだ作っていない未来があった。
```

### 10.4 文化・人間軸

#### GOOD-C1: 「私たちのプラットフォーム」

> 達成条件: 開発者信頼度 ≥ +5 かつ 利用者NPS ≥ +40

```
全社オールハンズで、ケンジが手を挙げた。
「俺、最初はあのチームに敵対してたんだけど。今は、
 あれを **俺たちのプラットフォーム** だって言いたいんだ」

それは小さな代名詞の変化だった。
「あなたたちの」から「私たちの」へ。
プラットフォームチームと利用者の境界は、その日、溶けた。
```

#### GOOD-C2: 伝説のプラットフォームチーム

> 達成条件: 全グッドエンディング達成条件のうち 5 つ以上を同時に満たす

```
3 年後、退職したあなたの元に、業界誌から取材依頼が来た。
「Aurora.inc のプラットフォームチームは、業界の参照実装と呼ばれています。
 何を意識して作ったのですか？」

あなたは少し考えて、こう答えた。
「機能ではなく、人を見ました。
 ツールではなく、信頼を作りました。
 そして、いつも『この機能、本当に作らない方が良いんじゃないか？』を、
 自分に問い続けました」
```
