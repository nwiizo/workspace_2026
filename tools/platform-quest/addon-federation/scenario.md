# Addon: Federation

> 「単一の脳が世界を動かす設計は、その脳が壊れた瞬間に世界が止まる」

フェデレーテッドコントロールプレーン、マルチリージョン展開のアドオン。

---

## 1. 中核概念

### 1.1 トポロジー選択

```
Hub & Spoke              Mesh                  Hierarchical
                                                       
   [Hub]                A ─── B            [Global Hub]
   /│\                  │ × │              /          \
  / │ \                 C ─── D       [Region1]   [Region2]
 A  B  C                                  /  \        /  \
                                         L1   L2    L3   L4
```

| トポロジー | 強み | 弱み |
|---|---|---|
| Hub & Spoke | 単純、運用容易 | Hub が単一障害点 |
| Mesh | 障害局所化 | 整合性が複雑 |
| Hierarchical | スケール容易 | 階層間の摩擦 |

### 1.2 整合性と可用性

```
CAP 定理の現実版:
  全リージョン一致 + 高可用 + 分断耐性 → 全部は無理

  選択:
   A) Strong Consistency + 一部停止許容（金融系）
   B) Eventually Consistent + 高可用（一般 SaaS）
   C) Per-Region Authority（規制対応・地理戦略）
```

### 1.3 ローカル vs グローバルの責務

| 領域 | 推奨 |
|---|---|
| IAM / 認証 | Global |
| 認可ポリシー | Global (定義) + Local (適用) |
| ワークロード | Local |
| データ | Local + 必要に応じてレプリカ |
| 監視・SLO | Local (一次) + Global (集約) |

## 3. NPC

### 3.1 アンナ（フェデレーションアーキテクト・新規）

- 役割: 元 CDN 企業。グローバル設計のベテラン
- セリフ:
  - 「単一障害点を作らないのは、技術ではなく規律です」
  - 「整合性モデルは、設計の前に**書け**」
- 特殊能力 **〈分散設計〉**: 関係値 +2 で、リージョン障害気候 -50%

### 3.2 リョウ（addon-control-plane から）

CP 設計者として、フェデレーション設計を主導。

### 3.3 玲奈（メインから・CTO）

事業のグローバル戦略を背負っている。
データレジデンシーの圧力源。

## 8. バッドエンディング（7 種）

### 8.1 BAD-FD1: Hub 融解（技術軸）

> 終局条件: Hub 単一障害点 + Hub 障害 + 全リージョン停止

```
Hub が落ちた。
すべてのリージョンが、新規デプロイも、変更も、観測も失った。
復旧 9 時間。

「フェデレーション」という言葉は使えたが、
実装は「分散した単一障害点」だった。
```

### 8.2 BAD-FD2: スプリットブレイン（技術軸）

> 終局条件: ネットワーク分断時に複数リージョンで Authority 主張

```
ネットワーク分断中、両リージョンが「自分が正しい」と動いた。
復旧後、同じユーザーが 2 つの設定を持っていた。
データのマージは手作業で 2 週間かかった。

整合性モデルは、書類にしか書かれていなかった。
```

### 8.3 BAD-FD3: レイテンシ災害（技術軸）

> 終局条件: グローバル CP コール多 + 利用者レイテンシ苦情多

```
すべての変更が Hub を経由した。
東京の利用者は、Hub（US）まで往復し、デプロイに 8 秒かかった。
「もういい」と言って、独自基盤を立てた事業部が出た。
```

### 8.4 BAD-FD4: リージョン責任者孤立（組織軸）

> 終局条件: ローカル CP 責任者の権限と責任の不整合

```
リージョン責任者は名目だけだった。
判断はすべて Hub 経由。緊急時の対応も、Hub の許可待ち。
責任者は退職した。
リージョンは、責任の空白地帯になった。
```

### 8.5 BAD-FD5: 地政学崩壊（組織軸）

> 終局条件: データレジデンシー要件 + 既存設計が満たさない

```
新法律で「自国データは自国に置け」。
あなたのアーキテクチャは、それを満たさなかった。
3 ヶ月の停止と再設計を強いられた。

地政学リスクは、技術問題として最後にやってくる。
ただ、来たときは最も重い。
```

### 8.6 BAD-FD6: マルチリージョンコスト破綻（経営財務軸）

> 終局条件: リージョン数 ≥ 5 + 利用率均等にならず + コスト過剰

```
5 リージョンに展開した。
4 つは閑古鳥だった。
最低稼働コストだけで、月 3,000 万円が消えていった。

「グローバル対応」は、コスト名分の麻薬だった。
```

### 8.7 BAD-FD7: 「うちのリージョンは別」文化（文化軸）

> 終局条件: リージョン毎の運用差異 顕著 + 標準化失敗

```
各リージョンの運用が分岐した。
「US はこうやる」「EU は違う」「APAC は独自」。

3 年後、グローバル研修ができなくなっていた。
全リージョンで通用するエンジニアが、いなくなった。
```

### 8.8 BAD-FD未確定

組織固有のフェデレーション失敗が描写される。

## 9. グッドエンディング（4 種）

### 9.1 GOOD-FD1: リージョン障害無影響（技術軸）

> 達成条件: リージョン障害発生時の他リージョン無影響継続 ≥ 3 回

```
US-East の AZ 全滅で、他リージョンは無事だった。
利用者は気づかなかった。トラフィックは自動で他リージョンに流れていた。

爆心距離は、最小だった。
```

### 9.2 GOOD-FD2: グローバル整合性の達成（技術軸）

> 達成条件: 整合性違反 0 + マルチリージョン展開 ≥ 4

```
4 リージョン稼働、整合性違反ゼロ。
グローバルポリシーは 30 分以内に全リージョンに伝播していた。

整合性モデルは、書類ではなく、コードとテストになっていた。
```

### 9.3 GOOD-FD3: グローバル投資 ROI（経営財務軸）

> 達成条件: 海外売上比率 ↑ + クラウドコスト効率維持

```
新リージョン展開が、海外顧客獲得を加速した。
1 リージョン追加につき、売上 +15%、コスト +5%。

フェデレーションは、事業の梃子になっていた。
```

### 9.4 GOOD-FD4: 「リージョンは家族」文化（文化軸）

> 達成条件: リージョン間のエンジニア交流 + 共通言語

```
US と EU と APAC のエンジニアが、同じ用語、同じツール、同じ運用で動いていた。
週次のリージョン横断ミーティングは、活気があった。

組織は、地理的に分散しながら、文化的に統合されていた。
```
