# Addon: Cost / FinOps

> 「コストは技術問題でも財務問題でもない。
>  それは**意思決定の問題**である」

FinOps・チャージバック・コスト透明性のアドオン。

---

## 1. 中核概念

### 1.1 コスト按分モデル

```
┌─────────────────────────────────────────────────────────┐
│  Showback   コストを「見せる」だけ。請求はしない          │
│              → 文化変革、軽い第一歩                     │
├─────────────────────────────────────────────────────────┤
│  Chargeback コストを利用部署に請求                       │
│              → 行動変容大、政治コスト大                 │
├─────────────────────────────────────────────────────────┤
│  Full Cost  プラットフォームの間接費まで含めて配賦       │
│              → 完全な経済モデル、運用負荷高             │
└─────────────────────────────────────────────────────────┘
```

### 1.2 ユニットエコノミクスの実装

```
プラットフォームコスト / 主要ビジネスユニット

例:
  1 取引あたりのプラットフォームコスト
  1 アクティブユーザーあたりの基盤コスト
  1 デプロイあたりの CI/CD コスト
```

事業の単位コストとリンクさせることで、
プラットフォーム投資が事業にどう響くか議論できる。

### 1.3 タグ戦略の鉄則

1. **設計が運用に先立つ**: タグ設計はインフラ作成前に
2. **コードで強制**: タグ未設定リソース作成不可
3. **進化を計画**: タグスキーマ変更の影響を予測
4. **同義語を作らない**: env=prod と Environment=production を分けない

タグ戦略の失敗は、後から修正が極めて困難。

## 2. 追加リソースとイベント

### 2.1 追加リソース

| リソース | 説明 |
|---|---|
| コスト透明性 | 利用者が自分のコストを把握できる度合い |
| 単価効率 | 単位ユニットあたりコストの推移 |
| 予算順守度 | 予算 vs 実績の精度 |

### 2.2 追加修正値

| 修正源 | 範囲 |
|---|---|
| Showback / Chargeback 実装済み | +2 |
| タグ強制 + 100% 網羅 | +2 |
| クラウドコストの理由を即答できる | +1 |
| タグ未設定リソース ≥ 20% | -2 |

### 2.3 追加気候イベント

| D6 | 気候 | 内容 |
|---|---|---|
| 1 | クラウド請求書ショック | 想定 +50%。CFO 緊急召喚 |
| 2 | 利用者の反発 | チャージバック導入で激しい反発 |
| 3 | コミットメント期限 | RI/SP の更新期限 |
| 4 | コスト最適化期限 | 経営層から削減目標 |
| 5 | 単価交渉 | クラウドベンダーと値引き交渉 |
| 6 | 平穏 | コスト推移が予測通り |

## 3. NPC

### 3.1 ナナミ（FinOps リード・新規）

- 役割: 元 CFO 配下の財務出身。コストとエンジニアの翻訳者
- セリフ:
  - 「コストは制約ではなく、優先度の翻訳です」
  - 「見せない費用は、ない費用と同じ。それが一番危険」
- 特殊能力 **〈財務翻訳〉**: 関係値 +2 で、ROI 気候イベントの被害 -50%

### 3.2 玲奈（メインから・CTO）

CFO との橋渡し。
ナナミと密に連携できるか。

### 3.3 ケンジ（メインから）

最大の利用者にしてコスト消費者。
チャージバックの最初の対象になりうる。

## 8. バッドエンディング（7 種）

### 8.1 BAD-CO1: タグカオス（技術軸）

> 終局条件: タグカバー率 ≤ 60% + 按分不能

```
タグは「いつかやる」ことだった。
3 年後、按分を試みた時、半分のリソースが「unknown」だった。

タグなしリソースは、責任不明のコストだった。
そして、責任不明のものは、削減できなかった。
```

### 8.2 BAD-CO2: コミット過剰（技術軸）

> 終局条件: RI/SP 過剰購入 + 利用率 ≤ 60%

```
「3 年コミットで 40% 割引」に飛びついた。
2 年目、サービスが移行され、コミット分が遊んだ。
3 年目、コミット解約不可で、無駄な数千万を払い続けた。

コミットメントは、未来予測に賭ける契約だった。
```

### 8.3 BAD-CO3: コスト見える化反発（組織軸）

> 終局条件: チャージバック導入失敗 + 経営層支持 ≤ -2

```
「うちはコスト管理してるのに、急に請求するな」
「按分ロジックが不公平」

3 つの事業部が抵抗し、CFO の支持も揺らいだ。
Chargeback はロールバックされ、コスト議論は霧の中に戻った。
```

### 8.4 BAD-CO4: FinOps 孤立（組織軸）

> 終局条件: ナナミ関係値 ≤ -1 + コスト議論断絶

```
ナナミは「データはあります、ただ、誰も見ません」と嘆いた。
そして去った。

コスト議論は、再び勘と政治で行われるようになった。
レポートは作られたが、開かれることはなかった。
```

### 8.5 BAD-CO5: 削減病（経営財務軸）

> 終局条件: コスト削減目的化 + 機能停滞 + 利用者離反

```
四半期目標は「コスト 20% 削減」だった。
プラットフォームチームは、コスト削減だけに専念した。
新機能はゼロ。利用者は「使えなくなった機能」を嘆いた。

コスト最適化は、価値創造を食い始めた。
```

### 8.6 BAD-CO6: ベンダー高騰（経営財務軸）

> 終局条件: ベンダー単価交渉失敗 + ロックイン

```
クラウドベンダーが値上げを通告した。
あなたは交渉した。負けた。
別ベンダーへの移行は、もはや 1 年がかりの大事業だった。

ロックインは、コスト交渉の力を失わせた。
```

### 8.7 BAD-CO7: 「あいつのせい」文化（文化軸）

> 終局条件: チャージバック後にチーム間非難文化 蔓延

```
コストレポートは「犯人探し」になっていた。
「あのチームが使いすぎ」「いや、あっちの方が」。
協調は消え、コスト最適化は責任のなすりつけ合いになった。
```

### 8.8 BAD-CO未確定

組織固有のコスト失敗が描写される。

## 9. グッドエンディング（4 種）

### 9.1 GOOD-CO1: コスト自治の達成（技術軸）

> 達成条件: チャージバック導入 + 各チームが自主最適化

```
各チームが、自分のダッシュボードを開いていた。
「今月はあと 200 万円使える」「ここは削れる」と判断し、行動していた。

コスト管理は、プラットフォームチームの仕事ではなくなった。
それは、組織全体の言語になっていた。
```

### 9.2 GOOD-CO2: タグ完全網羅（技術軸）

> 達成条件: タグ網羅率 ≥ 99% + 按分精度 高

```
クラウド請求書のすべてが、3 階層のタグで分類されていた。
「unknown」は 0%。

按分は議論ではなく、データの参照になっていた。
```

### 9.3 GOOD-CO3: ユニット効率の改善（経営財務軸）

> 達成条件: 単位ユニットコスト 半減 + 事業利益率 改善

```
取引 1 件あたりのプラットフォームコストが、3 年で半減した。
ベンダー交渉、アーキテクチャ最適化、利用者の自治。
3 つの組み合わせが、確実な改善を作っていた。

CFO は「FinOps は投資以上のリターンを返している」と言った。
```

### 9.4 GOOD-CO4: 「コストは選択」文化（文化軸）

> 達成条件: コスト議論に開発者が積極参加

```
スタンドアップで「これコストどれくらい？」が普通の質問になった。
コストは、後から請求されるものではなく、設計段階で考えるものになった。

ナナミは言った。「これが目指していた世界です」
```
