# Addon: Golden Path

> 「最高のゴールデンパスは、誰にも気づかれない。
>  気づくのは、それを外れた人だけ。
>  そして外れた人は、戻ってこられなければならない」

ゴールデンパス、テンプレート、スキャフォールドを設計するアドオン。

---

## 1. 中核概念

### 1.1 ゴールデンパス と ガードレール

```
┌────────────────────────────────────────────────────────────┐
│                                                              │
│   ガードレール  ───────────────────────────────              │
│       ↓                                                       │
│   ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─            │
│                                                              │
│                ╔══════════════════╗                         │
│                ║                  ║                         │
│                ║  ゴールデンパス     ║   ← 自然に通る道       │
│                ║                  ║                         │
│                ╚══════════════════╝                         │
│                                                              │
│   ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─            │
│       ↑                                                       │
│   ガードレール  ───────────────────────────────              │
└────────────────────────────────────────────────────────────┘

ゴールデンパスを外れる自由はある。
だが、外れる「コスト」がガードレールを越えた時の責任になる。
```

### 1.2 設計原則

| 原則 | 説明 |
|---|---|
| 90/10 規則 | 90% のケースで困らない設計を、10% の例外は明示的に許す |
| 摩擦のグラデーション | 順方向は摩擦ゼロ、逸脱は段階的に摩擦増 |
| 戻りやすさ | 逸脱した後でも、戻る道が必ずある |
| 学習不要 | 「READMEを読まなくても動く」が初期到達点 |
| 文書はゴール、コードは現実 | 文書化は重要だが、最良の文書は実行可能な雛形 |

### 1.3 段階的成熟

```
Lv0  README に「こうやれ」が書いてある
Lv1  CLI が1コマンドでテンプレ生成
Lv2  Backstage 等のポータルから3クリックで生成
Lv3  生成物が自動でデプロイ可能で、SLO/監視/CIすべて入る
Lv4  生成物がアップデート可能（テンプレ進化が伝播）
Lv5  利用者がテンプレを編集してPR返してくる
```

## 2. 追加リソースとイベント

### 2.1 追加リソース

| リソース | 説明 |
|---|---|
| GP 採用率 | ゴールデンパス経由のデプロイ比率 |
| 逸脱コスト | 逸脱者が直面する追加作業の重さ（軽すぎても重すぎてもダメ） |

### 2.2 追加修正値

| 修正源 | 範囲 |
|---|---|
| 90/10 規則に従っている | +1 |
| テンプレートをユーザーと共作 | +2 |
| 逸脱を犯罪化（罰則化）した | -2 |
| 例外申請プロセスを設けず | -1 |

### 2.3 追加気候イベント

| D6 | 気候 | 内容 |
|---|---|---|
| 1 | パワーユーザーの逸脱 | 影響力ある利用者がテンプレを外れる |
| 2 | テンプレ陳腐化 | クラウド機能更新でテンプレが時代遅れに |
| 3 | テンプレ衝突 | 複数の「公式テンプレ」が乱立 |
| 4 | 新人入社ラッシュ | テンプレの良し悪しがオンボーディング時間に直結 |
| 5 | リファクタ依頼 | 旧テンプレ利用者の新版移行が必要に |
| 6 | アハ体験 | 「これでデプロイできました」と感謝が届く |

## 3. NPC

### 3.1 シノ（テンプレートメンテナ・新規）

- 役割: ゴールデンパスを最も愛し、最も恐れる人。テンプレートの所有者
- セリフ:
  - 「テンプレートは一度作って終わりじゃないんです」
  - 「90% のチームに最適で、残り 10% を排除しない設計が、私の戦場です」
- 特殊能力 **〈テンプレ進化〉**: 関係値 +2 で、テンプレ陳腐化イベントの被害 -75%

### 3.2 ケンジ（メインから）

- このアドオンでは「最も逸脱したがる」ユーザーとして登場
- 彼を黄金の道に「自然に」誘導できるか

### 3.3 ユウト（メインから）

- 「ゴールデンパスの最初のユーザー」として登場
- 彼がテンプレで何分でデプロイできたかが KPI になる

---

## 4. シナリオ 0: 学習モード

3 ターンで「最初のテンプレート 1 本」を作る体験。
学習補正 +2。

```
T0: シノが言った。
「最初のテンプレ、何にしますか？」
  A) Web API (Node.js / Go / Python から選択)
  B) 非同期ワーカー
  C) フロントエンド SPA
```

選んだものの「失敗パターン」と「成功パターン」を 3 ターンで体験する。

---

## 5. シナリオ 1: 最初のテンプレート （★★）

8 ターン。Lv0 から Lv2 までの旅。
- 何を含めるか・含めないかの議論
- 監視・ロギング・CIの埋め込み
- 「3 分で本番デプロイ」のチャレンジ

---

## 6. シナリオ 2: 逸脱者との対話 （★★★）

10 ターン。パワーユーザーが堂々と逸脱を始めた。
- 罰するか、聞きに行くか
- テンプレを変えるか、ガードレールを上げるか
- 「逸脱した結果、テンプレが進化した」シナリオへ導けるか

---

## 7. シナリオ 3: テンプレ進化のジレンマ （★★★★）

12 ターン。100 個のリポジトリが旧テンプレで動いている。
- 新版へのマイグレーション戦略
- 自動更新 PR の信頼性
- 「旧版でもいい」ユーザーへの説明

---

## 8. バッドエンディング（7 種）

### 8.1 BAD-GP1: 黄金の檻（技術軸）

> 終局条件: 逸脱コスト過大 かつ NPS ≤ -10

```
あなたのテンプレは美しかった。
ベストプラクティスのすべてが入っていた。

そして、開発者は「触れないテンプレ」を「使わないテンプレ」と呼んだ。
逸脱は事実上禁止され、新しいアイディアは外で生まれた。
ゴールデンパスは、誰も歩かない黄金の床になった。
```

### 8.2 BAD-GP2: テンプレ墓場（技術軸）

> 終局条件: 公式テンプレ ≥ 8 種 かつ 利用率分散 大

```
3 年で 12 個のテンプレが生まれた。
誰がどれを使うかは慣習でしか決まらず、
新人は「どれを選べばいいですか」と毎週聞いた。

テンプレを増やすことが仕事になり、
テンプレを淘汰する勇気は、誰も持たなかった。
```

### 8.3 BAD-GP3: メンテ放棄（組織軸）

> 終局条件: シノ離職 または テンプレ更新 0 回 / 半年

```
シノが燃え尽きた。
「私一人で、これは無理です」

テンプレは凍結された。
利用者は「最新クラウド機能を使えない」と不満を言い、
独自実装に走り始めた。
ゴールデンパスは、化石になった。
```

### 8.4 BAD-GP4: 政治テンプレ（組織軸）

> 終局条件: 複数事業部間のテンプレ綱引きで合意失敗

```
「うちの事業部はうちのテンプレを推す」
「うちは別の方が良い」

テンプレは政治の道具になった。
標準化の議論は止まり、各事業部は自分の好みを推し続けた。
公式テンプレは形骸化し、影武者テンプレが主流になった。
```

### 8.5 BAD-GP5: テンプレ ROI 失敗（経営財務軸）

> 終局条件: テンプレ開発予算超過 かつ 採用率 ≤ 30%

```
テンプレに 1 年と予算を費やした。
そして、誰も使わなかった。

経営は「投資対効果は？」と聞き、
あなたは答えを持っていなかった。
テンプレは美しい遺物として、社内 GitHub に静かに眠った。
```

### 8.6 BAD-GP6: 強制移行の崩壊（経営財務軸）

> 終局条件: 全社移行強制 + 失敗 + 経営層支持 ≤ -3

```
あなたは「全チーム新テンプレへ移行」を強制した。
3 ヶ月後、本番障害が連鎖した。
旧テンプレの暗黙の依存が、新テンプレには無かった。

経営は移行を凍結した。
「ゴールデンパス」という言葉は、組織内で**信用を失った**。
```

### 8.7 BAD-GP7: アンチパターンの神格化（文化軸）

> 終局条件: 早期に固定したテンプレが時代遅れになっても更新せず

```
2 年前の「ベストプラクティス」が、まだテンプレに残っていた。
誰もそれを変えようとしなかった。
「公式が出してるんだから正しい」と新人は信じた。

時代遅れの実装は、組織のスタンダードとして定着した。
そして、業界から 3 年遅れていることに、誰も気づかなかった。
```

### 8.8 BAD-GP未確定

あなたの組織固有のゴールデンパス失敗が描写される。

## 9. グッドエンディング（4 種）

### 9.1 GOOD-GP1: 「自然な道」の達成（技術軸）

> 達成条件: GP 採用率 ≥ 85% かつ 認知負荷 ≤ +2

```
新入社員が初日に本番デプロイした。
「え、これで終わりですか？」と聞き、
シニアが「うん、終わりだよ」と答えた。

ゴールデンパスは、もう道として認識されていなかった。
それは、組織の **歩き方** になっていた。
```

### 9.2 GOOD-GP2: 進化するテンプレ（技術軸）

> 達成条件: ユーザーからのテンプレPR ≥ 20 件

```
テンプレは、もはやプラットフォームチームのものではなかった。
20 名以上の社内エンジニアがコミッターになり、
PR は毎週マージされた。

ゴールデンパスは、組織の集合知が結晶化した道だった。
```

### 9.3 GOOD-GP3: 移行時の信頼（組織軸）

> 達成条件: テンプレメジャー版アップグレード成功率 ≥ 95%

```
新テンプレ V2 への移行は、3 ヶ月で完了した。
障害は 1 件。
自動 PR が 80% のリポジトリで一発でマージされ、
残りの 20% は手厚いサポートで個別対応された。

利用者は「次の V3 が楽しみ」と言った。
```

### 9.4 GOOD-GP4: 「あなたたちのおかげで」（文化軸）

> 達成条件: シノ関係値 +3 かつ 全社オールハンズでテンプレが言及

```
オールハンズでケンジが言った。
「俺、最初はテンプレ嫌いだったんだ。
 でも、シノさんと一緒に作り直したら、これがうちのテンプレになった」

ゴールデンパスは、共有資産になった。
そしてシノは、その日、笑顔で乾杯した。
```
