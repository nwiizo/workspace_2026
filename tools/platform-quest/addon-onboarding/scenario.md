# Addon: Onboarding

> 「あなたのプラットフォームの第一印象は、
>  ドキュメントの最初の段落で決まる」

新規利用チームと新人エンジニアのオンボーディングを扱うアドオン。

---

## 1. 中核概念

### 1.1 「最初の 30 分」設計

```
0:00 - 0:05   ポータルに到達、自分のチーム所属を確認
0:05 - 0:10   テンプレートから新規サービス作成
0:10 - 0:20   コードを書く（"Hello"でも可）
0:20 - 0:25   コミット & プッシュ
0:25 - 0:30   開発環境で動いている URL を見る

この 30 分で、プラットフォームへの「信頼の種」が決まる。
```

### 1.2 マイルストーン設計

| マイルストーン | 目標時間 |
|---|---|
| Hello World | 30 分 |
| 開発環境デプロイ | 2 時間 |
| ステージング統合 | 1 日 |
| 本番初回デプロイ | 1 週間 |
| 自律運用開始 | 1 ヶ月 |

各マイルストーンで「離脱」「成功」「停滞」が記録される。

### 1.3 オンボーディングの 2 種類

| 種類 | 対象 | 重点 |
|---|---|---|
| 新規チームのオンボード | チーム単位 | プラットフォームに乗る判断と移行 |
| 新人エンジニアのオンボード | 個人 | 既存環境での生産性立ち上げ |

両者は別物。混同すると両方失敗する。

## 2. 追加リソースとイベント

### 2.1 追加リソース

| リソース | 説明 |
|---|---|
| TTFV (Time To First Value) | 最初の価値到達までの時間 |
| オンボーディング完走率 | 開始から本番デプロイまで完了する比率 |
| 新人体験 NPS | 最初の 1 ヶ月の満足度 |

### 2.2 追加修正値

| 修正源 | 範囲 |
|---|---|
| Hello World ≤ 30 分達成 | +2 |
| オンボーディングセルフサービス化 | +1 |
| ジュニア体験を直接観察 | +1 |
| ドキュメントが古い | -2 |

### 2.3 追加気候イベント

| D6 | 気候 | 内容 |
|---|---|---|
| 1 | 新人入社ラッシュ | 月 10 名新人入社 |
| 2 | 新規チームオンボード | 大規模プロジェクトが新規参加 |
| 3 | ドキュメント陳腐化指摘 | 「ドキュメント動きません」苦情 |
| 4 | オンボード長期化 | 1 名が 3 週間停滞 |
| 5 | 想定外の質問殺到 | サポート負荷急増 |
| 6 | スムーズオンボード | 「使いやすい」フィードバック |

## 3. NPC

### 3.1 ユウト（メインから・ジュニア）

このアドオンの主役（被験者）。
彼の体験が KPI そのもの。

### 3.2 ハナ（DevEx エンジニア・新規）

- 役割: 開発者体験の専属。オンボードを設計する
- セリフ:
  - 「『分かりにくい』を分解すると、設計の不備が見えます」
  - 「最初の 30 分は、製品のデモ画面と思ってください」
- 特殊能力 **〈最初の 30 分〉**: 関係値 +2 で、オンボード完走率 +20%

### 3.3 ケンジ（メインから）

既存利用チームの代表として、
新規参加チームの「招待者」役を果たすか。

---

## 4. シナリオ 0: 学習モード

3 ターン。最初のオンボードをユウトと一緒に走る。
学習補正 +2。

```
T0: ハナ「ユウトの最初の体験、どう設計しますか？」
  A) ハンズオン形式（人が付き添う）
  B) 完全セルフサービス（ドキュメント + テンプレ）
  C) ハイブリッド（最初 1h は付き添い）
```

---

## 5. シナリオ 1: 最初の 30 分の設計 （★★）

8 ターン。
- ハロー・ワールドの実装
- 観察セッションの実施
- ドキュメントの最適化
- セルフサービス化

---

## 6. シナリオ 2: 新規チームのオンボード （★★★）

10 ターン。10 名規模の新規プロジェクトを乗せる。
- 移行計画
- 既存環境からの引き継ぎ
- 摩擦の解消

---

## 7. シナリオ 3: 採用ラッシュ対応 （★★★★）

12 ターン。3 ヶ月で 50 名入社の波。
- スケールするオンボード
- メンタリング設計
- 既存メンバーへの負担

## 8. バッドエンディング（7 種）

### 8.1 BAD-OB1: 30 分の壁（技術軸）

> 終局条件: Hello World 平均時間 ≥ 2 時間

```
新人ユウトは、入社 3 日目で「使えない」と判断した。
理由はシンプルだった。最初のデプロイに 2 日かかった。

最初の 30 分は、製品のデモ画面だった。
あなたのデモは、長すぎた。
```

### 8.2 BAD-OB2: ドキュメント嘘の砂漠（技術軸）

> 終局条件: ドキュメント記載コマンドの実動作率 ≤ 60%

```
新人が試した:
  - README のコマンド: 動かない
  - 公式ガイドのフロー: 古い
  - サンプルコード: deprecated

新人は Slack で聞き、シニアが対応した。
プラットフォームのセルフサービス機能は、紙の上だけだった。
```

### 8.3 BAD-OB3: 環境別の地獄（技術軸）

> 終局条件: 開発と本番の差異が大きく、本番デプロイ事故発生

```
開発環境で動いていたコードが、本番で動かなかった。
差分が大きすぎた。新人はそれを「ガチャ」と呼んだ。

オンボードは終わったが、信頼は始まらなかった。
```

### 8.4 BAD-OB4: ハナ離反（組織軸）

> 終局条件: ハナ関係値 ≤ -1 + DevEx 投資打ち切り

```
ハナが言った。
「DevEx は、機能の後付けじゃないんです」

そして去った。
オンボードは、再びシニアの口頭伝承になった。
新人の離脱率は、上昇した。
```

### 8.5 BAD-OB5: メンター燃え尽き（組織軸）

> 終局条件: 新人 1 人に対するメンター工数 ≥ 1 日 / 週

```
新人が増えるたび、メンター工数が増えた。
シニアエンジニアの時間の 40% が、新人対応に消えた。
新機能開発が止まり、シニアが燃え尽き始めた。

スケールしないオンボードは、組織を壊した。
```

### 8.6 BAD-OB6: 育成 ROI 不明（経営財務軸）

> 終局条件: 新人離脱率 ≥ 30% + 採用投資の回収困難

```
人事レポート:
「過去 1 年の新人離職率 32%」
「主な理由: オンボーディング体験」

採用 1 名にかけた費用は 200 万。
その 32% が消えていく組織は、採用機械を空回りさせていた。
```

### 8.7 BAD-OB7: 「自分で頑張れ」文化（文化軸）

> 終局条件: 新人が孤立 + 「先輩に聞きにくい」雰囲気

```
新人が Slack に書いた:
「すいません、聞いていいですか...?」

返信に 2 時間。
新人は、聞かずに自分で解決することを学んだ。
そして、間違った設計が放置されることも、学んだ。
```

### 8.8 BAD-OB未確定

組織固有のオンボード失敗が描写される。

## 9. グッドエンディング（4 種）

### 9.1 GOOD-OB1: 「30 分の魔法」（技術軸）

> 達成条件: Hello World 平均 ≤ 30 分 + 完走率 ≥ 90%

```
新人ユウトが、入社初日の 25 分後に、初めての URL を見ていた。
彼は微笑んで、Slack に書いた。
「これ、本当にデプロイされてます！」

その夜、彼は早めに帰宅した。
プラットフォームは、彼を信じさせた。
```

### 9.2 GOOD-OB2: セルフサービスの楽園（技術軸）

> 達成条件: メンター工数 / 新人 ≤ 4 時間 + 完走率 高

```
ハナの設計で、ほとんどのオンボードはセルフサービスで完結した。
メンター工数は新人 1 名あたり 4 時間以内。
シニアは、本来の仕事に戻れた。
```

### 9.3 GOOD-OB3: 採用 ROI 達成（経営財務軸）

> 達成条件: 新人 6 ヶ月生産性立ち上がり ↑ + 離職率 低

```
新人は 6 ヶ月で、3 年目相当の生産性に到達していた。
離職率は半減した。
人事は「うちは PE 部に支えられている」と語った。
```

### 9.4 GOOD-OB4: 「ようこそ」文化（文化軸）

> 達成条件: ユウト関係値 +3 + 新人からのフィードバック PR ≥ 5

```
ユウトは、3 ヶ月後に新しい新人のメンターになった。
そして、自分が受けた体験を、次の人に再現した。

オンボードは、世代を超えて自己再生産する文化になった。
```
