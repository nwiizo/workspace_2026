# Addon: Control Plane

> 「コントロールプレーンは、プラットフォームの神経系である。
>  そして、神経系は最後に作るものではない」

宣言的 API・リコンサイル・コントロールプレーンを扱うアドオン。

---

## 1. 中核概念

### 1.1 コントロールプレーンの 3 層

```
┌──────────────────────────────────────────────────────────┐
│   利用者 API 層                                            │
│   "Database が欲しい" / "Service を立てたい" の宣言         │
└──────────────────────────────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────┐
│   リコンサイル層                                           │
│   宣言と現実の差分を観察し、現実を宣言に近づける             │
└──────────────────────────────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────┐
│   実行層 (Cloud Provider, Kubernetes, 自社システム)        │
│   実際にリソースが作られ、状態を返す                        │
└──────────────────────────────────────────────────────────┘
```

### 1.2 設計判断マトリクス

| 軸 | 選択肢 | トレードオフ |
|---|---|---|
| 実装 | 自作 vs Crossplane vs ArgoCD vs Pulumi Operator | 速度 vs 柔軟性 |
| 状態管理 | k8s etcd / DB / GitOps | 一貫性 vs 単純さ |
| 認可 | RBAC / OPA / 独自 | 表現力 vs 学習コスト |
| 同期方式 | プッシュ / プル / ハイブリッド | 即時性 vs 信頼性 |

### 1.3 リコンサイルループの設計原則

1. **冪等性**: 何回適用しても同じ結果
2. **可観測性**: 各ステップが状態として観測できる
3. **境界の明示**: どのリソースは誰のものか明確
4. **回復性**: 失敗からの自動再試行が組み込まれている
5. **手動上書き許容**: ただし「手動変更を承認する」プロセスを持つ

## 2. 追加リソースとイベント

### 2.1 追加リソース

| リソース | 説明 |
|---|---|
| CP 整合性 | 宣言と現実の一致度。低いと信頼喪失 |
| CP SLO | CP自体の可用性 |

### 2.2 追加修正値

| 修正源 | 範囲 |
|---|---|
| GitOps 化されている | +1 |
| 自動ロールバック設計あり | +1 |
| CP 自体が単一障害点 | -2 |
| 手動オペレーションが慣習化 | -1 |

### 2.3 追加気候イベント

| D6 | 気候 | 内容 |
|---|---|---|
| 1 | CP 障害 | コントロールプレーン自体がダウン |
| 2 | Drift 大量発生 | 手動変更で 50+ リソースが宣言から乖離 |
| 3 | 新クラウド機能 | リコンサイルロジックの更新を迫られる |
| 4 | 認可エスカレーション | 利用者が想定外の権限要求 |
| 5 | CP メジャー版アップグレード | k8s 等の依存基盤更新 |
| 6 | 平穏 | CP が静かに動き続ける |

## 3. NPC

### 3.1 リョウ（コントロールプレーンエンジニア・新規）

- 役割: 元 k8s コミッター。CP の設計者
- セリフ:
  - 「CP は自分自身を再構築できる必要がある」
  - 「リコンサイルは哲学です。実装は宗派です」
- 特殊能力 **〈リコンサイル設計〉**: 関係値 +2 で、Drift 系イベント被害 -50%

### 3.2 タクヤ（メインから・SRE リード）

- このアドオンでは「CP 自体の運用者」として登場
- CP の SLO 設計が彼の責務

### 3.3 ハルカ（メインから・セキュリティ）

- CP の認可モデル設計に深く関与
- OPA / RBAC の細部に妥協がない

## 4. シナリオ 0: 学習モード

3 ターン。最初の宣言的 API を 1 本作る。
学習補正 +2。

```
T0: リョウ「最初のリソースは何にしますか？」
  A) Database
  B) Service (HTTP エンドポイント)
  C) Secret Bundle
```

選んだリソースで「宣言 → リコンサイル → 観測」の 1 サイクルを体験する。

---

## 5. シナリオ 1: 最初の CP 設計 （★★）

8 ターン。Lv0 から「動く CP」まで。
- 自作 vs OSS の決断
- 最初の 3 リソース定義
- GitOps 統合
- 認可設計

---

## 6. シナリオ 2: Drift との戦い （★★★）

10 ターン。手動変更が常態化したクラウドを CP に取り込む。
- 既存リソースのインポート戦略
- 「手動変更歓迎モード」の設計
- リコンサイルの厳格性レベル

---

## 7. シナリオ 3: CP 自体のスケール （★★★★）

12 ターン。CP がボトルネックになり始める。
- リコンサイルの並列化
- リソース種別ごとのコントローラ分割
- CP 自体のマルチリージョン化

---

## 8. バッドエンディング（7 種）

### 8.1 BAD-CP1: 自作の沼（技術軸）

> 終局条件: 自作 CP 採用 + 開発 12 ヶ月超過 + 機能未達

```
あなたは「Crossplane では足りない」と判断し、自作 CP に踏み切った。
1 年半が経った。CP はまだ V1 リリースできていない。
プラットフォームエンジニアの大半が CP の保守に取られ、
利用者向けの機能開発は完全に止まっていた。

「車輪を再発明した」と CTO はつぶやいた。
```

### 8.2 BAD-CP2: 融解（技術軸）

> 終局条件: CP 障害 + 復旧時間 ≥ 8h + データロス発生

```
CP のデータベースが壊れた。
GitOps が無かったため、「現実の状態が真実」になっていた。
復旧には 14 時間。手動で 200 リソースを再宣言した。

ポストモーテムは長く、結論は短かった。
「CP 自身に SRE が必要だった」
```

### 8.3 BAD-CP3: ブラックボックス化（技術軸）

> 終局条件: CP 自体のオブザーバビリティ低 + 利用者からの問い合わせ急増

```
利用者が「Pod が立ち上がらない」と問い合わせた。
CP のログを見ても、何が起きているか分からなかった。
リコンサイルが沈黙しているのか、エラーなのか、判別できなかった。

CP はブラックボックスになっていた。
プラットフォームチームすら、その挙動を予測できなかった。
```

### 8.4 BAD-CP4: CP の警察化（組織軸）

> 終局条件: 認可ルール過剰 + 例外申請殺到

```
あなたは厳格な認可モデルを CP に組み込んだ。
すべての利用者が「権限がない」エラーに直面した。
例外申請は毎週 50 件。プラットフォームチームは申請審査に追われた。

CP は守護神ではなく、検問所になった。
```

### 8.5 BAD-CP5: ベンダー人質（経営財務軸）

> 終局条件: 特定 SaaS CP 依存 + ベンダー価格改定 + 移行不可

```
3 年使っていた SaaS の CP プロダクトが、価格を 4 倍にした。
移行は事実上不可能だった——すべての宣言が独自スキーマで書かれていた。

経営は支払いを承認した。仕方なかった。
そして次年度から、新しい予算項目「ベンダーリスク」が生まれた。
```

### 8.6 BAD-CP6: ROI 不明（経営財務軸）

> 終局条件: CP 開発投資 過大 + 利用者の体感改善 低

```
CP は完璧に動いていた。
利用者は「これがないと困る」と言わなかった。
「これがあって良かった」も言わなかった。

経営は質問した:「で、これに 5 億かけて、何が変わったの？」
あなたは答えに詰まった。
```

### 8.7 BAD-CP7: リョウ離反（文化軸）

> 終局条件: リョウ関係値 ≤ -1 + 設計判断強行

```
リョウが言った。
「私の設計判断、もう求められてないんですね」

そして退職した。
CP の哲学はリョウの頭の中にしかなかった。
3 ヶ月後、誰も「なぜこう設計したか」を説明できなくなった。
```

### 8.8 BAD-CP未確定

組織固有の CP 失敗が描写される。

## 9. グッドエンディング（4 種）

### 9.1 GOOD-CP1: 静かに動く神経系（技術軸）

> 達成条件: CP SLO ≥ 99.95% かつ Drift 自動修復率 ≥ 90%

```
CP は静かだった。
利用者はその存在を意識しなかった。
ただ、何かを宣言すれば、それがクラウドに現れた。

神経系は、痛む時にしか意識されない。
あなたの CP は、痛まなかった。
```

### 9.2 GOOD-CP2: 拡張可能なエコシステム（技術軸）

> 達成条件: 利用者定義カスタムリソース ≥ 10 種

```
利用者がカスタムリソースを定義し始めた。
「うちの事業ドメイン特有の宣言を、CP に乗せたい」

CP は、もはやプラットフォームチームのものではなかった。
それは、組織全体のオートメーション基盤になった。
```

### 9.3 GOOD-CP3: 投資の意味（経営財務軸）

> 達成条件: 手動オペレーション時間削減 ≥ 70%

```
SRE 工数の 60% を占めていた「手動デプロイ」「手動修復」が消えた。
タクヤは初めて、新機能設計の時間を持てた。

CP の投資は、人の時間を取り戻していた。
そしてその時間は、新しいプラットフォーム価値に再投資された。
```

### 9.4 GOOD-CP4: 「CP は仲間」文化（文化軸）

> 達成条件: 利用者からの CP 改善提案 ≥ 15 件

```
利用者は CP に対する Issue を立て始めた。
バグ報告ではなく、「こういう宣言ができたら嬉しい」という提案。

CP は、組織が一緒に育てるシステムになった。
```
