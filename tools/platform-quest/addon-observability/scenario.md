# Addon: Observability

> 「ダッシュボードを見て安心するな。
>  ダッシュボードが**何も語らない**時こそ、本当に怖い時だ」

シグナル駆動フィードバックループを扱うアドオン。

---

## 1. 中核概念

### 1.1 オブザーバビリティの 4 層

```
┌────────────────────────────────────────────────────────┐
│  Layer 4: Decision        意思決定（自動 or 人）          │
│           ↑                                              │
│  Layer 3: Signal          SLO / アラート / アノマリー    │
│           ↑                                              │
│  Layer 2: Telemetry       メトリクス / ログ / トレース    │
│           ↑                                              │
│  Layer 1: Instrumentation 計装（コード・基盤）            │
└────────────────────────────────────────────────────────┘
```

下から上に向かって価値が増す。
**Layer 4 に到達しないテレメトリは、コストでしかない**。

### 1.2 SLO の設計原則

| 原則 | 説明 |
|---|---|
| ユーザー視点 | プラットフォームの内部状態ではなく「利用者から見た成功」を測る |
| 達成可能性 | 100% は SLO ではない。99.5% などのリアルな目標 |
| エラーバジェット | 失敗を許容する明示的な「予算」 |
| 連鎖の理解 | 上流SLO < 下流SLO になりがち。掛け算で考える |

### 1.3 「黒いシグナル」の発見

良い兆候の不在ではなく、**悪い兆候の予兆**を捉える。

- ダッシュボードが「変化していない」のに、現場が「忙しい」
- リクエスト数は減っているのに、人の応対は増えている
- 障害は起きていないのに、シニアエンジニアが疲れている

これらは「観測されていない過負荷」のサイン。

## 2. 追加リソースとイベント

### 2.1 追加リソース

| リソース | 説明 |
|---|---|
| 信号品質 | アラート S/N 比。低いとアラート疲労 |
| 観測コスト | テレメトリ収集の月額。負債と紐づく |
| エラーバジェット消費率 | プラットフォームの累積信頼性 |

### 2.2 追加修正値

| 修正源 | 範囲 |
|---|---|
| SLO に基づく意思決定 | +2 |
| アラート S/N 比改善あり | +1 |
| メトリクス収集だけで使われていない | -1 |
| ダッシュボードが古い (3ヶ月以上未更新) | -1 |

### 2.3 追加気候イベント

| D6 | 気候 | 内容 |
|---|---|---|
| 1 | アラート疲労 | 偽陽性多発、SRE のページャー鈍麻 |
| 2 | 観測コスト急騰 | Datadog/NewRelic 費用が予算を圧迫 |
| 3 | 観測の穴 | 重大な障害が「観測されていなかった」と発覚 |
| 4 | SLO 違反連発 | エラーバジェット枯渇、機能凍結検討 |
| 5 | データ要求 | 経営層から「数字を見せて」要求 |
| 6 | 静謐 | 信号が安定、ダッシュボードが青のまま |

## 3. NPC

### 3.1 タクヤ（メインから・SRE リード）

このアドオンの主戦場。SLO 設計を率いる。

### 3.2 リン（テレメトリエンジニア・新規）

- 役割: 計装・テレメトリパイプラインの専門家
- セリフ:
  - 「すべてを記録するのは、何も記録しないのと同じです」
  - 「カーディナリティを甘く見ると、コストで死にます」
- 特殊能力 **〈シグナル設計〉**: 関係値 +2 で、観測コスト気候 -50%

### 3.3 玲奈（メインから・CTO）

「数字を出せ」という圧力源。
彼女が見たいダッシュボードを設計できるか。

3 ターン。最初の SLO を 1 本定義する。
学習補正 +2。

```
T0: リン「最初の SLO、何にしますか？」
  A) デプロイ成功率
  B) API リクエスト遅延
  C) コントロールプレーン整合性
```

## 5. シナリオ 1: 観測の旅 （★★）

8 ターン。Layer 1 から Layer 3 への到達。
- 計装の標準化（OpenTelemetry 採用判断）
- 最初のダッシュボード設計
- アラート設計の罠

---

## 6. シナリオ 2: アラート疲労との戦い （★★★）

10 ターン。チームがアラートを無視し始めた。
- アラートの整理（消す勇気）
- SLO ベースの再設計
- インシデントレビューとの統合

---

## 7. シナリオ 3: 観測 ROI の証明 （★★★★）

12 ターン。経営層から観測コスト削減 30% を要求される。
- カーディナリティ削減
- サンプリング戦略
- ビジネス指標と運用指標の統合

## 8. バッドエンディング（7 種）

### 8.1 BAD-OB1: 観測の穴（技術軸）

> 終局条件: 観測なしの重大障害発生 + 復旧 ≥ 4h

```
障害は静かに起きていた。
顧客が問い合わせて初めて、あなたは気づいた。
ダッシュボードはすべて緑だった。観測していない領域で、すべてが燃えていた。

「観測しているつもり」は、観測ではなかった。
```

### 8.2 BAD-OB2: シグナル過多（技術軸）

> 終局条件: アラート S/N 比 ≤ 10% + 真のインシデント見逃し

```
ページャーが鳴り続けた。
SRE は「またか」と無視するようになった。
そして、本当に重要なアラートも無視された。

シグナル疲労は、観測ゼロより危険だった。
```

### 8.3 BAD-OB3: ダッシュボード化石（技術軸）

> 終局条件: 主要ダッシュボード更新 0 / 6 ヶ月 + 利用率低

```
ダッシュボードは存在した。
ただ、誰も見ていなかった。
パネルは旧仕様のメトリクスを参照し、グラフは半分が「No Data」だった。

「観測している」と書類には書かれていた。
現実は、観測の遺跡だった。
```

### 8.4 BAD-OB4: SLO 違反の常態化（組織軸）

> 終局条件: エラーバジェット 3 期連続枯渇 + 機能凍結未実施

```
SLO 違反は数字だけになった。
誰もそれに基づいて行動を変えなかった。
「機能凍結します」と言う勇気を、誰も持っていなかった。

SLO は守られないルールになり、ルールは形骸化した。
```

### 8.5 BAD-OB5: ベンダーロック（組織軸）

> 終局条件: 観測ベンダー 1 社依存 + データ移植不可

```
すべてのテレメトリは特定 SaaS に集まっていた。
ベンダーが値上げを通告した時、移行は事実上不可能だった。

データはあなたの会社のものだった。
しかし、それを操る能力は、ベンダーのものだった。
```

### 8.6 BAD-OB6: 観測コスト破綻（経営財務軸）

> 終局条件: 観測予算がクラウド本体の 30% 超 + 削減失敗

```
四半期報告で、CFO が指摘した。
「観測ツールが、本番クラウドより高いんですが？」

カーディナリティ爆発、ログの過剰保存、トレースの全量サンプリング。
あなたの観測基盤は、観測対象より高価な怪物になっていた。
```

### 8.7 BAD-OB7: アラート文化崩壊（文化軸）

> 終局条件: SRE 離職 ≥ 2 名 + 「人力監視」復活

```
SRE が辞めていった。
「夜中に意味のないアラートで起こされる仕事は、続けられない」

残ったメンバーは、自動アラートを止めて「目で見る」運用に戻った。
21 世紀のプラットフォームに、20 世紀の運用が戻ってきた。
```

### 8.8 BAD-OB未確定

組織固有の観測失敗が描写される。

## 9. グッドエンディング（4 種）

### 9.1 GOOD-OB1: シグナル駆動運用（技術軸）

> 達成条件: SLO達成率 ≥ 95% + アラート S/N比 ≥ 80%

```
ページャーは、本当に重要な時しか鳴らなかった。
SRE は鳴った時、迷わず対応できた。
そして、対応した結果が次の SLO 改善に繋がった。

観測は、サイクルとして回り始めた。
```

### 9.2 GOOD-OB2: コスト効率（技術軸）

> 達成条件: 観測コスト/クラウドコスト ≤ 10% + 観測カバー率 高

```
カーディナリティを 80% 削減し、サンプリングを賢く設計した。
観測コストは半減したのに、見える情報は増えていた。

「観測は安くて、深い」が、組織の標準になった。
```

### 9.3 GOOD-OB3: ビジネス指標との接続（経営財務軸）

> 達成条件: ビジネス KPI と SLO がリンク

```
取締役会のスライドに、SLO の数字が乗った。
「プラットフォーム可用性 99.97% → 月次解約率 0.3% 低下」

観測は、もはやエンジニアのものではなかった。
経営の意思決定の材料になっていた。
```

### 9.4 GOOD-OB4: 「観測は仲間」文化（文化軸）

> 達成条件: 利用者がダッシュボードを自作 ≥ 20 件

```
利用者が自分のサービス用のダッシュボードを作り始めた。
SLO を自分で定義し、エラーバジェットを自分で管理し始めた。

観測は、プラットフォームチームだけのものではなかった。
組織全体の言語になった。
```
