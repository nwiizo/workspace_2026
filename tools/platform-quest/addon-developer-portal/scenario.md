# Addon: Developer Portal

> 「ポータルは、プラットフォームの**顔**である。
>  顔がしかめっ面なら、誰もその先には進まない」

開発者ポータル / IDP の設計と運用を扱うアドオン。

---

## 1. 中核概念

### 1.1 ポータルの 5 ケイパビリティ

```
┌──────────────────────────────────────────────────────────┐
│                                                            │
│  ┌────────────┐  ┌────────────┐  ┌────────────┐         │
│  │  カタログ   │  │ テンプレート │  │ ドキュメント │         │
│  │ (Discovery)│  │  (Create)   │  │  (Learn)    │         │
│  └────────────┘  └────────────┘  └────────────┘         │
│                                                            │
│  ┌────────────┐  ┌────────────┐                          │
│  │ スコアカード │  │  サポート   │                          │
│  │  (Improve) │  │   (Help)    │                          │
│  └────────────┘  └────────────┘                          │
│                                                            │
└──────────────────────────────────────────────────────────┘
```

### 1.2 構築選択

| 選択 | メリット | デメリット |
|---|---|---|
| Backstage | 業界標準、プラグイン豊富 | プラグイン地獄、フロント技術力必要 |
| Port (SaaS) | 迅速、運用負荷低 | 月額コスト、カスタマイズ限界 |
| 自作 | 完全制御 | 開発・保守コスト膨大 |
| 既存ツールの統合UI | 開発不要 | 体験の継ぎ目 |

### 1.3 「3 クリックの法則」

開発者は **最初の 3 クリック以内** で目的に到達できなければ離脱する。

- カタログ → サービス選択 → 詳細
- 新規作成 → テンプレ選択 → デプロイ
- 障害 → ダッシュボード → Runbook

これを満たさないポータルは、Slack で問い合わせるより遅い。

## 2. 追加リソースとイベント

### 2.1 追加リソース

| リソース | 説明 |
|---|---|
| ポータル DAU | デイリーアクティブユーザー |
| ポータルからの自己解決率 | 問い合わせを経ずに目的達成した比率 |
| カタログカバー率 | 全サービスのうちカタログに登録済みの比率 |

### 2.2 追加修正値

| 修正源 | 範囲 |
|---|---|
| カタログカバー率 ≥ 90% | +1 |
| 3 クリック法則達成 | +2 |
| ポータル UX デザイナー参画 | +1 |
| ドキュメントが古い | -2 |

### 2.3 追加気候イベント

| D6 | 気候 | 内容 |
|---|---|---|
| 1 | カタログ陳腐化 | 30% のサービスが「存在しない」とマーク |
| 2 | プラグイン地獄 | Backstage プラグインのメンテ破綻 |
| 3 | UX 苦情殺到 | 「使いにくい」フィードバック大量 |
| 4 | 新人体験悪化 | オンボーディング時間が伸びる |
| 5 | カスタムビュー要求 | 各事業部から独自表示要求 |
| 6 | 賛辞 | 「ポータル便利」が複数チームから |

## 3. NPC

### 3.1 ナギ（ポータル UX デザイナー・新規）

- 役割: 数少ない社内 UX デザイナー。プラットフォームに専任
- セリフ:
  - 「エンジニア向けでも、UX デザインは必要です」
  - 「3 クリックで終わらないなら、何かが間違っています」
- 特殊能力 **〈UX 直感〉**: 関係値 +2 で、UX 苦情気候を 1 回無効化

### 3.2 ユウト（メインから・ジュニア開発者）

ポータル UX の最も鋭い評価者。

### 3.3 シノ（addon-golden-path から）

ポータル経由のテンプレート利用率を担う。

## 4. シナリオ 0: 学習モード

3 ターン。最初のサービスカタログを 1 本登録する。
学習補正 +2。

```
T0: ナギ「カタログの最初の 1 件、どうします？」
  A) Payments サービス（最も影響力大）
  B) Helios 新規（テンプレ込みでカタログ登録）
  C) Legacy 基盤（最も汚い、難所）
```

## 5. シナリオ 1: Backstage 導入 （★★）

- 最初のプラグイン構成
- カタログ自動同期の設計
- UX レビュー

- ドキュメント更新の仕組み化

## 8. バッドエンディング（7 種）

### 8.1 BAD-DP1: プラグイン地獄（技術軸）

> 終局条件: Backstage プラグイン数 ≥ 30 + メンテ破綻

```
あなたは Backstage に 30 個のプラグインを入れた。
半年で 10 個が動かなくなり、3 個がセキュリティ脆弱性を持ち、
2 個はメンテナがいなくなっていた。

ポータルチームの仕事は、プラグイン保守になった。
ユーザー価値は、止まった。
```

### 8.2 BAD-DP2: カタログ嘘の墓場（技術軸）

> 終局条件: カタログカバー率 ≤ 40% + 古い情報 多

```
カタログには 200 のサービスが登録されていた。
そのうち 80 は既に存在せず、50 は所有者不明だった。

検索すれば結果は出る。出た結果は嘘だった。
誰もカタログを信じなくなり、Slack で「あれ誰の管轄？」が再開した。
```

### 8.3 BAD-DP3: 3 クリック未達（技術軸）

> 終局条件: ポータルからの自己解決率 ≤ 20%

```
利用者は、ポータルを開いた。
そして、5 分後に Slack で「これってどうやるの？」と質問していた。

ポータルは「見るための場所」になり、「動くための場所」にはならなかった。
```

### 8.4 BAD-DP4: 各事業部独自UI 化（組織軸）

> 終局条件: 事業部独自ポータル ≥ 3 個

```
「うちは独自のカスタムビューが必要」
「うちのデザインに合わせて」

3 つの事業部が、独自のポータルを作り始めた。
プラットフォームポータルは、薄いハブになった。
そして、薄いハブを誰も使わなくなった。
```

### 8.5 BAD-DP5: ナギ離反（組織軸）

> 終局条件: ナギ関係値 ≤ -1 + UX 苦情多発

```
ナギが言った。「UX レビューは形式的なんですね」

そして去った。
ポータルは、エンジニアだけが触る場所になった。
そして、エンジニアにとっても、使いづらい場所になった。
```

### 8.6 BAD-DP6: ポータル ROI 不明（経営財務軸）

> 終局条件: ポータル開発投資 ≥ 1 年工数 + DAU ≤ 30 名

```
1 年と工数をかけて作ったポータル。
日次利用者は 30 名。
経営は「これに 1 億かけたのか」と聞いた。

ポータルは存在した。利用者は、いなかった。
```

### 8.7 BAD-DP7: 「Slack の方が早い」文化（文化軸）

> 終局条件: Slack の質問数がポータル DAU を上回る状態が 3 期連続

```
組織の知識は、Slack のメッセージとして散らばっていた。
ポータルは知識を集約する場所のはずだった。
ただ、Slack で聞く方が早かった。そして検索性が低かった。

ポータルは博物館になり、Slack は混沌のジャングルになった。
```

### 8.8 BAD-DP未確定

組織固有のポータル失敗が描写される。

## 9. グッドエンディング（4 種）

### 9.1 GOOD-DP1: 「3 クリックの楽園」（技術軸）

> 達成条件: 自己解決率 ≥ 80% + DAU ≥ 200

```
新人ユウトが入社 3 日目で言った。
「ポータルでだいたい完結します。本当に分からない時だけ聞きます」

ポータルは、組織のセルフサービスの中心になった。
プラットフォームチームの問い合わせは、半減した。
```

### 9.2 GOOD-DP2: 自動同期エコシステム（技術軸）

> 達成条件: カタログ自動同期率 ≥ 95%

```
カタログは、誰もメンテしていなかった。
GitOps、コード、リポジトリの実態から自動同期されていた。

「カタログを更新する」という仕事が消えた。
それは、最高の状態だった。
```

### 9.3 GOOD-DP3: 投資の証明（経営財務軸）

> 達成条件: ポータル経由のオンボーディング時間 ≤ 旧来比 30%

```
新人のオンボーディング時間が、3 週間から 5 日になった。
年 30 名採用の組織で、年間 1,500 人日の削減。

ポータル投資は、人月で説明できた。
```

### 9.4 GOOD-DP4: 「私の家」文化（文化軸）

> 達成条件: ナギ関係値 +3 + ポータル NPS ≥ +50

```
利用者がポータルにブックマークを付け、
スタートページに設定し、
新人に「まずここを開け」と教え始めた。

ポータルは、組織の家になった。
```
