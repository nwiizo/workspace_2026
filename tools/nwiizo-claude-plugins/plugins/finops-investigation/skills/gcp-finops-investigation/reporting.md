# Reporting Discipline (GCP)

GCP 特有の階層構造とコスト単位を踏まえたレポート運用。

## レポートファイルの命名・配置

- `docs/cost_analysis_YYYYMMDD.md` — 日付付きで前回版を残す。上書き禁止
- `output/<resource>_YYYYMMDD.json` — 生データ（gcloud / BigQuery 結果）を日付付きで保存
- `output/billing_YYYYMMDD.sql` — 実行した BigQuery クエリを再現可能な形で保存
- `docs/finops_history.md` — マイルストーン・完了施策を追記式で管理
- IAM ロール依頼用の設定は `docs/*_additional_roles.yaml` や Custom Role JSON で別ファイル化

## スコープの明示

GCP はプロジェクト / フォルダ / 組織 / 請求アカウントが独立なので、レポート冒頭で必ず対象を明示：

- 対象: 組織 ID、フォルダ ID、プロジェクト ID 群、請求アカウント ID
- スコープ（単一プロジェクト分析か、請求アカウント全体か、組織横断か）
- 分析対象外（アクセス権なしで見えなかった範囲）

複数スコープを混在させると合計値が意味をなさないので分離する。

## 削減額の表現規律

一つの数字で語らない。レポートには必ず3通り併記：

- **月平均ベース** — 過去N ヶ月の平均との差。長期トレンド、外部共有の基準
- **直前確定月との差** — 前回調査時点からの短期改善
- **月末換算（進行中の月）** — N日実績 × 30/N。推定値と明記

Billing Export のクレジット計上が 2026 年から変わった影響で、長期比較時は「計算方式が異なる期間が混在」を注記する。

## 3段階優先度

- 🔴 **即実施可** — ラベル不要、担当者確認不要。未アタッチディスク、完全 idle リソース、明らかな残骸
- 🟡 **担当者確認要** — production ラベル、複数プロジェクト影響、DNS/SG 参照の可能性
- 🟢 **中期計画** — CUD 満期待ち、GKE 移行待ち、アーキ変更伴うもの

Recommender が出した推奨は基本 🔴 か 🟡 に分類、🟢 は人間による戦略的判断が必要なもの。

## 重複計上の排除

類似施策で対象が重なる典型：

- Idle VM と Idle PD（同じ VM の PD が両方で推奨対象）
- スケジュールスナップショット古参と手動スナップショット残骸
- Idle Address と Unused Load Balancer（LB に紐付いていた Address）

集計前に対象リソース ID を集合として確定、重複を検出して片方でのみカウント。

## 警告・注記の必須項目

- production ラベルのリソースには担当者確認必須マーク
- 削除系施策には実行順序の依存関係（VM 削除 → PD 削除 → スナップショット削除）
- CUD 購入済みインスタンスのダウンサイズ提案には「CUD 効率低下」リスク
- Cloud SQL HA → Zonal 変更提案には「RPO/RTO 要件確認」注記

## GCP 特有の表現

- コストの単位: 通貨（$ / JPY）+ SKU 単位（core-hour、GB-month、request-million 等）を併記
- CUD 効果は「年間 TCO 削減」、SUD 効果は「すでに効いている分」として分離して表示
- BigQuery のコストは「ストレージ」「クエリ（オンデマンド）」「スロット（Capacity）」で分離
- Multi-region / Dual-region / Regional のロケーション種別を明記（同じ PB でも単価違う）

## 独立レビューで検出されやすい誤り

- Recommender の推奨を**そのまま月額削減**として書く（実際には使用パターン依存）
- SUD が既に効いている分を CUD 購入削減の上限と誤認
- BigQuery のクエリコストを「サービス費」と「スキャン効率」で区別せずに合算
- リージョン間転送を「データ転送」として一括り、種別違いで単価が違うのに1数字で語る

## 履歴ファイルの更新規律

- マイルストーン一覧は追記のみ、過去データ編集禁止
- 施策ステータスはチェックボックス式（⬜ → ✅）、完了日記入
- Billing Export の列定義や CUD 購入イベント、Recommender の推奨発生日も追記
- 更新ログに誰が何を変更したか記録
