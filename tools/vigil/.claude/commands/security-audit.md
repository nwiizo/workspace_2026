# Security Audit — 包括的セキュリティ監査

対象プロジェクトの包括的セキュリティ監査を実行する。4つの分析フェーズを順に実行し、統合レポートを生成する。

## 実行手順

### Phase 1: アーキテクチャ理解

まず対象プロジェクトの全体像を把握する。

1. エントリポイントを特定（Web フレームワークのルーティング、main 関数、CLI エントリ）
2. ディレクトリ構成とファイル役割を把握
3. 使用フレームワーク・ライブラリを確認
4. DB 接続方式、認証方式、セッション管理を確認
5. 外部サービスとの通信を確認

以下を Grep/Glob/Read で調査:
- `Glob("**/routes*", "**/router*", "**/*controller*", "**/urls.py", "**/ctr.php")` でルーティング
- `Grep("require|import|include|use ")` で依存関係
- `Grep("mysql|postgres|sqlite|mongo|redis")` でデータストア
- `Grep("session|cookie|jwt|token|oauth")` で認証方式

### Phase 2: 脆弱性評価

Task ツールで `vulnerability-assessor` エージェントを起動:

```
以下の手順で脆弱性評価を行ってください。

1. 入力ポイントの全数列挙（$_GET, $_POST, $_REQUEST, request.params, req.body 等）
2. 各入力がサニタイズなしで使われる箇所を追跡
3. SQL クエリ構築パターンの分析（文字列結合、プリペアドステートメント、ORM）
4. XSS 出力ポイントの分析（テンプレートエンジンの自動エスケープ有無）
5. 認証・認可チェックの一貫性検証
6. ファイルアップロード・パストラバーサルの検証
7. セカンドオーダー攻撃の可能性（DB保存→取得→引用符なし使用）
8. デシリアライズ、SSRF、XXE の検証

出力形式:
- 脆弱性ごとに OWASP ID（例: A03-SQL-01）を付与
- 深刻度: Critical / High / Medium / Low
- 攻撃シナリオを具体的に記述
- 該当コードを引用し `// ← なぜ危険か` コメントを付記
```

### Phase 3: 侵害調査

Task ツールで `compromise-investigator` エージェントを起動:

```
以下の手順で侵害調査を行ってください。

1. Web シェル・バックドアの探索（既知パターン + 難読化検出）
2. 危険関数の全数検査（eval, exec, system, passthru, shell_exec 等）
3. 各危険関数の Web 到達性を判定
4. 不審なファイル（画像ディレクトリ内の .php、異常な更新日時）の検出
5. ハードコードされた認証情報・API キーの検出
6. デバッグ用コード・テスト用バックドアの検出

出力形式:
- 検出項目ごとにリスクレベルを付与
- Web シェルが疑われる場合は難読化の解読結果を提示
- 危険関数マトリクス（関数名 × ファイル × Web到達性）
```

### Phase 4: 統合レポート生成

Phase 2-3 の結果を統合し、以下のレポートを生成:

1. **エグゼクティブサマリー**: 脆弱性の総数、深刻度分布、最重要リスク上位5件
2. **脆弱性一覧**: OWASP ID、深刻度、ファイル:行番号、攻撃シナリオ
3. **修正優先度**: Phase 1（即時対応）→ Phase 5（モダナイゼーション）に分類
4. **修正案**: 上位 Critical 脆弱性の Before/After コード

レポートは `docs/SECURITY_AUDIT_REPORT.md` に出力する。

## 注意事項

- SAST ツール（Semgrep 等）で検出可能な単純パターンは省略し、セマンティック分析でしか発見できない脆弱性に注力する
- 誤検出を避けるため、各脆弱性に具体的な攻撃シナリオを必ず記述する
- プロジェクト固有の情報（URL、認証情報）は一切レポートに含めない
