# CUD / SUD / Spot の誤認パターン

GCP 特有の割引制度の仕様と、2026 年の変更点の理解。

## 3種類の割引制度

### SUD (Sustained Use Discount)

- **自動適用**、購入不要
- 対象: Compute Engine、Cloud SQL のコアと RAM
- 条件: 月内の継続稼働時間（25% / 50% / 75% / 100%）に応じて割引率増（最大 30%）
- 落とし穴: SUD は**自動**なので「効いている」と思い込みがち、追加最適化の余地あり
- N2/E2/Tau T2D 系は SUD 対象外（代わりに卸価格で安価）

### Resource-Based CUD（リソース単位）

- コミット対象: 特定リージョンの vCPU + メモリ（マシンタイプ/OS 非依存）
- 割引率: 標準 55%、メモリ最適化 70%、1年 or 3年
- 柔軟性**低**（リージョン固定）、割引率**高**
- スペック変更・リージョン移動で効かなくなる

### Spend-Based CUD（金額単位 / Flex CUD）

- コミット対象: 請求アカウント全体の時間あたり最低支出額（$/h）
- 割引率: 1年 28%、3年 46%
- 柔軟性**高**（リージョン・マシンタイプ横断）、割引率**低**
- 2026 年の仕様変更: **credit offset から SKU 価格直接適用に変更**、Cloud Run / H3 / M シリーズも対象化
- 変更前後で Billing Export の見え方が違うので混同しないこと

## 購入判断の鉄則

1. **先にゴミ掃除** — 未使用リソース削除、Rightsizing 完了
2. ベースラインを 60〜90 日観測（実測なしで買うと over-commitment 事故）
3. **SUD で既に効いている分**を差し引いて、追加削減可能額を算出
4. Spend-Based CUD でアカウント全体のベースラインをカバー（柔軟性優先）
5. 長期固定のワークロードは Resource-Based CUD で上乗せ（割引率優先）
6. バースト分は On-Demand、許容ワークロードは Spot VM

業界的に 60〜80% commitment coverage が推奨範囲。100% だとバースト対応できない。

## Spot VM（旧 Preemptible）の罠

- **Preemptible VM は 2023 年以降新規作成停止**、既存も 2025 年までに廃止予定
- 新規は Spot VM を使う。60〜91% 割引
- 24時間制限なし（Preemptible は 24時間強制終了だった）
- Graceful shutdown 30秒、Fault-tolerant でないワークロードには不向き
- Managed Instance Group + Spot で自動復旧構成にする

## 購入済みなのに効いていないパターン

- **停止中の VM に Resource CUD が乗っている** — Compute CUD は稼働時間ベース、停止中は割引適用されず
- **リージョン不一致** — Resource CUD は購入リージョンに固定
- **マシンファミリー不一致** — n2 の CUD は n1 / e2 には効かない
- **Cloud SQL** も CUD 対象だが、DB エンジンの種別（MySQL / PostgreSQL / SQL Server）で分かれる
- Billing Export の `system_labels.goog-reserved-instance` で実際に適用されているか確認可能

## 2026 年の主要変更

- Spend-Based CUD の計上方式変更（credit offset → SKU 直接適用）
- 対象 SKU 拡大: Cloud Run、H3、メモリ最適化 VM、HPC シリーズ
- 使用量やコミット額は変更なしで、見え方だけ変わる
- 長期トレンドで過去データと比較する際は、**2025 年末と 2026 年以降で計算式を分ける**

## ダウンサイズ提案時のチェック

- Resource-Based CUD がかかっている場合:
  - 同リージョン / 同ファミリーのまま small VM に分散する → CUD は vCPU/メモリの総量で見るので部分的に効く
  - 別ファミリーに移ると完全に空転、Marketplace 売却不可（AWS と違う）
- Spend-Based CUD の場合は横断して他ワークロードに吸収可、柔軟性が活きる
- 単純な削除・停止は Resource CUD を空転させるので、稼働継続可能な縮退先がないか先に検討

## レポート記載時の注意

- SUD 効果は「すでに効いている」前提で語る（購入じゃないので「施策」として提案してはいけない）
- CUD 購入は「年間 TCO 削減」として提示、月額削減という表現は誤解を招く
- 前払い額を月割りした場合と、純粋な使用料差分の両方を併記
- Resource CUD と Spend CUD の併用は複雑な計算になるので、カバレッジ率で説明するのが無難

## CUD 投資の正味の利益検証

「CUD で月 -$X 削減」と言う前に、前払い額に対して年間で実利益が出ているかを検算する。AWS の RI と同じ罠。

- CUD コスト: $A（Premium 一括前払いなら全額、月額前払いなら月割）
- Pre-CUD の対象部分の月額（割引前の VM 使用料など）: $B/月
- Post-CUD の対象部分の月額（割引対象外で残るストレージ・License など）: $C/月
- 年間の実利益: `($B - $C) × 12 - $A`

これがマイナスだと CUD 投資が元を取れていない可能性がある。原因の代表例:

- 購入直後に Rightsizing を実施し、CUD が空転（Resource CUD の場合に発生しやすい）
- リージョン / マシンファミリー不一致による未適用
- そもそも割引率の見積もりが甘かった

レポートには見かけの「月 -$X」だけでなく、年間 TCO 比較も併記する。

## 購入月のコストが見かけ上スパイクして見える

Premium 一括前払いを買った月は Billing Export の `cost` がその金額分だけ跳ねる。AWS の Cost Explorer で RI All Upfront 購入月に発生する見かけのスパイクと同じパターン。

- 月次推移グラフでは購入月のみ大きく出る
- 翌月以降は割引が効いて低めに見える
- 長期トレンドで議論する場合は、購入月を除外するか、按分後の値を使う
- 経理・財務に「予算超過」と誤認されないよう事前に説明しておく
