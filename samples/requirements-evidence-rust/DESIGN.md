# AI時代の要求工学をRustで実践する

## このサンプルが扱う問題

AIによって実装量が増えるほど、レビュー担当者が関数本体を一行ずつ読んで安全性を判断する方法は
詰まりやすくなる。しかし、解決すべき問題は「レビューを省略すること」ではない。曖昧な要求が
大量のコードへ高速に増幅され、判断理由と検証結果を追えなくなることが問題である。

このサンプルでは、口座間送金を題材に、要求を次の順で狭める。

```text
問題と目標
  -> 利用場面、イベント、データ、品質属性
    -> 一意な要求IDと業務ルール
      -> Rustの型と公開API
        -> 例示テスト、性質テスト、モデル検査
          -> Fuzzing、性能測定、攻撃者視点のテスト
            -> コメントと型シグネチャを入口にした人間レビュー
```

最後のレビューは、実装を読まなくてよいという意味ではない。変更の危険度に応じて本体を読む判断は
残る。狙いは、レビューの入口を「コードから意図を推測する」から「明示された意図と証拠の対応を
確認する」へ移すことである。

この文書に登場する利用者や組織は、実践方法を示すための仮定である。実案件では、AIがもっともらしい
回答を補ってはならない。各役割の本人に確認し、決定者の名前と判断日を記録する必要がある。

## 第1段階: 基盤を整える

### プラクティス #1: ソリューションより先に問題を理解する

最初に提示されたソリューションは「AIが書いたRustコードを強いテストで囲む」だった。しかし、
5 Whysで掘ると、中心にある問題はコード生成速度ではなく、要求の曖昧さとレビュー能力の差である。

1. なぜレビューが追いつかないのか。生成される変更量が増えたから。
2. なぜ変更量が問題になるのか。意図と実装の対応を関数本体から復元しているから。
3. なぜ復元が必要なのか。要求、業務ルール、受け入れ条件が一意に識別されていないから。
4. なぜ識別されていないのか。実装開始を要求分析の代わりにしているから。
5. なぜ実装から始めるのか。動くコードが最も早いフィードバックだと考えているから。

したがって、解く問題を「送金コードを書く」ではなく「要求から証拠までを追跡可能にし、レビュー時に
判断の抜けを見つけられるようにする」と置く。

### プラクティス #2: ビジネス目標と成功指標を定義する

このサンプルの目標は次の3つである。

- G-1: レビュー担当者が、要求IDから公開APIと検証結果までを15分以内に辿れること。
- G-2: 未認可送金、残高の破壊、同一要求の二重反映を、リリース前の自動検証で検出すること。
- G-3: 機能変更時に、更新すべき要求、型、テスト、品質ゲートをGit diffから特定できること。

15分はこの試作を評価するための目標値であり、達成済みの実測値ではない。実案件では、従来レビューの
所要時間や流出不具合を基準値として測り、改善幅を決める。

### プラクティス #3: ソリューションの範囲を決める

範囲内は、未信頼の送金入力の解析、口座所有者の認可、残高更新、再送制御、検証用の証拠である。
範囲外は、本人確認、認証トークン検証、永続DB、分散トランザクション、為替、手数料、HTTP、監査ログ、
可用性設計である。

`ActorId` は上流の認証済み主体を表す。このサンプルが本人確認まで行うわけではない。ここを曖昧にすると、
単なる整数比較を「認証・認可を実装した」と誤認するため、信頼する入力の開始地点を明示する。

### プラクティス #4: ステークホルダーを特定する

| 役割 | 関心 | 必要な参加 |
|---|---|---|
| 送金利用者 | 正しい宛先、再送しても二重に減らないこと | 利用場面とエラーの妥当性確認 |
| プロダクト責任者 | 業務ルール、優先順位、対象範囲 | 要求ベースラインの判断 |
| セキュリティ責任者 | なりすまし、改ざん、資金破壊 | 脅威と残余リスクの判断 |
| SRE | 性能、観測可能性、障害時の挙動 | 品質属性と運用条件の判断 |
| 開発者 | 実装可能性、保守性 | 型と状態モデルの評価 |
| テスト担当者 | 反証可能な受け入れ条件 | 同値クラスと攻撃ケースの設計 |
| レビュー担当者 | 変更理由と証拠の追跡 | 公開APIと追跡表の評価 |

攻撃者は要求を決める参加者ではないが、悪用の視点を欠かさないために脅威モデル上の主体として扱う。

### プラクティス #5: 判断者と判断方法を先に決める

実案件では個人名を割り当てる。このサンプルでは役割だけを置く。

- 業務ルールと優先順位: プロダクト責任者が判断する。
- 受容するセキュリティリスク: セキュリティ責任者が判断する。
- 検証技法と実装方法: 技術責任者が提案し、上記の判断を変更しない範囲で決める。
- 品質ゲートを外す例外: 影響を記録し、プロダクト責任者と該当領域の責任者が判断する。

AIは候補、矛盾、未回答事項を示せるが、判断者にはしない。

## 第2段階: 要求を引き出す

### プラクティス #6: 利用者が達成したいことを理解する

主要な利用場面は「口座所有者が、認証済みの操作主体として、別口座へ指定額を一度だけ移す」である。
支援する利用場面として、通信失敗後の安全な再送と、レビュー担当者による証拠確認がある。

正常系だけでは、実際の仕事を表せない。利用者は失敗理由を区別し、資金が動いていないことを確認し、
同じ要求IDで再送する必要がある。

### プラクティス #7: イベントと応答を特定する

| イベント | 条件 | 応答 | 状態変化 |
|---|---|---|---|
| 送金入力を受け取る | 形式と値域が正しい | `ParsedTransfer`を返す | なし |
| 認可を求める | 操作主体が送金元の所有者 | `AuthorizedTransfer`を返す | なし |
| 初回実行 | 残高と宛先上限を満たす | `Applied`を返す | 2口座と完了一覧を更新 |
| 同一内容を再送 | 要求IDと内容が一致 | `Replayed`を返す | なし |
| 要求IDを別内容で再利用 | 要求IDは同じで内容が異なる | `RequestIdConflict`を返す | なし |
| 不正入力または未認可操作 | いずれかの規則に違反 | 分類されたエラーを返す | なし |

### プラクティス #8: データ概念と関係を評価する

```text
Actor 1 --- owns ---> 0..* Account
TransferRequest --- source/destination ---> exactly 2 distinct Accounts
TransferRequest --- identified by ---> 1 RequestId
CompletedTransfer --- records ---> 1 TransferRequest
```

`ActorId`、`AccountId`、`RequestId`は同じ整数表現でも交換できない別の概念である。送金額は0を許さず、
口座残高は0を許す。要求IDは送金内容と結びつき、同じIDに別内容を結びつけてはならない。

### プラクティス #9: 品質属性を測定可能な場面にする

| ID | 刺激と環境 | 測定する応答 |
|---|---|---|
| QA-SEC-1 | 任意のバイト列を解析器へ渡す | panicせず、成功または分類済みエラーを返す |
| QA-REL-1 | 実行を再送する | 残高を再度変更せず`Replayed`を返す |
| QA-COR-1 | 任意の有効残高と送金額で成功する | 2口座の合計が`u128`上で保存される |
| QA-PERF-1 | release buildで10万件を逐次実行する | 開発機で2秒以内に完了する |
| QA-REV-1 | レビュー担当者が変更を見る | 要求IDから公開APIと実行コマンドへ15分以内に辿れる |

性能目標は環境依存であるため、結果にはCPU、Rust版、件数を残す。本番SLOの代用にはしない。

## 第3段階: 要求を分析する

### プラクティス #10: 個別要求と要求集合を分析する

要求を正確性、完全性、一貫性、実現可能性、必要性、優先順位、検証可能性で確認した。特に次の衝突を
解消する。

- 再送は成功させたいが、同じ要求IDによる内容改ざんは拒否したい。
- `u64`の残高を使いたいが、合計の検証時には加算オーバーフローを起こしたくない。
- 認可後に状態が変わると判断が古くなるため、認可済み値は`&mut Ledger`を保持して割り込みを防ぐ。
- 高速化より、拒否時に一部だけ残高が変わらないことを優先する。

業務判断の順序は、入力検証、認可、要求ID衝突、残高不足、宛先オーバーフロー、反映とする。早い段階で
拒否された入力ほど、後段の状態へ触れない。

### プラクティス #11: 複数のモデルで漏れを見る

型状態モデルは次のとおりである。

```text
&[u8] --parse--> ParsedTransfer --authorize--> AuthorizedTransfer --execute--> Receipt
   |                   |                          |                   |
   +-- InputError      +-- AuthorizationError     +-- Funds/ID error +-- Applied/Replayed
```

状態モデルとプラクティス #7のイベント表を照合し、各遷移に成功と拒否の要求があることを確認する。
残高更新は別の純粋関数としてモデル化し、Kaniが全`u64`入力を扱える大きさに保つ。

### プラクティス #12: 不確実な部分だけを試作する

不確実性は送金計算ではなく、公開APIが不正な順序を防ぎつつ使いやすいかにある。次の2案を比べる。

```rust,ignore
ledger.transfer(actor, parsed)
```

```rust,ignore
ledger.authorize(actor, parsed)?.execute()
```

後者を採用する。型シグネチャに認可工程が現れ、認可済み値が`&mut Ledger`を借用するため、認可から実行の
間に同じ台帳を変更できない。試作の評価項目は、正常系の行数、誤った順序がコンパイルされないこと、
エラーの区別、レビュー時に処理順を説明できることとする。

### プラクティス #13: 価値、損失、依存関係で優先順位を付ける

| 優先度 | 対象 | 理由 |
|---|---|---|
| Must | 型、認可、原子性、再送制御、例示テスト、攻撃ケース | 資金破壊へ直結する |
| Must | 残高保存のモデル検査 | 入力空間が広く、整数上限が危険である |
| Should | Fuzzing、性質テスト、性能測定 | 未知入力と退行を継続的に探す |
| Could | HTTP、DB、分散実行 | 今回の問題を解くためには不要である |
| Won't | 為替、手数料、口座凍結 | 別の業務判断が必要なため、この基準版へ入れない |

## 第4段階: 要求を仕様化する

### プラクティス #14: 一貫した形式で書く

各要求は「`WHEN <イベント> IF <条件> THEN the system SHALL <観測可能な応答>`」の形で書き、ID、理由、
優先度、受け入れ条件、証拠を持つ。詳細は`REQUIREMENTS.md`に置く。

### プラクティス #15: 情報を役割ごとに整理する

- `DESIGN.md`: 問題、関係者、モデル、判断理由、20プラクティスの適用。
- `REQUIREMENTS.md`: 基準版、業務ルール、機能要求、品質属性、追跡表。
- `src/lib.rs`: 型と実行可能な規則。
- `tests/`: 受け入れ、性質、攻撃者視点、性能の検証。
- `fuzz/`: 未信頼入力を継続探索する入口。
- `README.md`: 同じ検証を再実行する手順。

### プラクティス #16: 業務ルールを一意に識別する

- BR-1: 送金額は1以上1,000,000以下である。
- BR-2: 送金元と送金先は異なる口座である。
- BR-3: 認証済み主体だけが、自分の口座を送金元にできる。
- BR-4: 送金後の送金元残高は0未満にならない。
- BR-5: 送金後の送金先残高は`u64::MAX`を超えない。
- BR-6: 同じ要求IDと同じ内容の再送は、残高を変更しない。
- BR-7: 同じ要求IDと異なる内容の組み合わせは拒否する。
- BR-8: 失敗した送金は、どの台帳状態も変更しない。

### プラクティス #17: 用語を揃える

| 用語 | このサンプルでの意味 |
|---|---|
| 操作主体（Actor） | 上流で認証され、`ActorId`として渡された主体 |
| 口座所有者 | 口座の送金を認可できる操作主体 |
| 未信頼入力 | 解析と値域確認を通過していないバイト列 |
| 解析済み送金 | 構文、ID、金額、異なる2口座を確認した値 |
| 認可済み送金 | 送金元の所有者確認を通過し、台帳を排他的に借用する値 |
| 再送 | 同じ要求IDと同じ送金内容をもう一度実行すること |
| 要求ベースライン | ある時点で判断対象として固定した、識別可能な要求集合 |
| 証明 | このサンプルではKaniによる有界モデル検査で確認した性質 |

「証明」はシステム全体の正しさを意味しない。Kaniに渡したモデル、仮定、性質の範囲だけを指す。

## 第5段階: 要求の妥当性を確認する

### プラクティス #18: 要求をレビューし、テストする

検証技法は強さではなく、見つけたい誤りで使い分ける。

| 技法 | 主に見つける誤り |
|---|---|
| 型とコンパイル失敗例 | 工程の飛ばし、IDの取り違え、不正値の直接構築 |
| 例示テスト | 利用場面、イベント応答、エラー分類の不一致 |
| 性質テスト | 多数の値での保存則、原子性、再送性の破れ |
| Kani | 指定した全入力に対する整数安全性と保存則の反例 |
| Fuzzing | パーサーのpanic、極端なバイト列、想定外の組み合わせ |
| 性能テスト | 品質属性の退行 |
| 攻撃者視点のテスト | 未認可、ID再利用、巨大入力による悪用 |
| 人間レビュー | 問題設定、対象範囲、残余リスク、検証の穴 |

## 第6段階: 要求を管理する

### プラクティス #19: 要求ベースラインを管理する

`REQUIREMENTS.md`の`Baseline`欄とGitのコミットで要求集合を識別する。初期状態を`draft-0.1`、自動検証が
揃った状態を`candidate-0.1`とし、代表レビュー担当者が目標時間と理解可能性を評価した後に
`verified-0.1`へ更新する。基準版は凍結を意味しない。どの時点の要求に対する証拠かを再現するための印である。

### プラクティス #20: 変更の影響を評価してから取り込む

要求変更は次の順で扱う。

1. 変更する要求ID、理由、判断者を記録する。
2. 問題、対象範囲、業務ルール、品質属性への影響を確認する。
3. 追跡表から型、テスト、Kani harness、Fuzz target、性能条件への影響を列挙する。
4. 変更前に、追加または変更した受け入れテストが意図した理由で失敗することを確認する。
5. 実装し、すべての関連証拠を再実行する。
6. 判断者が結果と残余リスクを確認し、要求ベースラインを更新する。

たとえば上限額を1,000,000から増やす変更は、`TransferAmount`だけを直して終わらない。BR-1、入力の
同値クラス、Kaniの仮定、Fuzzingの辞書、性能ワークロード、記事の記述まで影響する。追跡表は変更を
止めるためではなく、必要な変更を見落とさないために使う。

## Architecture for Flowから見た補助線

要求から証拠までを増やすだけでは、変更のフローを悪化させる危険がある。型、テスト、Kani、Fuzzing、
性能、セキュリティを別々の専門チームへ渡せば、検証項目が増えるたびに待ち行列とハンドオフも増える。
このサンプルでは、変更を所有するチームが`./scripts/verify.sh`から一通りセルフサービスで実行できる形に
する。専門家は毎回の実行担当ではなく、検証方法の設計、高リスク変更の評価、仕組みの改善を支援する。

認知負荷も同じである。すべての要求へすべての技法を適用しない。追跡表で「どの誤りを、どの証拠で
見つけるか」を限定し、通常の変更では秒単位の型検査とテストを先に返す。モデル検査、Fuzzing、性能測定は
対象となる性質と実行時間を明示して後段へ置く。強いゲートを増やすことより、必要なフィードバックが
判断者へ戻るまでの遅延を短くすることを優先する。

要求ベースラインも静止画ではない。プラクティス #20の変更管理と、継続的なフィードバックによる
小さな修正を組み合わせる。AIが実装を速めるなら、大きな変更を一度に通す理由にはならない。仮説を
要求IDへ置き、小さな差分で反証し、証拠とともに次の基準版へ進めるほうが、学習の遅延を小さくできる。
